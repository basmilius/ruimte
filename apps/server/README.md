# @ruimte/server

The daemon. It owns terminal sessions and serves them to the UI over one WebSocket. Closing the UI never ends a session; only `session.kill` (or the daemon going down) does.

## Run

```sh
bun run --cwd apps/server start            # ws://127.0.0.1:4210/ws
bun run --cwd apps/server start -- --host 0.0.0.0 --port 4300
bun run --cwd apps/server dev              # ws://127.0.0.1:4211/ws, home ~/.ruimte-dev, restarts on file changes
```

The `dev` script runs on port `4211` with `RUIMTE_HOME` set from `RUIMTE_DEV_HOME`, defaulting to `~/.ruimte-dev`, so a checkout runs beside an installed Ruimte (`4210`, `~/.ruimte`) without sharing its id, its projects or its sessions. Its door on the local network listens on `4221` beside it, and `bun src/main.ts status --port 4211` says how clients reach it.

`ruimte login` puts the machine on a Pulsar account without the app: run it as the user and with the `RUIMTE_HOME` of the daemon (and `--port` when it is not `4210`), and it prints `https://station.ruimte.app/link?code=BCDF-GHJK`, the code and the machine's key fingerprint. A person opens that page anywhere, signs in, checks the name and the fingerprint and presses "Add to my account"; the command then has the daemon sign a registration for that account, prints `Added to <login>'s account` and a sentence on how clients now reach it, and exits 0. A denial, an expired or a withdrawn code exits 1, Ctrl+C withdraws the code and exits 130. The daemon writes down the account it signed for; a machine on another account refuses, the command withdraws the code and exits 1, and `ruimte logout` takes the machine off its account first (see "One account per machine"). `RUIMTE_PULSAR_URL` points it at another address book. Without a daemon answering, it says how to start one: `ruimte service install`, or `ruimte` in another terminal.

`ruimte status` asks the daemon on the local secret (`GET /machine/status`) and prints its version, whether it runs as the background service, its name, whether it is on an account, its broker and whether that broker took its signature, and the addresses of its door on the local network. It warns when neither the broker nor the door can bring a client in, and exits 0 when the daemon answers and 1 when it does not. `ruimte pair` only says that pairing links are gone and exits 1. `ruimte context` is the agent-side CLI behind the `ruimte-context` script.

## Compile

`bun run compile` (`scripts/compile.ts`) builds one executable with `bun build --compile` into `dist/<os>-<arch>/ruimte`, with `ruimte-context` and `ruimte.build` next to it, for this machine or with `--os mac|linux --arch arm64|x64` for another. `--target darwin-arm64` names the target the way the npm packages do and `--outdir` picks the folder. A macOS binary only compiles on macOS, since `codesign` has to repair the signature Bun leaves. `RUIMTE_VERSION` stamps a version in; the desktop app packages that folder as its `bin` resource.

## Without the app: `npx ruimte`

A machine without the desktop app runs the same binary from npm (`packages/npm`), with Node or Bun:

```sh
npx ruimte                                # the daemon, with every flag above
npx ruimte login                          # onto an account with a code
npx ruimte status                         # how clients reach it
npx ruimte logout                         # off its account again
npx ruimte service install [flags]        # the background service for this user
npx ruimte service status
npx ruimte service uninstall
npx ruimte closed-lid install             # let keep awake hold a closed lid on a Mac (asks for sudo)
npx ruimte closed-lid remove
npx ruimte --version
```

`ruimte service install` copies `ruimte`, `ruimte-context` and `ruimte.build` to `$RUIMTE_HOME/bin` and writes the LaunchAgent or systemd user unit the desktop app writes, pointing at that copy and never at the npx cache, with the flags after `install`, the PATH of the shell it ran in (without npx's own folders) and `RUIMTE_SERVICE=1`. Running it again with a newer version replaces the copy, and the daemon under the service moves to it once idle; different flags restart the service. It refuses to touch a service that runs another program, which is what the desktop app's service is to it, and on Linux it prints `loginctl enable-linger <user>` when lingering is off rather than turning it on. `uninstall` stops the service and removes the definition and the copy, and leaves the rest of `$RUIMTE_HOME` alone. `status` exits 0 only when it is installed and answers on `--port`.

A bare `ruimte` at a terminal says which address the machine listens on and names `ruimte login`, `ruimte service install` and `ruimte status`; under the service or the desktop app it logs its one `listening on` line. The port is tried before the daemon reads its home, touches a store or installs a hook, so a second start leaves no trace (`src/cli/start.ts`); the listen itself still catches a port taken in between. When the port is taken it says so in a sentence and exits 1, and when the program on that port answers `/health` as Ruimte it names its version, whether it is the background service, and what to run instead (`src/cli/fatal.ts`). An error that ends the binary, a daemon or a command, and every error the daemon logs, prints its message only (`src/error-text.ts`); `RUIMTE_DEBUG=1` prints the whole stack instead.

`GET /health` answers `{ ok: true, version, build, service }`, where `service` is whether the machine runs as the background service. `POST /hooks/<claude|codex>` takes a hook payload from an agent CLI (see below); a kind the daemon has no normalizer for (`gemini`, `copilot`) answers 404. Everything else goes over `/ws` using the frames in `packages/contracts`.

On the socket, `server.hello` answers the daemon's version, platform, home and, when the machine says what it is, its `model` (`src/machine-model.ts`, read once at startup: the marketing name out of macOS's device tree, the SMBIOS fields on Linux and Windows, the device tree of a board that has no SMBIOS). The field stays out of the answer when nothing there names the hardware, which is what a container does, and the client's row for that machine says "This machine" instead of "This MacBook Pro". `server.ping` takes nothing and answers `{ time }`, the daemon's clock in epoch milliseconds; the client times the round trip itself (two machines never share a clock), which is the ping the connection dot shows.

## The machine's name and icon

`endpoint.info` answers `{ id, label, nameSource, icon, platform, version, reachability, authenticated, publicKey }`, with `brokerUrl` and `lan` saying where a client signals a direct connection (see "Remote clients"). The `label` is the name: the one a person gave it, or, while `nameSource` is `default`, `--label`, else `RUIMTE_LABEL`, else the hostname. A fresh machine is therefore never nameless. The `icon` is `{ kind: 'lucide', value }`, the same closed set a project and a view pick from, and null while nobody picked one; there is no image kind, because a machine has no folder to keep a file in.

`endpoint.setIdentity { name, icon }` sets both, from any client the machine let in. A null name hands the machine back to the name it starts with and a null icon leaves it without one, so both fields are always sent. The name and the icon go into `endpoint.json` next to the id, not into one client's storage, and every other connected client is told with `endpoint.changed { id, label, nameSource, icon, agentsDeleteAnyView }`.

`agentsDeleteAnyView` rides along in all three: it is what an agent's `ruimte-context view delete` and `node delete` may remove on this machine (one switch, since freeing the views and holding back the nodes is a distinction nobody reading that row would guess; the settings row says views and nodes), false on a fresh one, and it belongs to the machine because the daemon is what enforces it and a client setting would hold nothing back. On `endpoint.setIdentity` it is optional rather than nullable, since the dialog that names a machine is a different control and leaving it out leaves it where it stands.

`resumeAtReset` rides along the same way: whether a chat whose turn stopped on a limit is taken up again on a clock, at the reset of a usage limit or 1, 5 and 15 minutes after an overload, through a `resume-limit` outbox entry. Off on a fresh machine; a chat can still say no with its own `resumeAtReset` (`chat.configure`), which absent follows the machine. `ChatInfo.resumeAt` says when the entry is due, and it lapses when a person writes first, stops the chat or turns either switch off. The time is shown before the entry is written, so a start loads every chat that shows one the outbox does not hold and owes it again at that time, or takes the time off when a switch is off by then.

`visualReplies` rides along as well: whether an agent in an AI chat may show a page above its reply (`ruimte-context visual show`, see "Canvas verbs"). On by default, so `endpoint.json` holds it only as `visualReplies: false`, once a person turned it off; any client the machine let in sets it, like `resumeAtReset`. Off, `visual show` refuses with `visuals-off` and a chat whose CLI starts from then on is not told about the noun; the pages already in a thread still show, `visual list` and `visual remove` still answer, and so does `chat.removeVisual`. A daemon from before visuals leaves the field out.

`keepAwake` (`off`, `working`, `always`), `keepAwakeOnBattery` and `keepAwakeDisplay` ride along too, and `endpoint.info` adds `keepAwakeAvailable`: whether this machine can hold a block on sleep at all. The daemon holds it itself (`src/power/keep-awake.ts`), so it holds with no window open, for a daemon from npm and when a phone set it. On macOS that is a `caffeinate -w <daemon pid>` child, so a daemon that dies never leaves the Mac awake: `-s` when it holds on the power adapter only, `-i` when it may hold on battery too, and `-d` for the display only under `always` and only with `-i`, since caffeinate has no display assertion that lets go on battery. `working` holds while a terminal agent is live and `running` or a chat is in a turn or has subagents at work, checked on every session and chat status change and never on a clock. Anywhere else `keepAwakeAvailable` is false and nothing is held. Off, on the adapter only and without the display on a fresh machine. A desktop client moves the setting it kept itself onto its own machine once, and against a daemon without these fields keeps holding the block through the shell as before.

### With the lid closed

The block does not cover a lid. macOS sleeps on a closed lid whatever assertion is held (`IOPMLib.h`: "The system may still sleep for lid close"), unless an external display and the power adapter are connected. The one general way is `pmset -a disablesleep 1` (`SleepDisabled` in `pmset -g`), which needs root, so `keepAwakeLidClosed` turns sleep off while the block holds (`src/power/closed-lid.ts`). The daemon never holds root. A person on the Mac installs a sudoers rule once, `/etc/sudoers.d/ruimte-closed-lid-<uid>` (named after the uid, since sudo skips a file whose name has a dot), which lets this user run exactly `/usr/bin/pmset -a disablesleep 1` and `/usr/bin/pmset -a disablesleep 0` without a password and nothing else. The daemon runs those two with `sudo -n`, which fails instead of asking.

`endpoint.info` adds `keepAwakeLidAvailable` (a Mac) and `keepAwakeLidRule` (the rule file is there, and sudo took it the last time it was asked). The rule file is read again on every `endpoint.info` and `ruimte status`, and a change goes out as `endpoint.changed`, so a phone learns of an install on the Mac. `endpoint.closedLidRule { install, prompt? }` installs or removes the rule, from the local secret only (`forbidden` otherwise), through `osascript ... with administrator privileges`: macOS's own dialog asks the person for an administrator, and the request waits for it (`closed-lid-cancelled` on Cancel, `closed-lid-failed` with the reason otherwise, for instance a daemon with no window session, `closed-lid-unavailable` off a Mac). The script and the dialog's line travel as arguments, never quoted into AppleScript. Installing writes the rule under a name with a dot, checks it with `visudo -c`, makes it `root:wheel 0440` and only then moves it into place. Removing turns sleep back on as root first and then deletes the file; the daemon lets go before it asks, and once the file is gone it turns `keepAwakeLidClosed` off with it. Any client may turn the switch off, and on only while the rule is installed (`closed-lid-no-rule` otherwise); a switch already on stays on when a phone sends the whole keep awake back.

It holds only while the block would (the mode, `working` and its battery choice), and only on a power reading: on the adapter, or on battery when `keepAwakeOnBattery` is on and the charge is at least `CLOSED_LID_BATTERY_FLOOR` (20%). The readings come from `pmset -g pslog`, which writes the source when it starts and again on every change, the charge included, so nothing polls; it runs while the switch, the rule and a mode other than `off` ask for it, and a stream that ends holds nothing until the next change starts it again. Sleep goes back on whenever that lets go, and when the daemon stops (with `spawnSync`, before anything is awaited). A daemon killed outright or one that crashes is covered by a watchdog: before sleep goes off the daemon starts a detached `/bin/sh` in a session of its own that waits on a pipe nothing writes to, ignores `HUP`, `INT` and `TERM`, and runs `sudo -n pmset -a disablesleep 0` once it reads the end of that pipe, which the kernel gives it when the daemon is gone however it went. Letting go dismisses it with a SIGKILL after sleep is on again. Before sleep goes off the daemon also writes `power/closed-lid-held`, removed once sleep is on again, so a start after a crash the watchdog missed or a power cut finds `SleepDisabled` with that marker and turns sleep back on at once. `SleepDisabled` without the marker was set by somebody else (a person's own `pmset`, a Ruimte with another home) and is left as it is, with a line in the log.

`ruimte closed-lid install|remove` does the same from a terminal (`src/cli/closed-lid.ts`): it prints the rule word for word, runs the script with `sudo /bin/sh -c`, which asks for the password there, and then asks the daemon on `--port` to read the rule again. `ruimte status` adds `Awake` and `Lid` lines from the `keepAwake` field of `/machine/status`.

`endpoint.info` also carries `update`, where the desktop app on this machine stands with its next version: the updater's `status`, `currentVersion`, `version`, `percent` and `error`, plus `app`, false while no app on the local secret is connected (a daemon from npm, the service while the app is closed), which is when an update has to be done on the computer itself. The daemon cannot install a release; the app holds the updater, so it reports every step with `endpoint.reportUpdate` (local secret only, `forbidden` otherwise) and the daemon tells every client with `endpoint.updateChanged`, once per step and per whole percent, not with `endpoint.changed`, which every client answers by asking for the whole info again. `endpoint.installUpdate { confirm }` may come from any client, a paired one included: it only installs a signed release of the app, and a paired client can already stop every terminal and chat one by one. With `confirm` false it only answers `ending`, the terminals and agents a restart of the app would end right now (none when the daemon runs as the service, which outlives the app and moves onto the new build once nothing runs); with `confirm` true it hands `endpoint.updateInstall` to the app window that reported last, which downloads first when it has not yet and then installs without asking again on the Mac, since the person confirmed what ends. It answers `update-no-app` without an app and `update-none` with nothing to install.

A name typed in a client wins over `--label` and `RUIMTE_LABEL`. Those two say what a machine nobody has named answers to; a rename that a restart undid would be a bug, and clearing the name is the way back to them. `endpoint.json` stays at `version: 1` with the name and the icon added as fields: a daemon from before them reads the file, keeps its id and leaves them alone, where a version bump would make it mint a new id and answer to every paired client as a stranger. A name or an icon that will not read is dropped on its own and the id and key pair survive it. A file that will not read at all is renamed to `endpoint.json.corrupt-<time>` before a new id is minted, so the old key pair can still be put back by hand, and every write of it is flushed to disk before it replaces the last one.

## `RUIMTE_HOME`

Where the daemon keeps its state. Defaults to `~/.ruimte` (`~/.ruimte-dev` under the `dev` script and in an unpackaged desktop app). Layout:

```
$RUIMTE_HOME/
  endpoint.json                    the daemon's own id and key pair, minted on first start, plus the name, icon, agent policy, keep awake and visual replies settings it was given
  power/                           mode 0700
    closed-lid-held                written before sleep goes off for a closed lid and removed once it is on again, so a start after a crash or a power cut turns it back on
  auth.json                        the clients paired with this daemon, by public key, the push subscription of each, and the one account the machine is on
  projects.json                    every canvas the daemon knows: id, name, color, folder, and when it was last closed
  providers.json                   the accounts of each agent CLI on this machine (`accounts.save`): per id a kind, a label, a color and the CLI's config folder, never a credential
  snoozes.json                     the nodes a person put aside (`snooze.set`), per project and node with when each runs out; a node leaves push alerts and the Live Activity counts until then
  projects/
    <projectId>.local.json         camera, focus, grid and panels of a project, where a client that never saw it starts
  scratch/                         the Chats project of this machine (`project.newChat`), made the first time a chat outside any project is asked for
    .ruimte/                       its project files, the same as in any project folder
    <chatId>/                      the folder one of its chats works in, named after the chat's view; nothing removes it
  language-servers/
```

File names are the id passed through `encodeURIComponent`, so an id can never name a path outside its directory.

One home belongs to one daemon. The id in `endpoint.json` is what a client calls this machine, and `projects.json` and the sessions are written as if nothing else touches them, so two daemons sharing a `RUIMTE_HOME` are two daemons a client cannot tell apart.

## Projects

A project is a folder, and it lives in two files. `<folder>/.ruimte/project.json` is the one a team commits: the name, the color, the icon and the views a person shared. `<folder>/.ruimte/private/project.json` holds everything else, and the `.gitignore` the daemon writes beside it (once, never touched again) keeps that whole directory out of the repository. Nothing is shared until a `project.save` names it in `shared`; a verb hands back content and no list, so an agent can never move a view between the two files.

The private file carries the `rev`, which goes up on every write and is what `baseRev` is checked against. It is deliberately not in the shared file: that line would change on every write and be the one thing that conflicts on every pull. It also carries the sidebar order over both files (a shared id it does not know falls in behind the one before it, so a view a colleague added arrives in the right place) and, per shared node, the fields that cannot travel: the session being resumed, the permission mode, the worktree and any path off this machine. Those are laid back over the node on the way in, so a client sees one document and knows nothing of the split.

A view goes whole or not at all: sharing half a canvas would give a colleague lines to nodes that are not there. A file view whose path points outside the project folder cannot be shared, since the path is the whole view. The shared file is only written when its text would change, so moving a private node never shows up in anybody's `git status`. Both files are written with every node, text, line and arrangement on a line of its own, the way the drawings and the diagrams have always been written, so two people who each add a node do not collide at the end of the same array. Node directories inside the folder are stored relative to it (`./apps/server`), so a clone on another machine resolves them against its own checkout.

A file from version 1 or 2 held everything at once, so opening one is also the moment the folder is split: what git tracks was committed on purpose and keeps its views shared, and what git does not track becomes that person's own. A file whose `version` is higher than this daemon writes is neither broken nor readable; it is refused with `project-too-new` and left exactly as it is, the same rule a drawing and a diagram follow. What belongs to a screen goes to `<projectId>.local.json`, never into the shared file: the camera (the world point in the middle of the cell plus the zoom), the focused node, the grid of views and, under `panels`, which panel is up and how wide, whether the preview is up and how wide, the open file tabs with the active one and their pins, and the directories the file tree had open. Every client keeps its own copy of this and lays it over the file on open, so the file is only where a client that never saw the project starts; the favicons under `panels` are the one part that always comes from here. Every field under `panels` is optional, so a file written before them still parses and the client falls back to its own defaults.

`project.open` requires an id or a folder. Opening a folder creates its project file when none exists. With `createFolder` a folder that is not there is made first, and every missing folder above it; a file sitting at that path is never written over and still answers `folder-not-found`, while a mkdir that fails answers `folder-create-failed`. Only the client's folder picker asks for it. A folder whose canvas places a node id that another project open on this machine (not under Recent) places too is refused with `project-ids-taken` before anything is written: two checkouts of one repository carry the same canvas, and a session or a chat is keyed on its node id, so the second would take over the first one's terminals and chats. The person closes the other project first. `project.save` names the `baseRev` the client loaded and answers `rev-conflict` when the file moved on. While a project is open the daemon watches its directory; a write it did not make itself arrives as a `project.changed` event with the document now on disk. A file that does not parse is moved aside as `project.json.corrupt-<timestamp>` and a fresh canvas takes its place; it is never overwritten, and neither is one from a newer Ruimte. Every write is a temp file plus rename, with a short retry for Windows. `project.delete` forgets the project and, when asked, removes the canvas file; a folder's other files are never touched.

Letting go of a project and closing one are two requests, and both go through the holds. A client that opens a project holds it until its socket goes, and the machine only stops the watcher and drops the drawings when the last hold on that project does: two clients on one project must not undo each other's watcher. `project.release` drops this client's hold, which is what a client does when it switches to another project on the same machine; the registry is untouched. `project.close` is a person closing the project. It drops this client's hold too, and if anyone else still holds it that is all it does, answering `{ ended: 0, otherClients }`; the last client out ends every session the project's document holds (read off the index, so a project nobody has on screen closes the same way), stamps `closedAt` on the registry entry and sends `project.summary` to every client. `project.closing` answers the same two numbers without doing anything, for the confirmation that asks first. A socket that drops ends nothing: a session outlives the client that opened its project. `project.list` answers with every project either way and carries `closedAt`, so the client shows the ones in use and keeps the closed ones under Recent. Only closing puts a project there and only `project.open` takes it out again (it clears `closedAt` and announces the summary), so neither age nor whether a project happens to be open right now moves it. Nothing is ever created by reading: a daemon with an empty registry answers `project.list` with an empty list.

### Name and icon

`project.newChat { provider?, account? }` starts a chat outside any project and answers `{ summary, viewId }` (`src/projects/scratch-project.ts`). Its chats live in one project per machine, the Chats project in `$RUIMTE_HOME/scratch`, which the daemon makes through the store the first time it is asked and makes again when its folder went (`ProjectStore.ensureProject`, under the store's lock, so two calls at once find one project). Each chat is a standalone `chat` view whose `node.cwd` is a folder of its own, `scratch/<viewId>`, claimed with a `mkdir` that is not recursive before the view lands through `ProjectStore.mutate`, so every client holding the project sees it and finds the folder there. The summary of that project carries `scratch: true`, and a client shows none of its folders. A chat view the daemon makes there carries `empty: true` until the first message of a person lands in its thread, which drops the mark (`dropEmptyMark`); such a chat is left out of every sidebar, and `project.newChat` answers with it, of the CLI and account asked for when the request names them, instead of making another, so two clients asking get the same chat. Before it does, a mark on a chat whose thread already holds a message is dropped. A home inside a git checkout answers `scratch-unavailable`, since every chat's folder and the project's files would sit in someone's repository. Removing a chat view leaves its folder.

`name` and an optional `icon` sit at the top of the canvas file. An icon there is `{ kind: 'lucide', value }` with a closed list of 170 names; an image is never a blob in the JSON. Without a chosen icon the daemon asks the folder, in this order: `.ruimte/icon.{svg,png,jpg,jpeg,gif,webp}`, `.idea/icon.{svg,png}`, `.vscode/icon.{svg,png}`, then `favicon.{svg,ico,png}`, `public/favicon.*`, `public/icon.*`, `app/favicon.ico`, `app/icon.*`, `src/favicon.*`, `src/app/favicon.ico`, `src/app/icon.*`, `assets/icon.*` and `assets/logo.*`, and finally the `href` of the first local `<link rel="icon">` in a root `index.html` (tried as `public/<href>`, then `<href>`). A `<name>_dark.<ext>` next to the file it found is the dark theme's variant. Every path is jailed inside the folder and re-checked after `realpath`, the type comes from the magic bytes and not the extension, and a file that is empty, over 256 KB or not an image is skipped. Nothing is left: the summary carries `{ kind: 'initial', value }`, the first letter of the name. The `name` is seeded when a folder gets its first canvas: from `.idea/.name` (first non-empty line, control characters stripped, 64 characters, file at most 4 KB) when it holds one, else the folder's own name. That file is read once and never again, so the canvas file owns the name from there on and only a rename changes it; `nameSource` says whether the name was chosen or is still the folder's own. What the folder says about its icon is cached in memory for five minutes per folder and never written back; `project.open` and `project.setIcon` re-read it, and a folder that could not be read at all is not cached.

`GET /projects/<projectId>/icon?v=<version>&theme=dark` serves the bytes, gated by the same rules as `/ws` (every client sends its ticket, its session token or the local secret as `?token=`). It answers with the sniffed `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: private, max-age=31536000, immutable` (the URL changes whenever the file does) and, for an SVG, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, so opening the URL directly runs nothing either. `project.list` never carries image bytes.

`project.setIcon { projectId, image: { mime, base64 } | null }` writes `<folder>/.ruimte/icon.<ext>` (PNG, JPEG, GIF, WebP or SVG, at most 256 KB, checked against the bytes' own magic, the other `icon.*` in that directory removed) or, with a null image, deletes it. It answers with the fresh summary and sends `project.summary` to every client. A Lucide choice needs no request of its own: the client writes `icon` into the canvas file through `project.save`. The watcher on `<folder>/.ruimte` covers `icon.*` as well as `project.json`, so an icon copied in by hand also arrives as `project.summary`.

### Inline edit chats

`project.newInlineChat { projectId, path, provider, model?, account? }` makes the chat an inline edit in the editor runs in (`src/projects/inline-chat.ts`) and answers `{ chatId, viewId }`, one id for both. In one `ProjectStore.mutate` a standalone `chat` view with `hidden: true` lands in the private project file, its `cwd` the project folder or, for a file inside one of the repository's worktrees, that worktree (a path outside both is `inline-path-outside`), its mode `supervised`; then the daemon creates the chat itself. A chat that will not start takes its view back. No sidebar lists a hidden view (`projectSidebarViews`), no view picker opens it (`isOpenableView`) and the chat's `ChatInfo` carries `hidden: true`, which `chat.list` hands every client so the phone can leave it out. `ChatManager.promptNotesFor` puts a heard-only preamble in front of the chat's first prompt (`src/chat/inline-edit.ts`, again after a clear): change no file and answer with one fenced block labeled `replacement` and at most two sentences. The preamble never reaches the thread, which shows what the person asked and the answer. `project.showInlineChat { projectId, viewId }` clears `hidden`, which is what Open as chat does so the chat stays a conversation of its own, and `project.removeInlineChat { projectId, viewId }` ends the chat, removes its record and then its view, and only ever for a view that is still hidden. Both are idempotent. The client keeps a record per file and has the old ones removed after seven days.

## Drawings

A drawing or diagram file follows its view: `.ruimte/drawings/<viewId>.json` while the view is shared, `.ruimte/private/drawings/<viewId>.json` while it is not, and sharing a view moves the file over. Both directories are watched, since a pull lands in the one and a person's own editor in either.

A drawing view holds nothing in `project.json` but its id and its name; its elements live in
`<folder>/.ruimte/drawings/<viewId>.json` (version 1, with a `rev`), which goes into git next to the
project file. The top level is indented and every element sits on one line, so a diff reads like a
drawing rather than like a list of coordinates. The file name is the view id through
`encodeURIComponent`, so a rename never moves a file.

`drawing.open { projectId, viewId }` answers with the document, or with an empty one when there is
no file: a drawing nobody touched leaves nothing on disk. `drawing.save` names the `baseRev` it was
built on and answers `rev-conflict` when the file moved on, `drawing.close` forgets it, and
`drawing.copy { projectId, from, to }` writes a copy at rev 0, which is what duplicating a view is.
A second non-recursive watcher on `.ruimte/drawings` (started with the first drawing of a project)
turns an outside write into `drawing.changed` with the document now on disk, 150 ms after the burst
settles and never for a write the daemon made itself. Broken JSON is set aside as
`<viewId>.json.corrupt-<timestamp>`; a file that parses but is not a drawing stays where it is and
the request answers `drawing-invalid`. A drawing view that leaves the project through `project.save`
takes its file with it; a view that disappears through an outside edit of `project.json` never does,
because a pull can drop a view whose file is still on its way.

## Sessions

- A session is keyed by the id the client chooses. `session.create` on an id that is still running answers `session-exists`; on an id whose shell has ended it starts a fresh shell and shows the old screen above a `[session restored, previous shell ended]` line.
- The shell is `$SHELL` (fallback `/bin/zsh` on macOS, `/bin/bash` elsewhere), started as a login shell where the shell takes `-l`, with `TERM=xterm-256color`, `COLORTERM=truecolor` and `RUIMTE_SESSION_ID` set.
- Every session runs a headless xterm in the daemon (10000 lines of scrollback). `session.attach` answers with the serialized screen, after which raw output streams in `session.output` events, coalesced per 16 ms. A screen that would weigh more than 4 MB as JSON loses its oldest scrollback, half at a time, until it fits (`src/sessions/fit-screen.ts`): a frame past 16 MB closes the socket, and the reconnect would meet the same screen.
- Several clients may attach to one session. Attaching with different `cols`/`rows` resizes the session; the last attacher wins.
- A client that cannot keep up does not grow a queue in the daemon. Per socket, once `getBufferedAmount()` passes 1 MB (`HIGH_WATER_MARK` in `src/backpressure.ts`) or a `session.output` frame comes back as dropped or backpressured, output for that client stops and every session that loses bytes is marked. Requests, replies and the other events are small and keep flowing. On Bun's `drain`, under 256 KB queued, each marked session gets a `session.resync` event (`{ sessionId, screen }`) with a fresh serialize and its stream continues; the mark is cleared in the same tick the serialize resolves, so a byte is either in that screen or in the stream after it, never in both.
- `session.clear` is what a native terminal's Clear does: the daemon clears its own buffer (the prompt line becomes the first) and pushes the fresh screen to every attached client as `session.resync`. The shell is never told, so nothing is typed into it and no scrollback survives a reload.
- A shell that exits on its own stays in `session.list` as `exited` with its `exitCode` so the last screen can still be read. `session.kill` removes it.
- `session.create` takes either `command` (a line typed into the fresh shell) or `agent` (`{ kind, runtimeMode?, model?, resume? }`), never both: with `agent` the daemon builds the line itself (`src/providers/launch.ts`) and types that. So every client starts a CLI the same way, and a flag never travels over the wire. `runtimeMode` becomes `--permission-mode` for Claude Code, `--ask-for-approval` plus `--sandbox` for Codex, `--approval-mode` for Gemini and nothing for Copilot; a `resume` fills the provider's resume template instead, with the fresh launch behind a `||` so a node whose session the CLI no longer has still ends with that CLI running. A CLI that is not installed ends as `command not found` in the shell, which is why the menus disable a row the daemon did not find. A session the daemon still has an agent record for gets no launch line at all: that agent is resumed after the attach (below), and starting the CLI here too would type a second command into the one already coming up. A line longer than 1000 bytes is not typed whole: the tty holds what comes before the shell reads in a queue macOS cuts at 1024 bytes, newline included, so the line goes into the shell's environment as `RUIMTE_START_LINE` and `eval "$RUIMTE_START_LINE"` is typed instead (`src/sessions/session.ts`).
- `session.login` (`{ sessionId, kind, account?, cols, rows }`) is a terminal no node stands for: a shell in the home folder, under the environment of that account (the CLI's default account when none is named), that types the CLI's own login command (`home.loginCommand` of its provider). It is never held, since the daemon chose the command and a person asked for it, and a CLI without a login answers `login-unavailable`. The session lives for the client that asked: it ends when that client's socket closes, it never writes a snapshot, and Processes names it `<CLI> login`. A client watches the account with `accounts.watchLogin` and kills the session itself once the login landed.

## Snapshots

Every 30 seconds, and on `SIGINT`/`SIGTERM`, the daemon writes each session's screen to `sessions/<sessionId>.txt` (temp file, then rename). When the daemon starts again and a client creates a session with an id that has a snapshot, the first attach shows the snapshot, the restored marker and then the fresh shell. `session.kill` deletes the snapshot on purpose: a killed session should not come back. The chats go down first and synchronously (`ChatManager.persistAllSync`), before the handler awaits anything, because a `bun --watch` reload restarts the module during that first await.

## Agent status via hooks

Hooks are per kind: Claude Code and Codex have an event table and a normalizer (`capabilities.hooks: true`), Gemini and GitHub Copilot do not, so they launch in a terminal and show the session's own status (running while attached, error on exit) and nothing more. The installer only visits the kinds with a hook path, and the receiver answers 404 for the others.

Every shell gets `RUIMTE_HOOK_URL` (`http://127.0.0.1:<port>/hooks`) and a per-session `RUIMTE_HOOK_TOKEN`. At startup the daemon puts one command hook per lifecycle event into `~/.claude/settings.json` and `~/.codex/hooks.json` (idempotent merge; hooks of other tools stay). The hook POSTs its stdin to `$RUIMTE_HOOK_URL/<kind>` with the token as bearer and prints the reply, and does nothing outside Ruimte. Codex asks you to trust the new hooks once (`/hooks`). It also writes `~/.codex/rules/ruimte.rules`, which lets Codex run `ruimte-context` outside its sandbox without asking: the sandbox blocks the daemon's loopback port, and the daemon checks every verb itself.

The reply is empty except on `SessionStart` and `UserPromptSubmit`, where the daemon answers `{ "hookSpecificOutput": { "hookEventName": ..., "additionalContext": ... } }` and the CLI folds that into the turn: Claude Code and Codex take the same shape, and Codex 0.154 adds it as a developer message (measured, also on `codex resume`, where `SessionStart` fires again with `source: "resume"`). `SessionStart` carries the sentence about the canvas verbs, with the linked-context line and any waiting message behind it; a CLI the node launched with the verbs on its line (Codex, as developer instructions) hears only the links and messages there, while one typed by hand in the shell still gets the verbs; `UserPromptSubmit` carries the linked-context line, then what changed since the previous turn and any message another node left for this one. The daemon remembers per session what each agent was last told about (`ContextStore.changeSince`), so a line drawn while the shell was already running is named at the next turn ("Added: ..."), which is the only way that change reaches a terminal agent at all; it is quiet when nothing moved, and never said at a `SessionStart`, which is handed the whole list anyway. That is how a Claude agent inside a terminal, which has no system prompt of ours, learns about `ruimte-context`. A chat never reaches these hooks: its CLI runs without the `RUIMTE_HOOK_*` variables and hears changes in front of its own prompts. The curl runs with `-f`, so an error page never ends up as context.

Codex 0.157 runs its sessions in a shared background server (`codex app-server --managed-daemon`) that runs the hooks with the environment of the terminal that started it, so a Codex a node launches gets `--no-daemon`, once `codex --help` at startup names the flag (`src/providers/launch.ts`). A `codex` typed by hand in a shell still joins that server, and its hooks carry whichever token started it.

The daemon folds the events into one status per session: `running`, `needs-you` (permission prompt, `AskUserQuestion`, elicitation), `idle` (turn ended) or `error` (the shell died under a live agent). Every client gets it as a `session.status` event with the CLI's session id and transcript path, and `session.list` carries the same `agent` field.

## Permission requests

A terminal agent's permission request is answered in its CLI's own prompt and nowhere else: a person chose the TUI for a reason. The hook only turns the status to `needs-you`. `agent.answerApproval` answers `{ accepted: false }` and `agent.setApprovals` does nothing, for clients built when a daemon still held the request; `session.approvals` is no longer sent. An AI chat's approvals are its own (`chat.approve`).

The record is also written to `sessions/<id>.agent.json`. When the daemon starts again and the session is restored from its snapshot, the agent comes back with `live: false`; the client answers with `agent.resume`, which types `claude --resume <id>` (or `codex resume <id>`) into the shell. One at a time: a second `agent.resume` is refused with `agent-resuming` while a typed resume has not produced a live agent, and allowed again 15 seconds later, so a CLI that never starts can still be retried.

A recorded session id is not a conversation, so the daemon looks before it resumes. The transcript path the hooks reported is the evidence: the file is still there and the resume line is typed; the file is gone (a CLI that was started and never used persists nothing, and a transcript can be deleted) and the session's own launch line is typed instead, so the node ends up with a working CLI rather than a bare shell. A hook that names no transcript at all leaves the choice to the shell, as `<resume> || <launch>`. Either way it is one line: two would land in the input box of the CLI the first one started.

## Computer use

An agent operates the apps of this Mac through `ruimte-context computer <action>`, which the daemon carries out through the helper app in `apps/computer-use` (`src/computer`). It is off until a person turns it on for the machine (`computer.setEnabled`), and while it is off every action refuses with `computer-use-off`, the helper is never started and the verbs note does not mention the noun. On but without both Accessibility and Screen Recording, every action refuses with `not-granted` and the note stays silent too; a daemon that starts with computer use on asks the helper for its grants right away, so the note knows. On, the daemon starts the helper with `open -g <app> --args --home $RUIMTE_HOME` the first time it needs it, puts the local secret on every request, and quits it when the feature is turned off or the daemon stops. The helper is `Contents/Helpers/Ruimte Computer Use.app` in Ruimte.app and `apps/computer-use/dist/Ruimte Computer Use Dev.app` in a checkout; a daemon from npm and one on Linux have none and refuse with `unavailable`.

`apps` asks nobody. Everything that reads or operates an app needs a person's yes for that app, by bundle id, in every permission mode. The first call raises a card (`computer.approvals`, to every client, answered with `computer.answer`) and holds for 6 seconds, under the 10 seconds some agent CLIs give a shell command by default. `--wait S` (1 to 110) sets that hold for one call, which goes on as soon as the person answers; the canvas route lets a verb run 240 seconds, since Bun would drop a request after 10 silent ones. Past the hold the call refuses with `awaiting-approval`, which tells the agent to call again with `--wait 60`, and the card stays up for ten minutes after the agent last asked, or until that agent exits or its node closes. "This time" lives in memory and holds until the agent's turn ends: its status leaves running (waiting on the person is still the turn) or its chat turn settles. One given between turns lasts through the next. Turning computer use off and a stop take every one back; "always" is written to `computer-use/grants.json`, which no verb writes. A no reaches the agent once, as `declined`. The helper is told the pid the person let in, never the name the agent typed.

An app that runs shells is refused with `terminal`, whatever was granted. The daemon reads that off the process table: a process up to three levels below the app has a controlling terminal the app does not share, so a shell under a pty host process counts too. An app once seen doing so is remembered in `grants.json`, so it stays refused between its shells. The common terminal apps (Terminal, iTerm2, Ghostty, WezTerm, Alacritty, kitty, Warp, Hyper, Tabby, Termius) are refused by their bundle id as well, so a window that has no shell yet is never operated (`terminal-apps.ts`). One that `open` launched is looked at as soon as it runs, before its tree or anything else of it goes back to the agent. The Ruimte desktop app (`app.ruimte.desktop`, `app.ruimte.desktop.dev`) is never a terminal: its shells run under the daemon and it gets a card like any other app. An agent let into Ruimte can do there whatever the person can, and that is the person's own risk: the daemon refuses nothing extra from the Ruimte window while an agent operates it, and the card says so.

`computer.grants` lists what stands until a person takes it back: the apps allowed for always and the apps remembered as terminals, each with its name, bundle id and when, and what agents hold for this time, with the chat or terminal and its title as the card named them. `computer.revoke` takes one back by bundle id and kind (`always`, `terminal`, `thisTime`, the last for one `nodeId` or for every agent that holds it) and answers `removed: false` when there was nothing to take. Taken back, an agent's next call in that app raises a card again; an app that is no terminal after all is looked at for shells again on its next call, and remembered again if it runs one. Every client hears the whole list as `computer.grants` whenever it changes, whichever path changed it. Only a person lists or revokes: no verb does.

One agent operates the Mac at a time, since the helper runs every action in one line and two agents' actions would interleave. The first agent whose call needs an app takes the Mac, before its card goes up, and holds it until its turn ends (`done` or `end` below), its node closes or its agent exits, the session ends in the helper (a stop, or the helper ending a quiet session by itself), or computer use is turned off. A call of that agent that outlived its turn and finds another agent holding the Mac never reaches the helper. Any other agent's call that needs an app refuses with `busy`, whose words name the chat or terminal that holds it by its title and tell the agent to call again with `--wait 60`. Without `--wait` that refusal comes at once, since a turn lasts far longer than the default hold; with it the call stands in line within the same budget as a card and a pause, and the line gets the Mac in the order it asked, the moment the holder lets go, so nobody who asked later gets there first. The card of an agent in line goes up while it waits, so the person can answer ahead; answering does not hand it the Mac. A node in line that closes leaves it with `not-in-session`. `apps` needs no app and is open to every agent. The holder lives in `src/computer/presence.ts`.

While an agent acts, the helper draws a phantom cursor, a session bar and a menu bar item. Between actions the daemon tells it what the agent is doing (`presence`, `src/computer/presence.ts`), and only for the agent that holds the Mac. It shows `permission` with the app while a card of that agent stands, `think` while its turn runs and no call is out, and `waiting` when its hooks or its chat say it needs the person. An action the helper refused shows nothing of its own: the agent reads the refusal and recovers. A turn that ends shows `done`, which ends the session once the checkmark faded; an agent that stops with an error shows `error` with those words, which ends it the same way; an interrupted turn, an agent that exits or a closed node sends `end`, which ends it at once, also while the person holds it. A send goes out only on a change, one at a time, and never holds up an action; one that fails is logged.

Every call works behind the person's work unless the agent passes `--front` (`front` on the helper's request), so the person can go on in another app. The helper then never brings the app forward, moves the pointer or posts to the system's event stream: it presses, focuses and opens menus through accessibility, types to the app's process alone, scrolls through the app's scroll bars, runs menu items and captures the window by itself, also while it is covered. What only the front can do (a click by pixel, a double click, a drag, the wheel, select all and the other edit commands, keys for a minimized window) it refuses with `needs-front`, which the daemon passes on under that code and never tries again in front on the agent's behalf. The verbs note tells the agent to work in the background and to ask the person before it uses `--front`. In the background the helper draws no cursor over the other apps, its session bar and menu bar item name the app the agent works in, and only the person bringing that app forward or clicking in its window takes over; `apps/computer-use/README.md` has what each command does there.

The person can pause the session (⌥Space), take the Mac over with their own mouse, or stop it (⌥⎋). A call made while the session is paused or taken over waits in the same budget as a card (the default 6 seconds, or `--wait`), asking the helper every half second, and refuses with `paused` or `taken-over` when the person has not given the Mac back by then; the refusal tells the agent to read the state again with `--wait 60` before it acts. An action the person cut off is refused the same way and never sent again, since it may have run halfway. After a stop every agent that made a computer call since computer use was last turned on hears `stopped` on its next call, whatever that is, and only once; it is told to ask the person. A call standing in line hears it at once. The daemon then has the helper forget the stop (`clear-stop`), so a stop is no ban: an agent that heard it may start again, and the first to take the Mac holds it. Every grant for this time goes with the stop. The daemon reads these from the helper's `code`, not its words.

Reading a window costs an agent tokens, so the daemon tells it only what is new to it. An action with `--state` answers with the lines of the tree that changed against the last whole tree that agent got for that app (`src/computer/tree-diff.ts`), marked `+` new, `-` gone and `~` changed, beside the window and screenshot rows. A line is the same element by its `[N]`, which the helper keeps for as long as it runs. The memory lives in the daemon and not in the helper, since the helper keeps one element map for every agent; it goes with the node and when computer use is turned off. The answer is whole, and says why, for the first state of an app, a new window or sheet, and a helper or app that started again (the helper puts an `instance` on every state for that); `--state=full` asks for the whole tree. `state` is always whole and is what the next change is told against, except with `--find T` (the elements that hold `T` and what they sit in) or `--within N` (one element and what is inside it), which read only part of the window. `read --element N` gives one element's texts whole, up to 20,000 characters each, and says when it cut one. `wait` holds until a text appears (`--text`), a text is gone (`--gone`) or an element has a value (`--element N --value V`), 10 seconds or `--timeout` up to 110, and answers with what changed; when the time is up it refuses with `timeout` and the same rows under it. The helper polls for it beside its queue, and the socket gives that request its timeout on top of the usual 20 seconds. `drag` presses on an element or pixel, moves to another and lets go; the helper checks the start the way it checks a click.

`computer.status` answers whether the helper is there, whether it runs and what it reported about Accessibility and Screen Recording; asking it starts the helper only while computer use is on. `session` says how the helper's session stood when the machine last heard: `null` while none runs, otherwise its `mode` (`running`, `paused`, `takenOver`) and the `nodeId` of the chat or terminal that holds it. `waiting` lists the chats and terminals in line for the Mac, first in line first, and is absent while none waits. While one runs the daemon asks the helper every two seconds, so a pause or a stop on the helper's own bar, keys or menu, and the helper ending an idle session, show without a call; it stops asking once none runs.

`computer.restart` quits the helper, waits until its socket closes and starts it again, since macOS applies a Screen Recording grant to a fresh launch only; the settings call it when a person comes back from System Settings. `computer.requestGrant` has the helper ask macOS for one grant, which is what lists it in that pane of System Settings for the person to switch on. `computer.control` is the session bar's buttons pressed in Ruimte (`pause`, `resume`, `stop`): the daemon forwards the press to a helper that runs, starts none for it, and answers with the status after it. The overlay speaks the interface language of the client that turned computer use on, and a client whose language changes says so with `computer.setLanguage`; while computer use is on the daemon writes `overlay.json` again, which the helper reads at its next action or presence.

## Providers and models

Each agent CLI is one `ChatProvider` value (`@adecore/agents/providers/provider.ts`; the daemon's list in `src/providers/registry.ts`, with `terminal-providers.ts` and `apple-provider.ts` beside it): its kind and name, its model catalog, what it can do, the command to run, the template a terminal resumes it with (`claude {flags} --resume {id}`, `codex resume {flags} {id}`, where `{flags}` is the mode and the model the node was started with) and how to make a backend for a chat. `ProviderRegistry` is the list of them plus the detection cache; nothing else in the daemon branches on which CLI a chat is. The catalog is Claude Code, Codex, Gemini and GitHub Copilot, in the order every menu lists them; the last two are terminal only and have no chat backend.

`provider.list` answers, per agent CLI, whether it is installed, its version, the models it offers, its resume template and its capabilities. The catalogs are `@adecore/agents/providers/claude-models.json` and `@adecore/agents/providers/codex-models.json`: a model points at a profile, a profile lists option descriptors (reasoning effort, context window, thinking) with their defaults and the context size per option. Adding a model is a JSON edit; a new profile is only needed for a new combination of options. The address book hands the same two files out on `GET /v1/models/catalog`, so a model added there reaches every machine after a deploy of `apps/pulsar-worker`, without a release. The daemon asks at start and on a `provider.list` once the last answer is six hours old (ten minutes after a failure), keeps the answer at `$RUIMTE_HOME/models/catalogs.json` and reads that copy before any chat is restored, so a chat on a model only that copy knows keeps it. Every catalog is checked against `ModelCatalogDataSchema` on its own, and one older than the catalog the app shipped with (`updatedAt`) is never taken, so a release that carries a newer file wins over a stale copy. A client reads the new list on its next `provider.list`, which it asks on every connection. The Codex catalog mirrors what `codex app-server` answers on `model/list` for 0.153 (six models, each with its own reasoning ladder and default); the context windows were measured per model through `thread/tokenUsage/updated`. A `ModelSelection` is `{ model, options }`; the daemon normalizes it (aliases like `opus` or `astra`, defaults for missing options, unknown options dropped).

The capabilities are the honest list of what a CLI does, so a client never offers what would be dropped: whether it can be opened as a chat, as a terminal or both, whether the daemon understands its hooks, whether it streams partial tool output, how it reports a file change (`unified`, `before-after` or `none`), whether it takes attachments and `@` mentions, whether a decline carries a reason, whether "always allow" exists, whether it asks questions the person may ignore, how it folds context (`native`, `prompt` or `none`), whether it reports cost, the context window, slash commands and what the model thought. Claude Code and Codex differ on most of them.

One mode travels with every chat: the runtime mode, the permission policy in one vocabulary for every provider (`supervised`, `auto-accept-edits`, `auto`, `full-access`, the default). For Claude it becomes `--permission-mode`, the selection becomes `--model <slug>[1m]` and `--effort`, and `ultrathink` is written into the prompt because the CLI has no flag for it.

For Codex (`@adecore/agents/providers/codex.ts`) the runtime mode becomes an approval policy plus a sandbox on `thread/start`: `supervised` is `untrusted` in a `read-only` sandbox, `auto-accept-edits` is `untrusted` in `workspace-write` (edits inside the workspace pass the sandbox, commands still ask unless Codex knows them as safe; the CLI has no "ask for commands, not for edits" policy), `auto` is `on-request` in `workspace-write` (Codex's own default) and `full-access` is `never` in `danger-full-access`. The reasoning effort travels as `effort` on every `turn/start`. The `approvals_reviewer` from `~/.codex/config.toml` is left alone; with `auto_review` some approvals never reach the person.

## Chats

One chat is three pieces, whichever CLI is behind it:

- `ChatSession` (`@adecore/agents/chat/chat-session.ts`) owns the thread, the turns, the process generation and when a new backend is needed. It is the same class for every provider.
- `ChatBackend` (`@adecore/agents/chat/backend.ts`) is one CLI process and the protocol it speaks. It reports what happened as `BackendEvent`s (`text.delta`, `tool.started`, `approval.requested`, `turn.done`, `exit`, ...) and never touches the thread. `ClaudeBackend` and `CodexBackend` implement it; the frames themselves are mapped in `claude-protocol.ts` and `codex-protocol.ts`, which are pure and unit tested.
- `ThreadProjector` (`@adecore/agents/chat/projector.ts`) is the only place that turns those events into thread items and the `chat.event`s to broadcast. Item ids carry the process generation, since a resumed CLI numbers its messages from the start again.

A third CLI is therefore a provider value, a backend and a protocol mapper; the session, the projector, the manager and the wire stay as they are.

A Claude chat is `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`, spawned on the first `chat.send` and kept alive between turns. The daemon folds the stream into thread items (turn, user, assistant, tool, subagent, approval, question, note, compaction), every item tagged with its turn, and broadcasts every change as a `chat.event` to the attached clients, numbered with a `seq` per chat; `chat.attach` answers the current thread with the `seq` it holds, so a reload rebuilds the view, and a client that offers `since` gets only the `events` after it while the daemon still holds all of them (not from before a clear, and not from before the log was last folded into the snapshot).

Beside that stream, every change of a chat's status goes to _every_ client as a `chat.status` event carrying the whole `ChatInfo`, whether or not that client attached: a node waiting on a person has to say so on a view nobody has open, which is what `session.status` has always done for a terminal. One event per change, never one per info event, so a streamed reply does not announce itself all the way down. A client asks `chat.list` on each fresh socket for the standing answer.

- A `can_use_tool` control request becomes an approval item and `needs-you`; `chat.approve` answers it with `allow`, `allow-always` (the CLI's own suggested rule goes back as `updatedPermissions`) or `deny`.
- An `AskUserQuestion` call becomes a question item instead; `chat.answer` returns the answers keyed by question index, the daemon keys them by question text for the CLI.
- `chat.dismiss { chatId, itemId }` settles a question item as `dismissed` without answering it. Only a question the CLI asked beside its turn (`async` on the item, which today is Codex's agent-message question) may be dismissed: the CLI keeps working and never hears about it, so nothing is left waiting. A blocking question and an approval are refused with `request-not-found`.
- `chat.configure` changes the selection or a mode. A running process keeps its flags until the turn ends; the next send starts a fresh process with `--resume` and the new flags.
- `chat.continueOn { chatId, account }` goes on after a last turn that stopped on a limit, under another account of the chat's CLI (`src/chat/continue-on.ts`). An account that reads the same transcripts (Codex accounts over one home) takes the chat over as `chat.configure` would and opens a turn at once; any other gets a fork cut after the limited turn, with the conversation handed over as text, whose first turn opens at once. The answer names the chat that goes on, with the fork's result when there is one, and the original's owed resume at the reset lapses. Refused with `not-limited` when the last turn did not stop on a limit and `same-account` for the account the chat already runs under.
- `chat.cancel` sends an interrupt and the turn ends as `aborted`. `chat.compact` follows the provider's capability: Claude Code gets `/compact` as a turn, Codex a call of its own.
- `chat.clear { chatId, force? }` starts the chat over: the CLI is killed without waiting for a turn, the items, the queue and the attachments go, `agentSessionId` becomes null and the empty thread is written and sent to every attached client as a `reset` event. The next send starts the CLI without `--resume` (Codex with `thread/start`). Provider, folder, selection, mode, cost and the turn count stay. A chat in the middle of a turn of the person's is refused with `chat-busy` unless `force` is set; a turn the CLI opened itself is not in the way.
- A settled tool item may carry `changes`, the files it touched with the unified diff per file, for a provider that reports one (Codex). Claude Code's edits only carry the text before and after in the tool input, which is why a turn takes a checkpoint of its own.
- A turn takes a checkpoint when it starts: `src/git/checkpoints.ts` writes the chat's folder as a git tree through an index file of ours (`GIT_INDEX_FILE` under `$RUIMTE_HOME/checkpoints`, `git add -A`, `git write-tree`), so the person's own index, stashes and commits are untouched and ignored files stay ignored. The tree id sits on the turn item as `checkpoint`. When the turn settles the daemon diffs the working tree against it and puts the answer on the turn as `checkpointDiff`: one unified diff per file with the added and deleted line counts, at most 100 files (`truncated` says there were more), no body for a binary file or a patch over the cap (`omitted`). `chat.turnDiff { chatId, turnId }` answers the same shape for a turn that has no stored diff yet, which is how a client asks while a turn is still running. A folder outside a repository, or a git that fails, leaves both fields off and the card falls back to what the CLI reported.
- A running tool item may carry `progress`: `startedAt` from the CLI's `tool_progress` frame (`elapsed_time_seconds`, verified on 2.1.266), `description` from its `task_started` frame, and `output` for a provider that streams partial output (a `delta` event on a tool item appends to it). Claude Code sends `tool_progress` for a local Bash only under its remote gate (`CLAUDE_CODE_REMOTE` or `CLAUDE_CODE_CONTAINER_ID`, once per 30 s) and never streams Bash output, so the client counts from the item's own timestamp when nothing came. The result drops `progress`.
- An `Agent` (or `Task`) call opens a `subagent` item instead of a tool item, keyed by the call's `tool_use_id`: the description, the subagent type, the prompt, whether it runs in the background, its status (`running`, `done`, `failed`), what the CLI says it is doing (`summary`, `lastTool`), what it spent (`usage`) and the report it ended with (`result`, markdown). Its own work stays in the thread as ordinary items that carry `parentToolUseId` (tool calls and the text it wrote), so streaming keeps working and the timeline gathers them under the row. `system/task_started` fills in the type and the background flag, `task_progress` the summary, the last tool and the usage. A foreground agent settles from the `tool_result` of its own call, with the CLI's `agentId ... <usage>` footer stripped off and the usage kept; a background one is answered at once with "Async agent launched successfully" and only settles on `task_notification`, where the report is the last text it wrote. One agent keeps at most 200 items and 64 KB of its own text; past that `itemsTruncated` says the row shows the beginning of its work. The turn the CLI wakes up with carries `taskToolUseId`, so its header can point at the row. Codex's `spawnAgent` maps to the same item (always background, status from Codex, no children and no report, since that agent works in a thread of its own).
- Not every turn starts with a message. Claude Code wakes the agent itself when a background task settles: after the `result` of the turn that launched it, and with no user frame in between, it sends `system/task_notification`, a fresh `system/init`, an assistant message and a new `result`. Content that arrives while no turn is open therefore opens one with `origin: 'agent'`, the notification's summary as its `label`, no user item, status `running` and a checkpoint of its own; the `result` settles it like any other turn. A frame that carries a `parent_tool_use_id` is a subagent talking inside its own row and never opens one. A message sent while such a turn is open is not refused as busy: the daemon settles that turn as stale first, and the `result` still coming for it is dropped instead of closing the turn that took its place. The composer offers stop while the turn runs, like any other.
- Every event goes to `chats/<id>.log` as it is broadcast (`@adecore/agents/chat/chat-log.ts`), so a daemon that goes down mid-turn keeps everything a client saw: reading a chat plays the log lines after the snapshot's `seq` over it and skips a torn last line. The snapshot, `chats/<id>.json`, is written on a chat's first write after it loads, when what no event carries changes (the preambles waiting for the next prompt, the task ids a clear dropped), and whenever the log is folded into it: when the log passes 1 MB at a write, after a line failed to reach the disk, on a clear and on shutdown. A chat whose process ended starts the CLI again with `--resume` on the next send.
- A turn that was running when the daemon went down is taken up again at start (`ChatManager.recoverInterrupted`, `src/outbox/resume-run.ts`): loading the chat owes a `resume-run` in the outbox, and the worker starts the CLI with `--resume` (Codex: `thread/resume`) under the same turn with `attempt: 2`, a note "Resumed after the machine restarted" and a prompt telling the agent to continue. Approvals and questions that were open are cancelled. A CLI that will not start is tried after 1, 5 and 30 seconds and the turn then ends `aborted` with a note; a turn without a CLI session, one already resumed once, or one no project holds (as a node on a canvas or as a chat view of its own) ends `aborted` as well, with a note "This turn could not be resumed after the machine restarted: <reason>" that names which of these it was.
- `chat.send` takes optional `mentions` (paths the person picked with `@`), which stay `@path` in the text for the CLI to expand itself and are stored on the user item so a client can draw them as chips.
- `chat.send` also takes optional `attachments`, any file type, at most 25 MB each and 8 per message, as `{ name, mime, data }` with base64 bytes. The daemon writes each one to `$RUIMTE_HOME/attachments/<chatId>/<id>.<ext>` (`@adecore/agents/chat/attachment-store.ts`) and keeps only `{ id, name, mime, size, path }` on the user item, so a thread with a video in it is still a small JSON file. The prompt names the files by path under the text ("Attached files: - /path (name)"): both CLIs open a file with their own tools, images included. A thread written before this carried its images inline; the read that opens the chat writes them out once and rewrites the record, before the schema sees it. `GET /attachments/<chatId>/<id>` serves the bytes behind the same access rules as `/ws` and the project icon (loopback free, any other client sends its ticket, or its session token, as `?token=`), `inline` for what a browser paints and `attachment` for the rest, with `nosniff`, an immutable cache and, for an SVG, the same `default-src 'none'` policy the icon route uses. The chat's own thread and queue are what say which id belongs to which file, so nothing else can be reached through the route.
- A visual is a page an agent showed with `ruimte-context visual show` (see "Canvas verbs"). The list is `chats/<chatId>.visuals.json` and each page `attachments/<chatId>/<visualId>.html`, so a client reads a page's bytes the way it reads an attachment: `GET /attachments/<chatId>/<visualId>`, or `bytes.read` with `{ kind: 'attachment', chatId, attachmentId: visualId }`. `ChatManager.findAttachment` reads the chat's list when the loaded chat does not know the id, so a page is found after a restart before anyone opened its chat. `text/html` is never in the route's inline list: a page goes out as a download with `nosniff` and is never painted on the daemon's own origin, so a client shows it only in a sandboxed frame on an origin of its own. `chat.attach` carries `visuals`, every change goes to the attached clients as `chat.visuals { chatId, visuals }` with the whole list, and `chat.removeVisual { chatId, visualId }` lets a person take one out, where one already gone is no refusal. A clear and a delete take the list and the pages along. A fork copies the visuals of the turns it copied, and those shown between turns until the end of the turn it was cut at, each with a page of its own.
- What the model thought before it answered becomes a `thinking` item. Claude Code's thinking blocks (streamed as `thinking_delta`, replayed as a `thinking` content block) and Codex's `item/reasoning/*` notifications both map onto one `thinking.delta` / `thinking.done` pair of backend events, and the projector keeps one item per stretch: consecutive blocks join with a blank line between them, and the first text, tool call or request of the turn closes the stretch. The provider capability `reportsThinking` says whether a CLI hands it over at all.
- A `chat.send` while a turn runs is not refused: the message joins the chat's queue and the request answers `{ queued: true }`. The queue sits on `ChatInfo.queue` (so it reaches every attached client as an info event and goes to disk with the thread, and a reload or a daemon restart keeps it), and the daemon sends the next message the moment the turn settles. `chat.unqueue { chatId, messageId }` drops one; `chat.sendNow { chatId, messageId }` puts one first and interrupts the turn in its way, so the settle sends it. One queue for both providers: Claude's steer folds into the running turn and Codex's app-server queues a second turn, and two semantics per CLI is harder to reason about than one.
- `skills.list { chatId }` answers the composer's `$` picker with `{ name, description, source }` per skill (`@adecore/agents/skills.ts`). A running Codex answers it itself over the app-server's `skills/list`; otherwise the daemon scans the roots the CLI uses. Claude: `$CLAUDE_CONFIG_DIR ?? ~/.claude/skills` (user), every `.claude/skills` from the chat's folder up to the repository root (project), and the `skills` folder of each entry in `~/.claude/plugins/installed_plugins.json`, named `<plugin>:<skill>` the way the init frame does (plugin). Codex: `~/.agents/skills`, `~/.codex/skills` and the `.agents/skills` folders of the project. A skill is a folder with a `SKILL.md`, named by its front matter's `name` or by the folder, described by its `description` (block scalars folded). The scan is cached for 30 seconds per CLI and folder; there is no watcher. Once the CLI announced its own `skills` in the init frame (`ChatInfo.skills`), the answer is narrowed to that list, so a skill turned off in the CLI's settings drops out.
- `chat.send` takes an optional `skills`, the names the person picked with `$`. The names stay `$name` in the text, which is what Codex expands. Claude Code expands a skill only from a text block that starts with `/name` and is the last block of the message, so the daemon splits the prompt (`@adecore/agents/chat/input.ts`): what came before the last `$name` is the leading text block with the earlier `$x` written as `/x`, then the images, then `/name <rest>` as the last block. A `$word` that names no known skill is left alone.
- `fs.search` answers the composer's `@` picker: a fuzzy search over the files under a folder, through `git ls-files` (tracked and untracked, minus `.gitignore`) inside a repo and a bounded walk (20k files, depth 12, no dot folders or `node_modules`) elsewhere. The file list is cached for ten seconds per folder.

## Language servers

`src/language` runs the language servers of the smart editor. The daemon is their LSP client (`@adecore/lsp`) and the one owner of every document's text and version, so any number of clients share what a server sees. The wire is `packages/contracts/src/language.ts`: `language.status`, `language.install`, `language.prefer`, `language.restart`, `language.log`, `language.document.open|change|close`, `language.request`, `language.command` and `language.edit.answer`, with the events `language.diagnostics`, `language.status`, `language.providers` and `language.edit`.

The catalog has these kinds, each one pinned install of an npm package, except `php-native`, which is a program:

| Kind                  | Package                                                                                                                                           | Serves                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `typescript`          | `typescript` 7, whose package brings the native language server, and TypeScript 6 behind typescript-language-server as a sidecar for code actions | TypeScript, JavaScript, JSX and TSX, with the inlay hints and auto imports on |
| `vue`                 | `@vue/language-server` paired with typescript-language-server and a TypeScript 6 tsserver that loads `@vue/typescript-plugin`                     | Vue, and the scripts of a project that uses it                                |
| `php-native`          | the native PHP server from `basmilius/language-server-php`, shown as PHP                                                                          | PHP, and `.phtml` templates                                                   |
| `php`                 | intelephense, shown as Intelephense                                                                                                               | PHP                                                                           |
| `css`, `html`, `json` | `vscode-langservers-extracted`, one install each                                                                                                  | CSS, SCSS and Less; HTML; JSON and JSONC                                      |
| `yaml`                | yaml-language-server                                                                                                                              | YAML                                                                          |
| `python`              | pyright                                                                                                                                           | Python                                                                        |
| `bash`                | bash-language-server                                                                                                                              | shell scripts (shellcheck is used when it is on PATH)                         |
| `docker`              | dockerfile-language-server-nodejs                                                                                                                 | Dockerfile                                                                    |
| `eslint`              | `vscode-langservers-extracted`                                                                                                                    | JavaScript, TypeScript and Vue, in a project with an ESLint config            |
| `tailwind`            | `@tailwindcss/language-server`                                                                                                                    | HTML, CSS, scripts, Vue and PHP, in a project that uses Tailwind              |

The JSON server opens `tsconfig*.json`, `jsconfig*.json`, `.eslintrc`, `.babelrc` and anything under `.vscode` as JSONC, so comments and trailing commas are no error there. It associates the schemas of `package.json`, `tsconfig.json`, `composer.json` and the other common config files by file name (`JSON_SCHEMAS`), and fetches a schema from its host the first time a matching file opens, never otherwise. The YAML server has its schema store off, since the store downloads its whole catalog when the server starts whatever file is open; it gets the schemas of GitHub workflows and actions, Dependabot and Compose by file name, fetched on a match like the JSON ones. The CSS family has `unknownAtRules` off, since `@apply`, `@theme` and friends are what a stylesheet of today holds. A server that is told the client pulls diagnostics stops pushing them, so a component with `pullDiagnostics` (`typescript`, `php-native`, `css`, `html`, `json`, `python`, `eslint`) is asked for them with `textDocument/diagnostic` when its document opens, 200 ms after typing pauses and when it sends `workspace/diagnostic/refresh`. `eslint` and `tailwind` are additions: they serve a document beside the kind of its language, and only in a project that calls for them. ESLint wants an `eslint.config.*` or `.eslintrc*` file in the project folder or an `eslintConfig` field in its `package.json`, Tailwind a `tailwind.config.*` file or a `tailwindcss` or `@tailwindcss/*` dependency (`activation` in `profiles.ts`). A document opens on every kind that serves it (`SharedDocument.kinds`, the one of its language first, and `servers` in the answer to `language.document.open` lists them, installed or not), each kind starts and ends on its own, and each process reports its own diagnostics under its name. A request goes to every server that offers the feature when the answers add up, which are completion, code actions and hover (`src/language/merge.ts`): items are concatenated and `itemServers` in the answer names the process of each, hovers become one list of marked strings, and the options of the features the document may ask are the first server's, with the trigger characters and action kinds of all of them. Any other feature, such as a definition or a rename, is the first server's that offers it. A resolve or a command goes to the process named in `server`, whichever kind it belongs to, and a server that fails or is not up leaves the answer of the others. The first server that can answer a merged call (the one of the document's language) is awaited without a deadline; every other one that has not answered within `MERGE_DEADLINE_MS` (1 second) is left out of that answer, its late answer is dropped and the log says so, so a slow ESLint or Tailwind never holds up the main server. A request to a single server has no timeout. A process that does not answer `initialize` within `INITIALIZE_TIMEOUT_MS` (30 seconds) is ended and the kind marked `crashed`, with a message saying so, instead of staying `starting`. Both timers belong to a request or a start that is under way and schedule nothing of their own. ESLint offers its fixes as commands that end in a `workspace/applyEdit`, so they take the path of `language.command` and `language.edit` below.

The `typescript` kind runs the native language server of TypeScript 7 (`tsc --lsp --stdio`, which names itself `typescript-go`). Its install is the `typescript` package at 7, which pulls in the package of the machine's platform and architecture (`@typescript/typescript-<platform>-<arch>`, an optional dependency that bun picks by itself) and holds a native executable. The daemon runs that executable as it is and not under its own runtime, with no Node. A project's own TypeScript wins when it is 7 or newer: the daemon looks for `node_modules/typescript` from the project folder upward, reads its version, and runs the platform package that sits beside the real folder of the package (`resolveNativeTypescript`, which holds for npm, bun and pnpm layouts). An older one, or one without a program for this platform, leaves the pinned install. The install is verified before it counts: the executable has to print the pinned version (`--version`).

The native server takes its settings from `workspace/configuration`, which asks for the sections `js/ts`, `typescript`, `javascript` and `editor`, the first with the highest precedence. The profile gives `js/ts` the inlay hints (`inlayHints.parameterNames.enabled: 'all'`, and `variableTypes`, `functionLikeReturnTypes` and `parameterTypes` on) and `suggest.autoImports`. Formatting takes `tabSize` and `insertSpaces` from the request, which the editor fills from `.editorconfig`, and has no further setting from Ruimte. Its initialization options are `disablePushDiagnostics`, since the daemon pulls, and `logVerbosity: 4`, since the server logs every snapshot it takes at its default. It has no setting for `completeFunctionCalls`, so a function completes as its name. The tsserver of the Vue kind has the setting off as well: the client adds the parentheses of a call itself, for every server, and a call snippet from the server would otherwise break a class member. Its code actions are quick fixes and the `source.*` actions (organize imports, remove unused imports, sort imports, fix all) and no refactors (extract function and the like), and its legend has no `local` modifier, so the semantic colors of variables follow `readonly` only. An install of an earlier version of the kind (typescript-language-server with tsserver) reads as `not-installed` with a message saying an install updates it, and pressing Install replaces its packages.

TypeScript 7 lacks most quick fixes (spelling, unused declarations, await, missing members) and every refactor, so the kind has a second process, the sidecar `typescript-actions`: typescript-language-server with a tsserver of TypeScript 6, the same pin the Vue kind installs. Its packages come with the same Install press as the native server: the install holds `typescript` 7, `typescript-language-server` and the TypeScript 6 SDK as `typescript-6` (an `npm:` alias of the same package), so a kind installed before reads as `not-installed` until Install runs again. A project's own `typescript` wins when it has a `tsserver.js`, as it does for Vue. The sidecar starts lazily, with the first `textDocument/codeAction` for a document it serves (the lightbulb, Alt+Enter, the refactor menu), except a request whose `only` names nothing but `source.*` kinds, which the native server answers alone. After that it is kept in step with every open document and file change, and it is asked for nothing but `textDocument/codeAction`, `codeAction/resolve` and `workspace/executeCommand` for its own actions, whose `workspace/applyEdit` takes the usual path through `language.command` and `language.edit`. Its diagnostics are dropped, since the native server's are the ones shown, and every other request skips it unless it is named in `server`. Its actions follow the native server's in the answer, an action with the same title and kind as a native one is dropped, so is a `source.*` kind the native server offers, and `itemServers` names `typescript-actions` for each of its items, so a resolve or a command goes back to it. The first request that starts it waits up to `SIDECAR_START_DEADLINE_MS` (10 seconds, for the process to start and load the project) and later ones `MERGE_DEADLINE_MS`; past that it is left out of the answer. A sidecar that cannot start, does not answer its handshake or ends is let go of while the kind carries on, and it stays away until the kind starts again; the status of the kind lists it under `sidecars` (`idle`, `starting`, `ready`, `crashed`), which the status popover and the language servers tab show as a line under the kind.

The server offers `diagnosticProvider` with `interFileDependencies`, so the daemon asks again for every open document of it, 200 ms after typing pauses in any of them, and not only the changed one. It does the same when the server sends `workspace/diagnostic/refresh`, and a report that carries `relatedDocuments` is reported for the documents the server has open.

`textDocument/selectionRange` is part of the wire (`LANGUAGE_METHODS`) and of the `LanguageService` seam. The editor's Extend Selection asks the server for the chain around each caret (`setSelectionRanges`, `apps/client/src/language/selection-ranges.ts`) and takes the first range that holds the selection and more, and Shrink Selection walks back through what was grown. Without a server that offers ranges, or when it fails, Extend Selection grows by the editor's own lexical rule. The server also offers call hierarchy and on-type formatting, which the editor does not use.

In a project that uses Vue (`vue`, `nuxt`, `@vue/*` or `@vitejs/plugin-vue` in its `package.json`, or a `.vue` file opening) the scripts go to the `vue` kind, which stays on TypeScript 6: TypeScript 7 has no plugin API, so its one TypeScript server is typescript-language-server with a tsserver that loads `@vue/typescript-plugin` for `.ts`, `.tsx`, `.js`, `.jsx` and `.vue` documents, so a script that imports a component is typed and only one tsserver runs, while `@vue/language-server` serves the `.vue` files beside it. That tsserver is the project's own `node_modules/typescript` when it has a `tsserver.js`, else the pinned SDK. A `.vue` file opening in a project that did not say so moves the scripts already open to the `vue` kind and ends the `typescript` server. The `vue` kind has to be installed for those scripts; a project on Vue has no scripts on the `typescript` kind. The pinned versions are in `src/language/versions.ts` and nowhere else.

A kind is installed only when a person presses Install (`language.install` from a client); no verb, no agent and no start of the daemon installs anything. The install writes a `package.json` with exact versions under `$RUIMTE_HOME/language-servers/<kind>` and runs `bun install --ignore-scripts` there, with the daemon's own executable acting as bun. A compiled daemon does that when `BUN_BE_BUN=1` is set, and the servers written in JavaScript run the same way (`<ruimte> <script>`), so the person needs no Node. Under `bun dev` the executable is bun itself. The servers run in a process group of their own, which a stop signals as a whole, tsserver included.

The PHP server (`php-native`) lives in [basmilius/language-server-php](https://github.com/basmilius/language-server-php) and has no npm dependency in Ruimte. Installation is still a person's Install action (`native.ts`, `installer.ts`). A development daemon looks for `../language-server-php` relative to Ruimte's source checkout, independently of its working directory. A Ruimte worktree also checks beside its primary checkout. An explicit `RUIMTE_PHP_LANGUAGE_SERVER_SOURCE` selects another checkout and takes priority over discovery. The locator reads existing files; it never clones, pulls or switches Git branches. `readNativeCheckout` reads the native version from `Cargo.toml` and the stubs commit from `crates/index/src/stubs.rs`.

With a valid PHP checkout, Install runs `cargo build --release --locked`, shows Cargo's output in the kind's log and uses that checkout's `target/release/php-language-server`. Cargo is found on `PATH` or in `~/.cargo/bin`. Without a valid checkout, the native policy uses the pinned release. A compiled daemon always uses the release, including when the source override is set.

A release install downloads the native asset pinned in `src/language/php-native-release.json` from the standalone repository's `v0.1.0` release into `$RUIMTE_HOME/language-servers/php-native/bin`. The pin copies the official [release descriptor](https://github.com/basmilius/language-server-php/releases/download/v0.1.0/php-language-server-release.json), including its source revision and stubs commit. It names each platform's URL, SHA-256, archive format and executable path. The checksum must match before extraction; absolute paths and entries that escape the installation folder are rejected. Install verifies `--version` against the native `version` (`0.1.0`) and fetches the pinned standard library stubs. The descriptor covers Apple silicon, Linux arm64/x64 and Windows x64. Its version is independent of ADE CORE's npm versions.

The stubs are the phpstorm-stubs of the commit the server was built against (the commit is read from `STUBS_COMMIT` in the checkout, or comes with the release). The server would fetch them itself on first run, which the product rule forbids, so Install downloads that commit's tarball, unpacks the `.php` files and the license into `<install>/storage/stubs/<commit>` and writes the `.commit` and `.complete` markers the server writes, so a partial download starts over. The server is started with `initializationOptions` `storagePath` (`<install>/storage`, where its index cache lives) and `stubsPath` (that folder), so it never goes to the network. It reads `composer.json` for the language level itself, announces that it pulls diagnostics, and registers its own file watching. The marker records the version, whether a checkout or a release supplied the binary and the stubs commit, so a server or a stubs pin that moved reads as not installed until Install runs again.

PHP is served by one of two kinds, which `choice: 'php'` in `profiles.ts` marks as alternatives to each other. The machine's pick lives in `$RUIMTE_HOME/language-servers/choices.json` (`choices.ts`), never in a project, and defaults to `php-native`. `language.prefer` (any client; both servers were installed by a person) saves it, moves every open document of every project to the chosen kind (clearing what the other reported), ends the other server once it holds no document, and tells every client through `language.status` events. A status of a kind that has an alternative carries `chosen`, and one that this build cannot install carries `unavailable`. A `.phtml` file the editor gives no language still goes to the PHP kind that names its pattern.

A person can add servers of their own beside the catalog: a name, the command and arguments that start it over stdio, an optional environment and initialization options (JSON), the LSP language ids and file patterns it serves (`*.zig`, `templates/**`, matched by `matchesFilePattern` in `packages/contracts/src/language-patterns.ts`), and the folders of the projects it runs for (every project without them). They live in `$RUIMTE_HOME/language-servers/custom.json` (`src/language/custom.ts`) and nowhere else: a project file can never name a server, and no verb adds or changes one. `language.custom.list` answers anyone, while `language.custom.save`, `language.custom.remove` and `language.custom.check` (does the command exist as an absolute path or on the PATH of the daemon, and where) answer the local secret only, since a save approves starting that exact command, arguments and environment on this machine; a client the machine let in is refused with `forbidden`. A saved entry carries a hash of the three, and an entry whose command, arguments or environment no longer match it because the file was edited by hand is held: listed as crashed with a sentence saying so, never started, until a person saves it again. A server of a person's own goes by `custom:<id>` wherever a kind goes (`language.restart`, `language.log`, a status, a diagnostics report, a `server` hint), runs as the command itself and not under the daemon's runtime, and starts, stops and crashes like a catalog server. Its status carries `name`, `languages` and `patterns`, since the client has no catalog entry for it. A save or a removal ends the server where it ran, gives every open document the servers it has now, so a server starts for the file that is open, and goes to every client as `language.custom.changed`.

One server runs per project per kind, shared by the clients of the project. It starts when the first document of its language opens in an installed kind, and keeps running when its last document closes; it ends when the last client closes the project (`ProjectStore.closeProject` calls `LanguageHost.end`) or when the daemon stops. Nothing retries on a clock. A process that ends by itself after the kind had been ready for `STABLE_AFTER_MS` (60 seconds, long enough that it was running and not looping on a bad project or install) is started again once, at once, on the exit event, with the documents as they are then, and the log says so; every process of a pair goes down and comes up together. Any other end marks the kind `crashed`, with the last line it wrote, and only `language.restart` brings it back: a process that ends before its handshake, one that ends within `STABLE_AFTER_MS` of becoming ready, and so the one started again when it ends within that time too. The documents stay held through a crash and a restart opens them again with the text and version they have then. The state of a kind is `not-installed`, `installing`, `stopped`, `starting`, `ready`, `indexing` (the server reports work in progress) or `crashed`, and `language.log` returns the last 500 lines of the install and of the server.

A file that changes on disk reaches the servers. The daemon advertises `workspace.didChangeWatchedFiles` (with dynamic registration and relative patterns) and, once a server of the project has registered for it through `client/registerCapability`, watches the project folder through `ProjectFileWatcher` (`src/language/file-watch.ts`): one recursive watch where the platform watches a tree in one call (macOS, Windows), and elsewhere the folder plus the directory of every open document. The watch ends when the last server unregisters, crashes or stops, and when the project closes. Each event is dropped unless a pattern of some server names its path (`watchesFile` in `@adecore/lsp`: string patterns relative to the project folder or absolute, relative patterns to their own base, the kinds a watcher asked for, and `node_modules`, `vendor` and `.git` only for a pattern that names that folder). What is left collects in the settle timer of `@adecore/agents/watch-seam` (200 ms, pushed back by every event, as the folder and git watchers do) and leaves as one batch. At the flush each path is looked at once: gone is deleted, a directory is skipped, and a file is created when the platform called its event a rename and changed otherwise. Each server then gets `workspace/didChangeWatchedFiles` with the changes its own patterns name. Nothing here runs on a clock of its own: the timer exists only after a watcher event, so it coalesces a burst and schedules no work.

`language.command` runs a server's `workspace/executeCommand` (on the process that offered the action, when `server` says which). While it runs, the server's `workspace/applyEdit` goes to the client that ran it as a `language.edit` event, and the server is answered from that client's `language.edit.answer`: an edit is made by the client, never by the daemon, and one asked for with no command of a client running, from a client that went away or that stays silent for 30 seconds is refused (`applied: false`). Creating, renaming and deleting files are not offered to the servers.

A client opens a document with its text, which replaces what the daemon holds when another client has the file open with other text. Every accepted `language.document.change` raises the version by one, and a change whose `baseVersion` is not the daemon's version is refused as `stale-document`, after which the client opens the document again with its whole text. The same code answers a `language.request` that names a version the document has left. A path is a stored path (`packages/contracts/src/stored-path.ts`) and goes through the same `MachineHome` line as `fs.read`. Diagnostics go to every client that has the project open, and the last close of a document sends an empty report per server so the clients let go of its problems. A server that crashes or is stopped does the same for every document it served, for every process of the kind (the TypeScript server of a Vue pair is cleared when the Vue server dies), and its diagnostics come back when it runs again. A document of a language no server serves is held all the same, so a client's calls stay uniform. For a `.vue` document the daemon asks Vue first and TypeScript inside a `<script>` and a template expression and for inlay hints, and falls back to the other when the first lacks the method.

## On-device help for the editor

`src/ondevice` runs one-shot generations on the machine's own model (Apple Foundation Models) for the editor's short help: an explanation in the hover, names in a rename and ghost text at the caret. The wire is `packages/contracts/src/ondevice.ts`: `ondevice.status` answers `{ available, reason? }`, `ondevice.generate { id, purpose, prompt, stream? }` answers `{ state: 'done' | 'aborted', text }` and `ondevice.cancel { id }` ends it. With `stream` the whole text so far goes to the asking client only, as `ondevice.text { id, text }`, which is how Explain fills in word by word; names and ghost text ask for the text once. A failure is an error with a code (`unavailable` with the reason, `failed`, `busy` past four requests at once).

`OnDeviceModel` (`src/ondevice/model.ts`) starts the same helper the Apple chat provider uses (`apps/foundation-models`, found by `src/providers/apple-helper.ts`) with `--oneshot`, on the first request, and keeps it until the daemon stops or the helper does, after which the next request starts another. The helper has no session store and no tools: it reads `generate` lines (`instructions`, `prompt`, `maxTokens`, `temperature`) and answers `text.snapshot` frames and a `done`, and a `cancel` by id ends one. Each purpose's instructions, token limit and temperature live in `src/ondevice/instructions.ts`, so a client sends the text to read and never an instruction. `ondevice.status` probes the helper on every call, since Apple Intelligence can be switched on or off while the daemon runs, and answers the platform's reasons in words (`deviceNotEligible`, `appleIntelligenceNotEnabled`, `modelNotReady`); a machine that is not an Apple silicon Mac says so without starting anything.

Code stays on the machine in two ways. The model is the system's own, on the device, and the helper opens no connection and has no tool that could (the web and MCP tools of the chat helper are not in this mode). And the prompt only travels from a client to the daemon, over the same link that already carries the project's files. Any client that may use the daemon may ask, as with the language requests; there is nothing to approve, since a generation reads text it is given and writes nothing. A client that goes away has its generation cancelled at the next text the model produces, and one that cancels does so by id, per socket.

## Files

`fs.grep { cwd, query, regex?, caseSensitive?, wholeWord?, limit? }` (`src/fs/grep.ts`) is the palette's find in files: every line under `cwd` that answers to the query, each with its path relative to `cwd`, its line number, where the hit sits in the line (offset and length in UTF-16 units, not bytes) and the two lines above and below it. Ripgrep does the work where it is on PATH (`--json`, one event per line, killed the moment the limit is reached); without it the same search runs in JavaScript over the file list `fs.search` caches, skipping anything over 2 MB and anything with a NUL in its first kilobyte. One hit per line, at most 200 in an answer, and `truncated` says the limit stopped it. A query is literal text unless `regex` says otherwise; a pattern that does not compile comes back as `invalid-query`. Ripgrep takes PCRE2 for a pattern with lookaround or a backreference (`--engine=auto`), and a pattern it still turns away is searched in JavaScript rather than answered with nothing. That search lets the rest of the daemon through every 50 ms, so a pattern that backtracks without end stalls no terminal, and it stops with `truncated` after ten seconds.

`fs.browse { partialPath, cwd?, hidden? }` (`src/fs/browse.ts`) is what the folder picker lists: the directories that complete what was typed, each with its name, its absolute path and `hasCanvas`. A path ending in a separator lists that directory whole; without one the last segment is a case-insensitive prefix filter on its parent, and `parentPath` says which directory the entries came from. `~` is this machine's home, a relative path counts from `cwd` and answers `cwd-required` without one, and a Windows-shaped path on a daemon that is not Windows answers `windows-path`. Dot-folders and build output such as `node_modules` stay out unless `hidden` asks for them or the typed prefix starts with a dot, and rubbish the operating system keeps to itself, `.git` and `.ruimte` stay out either way; git is never asked here, since this answers a keystroke. `exists` says whether `parentPath` is a directory that is there, which is what tells a folder that is missing from one that is empty or unreadable; a directory that cannot be read still lists as empty.

`fs.list { path, depth?, hidden? }` (`src/fs/list.ts`) answers one directory, or up to three levels of it, as a flat list where a directory is followed by what is under it: name, absolute path, kind (`file`, `directory`, `symlink`, `other`), size for a file, mtime, and the `hidden` and `ignored` flags. Directories come before files, then names compare with `numeric: true`, so `item2` sits before `item10`. A listing stops at 2,000 entries and says `truncated`. Symlinks are never walked into, so a link out of the folder is one entry and the listing stays inside the folder it was given. `hidden` is what waits until a person asks for everything: what `git check-ignore` says, build output by name (`node_modules`, `dist`, `DerivedData`), and a leading dot in a folder that has no checkout, where git cannot answer. Ignore status is asked once per level per checkout, so a submodule or a repository beside the project answers about itself. Rubbish the operating system keeps to itself (`.DS_Store`, `Thumbs.db`, AppleDouble) and the state a tool keeps in the folder (`.git`, `.ruimte`) are never listed, whatever the caller asks (`src/fs/visibility.ts`). The Files panel asks for everything and filters in the client, so its eye button costs no request.

`ignored` comes from one `git check-ignore -z --stdin` per level, with the listed directory as the working directory (`src/git/ignore.ts`, on the shared runner in `src/git/run.ts`). Exit code 1 means nothing matched and 128 means there is no repository; both leave every entry unignored. `.git` itself is flagged by hand, since git never reports its own directory, and an ignored directory is not walked into, so a deep listing never wanders into `node_modules`.

`fs.read { path }` (`src/fs/read.ts`) answers one file for the viewer, in one of three shapes. A text file comes back as `{ kind: 'text', text, encoding: 'utf-8', size, mtime, language? }`, where `language` is a highlighter id guessed from the extension (or from a bare name such as `Dockerfile`) and is left off when nothing recognizes it. A file the sniff calls binary comes back as `{ kind: 'binary', mime, size, mtime }` and its bytes never touch the socket: PNG, JPEG, GIF, WebP and PDF come from their magic bytes, an SVG from a head that opens as one (text, reported as an image, since that is how the viewer draws it), and everything else as `application/octet-stream`. A text file over 2 MB comes back as `{ kind: 'too-large', size, mtime }`, and the client fetches its bytes over `GET /fs/file` or `bytes.read` instead of pushing megabytes through one frame on the socket (up to 32 MB from its own machine and 8 MB from another, read only); the cap is on text alone, and an image of any size is still an image.

The sniff reads the first 8 KB. A NUL byte settles it, so does a head that will not decode as UTF-8, and more than a tenth of the head in control characters other than tab, newline, carriage return, form feed and escape does too (a log full of ANSI is still text). Text is then decoded whole, and a byte past the head that is not UTF-8 after all makes the file `application/octet-stream`, since text with replacement characters in it would be saved over the original. A UTF-8 byte order mark stays out of `text`, and `fs.write` puts it back on a file that had one. The path must be absolute and free of NUL, and the last component may not be a symlink: `fs.list` never walks into one either, so a link inside a folder cannot hand the viewer a file that folder does not hold. A path under `$RUIMTE_HOME` answers `machine-state`, by its name and by where it really leads, except the Chats project, the worktrees, the screenshots and the attachments (`src/fs/machine-home.ts`): a paired client is not the owner, and the local secret, the key pair and the approvals there are what tells the two apart. `fs.grep`, `fs.write`, `fs.create`, `fs.rename`, `fs.delete`, `bytes.read` and `GET /fs/file` draw the same line.

`fs.rename { path, to, projectId?, edits? }` (`src/fs/rename.ts`) moves or renames a file or folder, with the folders above `to` that are missing made, and answers `{ edited? }`. Both paths must be absolute (`bad-path`) and inside the roots of `fs.write`, the project folder itself stays where it is (`project-root`), `.git` at any level and `.ruimte` at the root stay closed on both sides, a name that is taken is never overwritten (`exists`, except a case-only change of the name on a volume that ignores case) and a folder cannot go inside itself (`into-itself`). A link is moved as the link. Every check is made before anything happens. With a `projectId` the language servers of the project hear of it (`LanguageHost.renameFiles`): each running process that registered `workspace/willRenameFiles` for a filter that takes the file says what it would change, the daemon makes those edits (a document a client holds open takes them in its editor through `language.edit`, any other file is written through `fs.write`'s own rules) and then moves the file, and the processes are told with `workspace/didRenameFiles`. A server that is slow (5 seconds each) or fails is left out and the move still happens; an edit that cannot be made ends the request before the move. `edits: false` skips the first half, for a client that made the edits itself. `edited` names the files the servers edited.

`fs.write { path, text, expectedMtime }` (`src/fs/write.ts`) saves a file `fs.read` answered as text and answers `{ size, mtime }`. `expectedMtime` is the `mtime` that read handed out; a file that carries another one now comes back as `stale`, and overwriting it anyway is a new write at the fresh mtime, so there is no force flag. The text is held to the same 2 MB, counted in UTF-8 bytes (`too-large`), and a file the sniff does not call text is never written over (`not-text`). Only a file that is there: nothing is created, removed or renamed. The path follows the read rules (`bad-path`, `not-found`, `not-a-file` for a directory or a symlink) and has to sit inside a project folder the calling client holds (`project.open` until it lets go or its socket drops) or a worktree of that folder's repository under `$RUIMTE_HOME/worktrees`, compared on real paths so neither `..` nor a symlinked folder leads out (`outside-project`). The `.ruimte` folder of such a root is refused on the same real paths (`ruimte-state`), since its files move only through `project.save` and its rev. The file is written in place, so its inode, its mode and its hard links stay; opening it without following a link and checking the inode against the one that was sniffed means a name swapped in between comes back as `stale` too. A file the daemon may not open for writing answers `not-writable`. Agents have no verb for this: they write with their own CLI.

`fs.create { path, kind, text? }` (`src/fs/create.ts`) makes one file or folder and answers `{ size, mtime }`, with the folders above it that are missing. The path must be absolute (`bad-path`) and may not be there yet, whatever is there, a dangling link included (`exists`); a file is made with `O_EXCL` so a name that appears in between is `exists` too, and a part of the path that is a file is `not-a-directory`. `text` starts a file and is held to the same 2 MB (`too-large`). The location is judged on real paths before anything is made, so a link out of the project creates nothing (`outside-project`), against the same roots as `fs.write`, and `.ruimte` at the root of one (`ruimte-state`) and `.git` at any level (`git-state`) stay closed, as for `fs.delete`. A path under `$RUIMTE_HOME` answers `machine-state` like the other file requests. A folder that cannot be written answers `not-writable`.

`GET /fs/file?path=<absolute>&v=<mtime>-<size>` (`src/fs/file-route.ts`) serves the bytes of an image, a video, sound or a PDF the viewer is drawing, and of a text file too large for `fs.read`, behind the same access rules as the socket, so a client sends its ticket, its session token or the local secret as `?token=`. Only those are served, decided by the same sniff: a route that hands arbitrary bytes to an `<img>` tag is a worse deal than one that does not. Text always goes out as `text/plain; charset=utf-8`, whatever its name, so an HTML file never runs in the origin of the page that asked. A video answers `Range` requests (206 with a `content-range`, 416 for bytes the file does not have) and every answer carries `accept-ranges: bytes`, without which a player can start a file and never seek in it. Headers match the project icon route: `content-type` from the sniff, `content-disposition: inline`, `x-content-type-options: nosniff`, a year of immutable caching (the URL carries the file's version, so a write moves the URL with it), and for an SVG a `content-security-policy` that allows nothing but its own styles. In dev, Vite proxies `/fs` to the daemon the way it proxies `/projects`.

`fs.watch { path }` and `fs.unwatch { path }` are per client, like a session attach (`src/fs/watch.ts`). A watch is recursive on macOS and Windows, where the platform does that in one call; elsewhere it covers only the directory it names and the client watches the folders it has open. Changes settle for 250 ms and go out as one `fs.changed { root, paths }` naming the directories that moved, so the client re-lists only what it has loaded; every batch also drops the `fs.search` cache. A recursive watch closes the watches below it, and a disconnect drops every watch the client had.

## Remote clients

Where a request comes from never grants anything: a tunnel, a reverse proxy or a port forward in front of the daemon makes every visitor a loopback address. What a process on the daemon's own machine presents instead is the local secret in `$RUIMTE_HOME/local.key`, which the daemon writes on its first start (`0600`, in a home of `0700`) and keeps across restarts. It rides where a ticket does (`?token=` or `Authorization: Bearer`) and is compared in constant time. The desktop app reads it from the home and hands it to its page over the bridge; `ruimte login`, `ruimte logout` and `ruimte status` read it and send it as a bearer. Scripts against a running daemon (`bun run smoke`, `scripts/calibrate-processes.ts`) read it from `RUIMTE_HOME` the same way. A client on the local secret is the owner of the machine (`isOwner` in `src/auth/access.ts`).

Every other client comes in through the account: a statement from the address book (see "One account per machine"), carried in the offer of a direct connection. There are no pairing links. The routes a client of before used for one (`/auth/pair`, `/auth/pairing-token`, `/auth/challenge`, `/auth/ticket`) answer 410 with a sentence, and `auth.pairingToken` and `auth.registerKey` answer `pairing-removed`; both go a release later. A record of a client a link or a session token let in is dropped as `auth.json` loads.

A direct connection is a WebRTC DataChannel (`src/pulsar/peers.ts`), and its signals reach the daemon one of two ways, both through one `SignalGate` (`src/pulsar/signal-gate.ts`): over the broker the machine announces itself to (`src/pulsar/broker-relay.ts`), or through the door on the local network. The gate drops a signal whose signature does not hold, answers an offer from a key the machine does not know with `not-paired` unless its statement lets that key in, and ties every attempt to the key that offered it on both routes at once. The channel then runs its own handshake (`src/pulsar/channel-auth.ts`): the daemon signs a challenge over the binding of the channel's DTLS fingerprints, the client signs it back with its key, and the daemon answers with a ticket. The binding is what keeps the route out of it: a broker or anything on the network that swaps a fingerprint breaks the handshake. The ticket rides on the HTTP routes an `<img>` fetches, is good for twelve hours from its last use and lives in the daemon's memory only. The daemon's key pair sits next to its id in `$RUIMTE_HOME/endpoint.json`; the clients' public keys sit in `$RUIMTE_HOME/auth.json`, listed with `auth.sessions` and cut off with `auth.revoke`, which drops that client's tickets and closes its open channels (code 4001). A revoked key stays out: its next statement gets nothing.

A browser sends its page's origin with the upgrade; the daemon accepts its own origin, the desktop app's (`app://ruimte`, `DESKTOP_APP_ORIGIN` in `packages/contracts/src/machine-http.ts`) and any loopback origin (the dev server), and refuses the rest. The desktop app's page is served by the shell and not by the daemon, so every HTTP request it makes here crosses origins: a request from an accepted origin gets `access-control-allow-origin` naming that origin (never `*`) and a preflight is answered with the methods, the headers and private network access (`crossOriginHeaders` and `preflightHeaders` in `src/auth/access.ts`). A credential rides as a bearer or in the query, never as a cookie, so that hands a page nothing it could not ask for already. The daemon serves no page of its own; `--serve` from a service definition of before is taken and ignored for one release.

### The door on the local network

`src/pulsar/lan-door.ts` is a listener of its own on every IPv4 interface, at the daemon's port plus 10 (`--lan-port`), that answers one WebSocket at `/signal` and a 404 for everything else, so the API stays on loopback while a client on the same network or the same tailnet signals without the broker. The client speaks first with a nonce of its own (`hello`), and the machine answers with its id, its key and its signature over that nonce (`lanDoorMessage` in `packages/pulsar/src/signing.ts`). A client sends nothing about itself until that signature holds for the key it pinned, so a stranger at a private address that another network reuses learns nothing of it. After that the frames carry the signed envelopes a broker relays (`packages/pulsar/src/lan-door.ts`). A signal before `hello`, a second key on one socket or a signature that does not hold closes the socket; one address opens at most 30 sockets a minute and holds at most 8. A socket carries the signals of one attempt only, and the channel outlives it.

`endpoint.info` and `endpoint.changed` carry `lan: { port, addresses }` while the door is open (null while it is closed), with the addresses read from the interfaces at the moment they are asked (`src/pulsar/lan-addresses.ts`: the private ranges first, then `100.64.0.0/10` for a tailnet, never a container or VM bridge), so a machine that moved to another network says so without a timer. A client remembers them and tries every one at once before it tries the broker. The door is open unless a person closed it (`lanDoor` through `endpoint.setIdentity`, kept in `endpoint.json`) or `--no-lan` keeps it closed (`lanDoorFixed`). A port that is not free leaves the door closed with one line in the log; the daemon runs on.

### Push notifications

A client with a key (the iPhone app) hands the daemon its push subscription with `push.subscribe`, and the daemon keeps it on that client's session in `auth.json`, so a revoke takes it along. The daemon decides every push itself (`src/push/service.ts`) and posts it signed and encrypted to the address book, which only relays it to APNs (`apps/pulsar-worker/APNS.md`). Nothing goes to a client while it holds a socket to the machine, and a snoozed node raises nothing until its snooze ends.

What a device hears of is its own choice. `notify` lists the kinds: `needs-you` (an agent waits on a person, a task failed or an agent's `alert`, and the approval cards too while `approvals` is on), `turn` (a turn ended, idle or with an error) and `process` (a warning of the process monitor about a node, once while it stays raised; one about no node has nowhere to open and is left out). `projects` holds a list of its own per project id, which wins over `notify` for every node that project places, and an empty list keeps the project quiet. Without `notify` a device hears of `needs-you` only, which is all a device heard of before it could choose, and a subscription that names no project follows `notify` everywhere. A kind this machine does not know is dropped from either list instead of refusing the subscription, so a newer app still subscribes to an older machine. A finished turn and a process warning travel as the existing alert kinds `turn` and `attention`, outside `push-attention.json`, so they mark nothing unread on another client, and each under a collapse id of its own per node (`pushCollapseIdMessage` with a lane), so neither replaces a wait or an approval still open on the phone. A read receipt clears by node and time and not by collapse id, so it still takes away the wait it acknowledges. `push.preferences` answers the asking client's own subscription with the defaults filled in, `subscribed: false` when it has none.

### One account per machine

A machine is on at most one address book account, and it is shared only with its owner. It goes on an account when it signs a registration: `endpoint.signRegistration` (only for the owner, `isOwner` in `src/auth/access.ts`; any other client gets `forbidden`), `POST /machine/registration` for `ruimte login`, and nothing else. The account is written to `auth.json` before the signature leaves the daemon, since anyone holding the signature can post it. The same account again signs as before; another one is refused with `machine-has-account` until a person on the machine takes it off, with `endpoint.leaveAccount` (Settings, Machines, the row of this machine) or `ruimte logout` (`POST /machine/leave-account`), both local secret only. `endpoint.info` names the account (`accountId`, null for none) to a client on the local secret and to no other.

A client the machine does not know yet gets in on a statement from the address book (`src/pulsar/statement.ts`). Besides the v1 signature over the machine id, the client key, the nonce and the times, a current address book signs v2 over the key its row lists the machine with and the account. A statement with v2 fields has to name this machine's own key and carry a v2 signature that holds, so an account that listed a known machine id under a key of its own gets nobody in. Which account it may name is decided in `AuthStore.admitStatement`, at the moment the key is let in:

- On an account, only a v2 statement of that account lets a client in; one without the v2 fields is refused, so a broker or an address book from before v2 cannot open a bound machine.
- Taken off its account by a person, no statement lets anyone in until the machine signs for an account again.
- On no account yet, a v2 statement of any account lets a client in, since its machine key says that account lists this machine, which only a registration the machine signed does; one without the v2 fields is refused (`account-required`). A statement never puts the machine on an account.

Each client a statement let in keeps the account it came through. Going on an account cuts off a client another account let in; leaving the account cuts off every client a statement let in, and closes their channels at once.

## Provenance

Which chat wrote which lines of a file, for the editor's bar in the gutter and the card on it (`src/provenance/`, invariants in its `CLAUDE.md`). It is an observer of `ChatCore` and only notes, in `$RUIMTE_HOME/provenance/<projectId>/<hash of the path>.json`: the line hashes of the file as the daemon last read it, and per run the chat, the turn (its place in the chat), the provider, when, the first 400 characters of the prompt, the lines (`start` and `end`, one-based and inclusive; `end` one below `start` for lines that were only removed), the lines it replaced (`before`, left out above 200 lines or 16 KB), a review state (`pending`, `kept`, `undone`) and `via`.

A write is noted when its tool call completes. Claude's `Edit`, `Write` and `MultiEdit` (the Apple backend uses the same names) name the file in `input.file_path` and carry the text they wrote; Codex's `ApplyPatch` lists its `changes`, each with a unified diff. The daemon reads the file again and diffs it against the tree the turn's checkpoint took when the turn began (the file's own record when there is no checkpoint), keeping the hunks the call explains by the lines it says it added and removed, so a person's edit saved in the meantime is not taken for the agent's. Without either version the lines are looked up in the file by what the call added. A turn that changed files only its checkpoint shows (a shell command, a formatter) gets runs with `via: 'checkpoint'` once the checkpoint settles, for the lines no run covers: there the author is a likelier guess than a fact. Only files inside the project's folder count, so a chat in a worktree marks the files of its own checkout and none of the main folder.

Every read and every record maps the runs through what changed in the file (a line diff of the hashes): lines move with the text, a run whose lines were all rewritten is dropped, and one cut by an edit stays as pieces that share its id. Provenance ends where git blame takes over: a line the file at HEAD holds unchanged is given up, checked at the next record or read, so a commit costs a run its lines at the next look. Runs older than 30 days go too, a file that is gone loses its record, a project that leaves the registry (`project.delete`) loses all of its records, and a project keeps at most 300 records and a file at most 500 runs.

`provenance.read { projectId, path }` answers `{ mtime, lines, runs }`, the runs mapped onto the text on disk now (a client holding another version asks again), and `provenance.review { projectId, path, runIds, state }` answers `{ updated }` and covers every piece of a run. Both refuse a path outside the project and under `$RUIMTE_HOME` like a file request does. `provenance.changed { projectId, path, chatId, turnId, live }` goes to every client that holds the project when a tool call starts or finishes writing a file (`live` while the turn runs), when a review changes and, with `live: false`, when the turn ends. No verb reaches this, and no setting turns it off: it is only written.

## Git status, diffs and staging

`git.status { cwd }` (`src/git/status.ts`) answers what the git panel draws: whether the folder is a repository at all, its root, the branch (null on a detached HEAD, which the `detached` flag tells apart), the upstream with `ahead` and `behind`, the base branch and the merge base against it, and the changed files. The parse is `git status --porcelain=v2 --branch -z --untracked-files=all`, with `git diff --cached --numstat -z` and `git diff --numstat -z` for the counts of each side; an untracked file has no history, so its count is one `git diff --no-index /dev/null <path>`, run for the first hundred of them. A file that is staged and changed again since is in two groups, each carrying the counts of its own side, which is what makes staging half a file readable. Renames keep the path they came from. The list stops at 1,000 files and says `truncated`. The base branch is `refs/remotes/origin/HEAD`, else `origin/main`, `origin/master`, `main`, `master`, remembered per repository for five minutes.

`git.watch { cwd }` and `git.unwatch { cwd }` are per client, like a folder watch (`src/git/status-watcher.ts`). The working tree and the git common dir are both watched (a linked worktree keeps its refs in the repository it came from), a burst settles for 300 ms, and a burst whose every path is a loose object, a lock file or something git ignores never costs a status run at all. Only a status that differs from the last one goes out, as `git.status { cwd, status }`; every burst that mattered also goes out as `git.changed { cwd }`, because a second edit to a file that was already modified leaves every word of the status alone while the diff of that file is another one, and an open diff tab reads the bytes. Watching is not free, so it gives up rather than slow the machine down: a repository with more than 5,000 tracked files never gets a watcher, and one whose status run takes longer than a second loses the one it had. The status then says `live: false` and the client goes back to refreshing on focus and after every change it makes itself.

`git.diff { cwd, path, scope, staged?, ignoreWhitespace? }` (`src/git/diff.ts`) answers one file's unified diff with its counts, a binary flag and an `omitted` reason when the diff is binary or past the caps (2,000 lines, 128 KB). `ignoreWhitespace` adds `--ignore-all-space` to the patch and to the numstat both, so the counts always match what the diff shows. `worktree` is the working tree against the index, or the index against HEAD with `staged`; `base` is the merge base against the working tree, so a file shows everything the branch did to it, committed or not. An untracked file is read against `/dev/null` with `--no-index`. One file in the `worktree` or `base` scope also answers `oldText` and `newText`, the whole file on either side of the patch (empty where it does not exist), so the tab can unfold the lines between hunks; both are left out when a side is not text, is past 512 KB, lies outside the repository or no longer matches the patch. `diffTrees` lives here too: a turn's checkpoint diff (`src/git/checkpoints.ts`) and the panel share it, so a diff is capped and shaped the same way wherever it shows up. `commit` is one commit against the one before it: with a `path` it answers that file, without one it answers the whole commit (`files`, `truncated` and the log row that names it), which is what a commit opened from the log draws. A commit with no parent is read against the empty tree. `base` names the ref the base scope measures from, through its merge base with HEAD, instead of the repository's base branch (a worktree's diff tab passes the branch it was made from; a ref that no longer resolves falls back). The base scope without a `path` answers every file of the checkout as `files`, untracked ones included: the working tree is written to a tree through a throwaway index copied from the checkout's own, so the person's index is never touched.

`git.blame { cwd, path }` (`src/git/blame.ts`) answers who wrote each line of a file as it stands in the working tree, for the editor's code vision: a table of the commits that wrote at least one line (hash, short hash, author name and email, author date, summary) and one index into it per line, `-1` for a line no commit holds yet, whether typed or staged. It is `git blame --porcelain`, whose per-line headers carry a commit's fields only the first time it shows up. `path` is relative to the repository root and held to the checkout the way a diff's path is. A file git has no history for (untracked, or a repository without a commit) answers no lines and `omitted: 'untracked'`, and one past 2 MB or 20,000 lines `omitted: 'too-large'`. Blame never runs for text the client has not saved: the client maps its lines through its own edits.

`git.stage { cwd, paths, staged }` stages the paths (`git add`, deletions included) or takes them back out (`git restore --staged`, or `git rm --cached` in a repository without a commit). `git.discard { cwd, paths }` throws work away without throwing it away: the paths go into a stash of their own named `ruimte-discard-<timestamp>` first (`git stash push --include-untracked`, which is also what resets the working tree), so `git stash pop` is the way back. It answers the stash's name, or null when git found nothing to stash.

## Git branches, the log and the actions

`git.refs { cwd }` (`src/git/refs.ts`) answers every branch the panel can switch to, local ones first and remote ones after, newest tip first (`for-each-ref --sort=-committerdate`), with the branch HEAD is on marked, the base branch marked as the default, and the checkout of a branch another worktree has out, since git refuses to check that one out twice. The stashes come along in the same answer (`stash list`), because the menu that pops one is the menu that lists the branches.

`git.log { cwd, limit?, cursor? }` (`src/git/log.ts`) is a page of the checkout's own history: hash, short hash, subject, author, author date and the refs pointing at the commit, parsed from one `log -z --format=...` per page. The cursor is how many commits were handed out before this page, not a hash to continue from, so a commit landing on top while the log is open does not make the next page skip one. A repository without a commit answers an empty log, not a failure.

`git.action { cwd, actionId, kind, ... }` (`src/git/actions.ts`) is every action the panel takes as one request: `fetch`, `pull`, `push`, `publish`, `force-push`, `sync`, `checkout`, `create-branch`, `rename-branch`, `delete-branch`, `merge`, `rebase`, `stash`, `stash-pop`, `commit`, `commit-push` and `create-pr`. Each is a list of git calls whose output is read while it runs (`streamCommand` in `src/git/run.ts`, which splits on both line endings, since git writes its progress with carriage returns); every line goes out as `git.progress { cwd, actionId, phase, line }` to the client that asked, and the reply carries a summary line, everything the commands wrote and, where there is one, the commit that was written or the pull request that was opened. A failure is a `git-failed` error whose message is that output, which is what the toast puts behind "Copy output". There is no shell anywhere: arguments are lists, so a branch name or a commit message is one argument however it is spelled. `GIT_TERMINAL_PROMPT=0` keeps a credential prompt from stalling a push nobody can type into, and a step that talks to a remote is given up on after two minutes. The client names the run, so `git.cancel { actionId }` ends the git that is going right now.

`push` without an upstream is `push --set-upstream origin <branch>`, which is what the panel calls "Publish branch"; `force-push` is `--force-with-lease`, so a push somebody else made in between stops it. `checkout` of a remote branch makes the local branch that follows it (`checkout --track`) unless a local branch of that name is already there, and `stash: true` parks a dirty working tree first. `delete-branch` needs `force` for a branch git has not merged anywhere. `create-pr` is the one step that is not git: it publishes the branch when the remote has never seen it and then runs `gh pr create --title ... --body ...`, answering the URL out of what `gh` printed.

`git.capabilities { cwd }` (`src/git/capabilities.ts`) says what this machine allows: whether `gh` is on the PATH, and which agent CLI would write a commit message, both cached for a minute.

`git.suggestMessage { cwd, actionId, provider? }` (`src/git/message.ts`) is that message. The staged patch (24 KB, `--unified=1`) and its name-status go into a prompt asking for one JSON object with a subject and a body, and the CLI runs in its own one-shot print mode: `claude -p <prompt> --output-format text`, `codex exec --sandbox read-only <prompt>`, `gemini --prompt <prompt>`, which is `oneShotArgs` on the provider value (`@adecore/agents/providers/provider.ts`). No chat, no session, no SDK. The answer is the last JSON object in whatever the CLI printed around it, and a run past sixty seconds, or one `git.cancel` names, is killed. With nothing staged the working tree is used instead; with no CLI installed the request fails and the client hides the button that would have asked.

## Worktrees

`git.worktree-add { repo, branch, projectId? }` answers the worktree for a branch of the repository, making it under `$RUIMTE_HOME/worktrees/<repo>-<hash>/<branch>` when it does not exist (a branch that does not exist yet is created from HEAD). The repository itself is never touched beyond what `git worktree` records. `<repo>` is the main checkout, the first entry of `git worktree list --porcelain`, so a path inside a worktree names the same repository as the project folder.

Beside those folders lies `worktrees.json` (`src/git/worktree-register.ts`), keyed by the path git reports: the branch, `from` (the branch the calling checkout was on, left out on a detached HEAD, and the commit the worktree's branch shares with it), the project, the node (written by the verbs once the node has an id), `madeBy`, `madeAt` and whether the daemon made the branch. Git stays the truth about which worktrees exist; the register only adds what git cannot say, and a worktree made by hand simply has none of it.

`git.worktree-list { repo, inspect? }` answers every worktree but the main checkout with the register laid over it, `missing` when the folder is gone (git's `prunable`, or a stat that fails, since a locked worktree is never prunable), `locked`, and a register entry whose worktree git no longer lists while its branch exists (listed as missing). With `inspect` each carries `work`: `changed` and `untracked` from one `status --porcelain=v2 -z -uall --ignore-submodules=all` (ignored files are not work, an untracked folder counts per file), `ahead` as `rev-list --count` of HEAD and every branch the worktree is or was on, against the target (`from.branch` while it exists, else the base, else `from.commit`, else every other branch), and `operation` for a rebase, merge, cherry-pick or revert that stopped halfway, since a stopped rebase leaves HEAD on the target while the branch still holds the commits. A missing worktree can only count commits.

`git.worktree-remove { repo, path, force?, keepBranch? }` refuses a worktree with any work in it (`worktree-has-work`, the three counts in the message) and a locked one (`worktree-locked`) unless `force`, then runs `git worktree remove --force` (twice for a lock), falling back to `git worktree prune` for a missing folder a git cannot remove. The branch goes along only when the register says the daemon made it and the worktree is still on it (an agent that switched branches leaves both), with `branch -D` once no commit on it is missing from the target or under force, never `-d`, which measures against the main checkout's HEAD. A branch outside the register goes only with `keepBranch: false`. The answer carries `branchDeleted` and `branchCommit`, the tip it had, since after `worktree remove` no reflog holds it. The register entry and the worktree's checkpoint index go too, removals run one at a time per repository, and every add, claim and removal tells every socket `git.worktrees { repo }`.

`git.worktree-merge { repo, path, actionId, strategy, commitFirst?, subject?, body?, remove?, stopAgent?, into? }` (`src/git/worktree-merge.ts`) lands a worktree's branch on the branch it was made from (`into` overrides it), in the checkout that has that branch out, never by moving a ref behind a working tree. It holds the same per-repository lock as a removal, so a second merge or removal of the same worktree waits and then finds it merged or gone (`worktree-not-found`). Refusals before anything changes: `worktree-missing`, `no-branch` (a detached HEAD), `worktree-busy` (an operation halfway in the worktree), `target-not-checked-out` (the message ends with the branch the main checkout is on), `target-busy`, and `agent-working` while a chat in the worktree has a turn or a terminal's hooks say its agent runs. With `stopAgent` every live chat or terminal in the worktree, and the node it was made for, is stopped the way a person stops it (`EndChildrenWiring.stopNode`, which also ends the agents it opened) before the work is counted again. Uncommitted and untracked files are committed in the worktree under `subject` with `commitFirst` and refused with `worktree-has-work` without it, so a merge never lands half of the work. Then `merge` runs `merge --no-edit --no-ff`, `squash` runs `merge --squash` and a commit with `subject`, and `rebase` rebases the worktree onto the target (a conflict there is `rebase --abort` and `merge-conflict` with the files) and fast-forwards the target. Every git call passes `-c merge.autoStash=false -c rebase.autoStash=false`, so nothing is ever stashed on anyone's behalf. Git refusing over a changed file of the person's comes back in git's words as `git-failed` and changes nothing. A conflict in a merge or squash stays in the target checkout for the panel to show: the answer is not an error but carries `conflicts` and `cwd`, and `git.worktree-abort { cwd }` takes it back (`merge --abort` with a MERGE_HEAD; `reset --merge` and the SQUASH_MSG removed for a squash, which keeps unrelated changes). With `remove` a merge that went through removes the worktree and its branch like `git.worktree-remove` without force (the commits of a squash no longer count as work), unless a chat or shell still runs in it, which `kept` says. Progress goes over `git.progress` under `actionId` and `git.cancel` stops it before its next step.

## Context links

A standalone AI-chat view has no canvas links. Its startup instructions tell the model to skip linked-context discovery and use native subagents for routine work. When a person names an agent or model, `agent --task` or `team --task` starts hidden agents whose results return to this chat. Canvas chats keep opening visible nodes on their own canvas. `--view` explicitly places an agent or team on a canvas, and the instructions reserve it for a person's canvas request.

Hidden agents live under `$RUIMTE_HOME/hidden-agents/<id>.json` (`src/agents/hidden-agents.ts`), outside the project's views and shared file. `ProjectIndex` includes them in session placement, titles and direct-child reads, while their linked-source list stays empty. The normal outbox, lineage, permission ceiling and task machinery start and resume them; task rows open their conversations and return their results. A hidden chat can receive another task or start a hidden helper within the same depth limits. Completed hidden agents free the concurrent-agent count while their conversations remain readable. Stopping a parent stops its hidden children; deleting the parent also removes their hidden placement after they stop.

An edge on the canvas into a terminal or chat node lets that agent read the source. The daemon derives what each agent node may read from the project documents it knows (`src/projects/project-index.ts`, which keeps every known project's last document, also after a client lets go of it): a text element or a note with its content, a file node as its path, a browser node with its address, a device node with the reference it points at, a terminal, chat or drawing by id. A group is the corner of the canvas it frames: a line out of it makes everything inside readable, each under its own title and a frame inside it included, while the frame itself is never a source. A drawing or diagram is listed under the id of the view it mirrors, and `read` also takes the id of the node it is linked through, which is the id `node list` and `link list` show; a node with no line into the caller stays refused. The one exception is a terminal or chat the caller opened itself with `agent` or `team`: the lineage under `$RUIMTE_HOME` that `answer` checks lets `read` take its id with no line from it, `--tail` and `--subagent` included, without listing it (`src/context/opened-child.ts`). Only that one step: a grandchild is its own parent's to read, and a child reads its parent no more than before. It reads terminals, chats, drawings, browser pages and devices live when asked. A drawing arrives as its texts in reading order with the arrows between them as `A -> B` lines, and the whole picture as an SVG behind a heading of its own, so an agent that only wants to know what the drawing says can stop at the list. An edge between two other nodes is only a line; it makes nothing readable. Every shell and chat gets `RUIMTE_CONTEXT_URL` (`http://127.0.0.1:<port>/context`), a bearer token (`RUIMTE_HOOK_TOKEN` in a shell, `RUIMTE_CONTEXT_TOKEN` in a chat) and the directory of `ruimte-context` in front of its PATH (`apps/server/bin` in a checkout, the app's `bin` resource when packaged), where `ruimte-context` lists the linked sources and `ruimte-context read <id>` prints one. A `read` without an id or of an id nobody linked is a refusal in the dialect a verb refuses in (`refused	<code>	<message>` on stderr, exit 3, codes `bad-arguments` and `unknown-source`) with the sources that are linked under it, so a caller that guessed an id gets the list instead of a failure. A daemon that answers 500 or does not answer at all stays exit 1.

What `read` gives back follows the kind: a text (a note, a text on the canvas) its own text, a terminal the last 2000 lines of its screen, a chat the thread as markdown (a question or an approval as one line with its state and request id), a drawing its reading order with the SVG under it, and a file its path with a line telling the agent to read it with its own tools. A browser answers its address and, under it, the text of the page, read the moment it is asked and capped at 40000 characters. A page this machine runs is read here; one a client draws itself (the desktop's `<webview>`) is asked of that client with a `text` drive, and the address is where the page is now. Nobody holding the page leaves the address from the project file, which the answer says. A device answers which device the node points at, looked up among the devices this machine has right now (`src/devices/manager.ts`): its name, platform, kind and runtime from the node, and the state, `deviceId` and `backendId` from the machine, so an agent asked to put something on it needs no second question. A device that is not there, unplugged or removed, is said to be gone instead of answered with ids that mean nothing. `ruimte-context help read` says the same, from the same constants.

`ruimte-context read <id> --tail N` is the cheap read next to the whole one: the last N lines, where the last fifteen of a neighbour is usually the whole answer. The CLI only checks that N is a positive whole number and sends it as `?tail=N`; the daemon does the counting, because only the side that renders a chat or a drawing knows what a line of it is, and because the wire then carries fifteen lines instead of two thousand. A line is a line of the screen for a terminal (the 2000-line cap stays the ceiling, so a larger N reaches no further back), a line of the rendered markdown for a chat, a line of the text for a text, and a line of the reading order for a drawing, which leaves the SVG out altogether: the picture is the expensive half and the last lines of it would be markup. A line of the page text for a browser, which keeps the address above it. A file and a device ignore it, since their whole answer is a handful of lines.

## Canvas verbs

Any other first word is a verb of its own or a noun: `ruimte-context <verb> ...` and `ruimte-context <noun> <action> ...` post `{ argv }` (the words after the first) to `POST /canvas/<verb or noun>` with the same bearer token, and the daemon parses them (`src/canvas`), so a CLI from an older build never disagrees with the daemon about what a verb takes. The registry in `src/canvas/verbs.ts` is a tree: a verb of its own (`defineVerb`) holds its synopsis, its help lines and its handler, and a noun (`defineNoun`) holds its actions (`defineAction`), each with the same three. The parser dispatches from that tree and `ruimte-context help` renders from it, so the two cannot drift. The actions of `view`, `node`, `link`, `task`, `plan`, `browser`, `worktree` and `operation`, and the verbs `notify`, `answer`, `done`, `agent` and `team`, are adapters over the daemon's own action handlers (`src/actions`, one registry in `server-actions.ts`): `defineActionVerb` (`defineStandaloneActionVerb` for a verb with no noun, both in `src/canvas/action-verb.ts`) turns the words into the input of a catalog action from `@ruimte/actions`, runs it as the agent under the caller's id and prints what it answers, so an agent runs the same named action, with the same input schema, as a person and Voice do. What those verbs enforce (who made a node or a view, the folders a `--cwd` stays in, that only `agent` and `team` start a CLI, the depth, the per-caller count and the mode ceiling of every start, which line a message or a page drive needs, who owns a task, what a plan lets an agent set, whose worktree an agent may merge) lives in the handlers, and the length limits a flag holds are in the action's input schema as well, so every caller of the action is held to them. Their `help` takes its about line and its field lines from the action definition. `node new`, `agent`, `team` and `plan new` are the ones of them that take `--dry-run`, which the registry passes to a handler that says it can preview and refuses for any other. `agent.start` and `team.start` answer `running` with an operation id instead of `completed`, since starting is not succeeding; the CLI prints what they made as it always did, `operation get` follows the rest and `operation cancel` stops the turns they set going. It also names `list` and `read` so one list documents everything the CLI does; those two are answered by `GET /context`, and `POST /canvas/list` or `/canvas/read` is a 404 refusal (`not-a-canvas-verb`) that points at the CLI. A noun without one of its actions is refused (`unknown-action`) with the synopsis of each; a first word that is neither a verb nor a noun is `unknown-verb`, with a `detail	ruimte-context help` row and the root rows under it. There are no aliases for spellings from before the nouns (`nodes`, `edges`, `rename`, `open`, `node <kind>`, a bare `link`): they are unknown like any other word.

- `help [noun] [action]`: without arguments one row per verb of its own, `verb	name	arguments	summary`, and one row per noun, `noun	name	action|action|...	summary`, so the root stays short; then the `scope`, `ids`, `dry run` and `detail` rows and the row about refusals and exit codes. Every row says in its first field what it is, so nothing below the list reads as a verb. The `scope` row says that `list` and `read` are what a person linked into this session while `node`, `link`, `view`, `task`, `agent`, `team`, `done`, `notify`, `answer` and `worktree` are the project itself and `plan` and `visual` the chat of the caller, and that a node an agent adds is readable through `read` only once a line runs from it into the caller; the same row is in the detail of `list`, `read` and `node list`, which is where an agent meets the confusion. The `dry run` row names what takes `--dry-run`, rendered from the registry. `help <noun>` prints the noun's own lines and an `action	noun action	arguments	summary` row per action; `help <noun> <action>` and `help <verb>` print everything that one takes: its synopsis, what it prints, which flag goes with which kind and what it is for, where a node lands, and how paths are resolved. Every line is tab-separated and comes out of the registry entry the same parse runs from (`detail` on the entry, the kind and flag columns derived from the tables `run` checks against), so help cannot claim a pairing the daemon refuses. A refusal over arguments ends with a `detail	ruimte-context help <verb>` or `detail	ruimte-context help <noun> <action>` line.
- `node <list|new|edit|rename|delete|group|arrange> ...`: the nodes of a canvas.
    - `node list [--view V]`: the nodes of a canvas, `id kind title x y w h group`, where x and y are the node's top left corner in canvas pixels and may be negative and `group` names the frame the node stands in (empty on the canvas itself, the innermost frame when they nest). The last line is not a node: it is `self` with the caller's own id, or `self -` when the caller is not a node on that canvas. A terminal session can also read its id off `RUIMTE_SESSION_ID`, but a chat backend is given no such variable, which is what the `self` row is for.
    - `node new <note|browser|drawing|diagram|file|terminal|chat> [--title T] [--text B] [--url U] [--path P] [--source V] [--cwd P] [--view V] [--beside N] [--dry-run]`: adds one node and prints `id kind viewId edgeId`. `--text` is a note's body, `--url` (http or https) is required for a browser, `--path` (a file) for a file node and `--source` (a drawing or diagram view of the project) for a drawing or diagram node; `--cwd` is only for a terminal or a chat and must lie inside the project folder or a worktree of its repository. A flag that does not belong to the kind is refused. A relative `--path` or `--cwd` is resolved against the project folder, never against the caller's own directory, which the daemon does not know; an absolute `--path` may point outside the folder and is then stored absolute. `--beside` puts the node right of that node wherever it sits; without it the node lands on the first free spot right of the caller, or right of everything on the canvas. Without `--title` a node is called what a person's click would have called it (a note `Note`, a file its own name, a drawing the name of its source). The verb draws one line, from the caller into the new node, so the canvas says where it came from: into a terminal or a chat it is a context line, the one `agent` draws, so that node can read the caller with `ruimte-context read`; into anything else it carries the role `origin`, which says who put the node there and grants nothing over it. A caller that is not a node on that canvas gets no line and a `-` in the last column. A canvas holds at most 500 nodes. A terminal or chat made this way starts no process until a client shows it.
    - `node edit <nodeId> --text B [--append] [--view V]`: writes the body of a note and prints `edited id lines characters`, counted on the note as it stands after the write. Only a note (`not-a-note`): a file node is the file system's and a browser, a terminal or a chat shows what it runs. Who may write is not `node delete`'s rule but a wider one, because a note two agents keep together is the point: a note the caller made, or one an edge joins it to, whichever way that edge runs, since the line is what a person drew and it is the same grant `notify` travels along. Without `--append` the text replaces the body, and an empty `--text` empties the note; with `--append` it lands on a line of its own under what is there, which is how two agents take turns without dropping each other's work. `\n`, `\t` and `\\` in `--text` are read as escapes and `--text -` takes the body from stdin, the way `node new --text` does. The body is read inside the mutation, under the project's lock, so two appends that cross keep both lines; a body that is already what the call would write changes nothing and is not a refusal.
    - `node rename <nodeId> --title T [--view V]`: renames one node and prints `id kind title`. It sets `titleSource: 'user'`, like `view rename` does for a row in the sidebar, so the session the node holds never renames over it again. One node per call, by id, and a rename to the title it already carries writes nothing.
    - `node delete <nodeId>`: removes one node and prints `deleted id kind title`, an `ended id kind` line when it held a session, an `edges <count>` line for the lines that ran into or out of it, and for a group a `members <count>` line. An id it cannot find is refused with the nodes this same call would remove, never with the caller's own node or a node it did not make, since an alternative that is refused a line later is worse than no list. The rule is `view delete`'s: only a node the caller made, unless the machine's setting frees every one; never the caller's own node (`deletes-caller`). A terminal or chat node is ended before the write, so no shell outlives the node it answered to. A group loses its frame and nothing else: the nodes inside it stay where they stand, because they are not the caller's to take along, which is also why there is no separate `ungroup` action. The node is looked for on every canvas of the project, so this takes no `--view`.
    - `node group --nodes A,B [--label L] [--color C] [--view V]`: draws a frame around nodes that already stand together and prints `id group label viewId members`, with an `also id kind title` line per node that was not named but ended up inside the frame. The frame is the box those nodes occupy plus the room and the title band a person's own grouping gives it, from `groupFrame` in `packages/contracts`, which the client's `groupSelection` runs as well, so the two ways to group cannot drift. `--color` is one of the node accents (the same closed set the client's swatches come from, `NODE_ACCENT_NAMES` in contracts) and a value that is not one is refused with all of them. A group is never one of `--nodes` (`not-groupable`), the way the client leaves one out of a selection, and every node has to stand in the same place already, all on the canvas or all inside one and the same group (`different-groups`, which names both nodes and where each of them stands). Inside a group that is folded shut the new frame joins its `memberIds`, since nothing reads geometry while it is collapsed. The frame takes the caller's own lines into what it now holds along with it and gets one line from the caller instead, the same line `node new` draws into what it makes, reported as `edges <count> <edgeId>`: a line into a group makes everything inside it readable at once, so a line per node says nothing more. Only a line whose ends are both the caller's goes, the rule `link delete` follows, and either direction counts; a line a person drew stays, and a frame the caller had no line into is left without one.
    - `node arrange --nodes A,B [--layout grid|row|column] [--cols N] [--view V]`: lays those nodes out without overlap, in the order they were named, and prints `id x y` per node. The block starts at the top left of the box they already occupy, so a canvas is straightened where it stands and nothing jumps out of sight; one node therefore never moves at all. A column is as wide as the widest node in it and a row as tall as the tallest, 40 px apart like everything else the daemon places, and nothing is resized. Without `--layout` it is a grid as square as the count allows (`gridColumns`); `--cols` only means something there and is refused on a row or a column (`flag-not-for-layout`), as is a number past the count (`too-many-columns`, which names both). A group carries whatever stands inside it, so it is not something to arrange (`not-arrangeable`). Nodes that already stand where this would put them are reported and nothing is written. The layouts themselves are `arrangeRects` in `src/canvas/placement.ts`, beside the other placing.
- `agent <claude|codex|gemini|copilot> [--terminal] [--prompt T | --prompt-file F] [--cwd P] [--view V] [--beside N] [--group G] [--title T] [--task T] [--model M] [--mode M] [--worktree [--branch B]] [--dry-run]`: opens an agent node that starts working and prints `id kind viewId cli edgeId`, and with `--task` the id of the task last (see tasks below). A CLI with a chat backend (Claude Code and Codex today) opens as a chat node fixed to that CLI, since its last answer settles a task where a terminal child has to call `done`; `--terminal` asks for a terminal node running that CLI instead, and a CLI without a chat backend is always one. A CLI that is not installed on this machine is refused with the ones that are. The node lands where `node new` would put it, unless `--group G` names a group node of that canvas: then it goes in a row under that group's title bar, the group grows if it has no room, and a collapsed group also takes the new id into its `memberIds`. `--group` and `--beside` cannot both say where the node goes. The verb draws one edge, from the caller into the new node, so the new agent can read the caller with `ruimte-context read`; a caller that is not a node on that canvas gets no edge and a `-` in the last column. `--mode` (see the ceiling below) is the permission mode the agent runs in, and `--worktree` starts it in a git worktree of its own (below); `--branch` names that worktree's branch and `--worktree` together with `--cwd` is refused (`worktree-and-cwd`).
- `team --label L --roles '<json>' [--view V] [--cwd P] [--task] [--mode M] [--worktree] [--dry-run]`: opens up to sixteen agents at once, in a group of their own, and prints `id kind title viewId cli edgeId` (plus the task id of each role under `--task`), the group first with its label in the title column and a dash for its CLI and its edge, and then one line per role in the order of `--roles`. The title is the column that tells two roles of one provider apart, which the order of `--roles` alone cannot, and it sits where `node list` has it. A role is `{ "title", "prompt", "provider", "terminal", "model" }` (`"terminal": true` makes that role a terminal node, as `--terminal` does for `agent`), checked against a zod schema in the registry entry, so a role that is wrong is refused by its place in the array (`role 1 (prompt): ...`); `--roles` that is not JSON is its own refusal (`bad-roles-json`), and both list the shape of a role under them. Every role gets the same prompt treatment `agent` gives one, so a terminal role starts on its prompt and a chat role has it as the first message of its thread. `--cwd` goes to all of them; a directory per role is `--worktree`, which gives every role a worktree of its own on a branch named after its title. `--mode` goes to every role. The agents stand in rows of at most four inside the frame, placed by the same `placeInGroup` a single `--group` uses, and the group is sized to hold them; it is not collapsed, so membership is geometry and there is no `memberIds` to write. One edge per role, from the caller into that agent, like `agent` draws one. Every role is started by the daemon the way `agent` starts one (below).
  For chat agents, `agent --model sol` or a team role with `"model": "sol"` selects `gpt-6.1-sol`. Model ids and catalog aliases are accepted; `help agent` and `help team` list the available ids. The selected model uses its catalog defaults. Without a model, the composer preference still applies. Unknown models and model selections on terminal agents are refused before any nodes are created, including during `--dry-run`. The explicit selection is stored with the start operation and takes precedence even if a client opens the chat before that operation runs.

- `done --result T | --result-file F`: reports the result of the task the caller was opened with and prints `done taskId parentId`. Only a node with an open task may call it (`no-open-task`); `--result -` takes the result from stdin, and a result is at most 32,000 characters. `\n`, `\t` and `\\` in `--result` are read as escapes, so a line break fits in plain single quotes: Codex's allow rule does not match a call it cannot split into plain words (`$'...'`, a heredoc), and that call waits on the person's approval. The brief under a task's prompt says so to a terminal child and tells a chat child that its last answer is the result, so it needs no call at all.
- `task list [--all]`: the tasks the caller gave and the task it was given, `task id gave|given status node title wake result batch`, where `node` is the other end and `result` the first line of the result. Without `--all` it lists only what is current: a task still open, or one the caller gave that settled and has yet to wake it (`isCurrentTask`). A `note` row counts what it left out, since an earlier run with the same titles otherwise reads as work still out.
- `task new <id> --prompt T | --prompt-file F [--title T]`: gives a task to an agent that is already open and prints `task taskId nodeId now|waiting`, followed by the same `next` line `--task` ends with; `now` means the agent is free and `waiting` that a turn of its own is still running. Without `--title` the task is called after the first line of the prompt. Only a chat may give one (`not-a-chat-parent`, the rule `--task` follows), and only to an agent it opened itself, read from the lineage under `$RUIMTE_HOME` and not from a line on the canvas (`not-yours`): two agents that read each other have lines both ways, so a line as the only condition would let them set each other to work in turn, endlessly and without a person asking for it, where lineage is a tree and cannot run in a circle. A terminal it opened is refused (`not-a-chat`): starting a turn there would mean typing into the shell a person types in, which no agent does; `notify` sends it a message and `agent --terminal --task` opens a terminal with a task on the line its CLI starts with. A task and a message are told apart by what comes back: a task brings its result to the chat that gave it and settles, a message does not, so an agent asks with a task when it needs the answer. A node that is not an agent (`not-an-agent`), one whose agent the machine has not started yet (`no-agent`) and one that is working on a task already (`task-running`, with that task's row under it) are refused as well: an agent holds one task at a time and nothing queues a second. No node is opened, so the depth, the per-caller cap and the mode ceiling have nothing to say here; the agent keeps the mode it was opened in, which was already no wider than the caller's.
- `link <list|new|delete> ...`: the lines of a canvas.
    - `link list [--view V]`: the lines of a canvas, `id from to label`, with an empty label where the line has none. `node list` says nothing about lines, so without this a caller cannot tell a link that is missing from one that only runs the other way; a canvas with no lines on it prints nothing at all.
    - `link new --to A,B [--from N] [--label L] [--view V]`: draws context lines on one canvas and prints `id from to new|existing out|back`, one line per edge. `--from` is the caller unless it names another node. Between two agent nodes the line goes both ways, since each of them then reads the other; the last column is what tells those two rows apart (`out` for the line that was asked for, `back` for the one the action drew by itself), because one `--to` answering in two rows otherwise reads as a bug. An edge that is already there is left alone and reported as `existing`, so running the same `link new` twice writes nothing; at most twenty ids in `--to`. Two edges between the same two nodes are one line with a head at both ends in the client, since two beziers along the same path lie on top of each other.
    - `link delete <edgeId> [--view V]`: removes one line and prints `deleted id from to label`; both nodes stay. The canvas is found the way `link new` finds it, and an id that is not a line there is refused (`unknown-edge`) with only the lines this same call would remove. Who drew a line is written down nowhere, so the rule is read off its ends with `node delete`'s own record: a line goes only when both ends are the caller or a node the caller made (`madeBy`), unless the machine's `agentsDeleteAnyView` frees every node, view and line. So an agent tidies the lines it drew between itself and what it opened, while a line that touches a person's node, or that a person drew into the agent as context, stays (`not-yours`, naming the end that is not the caller's and who made it). Between two agents it removes the one direction it names and leaves the other.
- `browser <state|go|back|forward|reload|stop|shot> <id>`: the page under a browser node. A line between the caller and that node is what allows it, whichever way a person drew it, the same line a `read` takes; anything else is refused (`not-linked`, `not-a-browser`, `unknown-node`). Every action prints `open	yes|no	<sentence>` and, where the page answered, `page	id	address	title`, `loading	yes|no`, `back	yes|no`, `forward	yes|no` and an `error` line when the load failed. `go --url U` takes a whole http or https address; on a node that has no address yet it writes that address into the project instead, the step a person's splash takes, and the page then opens for whoever shows that canvas. `reload --hard` loads past the cache. `shot` writes a png under `$RUIMTE_HOME/screenshots` and prints its path for the agent to open with its own tools, and shots older than a day are swept as a new one is written. Nobody with the page on screen is an answer and not a failure (`open	no`), the way `view open` says when nothing was showing.
  The page lives where it is shown, and both kinds go through one door (`src/browser/drive.ts`). A client without a browser of its own (the station, the phone) has the daemon run the page, and that one is driven here. The desktop shell draws the page in a `<webview>` of its own, so the daemon knows it only while that client says it holds it: the client reports where its page stands (`browser.hold`, `browser.release`, kept in `src/browser/pages.ts` per client and dropped with the socket) and answers an ask that goes back out over the same link (`browser.drive` with an `askId`, `browser.driveResult`, fifteen seconds before the verb answers with the last report instead). Two clients with the project open each draw their own page under one node, so an ask goes to all of them and the first answer is the one the agent reads. A click, a keystroke and a scroll are in none of this: an agent works a page by its address.
- `device <state|shot|tap|swipe|button|type|launch> <id>`: the device under a device node, a simulator, an emulator or a phone on this machine (`src/actions/device-actions.ts` behind `src/canvas/device-verb.ts`, reaching the devices through `CanvasHost.devices`, `src/devices/agent-driver.ts`). The same line a `read` takes is what allows it (`not-linked`, `not-a-device`, `unknown-node`, `no-device` for a node without a device picked); no card asks a person and computer use need not be on. The node's reference is looked up among the devices this machine has at the moment of the call, and one that is not there (`device-missing`) or not running (`device-not-booted`) is refused; an agent never boots one. `state` prints `device id name platform kind runtime`, `state`, `screen WxH|unknown`, `buttons` and one `can shot|input|type|launch|tree yes|no` row each, and under them the accessibility tree of what the device shows when it has one: `elements N WxH`, then a `tree` row per element (`[N] role "label" value= id= (x,y wxh)`, `offscreen`, `disabled`, indented by depth), in pixels of the screen, which are the pixels of a shot. `--find T` keeps the elements whose label, value or identifier holds T and what they sit in, with the numbers they have in the whole tree, and prints `matches N`. A tree that will not come is `tree none why`, and the rest of the state still stands. Reading it counts as looking, like a shot, so it passes the gate while the person holds the device. A simulator is read by the device bridge (`apps/ios-device-bridge`, `simulator-accessibility`), which `src/devices/simulator-tree.ts` keeps running per simulator from the first `state` until the agent's hold on the device ends, so a read after the first takes tens of milliseconds; a reply later than 15 s ends that process and the next read starts another. An Android device is read with `adb exec-out uiautomator dump /dev/tty` beside `wm size` (a device that cannot write there dumps to a file under `/data/local/tmp`, read and removed), and `src/devices/android-tree.ts` keeps only the nodes that say or do something, so the layouts between them drop out; a dump takes about two seconds. An iPhone has no tree and is worked in shots. The tree holds only the app in front (or an alert over it), no web content and only the rows of a list that are on screen. `shot` writes a png under `$RUIMTE_HOME/screenshots`, swept like a page's, and prints `shot path WxH`; every later coordinate is a pixel of the last shot of that device, and a call without one is refused (`no-shot`, `outside-shot`). `tap --element N` taps the middle of element N of the last `state` of that device and needs no shot; the numbers last until the next `state`, and one without a state behind it (none yet, or the hold ended) is refused (`stale-element`, `unknown-element`, `offscreen-element`). `tap --at X,Y`, `swipe --from X,Y --to X,Y [--ms N]` and `button --name B` (only a button the device announces, `unknown-button` lists them) go to the device as pointer and button input over a session the daemon holds as `agent:<caller>`, so they land whether or not a client shows the node, and a client that has it open sees them live. The hold ends a minute after the caller's last call and when the daemon stops. `type --text T` types into whatever has the focus, a newline as Return and a tab as Tab: a simulator pastes each piece through `simctl pbcopy` and a Command-V from the device helper (which replaces its pasteboard, and so takes any character), Android runs `input text` over adb (plain ASCII only), and a phone takes no text. `launch --app A` opens an installed app through the device's tools. A simulator is photographed with `simctl io screenshot`, an Android device with `adb exec-out screencap -p` and a phone with `devicectl device capture screenshot`; a phone takes taps only where its live stream is installed, and opens no app. Every step passes a gate first (`DeviceGate`, which is `DeviceControl` in `src/devices/control.ts`): it keeps, in memory, who has each device an agent operates, `running`, `paused` or `takenOver`, and every client hears each step and each change as a `device.operated` event with the device, the agent's node, the state and the step (its kind, a few words such as `button home` or `launch com.apple.Preferences`, a tap's point as a share of the screen, and a count that tells two taps apart); a fresh socket asks `device.operations` for the standing answer. A person pauses, resumes or takes over from the strip on the device node with `device.control`, from any client of theirs, and the gate then refuses every step but a shot with `paused` or `taken-over`, whose message tells the agent to wait and call again, or to stop and say what is left. An operation lasts a minute past the agent's last call, a refused one included, so a take-over ends once the agent stops asking and the clients hear `ended`; a pause stays until the person resumes.
- `alert --text "..."`: sends the person a notification from the caller's own session, only when they asked for one, such as "notify me when you are done". It respects device notification settings and prints `alerted nodeId` once queued, without promising delivery. A completed turn notifies only a device that chose finished turns (see push notifications under "Remote clients and pairing"). `--text -` reads the message from stdin; the limit is 500 characters.
- `visual <preview|show|list|remove>`: pages in the thread of the caller's own chat (`src/actions/visual-actions.ts` behind `src/canvas/visual-verb.ts`, reaching the chat through `CanvasHost.visuals`). `show --title T [--height H]` takes one self-contained HTML document on stdin, which the CLI sends untouched as `--html`, the way `view diagram` sends `--document`; `--height` is the most the frame may take, from 80 to 2000 CSS pixels, and 2000 without it. Before it is stored the page is measured at each of `VISUAL_MEASURE_WIDTHS`, so a client sizes the frame before the page loads; measuring takes at most 6 s, the wait for a free render child included, and on a timeout, a failure or a machine without Chrome the page is shown without heights and the log says why. The page then goes through `ChatCore.publishVisual` (`@adecore/agents/chat/visual-store.ts`), which stores it with the bootstrap in front and the heights beside it, and hangs it on the turn running at that moment. It prints `visual id title size` and a `shown` line telling the agent the person sees the page above its reply, so the reply neither mentions nor describes it. `list` prints `visual id title size` per visual; `remove <id>` prints `removed id title`, and an id the chat does not show is refused with `visual-not-found` and the list. Only an AI chat may call it (`visual-needs-chat` for a terminal), in every permission mode, since it changes nothing but the caller's own thread. With the machine's `visualReplies` off, `show` refuses with `visuals-off`, whose message tells the agent to answer in text and not to call it again. What the store refuses comes back under its own code and words: `visual-invalid` for an empty page, a missing or too long title or a height out of range, `visual-too-large` past 16 MiB. `preview [--width W] [--appearance dark|light]` takes the page the same way, draws it the way the chat would (`injectVisualBootstrap` with the theme of that appearance in the fragment, 768 CSS pixels wide unless `--width` says from 240 to 1600, dark by default) and prints `shot path` (a png under `$RUIMTE_HOME/screenshots`, swept like a page's shot, at most 4000 pixels tall with a `note` when the page is taller), `height px` (what the page needs at that width), one `console level text` per message (`log`, `info`, `warning`, `error`, `exception` with its stack, and what the browser failed to load; at most 20 of at most 500 characters, places in the page named `page.html:line:column` as the agent wrote them, a `note` for none or for the rest) and a `next` line saying that `show` publishes it. It refuses as `show` does, and with `preview-unavailable` on a machine without Chrome, whose message tells the agent to show the page without a preview, `preview-timeout` after 20 s and `preview-failed`. Both run in a render child (`src/visuals`): the daemon starts itself again as `ruimte visual-render` (`main.ts visual-render` with the same conditions in a checkout) in a process group of its own, at most two at once and the rest in line, and kills the group, Chrome included, at the limit and when the daemon stops; the child ends with its browser when its stdin closes, so a daemon that dies takes it along. A child runs the Chrome already on the machine through `Bun.WebView` (`BUN_CHROME_PATH` overrides where it looks), with a throwaway profile in a temporary folder the daemon removes, never the profile under `$RUIMTE_HOME/browser`. The page is answered from memory as `https://visual.invalid/page.html`, so it never loads from a file, and the main frame stays on it: a navigation away gets a 204 and a console line, a document no request reaches (about:blank, a blob) is loaded again once. Everything else Chrome sends goes through a SOCKS5 proxy of the child on loopback (`socks-proxy.ts`, CONNECT only), with the loopback bypass taken away, which resolves a name itself, refuses it when any address is local and connects only to the addresses it checked; local is loopback, the private, link-local, carrier-grade NAT, unique local, multicast, reserved and documentation ranges, IPv6 outside global unicast, the IPv4 address a mapped, NAT64, 6to4 or Teredo address carries, and every address an interface of the machine holds at that moment (`local-address.ts`). WebRTC is held to proxied UDP, which is none, through the profile's `webrtc.ip_handling_policy`, since the command line switch does not take in a headless Chrome; QUIC is off and a page opens no window. `help visual` carries the guides of `@adecore/agent-contracts/visual` (what a page may hold, how it is laid out, the theme variables) and an example with a heredoc. While the setting is on, a chat's CLI hears about the noun in one sentence of its verbs note (`VISUAL_NOTE`); a terminal agent and an inline edit never do.
- `notify <id> --text "..."`: sends a message of at most 500 characters to the agent in another node and prints `notified id now|waiting <what happened>`. The rule for who may notify whom is the one the canvas already draws: a line has to run from the caller into that node, the same direction that makes the caller readable to it, so a message travels exactly where a `read` already can and an agent cannot poke a node it has no relationship with. Anything else is a refusal that lists the nodes the caller can reach (`not-linked`, `not-an-agent`, `unknown-node`, `self-notify`, `not-on-a-canvas`). Where it lands depends on what is running in the receiver: a shell with no agent in it gets the line on its screen at once, dimmed, written to the screen and to whoever is attached but never into the PTY, the way the motd is; an agent that answers a context hook (Claude Code or Codex) hears it at the start of its next turn, since the hooks are the only channel into a running CLI; a CLI whose hooks are one way gets the line on the screen instead, and the answer says so; a chat between turns is given a turn on it; a chat that is in one hears it in front of its next turn; and a node that runs nothing yet keeps it until it starts, where it stands above the first prompt. A chat is woken because a person watching two agents cannot tell a message from an assignment, and a message nobody starts a turn for sits there until someone happens to prompt that chat: the daemon owes a `deliver-message` entry in the outbox (`@adecore/agents/messages/deliver-message.ts`, with Ruimte's words and terminals in `src/context/notices.ts`), whose handler opens the turn with `ChatSession.wake`, the senders in `messageFrom`, a note "Woken by a message" and a prompt telling the agent what the message above it is; the messages themselves ride in the turn's preamble, the same channel a person's own prompt reads them through, so one message is heard once either way. One step and no further: a turn with `messageFrom` wakes nobody, so a message sent from it waits for the next turn of the node it went to and the answer says so, which is what keeps two agents that read each other from waking each other on and on without a person ever asking for it. A terminal is never given a turn, since that would mean typing into the shell a person types in. The entry is one attempt and never waits: a chat that turned out to be in a turn reads the message in front of its next one, as it always did. What is waiting lives in `$RUIMTE_HOME/notices/<nodeId>.json` (`@adecore/agents/messages/notice-store.ts`), for the same reason a pending prompt does: the receiver may be a node nobody has mounted, and a restart must not lose what was left for it. It is delivered once, whichever channel gets there first, at most ten wait per node with the oldest dropped, and one nobody picked up in six hours is dropped rather than delivered late, since it is news about work that has moved on. A chat has a second reader the queue is not for: the person. A message left for a chat is a line in its thread the moment it lands, and one left for a chat nobody has started is in that thread the moment it loads, so a message waiting for hours is something a person can see instead of a file under `$RUIMTE_HOME`. That line is written once (`shown` on the message) and takes nothing away: the model still hears the message itself, once, in the turn that reads it.
- `answer <id> <request> --answer T | --answers J`: answers a question an agent the caller opened asked and waits on, and prints `answered id request`. Only an agent the caller opened itself, read from the lineage under `$RUIMTE_HOME` (`not-yours`), and only a question item that is still `pending`: an approval is refused (`not-a-question`) because it is a person's alone, and so is every other card. `--answer` is the answer to a request with one question (a choice label as written, several separated by a comma for one that takes more, or free text, the way a person's card sends it); `--answers` is a JSON object keyed by question id for a request with several. The answer goes through `ChatManager.answer`, the door a person's `chat.answer` goes through, so whoever answers first wins: a person after the agent gets `request-not-found`, the agent after a person `not-pending`. A refusal lists what the child still waits on. The request id stands in the `> Question` line `read <id>` prints for the child, which says whether the question still waits (an answered one keeps its id beside `answered`) and lists the question ids and choices under a waiting one, so a parent answers in the turn it reads; the note a waiting child leaves (below) names it too.
- `view <list|new|rename|icon|move|delete|open|diagram> ...`: the sidebar itself. The table those actions come from is also what `help view` renders, so an action is documented by being defined.
    - `view list`: the views of the project in sidebar order, `id kind name delete why icon`; a separator is in the list with an empty name. The fourth column is `yes` or `no`: whether `view delete` would remove that row for this caller, which is the one question the list cannot be read off (the maker is in the file but not on the wire, and the machine setting is not in the project at all). The fifth says why, because the answer alone explains nothing: `yours`, `this machine frees every view`, `a person made it`, `<id> made it`, or `you are in it`. Without it a caller on a machine that frees everything reads a column of `yes` beside views it never made and takes it for a bug. The sixth is the Lucide name `view icon` gave the view, or `-` for one that wears the mark of its kind; it came last so a script that reads the first five reads them where they were. The last line is `self` with the view the caller stands in: the canvas for a node, its own id for a session that is a view.
    - `view new <name> [--kind canvas|chat|terminal|browser|drawing|file|separator] [--path P] [--url U] [--after V]`: adds a row and prints `id kind name`. The kinds are read off the union in `packages/contracts`, so a kind added there is one this verb makes without a line of its own. `--path` is required for a file and `--url` for a browser, both refused on any other kind and resolved the way `node new` resolves them; `--after` puts the row under that view instead of last. A project holds at most 100 views.
    - `view rename <viewId> <name>`: prints `id kind name` and sets `titleSource: 'user'`, the rule a person renaming follows, so nothing the view hosts renames over it. A rename to the name it already carries writes nothing and is not a refusal.
    - `view icon <viewId> <lucide-name>`: prints `id kind lucide mark`. Anything that is not one of the 170 Lucide names is refused with all of them in rows of ten, which answers a typo and a mark of one's own alike. A separator has no room for one (`not-markable`).
    - `view move <viewId> --after V | --first`: prints `id kind index`, the place it now has counted over every row. Exactly one of the two flags, and never under itself (`two-places`).
    - `view delete <viewId>`: prints `deleted id kind name`, an `ended id kind` line per session the view held, and for a canvas a `nodes <count>` line with a `node id kind title` line per node (the first twenty), so what went is named rather than implied. Only a view whose `createdBy` is the caller, unless the machine's `agentsDeleteAnyView` frees all of them; the refusal (`not-yours`) names who made it, who is asking and what the setting does. Never the view the caller is standing in (`deletes-caller`), which is also why this verb can never empty the sidebar.
    - `view open <viewId>`: shows a view to whoever has this project on screen. It prints `showing id kind name` and then `sent yes ...` or `sent no ...`, and it is the one action that writes nothing: making is shared and lands in `project.json`, looking is one person at one screen. So it is an event, `project.showView { projectId, viewId, by }`, rather than a change to the document; `by` is the caller's id, never a title, so a client that wants to name the agent reads the name out of the document it already holds. It goes only to the clients that have that project open, which is the one event that is aimed rather than broadcast: `project.changed` reaches every socket because a client that let go of a project may still hold its document, while being shown a view is something that happens to a person. The store keeps that per socket, in the same holds a close counts (`hold` on `project.open`, `letGo` on `project.release`, everything dropped when the socket goes). Nobody watching is not a failure, which is what the `sent no` line says: nothing is held for later, and the same call a minute later shows the view to whoever is there then. A separator never opens (`never-opens`) and an id the project does not have is refused with the views it does (`unknown-view`). No `--dry-run`, since there is nothing to undo.
    - `view diagram <viewId> < document.json`: replaces the whole diagram of a diagram view with the JSON document on stdin and prints `view rev nodes groups edges`. The CLI sends stdin as `--document`, untouched; a document that breaks the schema is refused by path (`bad-document`), and `help view diagram` lists every field of it.
- `operation get <id>`: where a start stands, read off what the daemon already keeps and never off a store of its own (`src/actions/operation-actions.ts`, the node states from `src/agents/agent-state.ts`). The id names the action and the nodes it started, `agent.start:<id>` or `team.start:<id>,<id>` with the roles in the order `team` printed them, so it means the same after a restart. It prints `operation id action status` and one `agent id status task detail` row per node. With a task the task decides (`open` is running, or queued while the outbox still owes the start; `done`, `failed` and `cancelled` end it); without one the start is queued while the outbox owes it, running while the agent works or waits on a person, completed once it is idle or its CLI exited, failed on an error or when nothing runs in the node at all, and cancelled when ending its opener ended it or the node is gone. A team is running while any role is, failed when any role failed. Only the caller that started it may read it (`not-yours`; `unknown-operation` for an id that names nothing of the caller's). Nothing about it wakes anyone: a task still wakes its parent through the outbox.
- `operation cancel <id>`: stops what a start of the caller's own set going, under the same id and the same `not-yours` rule. A chat node's turn stops (`cancelled`), the way a person's stop does, and its thread, its node and its task stay. A terminal agent is `left` running, since nothing sends a signal a person did not press, and so is a start the outbox still owes; a node with nothing running is `over`. It prints one `operation id status detail` row per node, the detail starting with the node's id. Nothing is rolled back.
- `worktree <list|diff|merge>`: the worktrees of the project's repository (`src/actions/worktree-actions.ts` behind `src/canvas/worktree-verb.ts`, reaching git through `CanvasHost.worktrees`, `src/git/worktree-host.ts`). `list` prints `branch path nodes from changed new commits`, the nodes being the one the worktree was made for and every terminal or chat whose `cwd` is in it. `diff <branch> [--stat] [--tail N]` prints what the worktree holds over where it left its `from` branch, uncommitted and new files included (the same `diffCheckout` the panel's worktree tab reads), or `file path added removed` per file with `--stat`. `merge <branch> [--squash | --rebase] [--message M]` runs `WorktreeMerge` for an agent under three limits that cannot be turned off: only the worktree of a node the caller opened, directly or through agents it opened (`madeBy` up the lineage, else `not-yours`); only into a target checkout without changes to tracked files (`target-dirty`; untracked files are left to git, which refuses to overwrite one); and a conflict is taken back at once and refused with `merge-conflict` and its files. Loose work in the worktree is always committed first, under `--message` or the node's title. An agent in a turn there is refused (`agent-working`). The verb only merges: it stops no agent and never removes the worktree or its branch, and its last line `kept` says both stay until a person removes them, from the git panel or the delete question of the node.

What a client does with `project.showView` is the client's own: by default nothing moves and the request waits in the banner over the views, naming the agent and the view with a "Go there" button. A client setting turns that into following, where the view takes the place of the one in the cell that has the focus, a view already standing in another cell takes the focus instead of appearing twice, and the same banner names the agent and the view with a way back. A client that does not have the project open ignores the event altogether. That is the whole of why this is a verb a person can refuse to follow: the daemon executes and never asks, but showing is the one thing that was never the daemon's to decide.

Every view an agent makes carries `createdBy` with the caller's id in `project.json`, a separator included, and that is the whole of the delete rule. It is in the shared file rather than beside the node like a depth, because a maker is a fact both sides read and nothing has to be defended with it: a person deleting a view of their own is not what the rule is about. A node's maker is the other way round, in the lineage beside the project (below): a node is made by a verb and by a person's own drag, the client never sends a maker, and an agent with a shell in the project folder could write itself into `project.json` as the maker of anything. Deleting a canvas takes its nodes with it, so the daemon ends their sessions first, under the same lock the write takes and before the new document is handed back: `SessionManager.kill` for a terminal and `ChatManager.kill` for a chat, an id neither knows counting as already ended. That is what makes the verb work with no client connected, where a project closing in the client is the same rule run from the other side. The prompt and the lineage record of a node that went are pruned by the `ProjectIndex.onPlaces` hook the write already fires.

The operations themselves are pure functions in `packages/contracts/src/project-views.ts` (`withView`, `withRenamedView`, `withViewIcon`, `withMovedView`, `withDuplicatedView`, `withoutView`, `withNodeAsView`, `withViewAsNode`, `withNodeOnView`, `sessionNodesOfView`), which the client's document store runs as well, so the sidebar and the verb cannot drift on what a view id, a separator, a cross-view edge or the last view of a project means. What only the client knows stays there: the camera, the focus and the split layout.

`--prompt` is what the new agent starts working on, and it never reaches `project.json`: the daemon holds it against the node id under `$RUIMTE_HOME/prompts/<nodeId>.json` and delivers it once, the moment the session or the chat for that id is made (`src/agents/pending-prompts.ts`). That is the only place where "exactly once" can be promised, since a project open in two windows would otherwise send it twice, and it is on disk because the node may well be made on a daemon that restarts before it starts the node. A terminal agent gets the prompt on the line the daemon types into its shell, as the CLI's own prompt argument (`firstPromptArgs` per provider: a positional for `claude` and `codex`, `-i` for `gemini`, `-p` for `copilot`), because nothing can tell when a CLI is ready for typed input and the line is built at `session.create` anyway; the person then sees the prompt in the shell as a line they could have typed. A chat agent gets it as the first message of its thread, which is what spawns its process. A prompt is at most 2000 characters: the launch line waits in the tty's canonical buffer until the shell reads it, and a longer line is cut off there without a word. `--prompt-file` reads the same prompt from a file, resolved against the project folder and, like `--cwd`, refused outside the folder and the worktrees of its repository. A node deleted before anyone ran it takes its prompt with it (`ProjectIndex.onPlaces`).

The daemon starts what `agent` and `team` make itself, whether or not a client has the canvas open. Once the write has landed, the verb holds the prompt and puts a `start-agent` entry in `$RUIMTE_HOME/outbox/<id>.json` (`src/outbox`) with the kind of node, the CLI, the directory a client would have started it in (the node's `--cwd`, else the project folder) and, for a chat opened by a chat, that chat's permission mode. `OutboxWorker` works the outbox off without waiting for any socket, from the moment hooks have an address: oldest first, one entry per node at a time, each removed once its work is done, and whatever an earlier run still owed is loaded at start. The `start-agent` handler (`src/outbox/start-agent.ts`) calls `ChatManager.create` for a chat, which takes the prompt and sends it, with the model and mode of the composer preference the connected clients told it (`chat.setPreferences`, `@adecore/agents/chat/composer-preferences.ts`: held per socket and dropped with it, the newest `changedAt` among them wins, the model narrowed to the chat's CLI; with no client connected the defaults, `full-access` and the CLI's own model), and the mode of a chat that opened it before the preference's, or `SessionManager.create` for a terminal at 120 columns by 40 rows, which the first client to attach resizes to itself. It does nothing for a node that already runs or that no project places any more, and it ends what it made when the node went while the start was on its way; an entry for a deleted node is pruned with the prompt. A start that fails is logged and not tried again, because the create already took the prompt, and a client that mounts the node later starts it the way it always did. A client that mounts a running node attaches to it: `chat.create` answers the existing chat and `session.create` answers `session-exists`. Both managers make one id at a time, so a client mounting the node while the daemon starts it shares that one create instead of making a second shell or chat, and a kill that arrives meanwhile waits for it. A permission request of a terminal agent nobody is attached to is not held (unless an offline device can answer it through a push), so the CLI's own prompt asks, as it would for a client that turned approvals off.

A chat may give the node it opens a task: `agent ... --task T` (the prompt is the assignment, T its title and the node's title) or `team ... --task` (every role a task titled after it), and `task new <id> --prompt T` gives one to an agent it opened earlier that is already running. Both end their output with a `next` line telling the caller to end its turn, since an agent that is not told so polls `task list` and reads its children while the wake comes anyway. Anything but a chat is refused with `not-a-chat-parent`, since the point of a task is that its result wakes the chat that gave it and nothing else can be woken. The machinery is `@adecore/agents` (`@adecore/agents/tasks`), which `src/tasks/wiring.ts` binds to Ruimte: its terminals, the task rows of `ChatManager`, the words of `ruimte-context` and a note about work the outbox gave up on (`src/tasks/parked-note.ts`). The task is a record under `$RUIMTE_HOME/tasks/<taskId>.json` (`tasks/task-store.ts`), written before the agent starts, and the child hears under its prompt how to report back. A task from `task new` is written the same way and then owes a `give-task` entry (`tasks/give-task.ts`), which opens a turn in the child with `ChatSession.wake`: the prompt with that same brief under it, the task's title as the turn's label and its id in `taskIds`. A child that is in a turn makes the handler answer `wait`, the way a wake waits, so the task opens the turn after the one it found running, which is what a person's message does while a chat works. The turn that names it is also the only one that settles it: while the entry is still owed no turn of the child is its answer, and once the turn is there only that turn is (`TaskCoordinator.answers`), so the turn it waited out never comes back as its result. A `give-task` entry the outbox gives up on fails the task, so the chat that asked is not left waiting on it. It settles on the first of three things (`tasks/task-coordinator.ts`, an observer on the chats that only writes the task store and the outbox; `src/tasks/terminal-tasks.ts` tells it when a terminal ends): `ruimte-context done`; the end of a chat child's turn, whose last answer is the result (a turn that errs or is stopped fails the task), unless the child gave tasks of its own that are still open or have yet to wake it, in which case the turn after they did; or a terminal child that exits (or whose agent reports `exited`) without `done`, which fails the task with "It ended without a result". A settled task owes a `wake-parent` entry in the outbox, and a failed one raises attention on the child through the push service. The handler (`tasks/wake-parent.ts`) takes every settled task of that chat that has not woken it, and when the chat has no turn running opens one turn with `origin: 'agent'`, the titles as its label, `taskIds` and a note "Woken by N finished tasks", and sends the CLI the results (8 KiB each, with the child's id); no message of a person is made up. A chat in a turn makes the handler answer `wait`: the entry stays without costing an attempt and runs again when `OutboxWorker.wake` names that chat, which the daemon calls whenever a chat's event leaves it idle, never on a clock. The turn goes out before the tasks are marked `sent`, and a task a turn of the thread already names is marked without a second turn, so a restart between the two wakes nobody twice. The chat that gave a task shows it as a subagent row with `origin: 'ruimte'` and `childId`, written from the task (deferred out of the child's broadcast, and laid down again when the chat is loaded), and `chat.subagent` on that row reads the child's own thread a page at a time, so the side panel opens it like a native subagent. A child with an open task that asks a question or waits for an approval leaves its parent one note: `WaitingObserver` (`tasks/waiting-child.ts`) owes a `deliver-waiting` entry per request, due `WAITING_GRACE_MS` (15 seconds) after the request came, whose handler writes the note under `waiting-<childId>-<requestId>` with a preamble the parent's CLI hears in front of its next turn, naming the child, the kind of block and, for a question, the `answer` call; a request that no longer waits by then (answered, allowed, taken back by its CLI, or cancelled by a restart) gets none, so a person who settles it at once leaves the parent nothing to read. The parent is not woken for it. A child a person removes cancels its open task (no wake, the row fails with a note); a chat that is removed takes its tasks with it. An outbox entry given up on leaves a note in the chat it was for: the chat that opened the node for a start or a resume, the chat itself for a wake (which also raises attention). Clients read the tasks with `task.list { projectId }` and hear `task.changed`.

`--worktree` makes a worktree per agent with `Worktrees.add` under `$RUIMTE_HOME/worktrees/<repo>-<hash>/<branch>` before the project is written, on a new branch from HEAD, and the node's `cwd` is that worktree (`src/canvas/worktree.ts`). The branch is the slug of the task title, else of the node title, else the CLI, with `-2`, `-3` when a branch of that name exists, so two agents never share a checkout; `agent --branch B` takes that branch instead and checks out one that exists as it is. A project outside a repository is refused (`not-a-repository`), a worktree git will not make is refused with git's own words (`worktree-failed`), and a write the store refuses afterwards removes the worktrees the call made. A team's group gets no `worktree` field: that field means every node made inside the group starts in one checkout, which a team of worktrees is not. Every worktree a verb makes is written into the register with its project and, once the write landed, its node. Nothing removes a worktree on its own. Because a chat's checkpoint runs in its own `cwd` (`git rev-parse --show-toplevel` of a worktree is the worktree), two roles that edit the same file each see only their own change in their turn diff, and the diff of a chat in a subfolder of a repository is narrowed to that subfolder (`--show-prefix`).

The permission mode of an agent a verb opens is never wider than the caller's own (`src/canvas/mode.ts` over `@adecore/agents/modes.ts`), in the order `supervised < auto-accept-edits < auto < full-access`, which every CLI's flags follow. The caller's mode is a chat's `runtimeMode`, or for a terminal agent the mode the daemon started its CLI with (`launchedMode` in `src/providers/launch.ts`: a fresh launch without one got `full-access`, and a resume without one or a CLI typed into a plain shell counts as `supervised`, since the daemon cannot know). A `--mode` above it is refused with `mode-above-parent` and the modes the caller may give. Without `--mode` a chat opened by a chat takes that chat's mode, a chat opened by anything else takes the composer preference narrowed to the caller, and a terminal agent takes the terminal mode the connected clients told the daemon (`terminalRuntimeMode` in `chat.setPreferences`), narrowed the same way and written onto the node so a reload starts the same line. Every `start-agent` entry carries the caller's mode as `ceiling`, read when the verb runs, and the handler narrows whatever it starts with to it, the composer preference included. The lineage record keeps the same ceiling. `SessionManager.create` and `ChatManager.create` narrow the mode to it at every start, a restart and a client's mount included, because the mode on the node lives in a project file that an agent with a shell can rewrite. A person may still widen a child's mode from its composer until the next start. A terminal agent no agent opened is held the same way to the mode a person's `project.save` last gave it (`src/sessions/mode-approvals.ts`, under `$RUIMTE_HOME/mode-approvals`), so a mode an agent writes into `.ruimte/private/project.json` starts nothing wider; a node no save named yet is held to the terminal mode the connected clients pick (`terminalRuntimeMode`), and to `supervised` with no client telling one. A resume that names no mode counts as `supervised` there, as `launchedMode` reads it.

The daemon types the command of a terminal node only once a person on this machine has approved it for that node, since a committed `project.json` or an agent with a shell can put any command there. `session.create` looks it up in `$RUIMTE_HOME/command-approvals` (a hash of the project folder, the node id and the command). Without an approval the shell starts bare and the session carries the command as `heldCommand`, which a client shows as a question. `session.runHeld` writes the approval down and types the command. A person's `project.save` that sets or changes a command approves it too. It also types the command into a session that holds exactly that command, which is how a terminal a person just made runs its command without asking. A verb never approves anything, and cannot set a command either.

A launch is a run configuration of a project (`src/launches`): a service, a task or a group of both. `.ruimte/launches.json` holds the shared ones and `.ruimte/private/launches.json` this person's, the `rev`, the menu order and per shared launch an overlay with what cannot travel (an absolute folder, a token). A save goes against the rev like `project.save`, and a launch this release does not know is written back as it stood. Each launch runs in a session of its own, with an id the daemon derives from the project and the launch so a client finds the output again after a reload, as `$SHELL -l -i -c <command>`: the command ends the session and its exit code is the launch's. A launch starts only once a person on this machine approved its command, folder and variables as they stand (`command-approvals`); a person's `launches.save` approves what it adds or changes, `launch.start` with `approve` approves the rest, and anything else, an agent's verb or a launch marked `autostart` when its project opens, gets `held` back and starts nothing. A service with an address is `starting` until its port takes a TCP connection and `running` from then on. A stop is Ctrl+C in the terminal, then SIGTERM to its foreground group after five seconds; only `force` sends SIGKILL. A start whose port another launch holds answers `busy`, and `replace` stops that launch first. Nothing starts again on its own, and the launches of a project end when the last client closes it, with its sessions.

Every start of a node an agent made checks its directory again (`startCwdGuard` in `src/canvas/project-paths.ts`), in the `start-agent` handler and in both managers. The verb checked a path that may be a symlink, and by the time the node starts that link may point outside the project. A refusal carries the verb's own code, `cwd-outside-project` or `bad-cwd`.

Stopping or deleting a node ends the agents it opened, and the ones those opened (`src/outbox/end-children.ts`). `chat.kill`, `session.kill` on a shell that has not exited, the verbs that end a session (`node delete`, `view delete`) and a node leaving the document by any other way (`ProjectIndex.onPlaces`, for a lineage record whose opener the project no longer places) all owe one `end-children` entry for that node, with the ids of its descendants at that moment, before the node itself goes. On disk first, so a restart between a person's confirmation and the children ending still ends them; a second trigger for the same node owes nothing more, and `OutboxStore.prune` keeps the entry although its target is gone. While it runs the entry holds the lanes of every child as well, so a start or a resume of one never runs beside it. The handler marks every descendant `endedAt` in its lineage record, removes the `start-agent`, `resume-run` and `wake-parent` entries owed for them, cancels their open tasks with the reason as the result (a cancelled task wakes nobody, and a stopped chat is not woken about its own tasks either), and then stops the leaves before the nodes that opened them: a chat through `ChatManager.stop`, which ends its CLI and its running turn with a note and keeps the thread, a terminal through `SessionManager.end`, which ends the shell and keeps the session listed as exited. The nodes stay on the canvas, since removing them is a person's call. A stored chat that was not loaded is left as it is, and when it is loaded later a turn that started before its `endedAt` is not resumed. `agent.children { nodeId }` answers the descendants that still run, which is what a client counts in its confirmation.

An agent that opens agents is capped by how deep the chain already runs (`src/canvas/depth.ts`). A node a person opened is depth 0 and a node an agent verb opens is one deeper; `agent` opens up to depth 2, `team` up to depth 1, so a person's agent may open a team while the agents in that team may not open another one, and a hand-made chain of single agents still gets two links. Both refusals (`too-deep`) name the depth the caller sits at and the depth each verb reaches. Every node a verb makes is written down beside the project under `$RUIMTE_HOME/lineage/<nodeId>.json` (`AgentLineageStore`, `@adecore/agents/lineage.ts`): who made it, how deep it sits and whether it is an agent node. The depth and the per-caller cap are about the agent ones only, so a caller that makes twenty notes still has its room for agents; the maker is what `node delete` asks for, which is why a note is written down at all. A record from before that (no `agent` field) is read as an agent node. It is not a field on the node: an agent has a shell in the project folder and could rewrite `.ruimte/project.json` to call itself depth 0, and a field the client does not know is stripped by zod on the way through anyway. On disk, because a restart is exactly when a loop would otherwise start counting over. The same record caps one caller at 16 agent nodes open at a time (`too-many-agents`), which is the narrow limit under the canvas's own 500; a node the person removes frees the count, through the same `ProjectIndex.onPlaces` that prunes a pending prompt.

`--dry-run` is on `node new`, `agent`, `team` and `plan new` only. It runs every check under the same lock a write takes and then writes nothing; the answer is the same columns with `dry-run` in the first field, and where a real call would draw an edge the last column names its ends (`term-1 -> <new node>`) rather than the bare word, so the direction can be read before anything is made. A team names the role in the place of that placeholder (`term-1 -> <Lexer>`), since a dry run of many roles is a plan and two roles of one provider are otherwise the same row twice. Every other verb and action refuses the flag by name (`no-dry-run`) and lists the ones that take it, so a dry run is never a silent nothing. Help says that a refused call makes nothing either (a team checks every role before it makes one, and a write refused after `--worktree` removes the worktrees it made), so an agent does not pay for a dry run before every real call.

A name on the canvas is at most 120 characters, whether it arrives as `--title`, as a team's `--label`, as a role's `title` or as the label of a line (`titleField` in `src/canvas/verb.ts`). It is never unique: two nodes may carry the same title and two groups the same label, because an id is what names a node and a title is what a person reads. Every refusal that counts says both numbers, the one that came in and the one that fits, since a caller that only hears the limit has to count its own JSON: `--roles has 17 roles and a team takes at most 16`, `The prompt is 2001 characters and at most 2000 fit`, `Board holds 500 nodes and this would add 2 more`.

`--text` is read for the escapes `\n`, `\t` and `\\`, and nothing else (`src/canvas/text-escapes.ts`), since a shell hands `--text "a\nb"` to the daemon with the backslash still in it. For a body with exact bytes there is `--text -`, which is the CLI's own step: it reads stdin, escapes it back and sends one `--text=` argument, so the daemon only ever sees the final string and a heredoc arrives as it was typed.

The caller is the session or chat its token belongs to, looked up in every project the daemon knows (`ProjectIndex.locate`), open or released; one that no project places gets nothing. A verb that works on a canvas takes `--view` or the canvas the caller is a node on, and a caller that is a view of its own must pass `--view`. Selectors are ids, never titles. A change is applied by `ProjectStore.mutate` to the file on disk under the lock `project.save` takes, at `rev + 1`, and reaches every connected client as `project.changed`.

Answers are `text/plain`, one tab-separated line per result. A refusal is a 422 (a 404 for an unknown verb) whose first line is `refused	<code>	<message>`, followed by what the caller can pick instead wherever the set is closed: the verbs after an unknown verb, the canvases after a `--view` that is not one, the drawings after a bad `--source`, the flags of the kind after a missing or misplaced one, the nodes of the canvas after a `--beside` that names none (over twenty of them it points at `ruimte-context node list` instead), and everywhere a list is offered it holds only what that same call would take: no group under a `node group --nodes` or `node arrange --nodes` that names none, not the node a `link new --to` would start from, under `node delete` only the nodes it would really remove, under `node edit` only the notes it would write in and under `link delete` only the lines it would, the groups of the canvas after a `--group` that names none, the CLIs that are installed after one that is not, the shape of a role after `--roles` that does not parse, the depths each verb reaches after one that is too deep, the verbs that take `--dry-run` after the flag on one that does not, the views of the project after an id that names none, the Lucide names after a mark that is not one, the node accents after a `--color` that is not one, and the project folder with the worktrees of its repository after a `--cwd` or a `--prompt-file` outside all of them. A closed set that happens to be empty is a `note` row saying so (a canvas with no groups on it, a project with no drawing views), never an empty list, which would read as a daemon that lost them. Where nothing can be listed, a URL, a path, a directory that is not there, the sentence itself says what is allowed and no list is invented. An unknown verb whose name holds a space, which is a caller that quoted the whole line, gets a `note` saying a verb and its arguments are separate words. Arguments a verb or an action could not parse end with `detail	ruimte-context help <verb>` or `detail	ruimte-context help <noun> <action>`. The codes: `unknown-verb`, `unknown-action`, `not-a-canvas-verb`, `bad-request`, `unknown-flag`, `missing-value`, `duplicate-flag`, `bad-arguments`, `not-in-project`, `view-required`, `not-a-canvas`, `flag-not-for-kind`, `missing-flag`, `bad-url`, `bad-path`, `bad-cwd`, `no-folder`, `cwd-outside-project`, `not-a-drawing`, `unknown-node`, `canvas-full`, `unknown-group`, `two-places`, `cli-not-installed`, `bad-roles-json`, `bad-roles`, `too-deep`, `too-many-agents`, `mode-above-parent`, `not-a-repository`, `worktree-failed`, `worktree-and-cwd`, `branch-needs-worktree`, `prompt-twice`, `empty-prompt`, `prompt-too-long`, `bad-prompt-file`, `prompt-file-outside-project`, `self-link`, `too-many-links`, `unknown-edge`, `self-notify`, `not-on-a-canvas`, `not-an-agent`, `not-linked`, `not-a-note`, `no-dry-run`, `unexpected-value`, `unknown-view`, `too-many-views`, `unknown-icon`, `not-markable`, `not-yours`, `deletes-caller`, `unknown-worktree`, `two-strategies`, `worktree-missing`, `worktree-busy`, `no-branch`, `target-not-checked-out`, `target-busy`, `target-dirty`, `agent-working`, `merge-conflict`, `self-answer`, `unknown-request`, `not-a-question`, `not-pending`, `answer-twice`, `answers-needed`, `unknown-question`, `empty-answer`, `bad-answers-json`, `unknown-operation`, `no-operations`, `unknown-color`, `not-groupable`, `different-groups`, `not-arrangeable`, `flag-not-for-layout`, `too-many-columns`, plus `project-missing` and `project-invalid` when the file is gone or broken, and `unknown-source` from the CLI's own `read`. The CLI prints an answer to stdout and a refusal to stderr, and exits 0 on success, 1 when the daemon cannot be reached or fails, 2 outside a live session (no token, or a 401 for a token the daemon does not know, such as one from a session that ended) and 3 on a refusal.

How an agent hears that the CLI exists depends on where it runs:

- Every chat process starts with one sentence about the verbs (`VERBS_NOTE`): Claude Code in its system prompt (`--append-system-prompt`), Codex in front of the first prompt, since the app-server protocol has no system prompt. A chat that has links at that moment gets a second sentence about them in the same place. When the set of links changes between two turns (added or removed, matched by id), the daemon puts a note in front of the next prompt naming what came and went (`src/context/context-note.ts`, `contextChangeNote`) and shows it in the thread as an info note. A slash command is sent untouched; the note waits for the next real prompt.
- A shell that has links the moment it is created shows one dimmed line above its first prompt (`contextHint`), written to the screen only, never to the PTY, with anything `notify` left for that node under it. A link made while the shell runs is not announced on the screen; the terminal node's header shows a "context" chip, and a Claude Code or Codex agent inside the shell hears what changed at its next turn through its prompt hooks (above).

A Codex chat (`provider: 'codex'` on `chat.create`) is `codex app-server`, JSON-RPC over stdio (`@adecore/agents/chat/codex-transport.ts`, `codex-backend.ts`, `codex-protocol.ts`). The first send spawns it and handshakes: `initialize`, `initialized`, then `thread/start` with cwd, model, approval policy and sandbox, or `thread/resume` with the stored thread id (a thread Codex no longer has falls back to a fresh one with a warning on the thread). Every message is a `turn/start`; the notifications fold into the same thread items, so the client does not know the difference:

- `agentMessage` items stream through `item/agentMessage/delta` into assistant items; `plan` items are assistant text too. Reasoning items are not shown.
- `commandExecution` is a `Bash` tool item (the `/bin/zsh -lc` wrapper stripped, `aggregatedOutput` as output) whose partial output streams in through `item/commandExecution/outputDelta` while it runs, `fileChange` an `ApplyPatch` tool item with the unified diffs in `changes`, `mcpToolCall` and `dynamicToolCall` tool items under their own names, `collabAgentToolCall` (Codex's own multi-agent calls) a tool item too, except `spawnAgent`, which is a subagent item, `contextCompaction` a compaction marker.
- `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` are approval items. `allow` answers `accept`, `allow-always` the execpolicy amendment Codex proposed (or `acceptForSession`), `deny` answers `decline`; Codex takes no reason with a decline, so `message` stays on the daemon. `serverRequest/resolved` cancels an approval that Codex withdrew.
- `item/tool/requestUserInput` (blocking) is a question item answered by Codex's own question ids. An agent message that carries `questions` (Codex asking without blocking, it polls with `sleep` until the person answers) is a question item too, marked `async`; `chat.answer` sends the chosen labels with `turn/steer` into the running turn, and `chat.dismiss` drops it locally so the person can ignore it.
- `chat.cancel` is `turn/interrupt` (the turn ends `interrupted`, shown as aborted), `chat.compact` is `thread/compact/start`, which Codex runs as a turn of its own.
- Usage comes from `thread/tokenUsage/updated` (`last.totalTokens` as the context in use, `modelContextWindow` as the window). Codex reports no cost, so `costUsd` stays zero and the turn fold only shows the duration. Slash commands stay empty.
- `item/permissions/requestApproval`, MCP elicitations and any other server request the daemon does not understand are refused with a JSON-RPC error, so Codex never waits on an answer that will not come.
- The thread id is what a terminal resumes with `codex resume <id>`, and "Open in chat" on a terminal that ran Codex opens a chat on the same thread.

## Usage

`@adecore/agents/usage` answers what both CLIs cost and what is left of their plans. Nothing here calls an API and nothing reads a credential.

The scanner walks the transcript folder of every account (`transcriptFolder`, which for a default account is `CLAUDE_CONFIG_DIR ?? ~/.claude` plus `/projects` and `CODEX_HOME ?? ~/.codex` plus `/sessions`, the same variables the hooks installer reads) for `*.jsonl`, prefilters every line on the words that can carry counts before it parses one, and remembers each file by size, modification time, byte offset and, for Codex, the parser state (`readers/`): unchanged is skipped without opening the file, grown is read from the offset on top of what is there, anything else is read again from the start. The line at the end of a file that is still being written is parsed but not counted towards the offset, so it is read once when it is finished. Claude repeats one message over several lines and copies finished ones into a resumed transcript, so the largest value per field per `message.id` wins; Codex reports a cumulative total per turn, so a call is the difference with the line before it, falling back to `last_token_usage` when a compaction makes that difference negative, and the burst a forked or spawned thread replays at its start is dropped. The index is at `$RUIMTE_HOME/usage/index.json` as interned tuples: throwing it away costs one cold scan (2.2 s over 1,400 transcripts on an M-series Mac; a warm pass is 50 ms), and a file that Claude Code has since cleaned up keeps its records.

Every record keeps the account it was made under. A folder one account writes in is that account's; the sessions Codex accounts over one home share (a shadow home included) go to the account of the chat or terminal the daemon knows ran that session, and to the CLI's default account when it knows none, which is the only account a session started outside Ruimte can have run under. The account is resolved when a line is first read, so a session the daemon no longer holds by then counts for the default account. An index of version 1, from before accounts, reads as the default account's without a scan. A `usage.summary` with `accounts` counts only those and splits its buckets and models per account; without it the answer is what it was before accounts. Either way it lists the accounts to filter by, a removed one that records still name included.

Prices come from LiteLLM's `model_prices_and_context_window.json` with a 24 hour lifetime and a 10 second timeout, kept at `$RUIMTE_HOME/usage/prices.json`, with a snapshot bundled in the repo as the offline fallback (`bun run --cwd apps/server snapshot-prices` refreshes it). A model matches exactly, then without its date suffix, then on the longest family before a dash; a bare family name (`opus`, `gpt`) prices nothing and travels as `costUsd: null`, which every consumer shows as a question mark rather than as free. Missing cache rates default to 10% of input for a read, 125% for a write and twice input for the one hour kind. A Claude line whose model is `<synthetic>`, and one whose four counts are all zero, never reached the API and is not counted as a call. `usage.summary` scans when the last pass is over a minute old and aggregates in the time zone the request carries; `usage.subscribe` keeps that pass running once a minute while a client has the page open and announces a change with `usage.changed`.

Every price is in dollars. Beside the price table the daemon asks frankfurter.app for the ECB reference rate of the day (`from=USD&to=EUR`), on the same 24 hour lifetime and the same 10 second timeout, kept at `$RUIMTE_HOME/usage/exchange-rate.json` and travelling on `usage.summary` as `rate`. `--no-price-fetch` turns both off. Without a rate the page stays in dollars rather than putting a euro sign in front of a dollar amount; the conversion itself is the client's, so two people looking at one daemon can read it in different money.

`usage/limits` asks the CLIs what is left of the plan, per account: the default account of every CLI, first of its kind and in the shape an entry had before accounts, and every other account that is on and signed in, each read in its own environment (`envFor`). Claude Code gets a `claude -p` on the stream-json protocol, an `initialize` control request (without it the process waits and answers nothing) and then `get_usage`; Codex gets a `codex app-server`, the usual handshake and `account/rateLimits/read`. Both processes end as soon as they have answered. A pass runs every five minutes, doubles to an hour after a failure and leaves the last good numbers up; a CLI that is not installed is reported as such. An account other than the default one is only on that clock while a chat or a terminal started under it in the last 24 hours (remembered in memory, so a restart forgets it); otherwise only `usage.refreshLimits` reads it. In between, the `rate_limit_event` frames of a running Claude turn and the `account/rateLimits/updated` notifications of a Codex one fold onto the same windows by id, keeping the reset and the length the event leaves out, on the entry of the account the running CLI was started under. `usage.limits` reads the snapshot, `usage.refreshLimits` forces a pass, `usage.limitsChanged` announces one.

## Smoke test

With a daemon running:

```sh
bun run --cwd apps/server smoke            # or: smoke ws://host:port/ws
```

It creates a session, runs `uname`, prints the streamed output and the screen a reattach would receive, then kills the session.

## A remote daemon in Docker

`docker/` builds a second daemon on Linux, reachable from this machine on `127.0.0.1:4310`, with two
git repositories of its own under `/work`. It is how a client let in on a statement, the door on the
local network, a direct channel and the `lan` reachability get tested against a machine that is really
not the client's. `bun run --cwd apps/server docker:up` starts it, and `docker:login` puts it on your
account with `ruimte login`. The app reaches it through a broker (`RUIMTE_BROKER_URL`), since the
addresses of a container's door are its own network's, so its door stays closed (`--no-lan`).
`docker:test` runs the suite against a fresh container of its own, which believes a statement key made
per run, publishes its door on `127.0.0.1:4330` and lets the suite's clients in the way the app gets in;
the owner uses the local secret read from the container. The tests skip themselves unless
`RUIMTE_DOCKER=1` is set. The machine keeps its home and its `/work` in two named volumes across a
`docker:down`, and `docker:reset` is what empties them. See `docker/README.md`.

With `RUIMTE_BROKER_URL` and `RUIMTE_BROKER_ADVERTISE_URL` set when compose runs, the container announces
itself to a broker on this machine (`apps/pulsar-broker/README.md` has the steps); without them compose
passes `off`, so the container never announces itself to the public default broker. The test container
always dials one on port 4420, which the suite starts and stops itself.
