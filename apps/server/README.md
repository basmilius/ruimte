# @ruimte/server

The daemon. It owns terminal sessions and serves them to the UI over one WebSocket. Closing the UI never ends a session; only `session.kill` (or the daemon going down) does.

## Run

```sh
bun run --cwd apps/server start            # ws://127.0.0.1:4210/ws
bun run --cwd apps/server start -- --host 0.0.0.0 --port 4300
bun run --cwd apps/server dev              # ws://127.0.0.1:4211/ws, home ~/.ruimte-dev, restarts on file changes
```

The `dev` script runs on port `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, so a checkout runs beside an installed Ruimte (`4210`, `~/.ruimte`) without sharing its id, its projects or its sessions. Pairing in dev therefore asks the dev daemon: `bun src/main.ts pair --port 4211`.

| Flag                      | Default     | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--host`                  | `127.0.0.1` | Interface to listen on.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `--port`                  | `4210`      | Port for `/ws`, `/health` and `/hooks`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `--no-hooks`              | off         | Do not write the status hooks into the CLIs' settings files at startup.                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `--serve <dir>`           | off         | Serve a built client from `dir` next to the socket; unknown paths fall back to its `index.html`. Every response carries the client's `Content-Security-Policy` (`CLIENT_CSP` in `src/daemon.ts`), the twin of the `<meta http-equiv>` in `apps/client/index.html`: scripts and workers from the daemon itself plus `'wasm-unsafe-eval'` for shiki and `blob:` for the diff worker, inline styles allowed, no `'unsafe-eval'`, no frames, and `connect-src`, `img-src` and `media-src` wide enough for a paired endpoint on any host. |
| `--label <name>`          | hostname    | What the daemon calls itself towards clients until someone names it from a client (`RUIMTE_LABEL` works too).                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `--allow-origin <origin>` | none        | Extra browser origins allowed on the socket, on top of loopback and the daemon's own. Repeatable.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `--no-price-fetch`        | off         | Never ask LiteLLM for the model price table; the snapshot bundled with the app prices everything instead.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `--no-approvals`          | off         | Never hold a terminal agent's permission request for a client; every one is left to the CLI's own prompt.                                                                                                                                                                                                                                                                                                                                                                                                                            |

`ruimte pair` (in a checkout: `bun src/main.ts pair`) asks the daemon running on this machine for a fresh pairing URL and prints it; tokens never travel as arguments. `ruimte context` is the agent-side CLI behind the `ruimte-context` script.

## Compile

`bun run compile` (`scripts/compile.ts`) builds one executable with `bun build --compile` into `dist/<os>-<arch>/ruimte`, with `ruimte-context` next to it, for this machine or with `--os mac|linux --arch arm64|x64` for another. `RUIMTE_VERSION` stamps a version in; the desktop app packages that folder as its `bin` resource.

`GET /health` answers `{ ok: true, version }`. `POST /hooks/<claude|codex>` takes a hook payload from an agent CLI (see below); a kind the daemon has no normalizer for (`gemini`, `copilot`) answers 404. Everything else goes over `/ws` using the frames in `packages/contracts`.

On the socket, `server.hello` answers the daemon's version, platform, home and, when the machine says what it is, its `model` (`src/machine-model.ts`, read once at startup: the marketing name out of macOS's device tree, the SMBIOS fields on Linux and Windows, the device tree of a board that has no SMBIOS). The field stays out of the answer when nothing there names the hardware, which is what a container does, and the client's row for that machine says "This machine" instead of "This MacBook Pro". `server.ping` takes nothing and answers `{ time }`, the daemon's clock in epoch milliseconds; the client times the round trip itself (two machines never share a clock), which is the ping the connection dot shows.

## The machine's name and icon

`endpoint.info` answers `{ id, label, nameSource, icon, platform, version, reachability, authenticated, publicKey }`, and the answer to `POST /auth/pair` carries the same object, so a client that has just paired already knows what to call the machine. The `label` is the name: the one a person gave it, or, while `nameSource` is `default`, `--label`, else `RUIMTE_LABEL`, else the hostname. A fresh machine is therefore never nameless. The `icon` is `{ kind: 'emoji', value }` or `{ kind: 'lucide', value }`, the same closed set a project and a view pick from, and null while nobody picked one; there is no image kind, because a machine has no folder to keep a file in.

`endpoint.setIdentity { name, icon }` sets both, from any client that paired with this daemon. A null name hands the machine back to the name it starts with and a null icon leaves it without one, so both fields are always sent. The name and the icon go into `endpoint.json` next to the id, not into one client's storage, and every other connected client is told with `endpoint.changed { id, label, nameSource, icon, agentsDeleteAnyView }`.

`agentsDeleteAnyView` rides along in all three: it is what an agent's `ruimte-context view delete` and `node delete` may remove on this machine (one switch, since freeing the views and holding back the nodes is a distinction nobody reading that row would guess; the settings row says views and nodes), false on a fresh one, and it belongs to the machine because the daemon is what enforces it and a client setting would hold nothing back. On `endpoint.setIdentity` it is optional rather than nullable, since the dialog that names a machine is a different control and leaving it out leaves it where it stands.

A name typed in a client wins over `--label` and `RUIMTE_LABEL`. Those two say what a machine nobody has named answers to; a rename that a restart undid would be a bug, and clearing the name is the way back to them. `endpoint.json` stays at `version: 1` with the name and the icon added as fields: a daemon from before them reads the file, keeps its id and leaves them alone, where a version bump would make it mint a new id and answer to every paired client as a stranger. A name or an icon that will not read is dropped on its own and the id and key pair survive it.

## `RUIMTE_HOME`

Where the daemon keeps its state. Defaults to `~/.ruimte` (`~/.ruimte-dev` under the `dev` script and in an unpackaged desktop app). Layout:

```
$RUIMTE_HOME/
  endpoint.json                    the daemon's own id and key pair, minted on first start, plus the name, icon and agent policy it was given
  auth.json                        the clients paired with this daemon, by public key
  projects.json                    every canvas the daemon knows: id, name, color, folder, and when it was last closed
  projects/
    <projectId>/project.json       a canvas that is not in a folder
    <projectId>/drawings/<viewId>.json   the drawings of a canvas that is not in a folder
    <projectId>.local.json         camera, focus, grid and panels of a project, where a client that never saw it starts
  sessions/                        mode 0700
    <sessionId>.txt                serialized screen plus scrollback of one session
    <sessionId>.agent.json         the agent CLI last seen in that session, for a cold resume
  prompts/                         mode 0700
    <nodeId>.json                  the first prompt of an agent node, until its session or chat is made
  lineage/                         mode 0700
    <nodeId>.json                  who opened an agent node and how deep it sits, for as long as the node does
  notices/                         mode 0700
    <nodeId>.json                  the messages `notify` left for that node, until its agent picks them up
  chats/                           mode 0700
    <chatId>.json                  the thread and info of one chat node
  attachments/                     mode 0700
    <chatId>/<id>.<ext>            one file someone attached to a message in that chat
  checkpoints/                     mode 0700
    <repo>-<hash>.index            the private git index a turn's checkpoint is written through
  usage/                           mode 0700
    index.json                     every transcript the scanner read, with where it stopped in each
    prices.json                    the last LiteLLM price table, with when it was fetched
    exchange-rate.json             the last euro rate for a dollar, with the day it is of
```

File names are the id passed through `encodeURIComponent`, so an id can never name a path outside its directory.

One home belongs to one daemon. The id in `endpoint.json` is what a client calls this machine, and `projects.json` and the sessions are written as if nothing else touches them, so two daemons sharing a `RUIMTE_HOME` are two daemons a client cannot tell apart.

## Projects

A project is a folder; its canvas is `<folder>/.ruimte/project.json`, pretty-printed with a `rev` that goes up on every write, so it diffs and merges like any other file in the repository. Node directories inside the folder are stored relative to it (`./apps/server`), so a clone on another machine resolves them against its own checkout. A canvas without a folder lives under `projects/` in the app data dir. What belongs to a screen goes to `<projectId>.local.json`, never into the shared file: the camera (the world point in the middle of the cell plus the zoom), the focused node, the grid of views and, under `panels`, which panel is up and how wide, whether the preview is up and how wide, the open file tabs with the active one and their pins, and the directories the file tree had open. Every client keeps its own copy of this and lays it over the file on open, so the file is only where a client that never saw the project starts; the favicons under `panels` are the one part that always comes from here. Every field under `panels` is optional, so a file written before them still parses and the client falls back to its own defaults.

`project.open` takes an id, a folder (the canvas is created there when the folder has none) or nothing (a fresh canvas without a folder). With `createFolder` a folder that is not there is made first, and every missing folder above it; a file sitting at that path is never written over and still answers `folder-not-found`, while a mkdir that fails answers `folder-create-failed`. Only the client's folder picker asks for it. `project.save` names the `baseRev` the client loaded and answers `rev-conflict` when the file moved on. While a project is open the daemon watches its directory; a write it did not make itself arrives as a `project.changed` event with the document now on disk. A file that does not parse is moved aside as `project.json.corrupt-<timestamp>` and a fresh canvas takes its place; it is never overwritten. Every write is a temp file plus rename, with a short retry for Windows. `project.delete` forgets the project and, when asked, removes the canvas file; a folder's other files are never touched.

Letting go of a project and closing one are two requests. `project.release` stops the watcher and drops the drawings, which is what a client does when it switches to another project on the same machine; the registry is untouched. `project.close` is a person closing the project: it releases it too, stamps `closedAt` on its registry entry and sends `project.summary` to every client. `project.list` answers with every project either way and carries `closedAt`, so the client shows the ones in use and keeps the closed ones under Recent. Only closing puts a project there and only `project.open` takes it out again (it clears `closedAt` and announces the summary), so neither age nor whether a project happens to be open right now moves it. Nothing is ever created by reading: a daemon with an empty registry answers `project.list` with an empty list.

### Name and icon

`name` and an optional `icon` sit at the top of the canvas file. An icon there is `{ kind: 'emoji', value }` or `{ kind: 'lucide', value }` with a closed list of 40 names; an image is never a blob in the JSON. Without a chosen icon the daemon asks the folder, in this order: `.ruimte/icon.{svg,png,jpg,jpeg,gif,webp}`, `.idea/icon.{svg,png}`, `.vscode/icon.{svg,png}`, then `favicon.{svg,ico,png}`, `public/favicon.*`, `public/icon.*`, `app/favicon.ico`, `app/icon.*`, `src/favicon.*`, `src/app/favicon.ico`, `src/app/icon.*`, `assets/icon.*` and `assets/logo.*`, and finally the `href` of the first local `<link rel="icon">` in a root `index.html` (tried as `public/<href>`, then `<href>`). A `<name>_dark.<ext>` next to the file it found is the dark theme's variant. Every path is jailed inside the folder and re-checked after `realpath`, the type comes from the magic bytes and not the extension, and a file that is empty, over 256 KB or not an image is skipped. Nothing is left: the summary carries `{ kind: 'initial', value }`, the first letter of the name. The `name` is seeded when a folder gets its first canvas: from `.idea/.name` (first non-empty line, control characters stripped, 64 characters, file at most 4 KB) when it holds one, else the folder's own name. That file is read once and never again, so the canvas file owns the name from there on and only a rename changes it; `nameSource` says whether the name was chosen or is still the folder's own. What the folder says about its icon is cached in memory for five minutes per folder and never written back; `project.open` and `project.setIcon` re-read it, and a folder that could not be read at all is not cached.

`GET /projects/<projectId>/icon?v=<version>&theme=dark` serves the bytes, gated by the same rules as `/ws` (every client sends its ticket, its session token or the local secret as `?token=`). It answers with the sniffed `Content-Type`, `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: private, max-age=31536000, immutable` (the URL changes whenever the file does) and, for an SVG, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, so opening the URL directly runs nothing either. `project.list` never carries image bytes.

`project.setIcon { projectId, image: { mime, base64 } | null }` writes `<folder>/.ruimte/icon.<ext>` (PNG, JPEG, GIF, WebP or SVG, at most 256 KB, checked against the bytes' own magic, the other `icon.*` in that directory removed) or, with a null image, deletes it. It answers with the fresh summary and sends `project.summary` to every client. An emoji or a Lucide choice needs no request of its own: the client writes `icon` into the canvas file through `project.save`. The watcher on `<folder>/.ruimte` covers `icon.*` as well as `project.json`, so an icon copied in by hand also arrives as `project.summary`.

## Drawings

A drawing view holds nothing in `project.json` but its id and its name; its elements live in
`<folder>/.ruimte/drawings/<viewId>.json` (version 1, with a `rev`), which goes into git next to the
project file. The top level is indented and every element sits on one line, so a diff reads like a
drawing rather than like a list of coordinates. The file name is the view id through
`encodeURIComponent`, so a rename never moves a file.

`drawing.open { projectId, viewId }` answers with the document, or with an empty one when there is
no file: a drawing nobody touched leaves nothing on disk. `drawing.save` names the `baseRev` it was
built on and answers `rev-conflict` when the file moved on, `drawing.close` forgets it, and
`drawing.copy { projectId, from, to }` writes a copy at rev 0, which is what duplicating a view is.
A second non-recursive watcher on `.ruimte/drawings` (started with the first drawing of a project)
turns an outside write into `drawing.changed` with the document now on disk, 150 ms after the burst
settles and never for a write the daemon made itself. Broken JSON is set aside as
`<viewId>.json.corrupt-<timestamp>`; a file that parses but is not a drawing stays where it is and
the request answers `drawing-invalid`. A drawing view that leaves the project through `project.save`
takes its file with it; a view that disappears through an outside edit of `project.json` never does,
because a pull can drop a view whose file is still on its way.

## Sessions

- A session is keyed by the id the client chooses. `session.create` on an id that is still running answers `session-exists`; on an id whose shell has ended it starts a fresh shell and shows the old screen above a `[session restored, previous shell ended]` line.
- The shell is `$SHELL` (fallback `/bin/zsh` on macOS, `/bin/bash` elsewhere), started as a login shell where the shell takes `-l`, with `TERM=xterm-256color`, `COLORTERM=truecolor` and `RUIMTE_SESSION_ID` set.
- Every session runs a headless xterm in the daemon (10000 lines of scrollback). `session.attach` answers with the serialized screen, after which raw output streams in `session.output` events, coalesced per 16 ms.
- Several clients may attach to one session. Attaching with different `cols`/`rows` resizes the session; the last attacher wins.
- A client that cannot keep up does not grow a queue in the daemon. Per socket, once `getBufferedAmount()` passes 1 MB (`HIGH_WATER_MARK` in `src/backpressure.ts`) or a `session.output` frame comes back as dropped or backpressured, output for that client stops and every session that loses bytes is marked. Requests, replies and the other events are small and keep flowing. On Bun's `drain`, under 256 KB queued, each marked session gets a `session.resync` event (`{ sessionId, screen }`) with a fresh serialize and its stream continues; the mark is cleared in the same tick the serialize resolves, so a byte is either in that screen or in the stream after it, never in both.
- `session.clear` is what a native terminal's Clear does: the daemon clears its own buffer (the prompt line becomes the first) and pushes the fresh screen to every attached client as `session.resync`. The shell is never told, so nothing is typed into it and no scrollback survives a reload.
- A shell that exits on its own stays in `session.list` as `exited` with its `exitCode` so the last screen can still be read. `session.kill` removes it.
- `session.create` takes either `command` (a line typed into the fresh shell) or `agent` (`{ kind, runtimeMode?, model?, resume? }`), never both: with `agent` the daemon builds the line itself (`src/providers/launch.ts`) and types that. So every client starts a CLI the same way, and a flag never travels over the wire. `runtimeMode` becomes `--permission-mode` for Claude Code, `--ask-for-approval` plus `--sandbox` for Codex, `--approval-mode` for Gemini and nothing for Copilot; a `resume` fills the provider's resume template instead, with the fresh launch behind a `||` so a node whose session the CLI no longer has still ends with that CLI running. A CLI that is not installed ends as `command not found` in the shell, which is why the menus disable a row the daemon did not find. A session the daemon still has an agent record for gets no launch line at all: that agent is resumed after the attach (below), and starting the CLI here too would type a second command into the one already coming up.

## Snapshots

Every 30 seconds, and on `SIGINT`/`SIGTERM`, the daemon writes each session's screen to `sessions/<sessionId>.txt` (temp file, then rename). When the daemon starts again and a client creates a session with an id that has a snapshot, the first attach shows the snapshot, the restored marker and then the fresh shell. `session.kill` deletes the snapshot on purpose: a killed session should not come back. The chats go down first and synchronously (`ChatManager.persistAllSync`), before the handler awaits anything, because a `bun --watch` reload restarts the module during that first await.

## Agent status via hooks

Hooks are per kind: Claude Code and Codex have an event table and a normalizer (`capabilities.hooks: true`), Gemini and GitHub Copilot do not, so they launch in a terminal and show the session's own status (running while attached, error on exit) and nothing more. The installer only visits the kinds with a hook path, and the receiver answers 404 for the others.

Every shell gets `RUIMTE_HOOK_URL` (`http://127.0.0.1:<port>/hooks`) and a per-session `RUIMTE_HOOK_TOKEN`. At startup the daemon puts one command hook per lifecycle event into `~/.claude/settings.json` and `~/.codex/hooks.json` (idempotent merge; hooks of other tools stay). The hook POSTs its stdin to `$RUIMTE_HOOK_URL/<kind>` with the token as bearer and prints the reply, and does nothing outside Ruimte. Codex asks you to trust the new hooks once (`/hooks`).

The reply is empty except on Claude Code's `SessionStart` and `UserPromptSubmit`, where the daemon answers `{ "hookSpecificOutput": { "hookEventName": ..., "additionalContext": ... } }` and the CLI folds that into the turn. `SessionStart` always carries the sentence about the canvas verbs, with the linked-context line behind it when the session has links; `UserPromptSubmit` carries the linked-context line, then what changed since the previous turn and any message another node left for this one. The daemon remembers per session what each agent was last told about (`ContextStore.changeSince`), so a line drawn while the shell was already running is named at the next turn ("Added: ..."), which is the only way that change reaches a terminal agent at all; it is quiet when nothing moved, and never said at a `SessionStart`, which is handed the whole list anyway. That is how a Claude agent inside a terminal, which has no system prompt of ours, learns about `ruimte-context`. The curl runs with `-f`, so an error page never ends up as context.

The daemon folds the events into one status per session: `running`, `needs-you` (permission prompt, `AskUserQuestion`, elicitation), `idle` (turn ended) or `error` (the shell died under a live agent). Every client gets it as a `session.status` event with the CLI's session id and transcript path, and `session.list` carries the same `agent` field.

## Answering a permission from a client

Claude Code's `PermissionRequest` is the one hook the daemon answers late. It fires just before the CLI shows its own permission prompt, and both stay live, so a client is a second way to answer the same question and never the only one: whoever is first wins. Answering in the CLI's own screen does not end the hook (measured against Claude Code 2.1.270), so a request the person answered there is let go when the turn does, not at the moment they pressed a key. `ApprovalStore` (`src/agents/approvals.ts`) holds the request against the session for 110 seconds, under curl's 120 and the 125 written into the settings file, so the daemon is always the first of the three to let go. Letting go prints nothing at all, which leaves the CLI's prompt standing: nobody connected, `--no-approvals`, a session that ended and a hold that ran out all end there, and an agent started with bypass permissions is never asked.

Whether anybody is there to ask is a question about the clients, not about the daemon. Each socket says what it does with a permission request through `agent.setApprovals` (`{ enabled }`), and a socket that says nothing wants them, which is what every client written before this meant. Nothing is held while every attached client has said no, so a client with the switch off costs a turn nothing rather than parking a hook for 110 seconds nobody can answer; a second client that does want them is asked exactly as before. The preference lives with the socket, so a reconnect is a fresh one and the client says it again. `--no-approvals` is the same answer one level up: it is the machine's, it holds for every client, and it is what an operator reaches for.

The request goes out as `session.approvals` with the whole pending list of that session (so a client that arrives late and one that missed a settle agree), and `session.list` carries the same `approvals` field. A client answers with `agent.answerApproval` (`sessionId`, `requestId`, `choiceId`), which replies whether it was in time. The choices are the CLI's own `permission_suggestions`, kept on the daemon and handed back verbatim as `updatedPermissions`, so a client never has to know a CLI's permission vocabulary; the reply is `{ "hookSpecificOutput": { "hookEventName": "PermissionRequest", "decision": { "behavior": "allow" | "deny", ... } } }`.

The record is also written to `sessions/<id>.agent.json`. When the daemon starts again and the session is restored from its snapshot, the agent comes back with `live: false`; the client answers with `agent.resume`, which types `claude --resume <id>` (or `codex resume <id>`) into the shell. One at a time: a second `agent.resume` is refused with `agent-resuming` while a typed resume has not produced a live agent, and allowed again 15 seconds later, so a CLI that never starts can still be retried.

A recorded session id is not a conversation, so the daemon looks before it resumes. The transcript path the hooks reported is the evidence: the file is still there and the resume line is typed; the file is gone (a CLI that was started and never used persists nothing, and a transcript can be deleted) and the session's own launch line is typed instead, so the node ends up with a working CLI rather than a bare shell. A hook that names no transcript at all leaves the choice to the shell, as `<resume> || <launch>`. Either way it is one line: two would land in the input box of the CLI the first one started.

## Providers and models

Each agent CLI is one `ChatProvider` value (`src/providers/provider.ts`, `claude-provider.ts`, `codex-provider.ts`, `terminal-providers.ts`): its kind and name, its model catalog, what it can do, the command to run, the template a terminal resumes it with (`claude {flags} --resume {id}`, `codex resume {flags} {id}`, where `{flags}` is the mode and the model the node was started with) and how to make a backend for a chat. `ProviderRegistry` is the list of them plus the detection cache; nothing else in the daemon branches on which CLI a chat is. The catalog is Claude Code, Codex, Gemini and GitHub Copilot, in the order every menu lists them; the last two are terminal only and have no chat backend.

`provider.list` answers, per agent CLI, whether it is installed, its version, the models it offers, its resume template and its capabilities. The catalogs are `src/providers/claude-models.json` and `src/providers/codex-models.json`: a model points at a profile, a profile lists option descriptors (reasoning effort, context window, thinking) with their defaults and the context size per option. Adding a model is a JSON edit; a new profile is only needed for a new combination of options. The Codex catalog mirrors what `codex app-server` answers on `model/list` for 0.153 (six models, each with its own reasoning ladder and default); the context windows were measured per model through `thread/tokenUsage/updated`. A `ModelSelection` is `{ model, options }`; the daemon normalizes it (aliases like `opus` or `astra`, defaults for missing options, unknown options dropped).

The capabilities are the honest list of what a CLI does, so a client never offers what would be dropped: whether it can be opened as a chat, as a terminal or both, whether the daemon understands its hooks, whether it streams partial tool output, how it reports a file change (`unified`, `before-after` or `none`), whether it takes attachments and `@` mentions, whether a decline carries a reason, whether "always allow" exists, whether it asks questions the person may ignore, how it folds context (`native`, `prompt` or `none`), whether it reports cost, the context window, slash commands and what the model thought. Claude Code and Codex differ on most of them.

One mode travels with every chat: the runtime mode, the permission policy in one vocabulary for every provider (`supervised`, `auto-accept-edits`, `auto`, `full-access`, the default). For Claude it becomes `--permission-mode`, the selection becomes `--model <slug>[1m]` and `--effort`, and `ultrathink` is written into the prompt because the CLI has no flag for it.

For Codex (`src/providers/codex.ts`) the runtime mode becomes an approval policy plus a sandbox on `thread/start`: `supervised` is `untrusted` in a `read-only` sandbox, `auto-accept-edits` is `untrusted` in `workspace-write` (edits inside the workspace pass the sandbox, commands still ask unless Codex knows them as safe; the CLI has no "ask for commands, not for edits" policy), `auto` is `on-request` in `workspace-write` (Codex's own default) and `full-access` is `never` in `danger-full-access`. The reasoning effort travels as `effort` on every `turn/start`. The `approvals_reviewer` from `~/.codex/config.toml` is left alone; with `auto_review` some approvals never reach the person.

## Chats

One chat is three pieces, whichever CLI is behind it:

- `ChatSession` (`src/chat/chat-session.ts`) owns the thread, the turns, the process generation and when a new backend is needed. It is the same class for every provider.
- `ChatBackend` (`src/chat/backend.ts`) is one CLI process and the protocol it speaks. It reports what happened as `BackendEvent`s (`text.delta`, `tool.started`, `approval.requested`, `turn.done`, `exit`, ...) and never touches the thread. `ClaudeBackend` and `CodexBackend` implement it; the frames themselves are mapped in `claude-protocol.ts` and `codex-protocol.ts`, which are pure and unit tested.
- `ThreadProjector` (`src/chat/projector.ts`) is the only place that turns those events into thread items and the `chat.event`s to broadcast. Item ids carry the process generation, since a resumed CLI numbers its messages from the start again.

A third CLI is therefore a provider value, a backend and a protocol mapper; the session, the projector, the manager and the wire stay as they are.

A Claude chat is `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool stdio`, spawned on the first `chat.send` and kept alive between turns. The daemon folds the stream into thread items (turn, user, assistant, tool, subagent, approval, question, note, compaction), every item tagged with its turn, and broadcasts every change as a `chat.event` to the attached clients; `chat.attach` answers the current thread, so a reload rebuilds the view.

- A `can_use_tool` control request becomes an approval item and `needs-you`; `chat.approve` answers it with `allow`, `allow-always` (the CLI's own suggested rule goes back as `updatedPermissions`) or `deny`.
- An `AskUserQuestion` call becomes a question item instead; `chat.answer` returns the answers keyed by question index, the daemon keys them by question text for the CLI.
- `chat.dismiss { chatId, itemId }` settles a question item as `dismissed` without answering it. Only a question the CLI asked beside its turn (`async` on the item, which today is Codex's agent-message question) may be dismissed: the CLI keeps working and never hears about it, so nothing is left waiting. A blocking question and an approval are refused with `request-not-found`.
- `chat.configure` changes the selection or a mode. A running process keeps its flags until the turn ends; the next send starts a fresh process with `--resume` and the new flags.
- `chat.cancel` sends an interrupt and the turn ends as `aborted`. `chat.compact` follows the provider's capability: Claude Code gets `/compact` as a turn, Codex a call of its own.
- `chat.clear { chatId, force? }` starts the chat over: the CLI is killed without waiting for a turn, the items, the queue and the attachments go, `agentSessionId` becomes null and the empty thread is written and sent to every attached client as a `reset` event. The next send starts the CLI without `--resume` (Codex with `thread/start`). Provider, folder, selection, mode, cost and the turn count stay. A chat in the middle of a turn of the person's is refused with `chat-busy` unless `force` is set; a turn the CLI opened itself is not in the way.
- A settled tool item may carry `changes`, the files it touched with the unified diff per file, for a provider that reports one (Codex). Claude Code's edits only carry the text before and after in the tool input, which is why a turn takes a checkpoint of its own.
- A turn takes a checkpoint when it starts: `src/git/checkpoints.ts` writes the chat's folder as a git tree through an index file of ours (`GIT_INDEX_FILE` under `$RUIMTE_HOME/checkpoints`, `git add -A`, `git write-tree`), so the person's own index, stashes and commits are untouched and ignored files stay ignored. The tree id sits on the turn item as `checkpoint`. When the turn settles the daemon diffs the working tree against it and puts the answer on the turn as `checkpointDiff`: one unified diff per file with the added and deleted line counts, at most 100 files (`truncated` says there were more), no body for a binary file or a patch over the cap (`omitted`). `chat.turnDiff { chatId, turnId }` answers the same shape for a turn that has no stored diff yet, which is how a client asks while a turn is still running. A folder outside a repository, or a git that fails, leaves both fields off and the card falls back to what the CLI reported.
- A running tool item may carry `progress`: `startedAt` from the CLI's `tool_progress` frame (`elapsed_time_seconds`, verified on 2.1.266), `description` from its `task_started` frame, and `output` for a provider that streams partial output (a `delta` event on a tool item appends to it). Claude Code sends `tool_progress` for a local Bash only under its remote gate (`CLAUDE_CODE_REMOTE` or `CLAUDE_CODE_CONTAINER_ID`, once per 30 s) and never streams Bash output, so the client counts from the item's own timestamp when nothing came. The result drops `progress`.
- An `Agent` (or `Task`) call opens a `subagent` item instead of a tool item, keyed by the call's `tool_use_id`: the description, the subagent type, the prompt, whether it runs in the background, its status (`running`, `done`, `failed`), what the CLI says it is doing (`summary`, `lastTool`), what it spent (`usage`) and the report it ended with (`result`, markdown). Its own work stays in the thread as ordinary items that carry `parentToolUseId` (tool calls and the text it wrote), so streaming keeps working and the timeline gathers them under the row. `system/task_started` fills in the type and the background flag, `task_progress` the summary, the last tool and the usage. A foreground agent settles from the `tool_result` of its own call, with the CLI's `agentId ... <usage>` footer stripped off and the usage kept; a background one is answered at once with "Async agent launched successfully" and only settles on `task_notification`, where the report is the last text it wrote. One agent keeps at most 200 items and 64 KB of its own text; past that `itemsTruncated` says the row shows the beginning of its work. The turn the CLI wakes up with carries `taskToolUseId`, so its header can point at the row. Codex's `spawnAgent` maps to the same item (always background, status from Codex, no children and no report, since that agent works in a thread of its own).
- Not every turn starts with a message. Claude Code wakes the agent itself when a background task settles: after the `result` of the turn that launched it, and with no user frame in between, it sends `system/task_notification`, a fresh `system/init`, an assistant message and a new `result`. Content that arrives while no turn is open therefore opens one with `origin: 'agent'`, the notification's summary as its `label`, no user item, status `running` and a checkpoint of its own; the `result` settles it like any other turn. A frame that carries a `parent_tool_use_id` is a subagent talking inside its own row and never opens one. A message sent while such a turn is open is not refused as busy: the daemon settles that turn as stale first, and the `result` still coming for it is dropped instead of closing the turn that took its place. The composer offers stop while the turn runs, like any other.
- The thread is written to `chats/<id>.json` when a turn opens, after every tool call and every task that settles (debounced to 500 ms once the record passes 256 KB) and when the turn ends, so a daemon that goes down mid-turn keeps what was said. A chat whose process ended (or a daemon that restarted) starts the CLI again with `--resume` on the next send.
- `chat.send` takes optional `mentions` (paths the person picked with `@`), which stay `@path` in the text for the CLI to expand itself and are stored on the user item so a client can draw them as chips.
- `chat.send` also takes optional `attachments`, any file type, at most 25 MB each and 8 per message, as `{ name, mime, data }` with base64 bytes. The daemon writes each one to `$RUIMTE_HOME/attachments/<chatId>/<id>.<ext>` (`src/chat/attachment-store.ts`) and keeps only `{ id, name, mime, size, path }` on the user item, so a thread with a video in it is still a small JSON file. The prompt names the files by path under the text ("Attached files: - /path (name)"): both CLIs open a file with their own tools, images included. A thread written before this carried its images inline; the read that opens the chat writes them out once and rewrites the record, before the schema sees it. `GET /attachments/<chatId>/<id>` serves the bytes behind the same access rules as `/ws` and the project icon (loopback free, any other client sends its ticket, or its session token, as `?token=`), `inline` for what a browser paints and `attachment` for the rest, with `nosniff`, an immutable cache and, for an SVG, the same `default-src 'none'` policy the icon route uses. The chat's own thread and queue are what say which id belongs to which file, so nothing else can be reached through the route.
- What the model thought before it answered becomes a `thinking` item. Claude Code's thinking blocks (streamed as `thinking_delta`, replayed as a `thinking` content block) and Codex's `item/reasoning/*` notifications both map onto one `thinking.delta` / `thinking.done` pair of backend events, and the projector keeps one item per stretch: consecutive blocks join with a blank line between them, and the first text, tool call or request of the turn closes the stretch. The provider capability `reportsThinking` says whether a CLI hands it over at all.
- A `chat.send` while a turn runs is not refused: the message joins the chat's queue and the request answers `{ queued: true }`. The queue sits on `ChatInfo.queue` (so it reaches every attached client as an info event and goes to disk with the thread, and a reload or a daemon restart keeps it), and the daemon sends the next message the moment the turn settles. `chat.unqueue { chatId, messageId }` drops one; `chat.sendNow { chatId, messageId }` puts one first and interrupts the turn in its way, so the settle sends it. One queue for both providers: Claude's steer folds into the running turn and Codex's app-server queues a second turn, and two semantics per CLI is harder to reason about than one.
- `skills.list { chatId }` answers the composer's `$` picker with `{ name, description, source }` per skill (`src/skills/skills.ts`). A running Codex answers it itself over the app-server's `skills/list`; otherwise the daemon scans the roots the CLI uses. Claude: `$CLAUDE_CONFIG_DIR ?? ~/.claude/skills` (user), every `.claude/skills` from the chat's folder up to the repository root (project), and the `skills` folder of each entry in `~/.claude/plugins/installed_plugins.json`, named `<plugin>:<skill>` the way the init frame does (plugin). Codex: `~/.agents/skills`, `~/.codex/skills` and the `.agents/skills` folders of the project. A skill is a folder with a `SKILL.md`, named by its front matter's `name` or by the folder, described by its `description` (block scalars folded). The scan is cached for 30 seconds per CLI and folder; there is no watcher. Once the CLI announced its own `skills` in the init frame (`ChatInfo.skills`), the answer is narrowed to that list, so a skill turned off in the CLI's settings drops out.
- `chat.send` takes an optional `skills`, the names the person picked with `$`. The names stay `$name` in the text, which is what Codex expands. Claude Code expands a skill only from a text block that starts with `/name` and is the last block of the message, so the daemon splits the prompt (`src/chat/input.ts`): what came before the last `$name` is the leading text block with the earlier `$x` written as `/x`, then the images, then `/name <rest>` as the last block. A `$word` that names no known skill is left alone.
- `fs.search` answers the composer's `@` picker: a fuzzy search over the files under a folder, through `git ls-files` (tracked and untracked, minus `.gitignore`) inside a repo and a bounded walk (20k files, depth 12, no dot folders or `node_modules`) elsewhere. The file list is cached for ten seconds per folder.

## Files

`fs.grep { cwd, query, regex?, caseSensitive?, wholeWord?, limit? }` (`src/fs/grep.ts`) is the palette's find in files: every line under `cwd` that answers to the query, each with its path relative to `cwd`, its line number, where the hit sits in the line (offset and length in UTF-16 units, not bytes) and the two lines above and below it. Ripgrep does the work where it is on PATH (`--json`, one event per line, killed the moment the limit is reached); without it the same search runs in JavaScript over the file list `fs.search` caches, skipping anything over 2 MB and anything with a NUL in its first kilobyte. One hit per line, at most 200 in an answer, and `truncated` says the limit stopped it. A query is literal text unless `regex` says otherwise; a pattern that does not compile comes back as `invalid-query`.

`fs.browse { partialPath, cwd?, hidden? }` (`src/fs/browse.ts`) is what the folder picker lists: the directories that complete what was typed, each with its name, its absolute path and `hasCanvas`. A path ending in a separator lists that directory whole; without one the last segment is a case-insensitive prefix filter on its parent, and `parentPath` says which directory the entries came from. `~` is this machine's home, a relative path counts from `cwd` and answers `cwd-required` without one, and a Windows-shaped path on a daemon that is not Windows answers `windows-path`. Dot-folders stay out unless `hidden` asks for them or the typed prefix starts with a dot. `exists` says whether `parentPath` is a directory that is there, which is what tells a folder that is missing from one that is empty or unreadable; a directory that cannot be read still lists as empty.

`fs.list { path, depth?, hidden? }` (`src/fs/list.ts`) answers one directory, or up to three levels of it, as a flat list where a directory is followed by what is under it: name, absolute path, kind (`file`, `directory`, `symlink`, `other`), size for a file, mtime, and the `hidden` and `ignored` flags. Directories come before files, then names compare with `numeric: true`, so `item2` sits before `item10`. A listing stops at 2,000 entries and says `truncated`. Symlinks are never walked into, so a link out of the folder is one entry and the listing stays inside the folder it was given. `hidden` (a leading dot) is left out unless asked for; the Files panel asks for everything and filters in the client, so its eye button costs no request.

`ignored` comes from one `git check-ignore -z --stdin` per level, with the listed directory as the working directory (`src/git/ignore.ts`, on the shared runner in `src/git/run.ts`). Exit code 1 means nothing matched and 128 means there is no repository; both leave every entry unignored. `.git` itself is flagged by hand, since git never reports its own directory, and an ignored directory is not walked into, so a deep listing never wanders into `node_modules`.

`fs.read { path }` (`src/fs/read.ts`) answers one file for the viewer, in one of three shapes. A text file comes back as `{ kind: 'text', text, encoding: 'utf-8', size, mtime, language? }`, where `language` is a highlighter id guessed from the extension (or from a bare name such as `Dockerfile`) and is left off when nothing recognizes it. A file the sniff calls binary comes back as `{ kind: 'binary', mime, size, mtime }` and its bytes never touch the socket: PNG, JPEG, GIF, WebP and PDF come from their magic bytes, an SVG from a head that opens as one (text, reported as an image, since that is how the viewer draws it), and everything else as `application/octet-stream`. A text file over 2 MB comes back as `{ kind: 'too-large', size }`, so the panel can say so instead of pushing megabytes through the socket; the cap is on text alone, and an image of any size is still an image.

The sniff reads the first 8 KB. A NUL byte settles it, so does a head that will not decode as UTF-8, and more than a tenth of the head in control characters other than tab, newline, carriage return, form feed and escape does too (a log full of ANSI is still text). The path must be absolute and free of NUL, and the last component may not be a symlink: `fs.list` never walks into one either, so a link inside a folder cannot hand the viewer a file that folder does not hold.

`GET /fs/file?path=<absolute>&v=<mtime>-<size>` (`src/fs/file-route.ts`) serves the bytes of an image or a video the viewer is drawing, behind the same access rules as the socket, so a client sends its ticket, its session token or the local secret as `?token=`. Only those two are served, decided by the same sniff: a route that hands arbitrary bytes to an `<img>` tag is a worse deal than one that does not. A video answers `Range` requests (206 with a `content-range`, 416 for bytes the file does not have) and every answer carries `accept-ranges: bytes`, without which a player can start a file and never seek in it. Headers match the project icon route: `content-type` from the sniff, `content-disposition: inline`, `x-content-type-options: nosniff`, a year of immutable caching (the URL carries the file's version, so a write moves the URL with it), and for an SVG a `content-security-policy` that allows nothing but its own styles. In dev, Vite proxies `/fs` to the daemon the way it proxies `/projects`.

`fs.watch { path }` and `fs.unwatch { path }` are per client, like a session attach (`src/fs/watch.ts`). A watch is recursive on macOS and Windows, where the platform does that in one call; elsewhere it covers only the directory it names and the client watches the folders it has open. Changes settle for 250 ms and go out as one `fs.changed { root, paths }` naming the directories that moved, so the client re-lists only what it has loaded; every batch also drops the `fs.search` cache. A recursive watch closes the watches below it, and a disconnect drops every watch the client had.

## Remote clients and pairing

Where a request comes from never grants anything: a tunnel, a reverse proxy or a port forward in front of the daemon makes every visitor a loopback address. What a process on the daemon's own machine presents instead is the local secret in `$RUIMTE_HOME/local.key`, which the daemon writes on its first start (`0600`, in a home of `0700`) and keeps across restarts. It rides where a ticket does (`?token=` or `Authorization: Bearer`) and is compared in constant time. The desktop app reads it from the home and hands it to its page over the bridge; `ruimte pair` reads it and sends it as a bearer. Scripts against a running daemon (`bun run smoke`, `scripts/calibrate-processes.ts`) read it from `RUIMTE_HOME` the same way.

Every other client pairs first, a browser tab on the same machine included: the daemon prints `http://<host>:<port>/pair#<token>` when it listens beyond loopback (and on `bun src/main.ts pair`), and the client posts that one-time token to `POST /auth/pair` with a label for itself and its own ed25519 public key. Pairing tokens die after one use or ten minutes. Only a client on the local secret may mint a pairing URL: `POST /auth/pairing-token` answers 403 without it, and `auth.pairingToken` over the socket answers `forbidden` to a paired client, wherever it connects from. The two share one rule (`mayInvite` in `src/auth/access.ts`); the socket request is what the settings dialog's "Show pairing link" uses, the same way `ruimte pair` uses the HTTP route. `endpoint.info` tells a client the daemon's label, platform, how far away it is and the daemon's public key.

From there nothing long lived travels. Every connection asks `POST /auth/challenge` for a nonce, which the daemon returns with its own id, its public key and its signature over the nonce; the client checks that against the key it pinned at pairing and signs the nonce back to `POST /auth/ticket`, which answers with a ticket. The ticket rides in `?token=` on the socket URL (a browser cannot set a header on a WebSocket handshake) and on the HTTP routes an `<img>` fetches, is good for twelve hours from its last use, lives in the daemon's memory only and is different on every connection. Both signed messages carry the daemon id, so a signature collected by one machine proves nothing to another. The daemon's key pair sits next to its id in `$RUIMTE_HOME/endpoint.json`; the clients' public keys sit in `$RUIMTE_HOME/auth.json`, listed with `auth.sessions` and cut off with `auth.revoke`, which drops that client's tickets and closes its open sockets (code 4001).

A client that paired before there were key pairs holds a session token, stored as a hash in the same file, and keeps working: `auth.registerKey` hangs a public key on its own session over the connection the token already authenticated, and the token is dropped the first time a signature lands. Nothing has to be paired again, and a client that cannot sign at all (a browser without ed25519 in WebCrypto) stays on its token. Everything phase 7 added to the wire is optional, so a daemon and a client of either generation still talk to each other.

A browser sends its page's origin with the upgrade; the daemon accepts its own origin, any loopback origin (the desktop app, the dev server) and what `--allow-origin` adds, and refuses the rest. Serving over the network in the clear still means anyone on the path can read what travels, tickets included, and can read and change everything on the socket: put a reverse proxy with TLS in front (nginx, Caddy) that forwards `/ws` as a WebSocket and hands the daemon the `Host` and `Origin` headers, and pair with the proxy's `https://` address. The `Relay` seam (`src/auth/relay.ts`) is where a rendezvous service for daemons behind NAT would go; the default does nothing.

`bun run serve` at the root builds the client and starts the daemon on every interface serving it, which is the Server Edition: open `http://<machine>:4210/` from any browser on the network and pair.

## Git status, diffs and staging

`git.status { cwd }` (`src/git/status.ts`) answers what the git panel draws: whether the folder is a repository at all, its root, the branch (null on a detached HEAD, which the `detached` flag tells apart), the upstream with `ahead` and `behind`, the base branch and the merge base against it, and the changed files. The parse is `git status --porcelain=v2 --branch -z --untracked-files=all`, with `git diff --cached --numstat -z` and `git diff --numstat -z` for the counts of each side; an untracked file has no history, so its count is one `git diff --no-index /dev/null <path>`, run for the first hundred of them. A file that is staged and changed again since is in two groups, each carrying the counts of its own side, which is what makes staging half a file readable. Renames keep the path they came from. The list stops at 1,000 files and says `truncated`. The base branch is `refs/remotes/origin/HEAD`, else `origin/main`, `origin/master`, `main`, `master`, remembered per repository for five minutes.

`git.watch { cwd }` and `git.unwatch { cwd }` are per client, like a folder watch (`src/git/status-watcher.ts`). The working tree and the git common dir are both watched (a linked worktree keeps its refs in the repository it came from), a burst settles for 300 ms, and a burst whose every path is a loose object, a lock file or something git ignores never costs a status run at all. Only a status that differs from the last one goes out, as `git.status { cwd, status }`. Watching is not free, so it gives up rather than slow the machine down: a repository with more than 5,000 tracked files never gets a watcher, and one whose status run takes longer than a second loses the one it had. The status then says `live: false` and the client goes back to refreshing on focus and after every change it makes itself.

`git.diff { cwd, path, scope, staged?, ignoreWhitespace? }` (`src/git/diff.ts`) answers one file's unified diff with its counts, a binary flag and an `omitted` reason when the diff is binary or past the caps (2,000 lines, 128 KB). `ignoreWhitespace` adds `--ignore-all-space` to the patch and to the numstat both, so the counts always match what the diff shows. `worktree` is the working tree against the index, or the index against HEAD with `staged`; `base` is the merge base against the working tree, so a file shows everything the branch did to it, committed or not. An untracked file is read against `/dev/null` with `--no-index`. `diffTrees` lives here too: a turn's checkpoint diff (`src/git/checkpoints.ts`) and the panel share it, so a diff is capped and shaped the same way wherever it shows up. `commit` is one commit against the one before it: with a `path` it answers that file, without one it answers the whole commit (`files`, `truncated` and the log row that names it), which is what a commit opened from the log draws. A commit with no parent is read against the empty tree.

`git.stage { cwd, paths, staged }` stages the paths (`git add`, deletions included) or takes them back out (`git restore --staged`, or `git rm --cached` in a repository without a commit). `git.discard { cwd, paths }` throws work away without throwing it away: the paths go into a stash of their own named `ruimte-discard-<timestamp>` first (`git stash push --include-untracked`, which is also what resets the working tree), so `git stash pop` is the way back. It answers the stash's name, or null when git found nothing to stash.

## Git branches, the log and the actions

`git.refs { cwd }` (`src/git/refs.ts`) answers every branch the panel can switch to, local ones first and remote ones after, newest tip first (`for-each-ref --sort=-committerdate`), with the branch HEAD is on marked, the base branch marked as the default, and the checkout of a branch another worktree has out, since git refuses to check that one out twice. The stashes come along in the same answer (`stash list`), because the menu that pops one is the menu that lists the branches.

`git.log { cwd, limit?, cursor? }` (`src/git/log.ts`) is a page of the checkout's own history: hash, short hash, subject, author, author date and the refs pointing at the commit, parsed from one `log -z --format=...` per page. The cursor is how many commits were handed out before this page, not a hash to continue from, so a commit landing on top while the log is open does not make the next page skip one. A repository without a commit answers an empty log, not a failure.

`git.action { cwd, actionId, kind, ... }` (`src/git/actions.ts`) is every action the panel takes as one request: `fetch`, `pull`, `push`, `publish`, `force-push`, `sync`, `checkout`, `create-branch`, `rename-branch`, `delete-branch`, `merge`, `rebase`, `stash`, `stash-pop`, `commit`, `commit-push` and `create-pr`. Each is a list of git calls whose output is read while it runs (`streamCommand` in `src/git/run.ts`, which splits on both line endings, since git writes its progress with carriage returns); every line goes out as `git.progress { cwd, actionId, phase, line }` to the client that asked, and the reply carries a summary line, everything the commands wrote and, where there is one, the commit that was written or the pull request that was opened. A failure is a `git-failed` error whose message is that output, which is what the toast puts behind "Copy output". There is no shell anywhere: arguments are lists, so a branch name or a commit message is one argument however it is spelled. `GIT_TERMINAL_PROMPT=0` keeps a credential prompt from stalling a push nobody can type into, and a step that talks to a remote is given up on after two minutes. The client names the run, so `git.cancel { actionId }` ends the git that is going right now.

`push` without an upstream is `push --set-upstream origin <branch>`, which is what the panel calls "Publish branch"; `force-push` is `--force-with-lease`, so a push somebody else made in between stops it. `checkout` of a remote branch makes the local branch that follows it (`checkout --track`) unless a local branch of that name is already there, and `stash: true` parks a dirty working tree first. `delete-branch` needs `force` for a branch git has not merged anywhere. `create-pr` is the one step that is not git: it publishes the branch when the remote has never seen it and then runs `gh pr create --title ... --body ...`, answering the URL out of what `gh` printed.

`git.capabilities { cwd }` (`src/git/capabilities.ts`) says what this machine allows: whether `gh` is on the PATH, and which agent CLI would write a commit message, both cached for a minute.

`git.suggestMessage { cwd, actionId, provider? }` (`src/git/message.ts`) is that message. The staged patch (24 KB, `--unified=1`) and its name-status go into a prompt asking for one JSON object with a subject and a body, and the CLI runs in its own one-shot print mode: `claude -p <prompt> --output-format text`, `codex exec --sandbox read-only <prompt>`, `gemini --prompt <prompt>`, which is `oneShotArgs` on the provider value (`src/providers/provider.ts`). No chat, no session, no SDK. The answer is the last JSON object in whatever the CLI printed around it, and a run past sixty seconds, or one `git.cancel` names, is killed. With nothing staged the working tree is used instead; with no CLI installed the request fails and the client hides the button that would have asked.

## Worktrees

`git.worktree-add { repo, branch }` answers the worktree for a branch of the repository, making it under `$RUIMTE_HOME/worktrees/<repo>-<hash>/<branch>` when it does not exist (a branch that does not exist yet is created from HEAD). `git.worktree-list` and `git.worktree-remove` do what they say. The repository itself is never touched beyond what `git worktree` records.

## Context links

An edge on the canvas into a terminal or chat node lets that agent read the source. The daemon derives what each agent node may read from the project documents it knows (`src/projects/project-index.ts`, which keeps every known project's last document, also after a client lets go of it): a text element or a note with its content, a browser node as its address, a file node as its path, a terminal, chat or drawing by id. A drawing or diagram is listed under the id of the view it mirrors, and `read` also takes the id of the node it is linked through, which is the id `nodes` and `edges` show; a node with no line into the caller stays refused. It reads terminals, chats and drawings live when asked. A drawing arrives as its texts in reading order with the arrows between them as `A -> B` lines, and the whole picture as an SVG behind a heading of its own, so an agent that only wants to know what the drawing says can stop at the list. An edge between two other nodes is only a line; it makes nothing readable. Every shell and chat gets `RUIMTE_CONTEXT_URL` (`http://127.0.0.1:<port>/context`), a bearer token (`RUIMTE_HOOK_TOKEN` in a shell, `RUIMTE_CONTEXT_TOKEN` in a chat) and the directory of `ruimte-context` in front of its PATH (`apps/server/bin` in a checkout, the app's `bin` resource when packaged), where `ruimte-context` lists the linked sources and `ruimte-context read <id>` prints one. A `read` without an id or of an id nobody linked is a refusal in the dialect a verb refuses in (`refused	<code>	<message>` on stderr, exit 3, codes `bad-arguments` and `unknown-source`) with the sources that are linked under it, so a caller that guessed an id gets the list instead of a failure. A daemon that answers 500 or does not answer at all stays exit 1.

What `read` gives back follows the kind: a text (a note, a text on the canvas, a browser address) its own text, a terminal the last 2000 lines of its screen, a chat the thread as markdown, a drawing its reading order with the SVG under it, and a file its path with a line telling the agent to read it with its own tools. `ruimte-context help read` says the same, from the same constants.

`ruimte-context read <id> --tail N` is the cheap read next to the whole one: the last N lines, where the last fifteen of a neighbour is usually the whole answer. The CLI only checks that N is a positive whole number and sends it as `?tail=N`; the daemon does the counting, because only the side that renders a chat or a drawing knows what a line of it is, and because the wire then carries fifteen lines instead of two thousand. A line is a line of the screen for a terminal (the 2000-line cap stays the ceiling, so a larger N reaches no further back), a line of the rendered markdown for a chat, a line of the text for a text, and a line of the reading order for a drawing, which leaves the SVG out altogether: the picture is the expensive half and the last lines of it would be markup. A file ignores it, since its whole answer is a path and a sentence.

## Canvas verbs

Any other first word is a verb: `ruimte-context <verb> ...` posts `{ argv }` (the words after the verb) to `POST /canvas/<verb>` with the same bearer token, and the daemon parses them (`src/canvas`), so a CLI from an older build never disagrees with the daemon about what a verb takes. `ruimte-context help` lists them from the registry in `src/canvas/verbs.ts`, which also names `list` and `read` so one list documents everything the CLI does; those two are answered by `GET /context`, and `POST /canvas/list` or `/canvas/read` is a 404 refusal (`not-a-canvas-verb`) that points at the CLI:

- `help [verb]`: one row per verb, `verb	name	arguments	summary`, with a `detail` row and the row about refusals and exit codes under it. Every row says in its first field what it is, so nothing below the list reads as a verb. A `scope` row under the list says that `list` and `read` are what a person linked into this session while `nodes`, `edges`, `views`, `node`, `agent`, `team`, `link`, `notify`, `view`, `open`, `group`, `arrange` and `rename` are the project itself, and that a node an agent adds is readable through `read` only once a line runs from it into the caller; the same row is in the detail of `list`, `read` and `nodes`, which is where an agent meets the confusion. A `dry run` row names the verbs that take `--dry-run`, rendered from the registry. With a verb it prints that one verb's detail instead: its synopsis, what it prints, which flag goes with which kind and what it is for, where a node lands, and how paths are resolved. Every line is tab-separated and comes out of the registry entry the same parse runs from (`detail` on the verb, the kind and flag columns derived from the tables `run` checks against), so help cannot claim a pairing the daemon refuses. A refusal over arguments ends with a `detail	ruimte-context help <verb>` line.
- `nodes [--view V]`: the nodes of a canvas, `id kind title x y w h group`, where x and y are the node's top left corner in canvas pixels and may be negative and `group` names the frame the node stands in (empty on the canvas itself, the innermost frame when they nest). The last line is not a node: it is `self` with the caller's own id, or `self -` when the caller is not a node on that canvas. A terminal session can also read its id off `RUIMTE_SESSION_ID`, but a chat backend is given no such variable, which is what the `self` row is for.
- `edges [--view V]`: the lines of a canvas, `id from to label`, with an empty label where the line has none. `nodes` says nothing about lines, so without this a caller cannot tell a link that is missing from one that only runs the other way; a canvas with no lines on it prints nothing at all.
- `views`: the views of the project in sidebar order, `id kind name delete why`; a separator is in the list with an empty name. The fourth column is `yes` or `no`: whether `view delete` would remove that row for this caller, which is the one question the list cannot be read off (the maker is in the file but not on the wire, and the machine setting is not in the project at all). The fifth says why, because the answer alone explains nothing: `yours`, `this machine frees every view`, `a person made it`, `<id> made it`, or `you are in it`. Without it a caller on a machine that frees everything reads a column of `yes` beside views it never made and takes it for a bug. The last line is `self` with the view the caller stands in: the canvas for a node, its own id for a session that is a view.
- `node <note|browser|drawing|file|terminal|chat> [--title T] [--text B] [--url U] [--path P] [--source V] [--cwd P] [--view V] [--beside N] [--dry-run]`: adds one node and prints `id kind viewId`. `--text` is a note's body, `--url` (http or https) is required for a browser, `--path` (a file) for a file node and `--source` (a drawing view of the project) for a drawing node; `--cwd` is only for a terminal or a chat and must lie inside the project folder or a worktree of its repository. A flag that does not belong to the kind is refused. A relative `--path` or `--cwd` is resolved against the project folder, never against the caller's own directory, which the daemon does not know; an absolute `--path` may point outside the folder and is then stored absolute. `--beside` puts the node right of that node wherever it sits; without it the node lands on the first free spot right of the caller, or right of everything on the canvas. Without `--title` a node is called what a person's click would have called it (a note `Note`, a file its own name, a drawing the name of its source). A canvas holds at most 500 nodes. A terminal or chat made this way starts no process until a client shows it.
- `node delete <nodeId>`: removes one node and prints `deleted id kind title`, an `ended id kind` line when it held a session, an `edges <count>` line for the lines that ran into or out of it, and for a group a `members <count>` line. An id it cannot find is refused with the nodes this same call would remove, never with the caller's own node or a node it did not make, since an alternative that is refused a line later is worse than no list. The rule is `view delete`'s: only a node the caller made, unless the machine's setting frees every one; never the caller's own node (`deletes-caller`). A terminal or chat node is ended before the write, so no shell outlives the node it answered to. A group loses its frame and nothing else: the nodes inside it stay where they stand, because they are not the caller's to take along, which is also why there is no separate `ungroup` verb. The node is looked for on every canvas of the project, so this takes no `--view`. It is a word after `node` rather than a verb of its own, since everything else `node` does is `node <kind>`; the registry entry dispatches on the first word and `help` renders the subcommand the way it does `view`'s.
- `agent <claude|codex|gemini|copilot> [--chat] [--prompt T | --prompt-file F] [--cwd P] [--view V] [--beside N] [--group G] [--title T] [--dry-run]`: opens an agent node that starts working and prints `id kind viewId cli edgeId`. Without `--chat` it is a terminal node running that CLI, with it a chat node fixed to that CLI, which only a provider with a chat backend takes (Claude Code and Codex today). A CLI that is not installed on this machine is refused with the ones that are. The node lands where `node` would put it, unless `--group G` names a group node of that canvas: then it goes in a row under that group's title bar, the group grows if it has no room, and a collapsed group also takes the new id into its `memberIds`. `--group` and `--beside` cannot both say where the node goes. The verb draws one edge, from the caller into the new node, so the new agent can read the caller with `ruimte-context read`; a caller that is not a node on that canvas gets no edge and a `-` in the last column.
- `team --label L --roles '<json>' [--view V] [--cwd P] [--dry-run]`: opens up to eight agents at once, in a group of their own, and prints `id kind title viewId cli edgeId`, the group first with its label in the title column and a dash for its CLI and its edge, and then one line per role in the order of `--roles`. The title is the column that tells two roles of one provider apart, which the order of `--roles` alone cannot, and it sits where `nodes` has it. A role is `{ "title", "prompt", "provider", "chat" }`, checked against a zod schema in the registry entry, so a role that is wrong is refused by its place in the array (`role 1 (prompt): ...`); `--roles` that is not JSON is its own refusal (`bad-roles-json`), and both list the shape of a role under them. Every role gets the same prompt treatment `agent` gives one, so a terminal role starts on its prompt and a chat role has it as the first message of its thread. `--cwd` goes to all of them, since a directory per role is not a thing. The agents stand in rows of at most four inside the frame, placed by the same `placeInGroup` a single `--group` uses, and the group is sized to hold them; it is not collapsed, so membership is geometry and there is no `memberIds` to write. One edge per role, from the caller into that agent, like `agent` draws one.
- `link --to A,B [--from N] [--label L] [--view V]`: draws context lines on one canvas and prints `id from to new|existing out|back`, one line per edge. `--from` is the caller unless it names another node. Between two agent nodes the line goes both ways, since each of them then reads the other; the last column is what tells those two rows apart (`out` for the line that was asked for, `back` for the one the verb drew by itself), because one `--to` answering in two rows otherwise reads as a bug. An edge that is already there is left alone and reported as `existing`, so running the same `link` twice writes nothing; at most twenty ids in `--to`. Two edges between the same two nodes are one line with a head at both ends in the client, since two beziers along the same path lie on top of each other.
- `notify <id> --text "..."`: leaves a message of at most 500 characters for the agent in another node and prints `notified id now|waiting <what happened>`. The rule for who may notify whom is the one the canvas already draws: a line has to run from the caller into that node, the same direction that makes the caller readable to it, so a message travels exactly where a `read` already can and an agent cannot poke a node it has no relationship with. Anything else is a refusal that lists the nodes the caller can reach (`not-linked`, `not-an-agent`, `unknown-node`, `self-notify`, `not-on-a-canvas`). Where it lands depends on what is running in the receiver: a shell with no agent in it gets the line on its screen at once, dimmed, written to the screen and to whoever is attached but never into the PTY, the way the motd is; an agent that answers a context hook (Claude Code today) hears it at the start of its next turn, since the hooks are the only channel into a running CLI; a CLI whose hooks are one way gets the line on the screen instead, and the answer says so; a chat hears it in front of its next prompt, beside the note about links that changed; and a node that runs nothing yet keeps it until it starts, where it stands above the first prompt. What is waiting lives in `$RUIMTE_HOME/notices/<nodeId>.json` (`src/context/notices.ts`), for the same reason a pending prompt does: the receiver may be a node nobody has mounted, and a restart must not lose what was left for it. It is delivered once, whichever channel gets there first, at most ten wait per node with the oldest dropped, and one nobody picked up in six hours is dropped rather than delivered late, since it is news about work that has moved on.
- `view <new|rename|icon|move|delete> ...`: the sidebar itself. It is the one verb with words of its own, and the table those words come from is also what `help view` renders, so a subcommand is documented by being defined (`subcommands` on the registry entry, printed by `help` under the verb's own lines). A first word that is not one of them is a refusal (`unknown-subcommand`) with the synopsis of each.
  - `view new <name> [--kind canvas|chat|terminal|browser|drawing|file|separator] [--path P] [--url U] [--after V]`: adds a row and prints `id kind name`. The kinds are read off the union in `packages/contracts`, so a kind added there is one this verb makes without a line of its own. `--path` is required for a file and `--url` for a browser, both refused on any other kind and resolved the way `node` resolves them; `--after` puts the row under that view instead of last. A project holds at most 100 views.
  - `view rename <viewId> <name>`: prints `id kind name` and sets `titleSource: 'user'`, the rule a person renaming follows, so nothing the view hosts renames over it. A rename to the name it already carries writes nothing and is not a refusal.
  - `view icon <viewId> <lucide-name|emoji>`: prints `id kind lucide|emoji mark`. A value made of letters, digits and dashes that is not one of the 60 Lucide names is a typo rather than a mark, so it is refused with all of them in rows of ten rather than written into the file as an emoji nothing can draw. A separator has no room for one (`not-markable`).
  - `view move <viewId> --after V | --first`: prints `id kind index`, the place it now has counted over every row. Exactly one of the two flags, and never under itself (`two-places`).
  - `view delete <viewId>`: prints `deleted id kind name`, an `ended id kind` line per session the view held, and for a canvas a `nodes <count>` line with a `node id kind title` line per node (the first twenty), so what went is named rather than implied. Only a view whose `createdBy` is the caller, unless the machine's `agentsDeleteAnyView` frees all of them; the refusal (`not-yours`) names who made it, who is asking and what the setting does. Never the view the caller is standing in (`deletes-caller`), which is also why this verb can never empty the sidebar.

- `group --nodes A,B [--label L] [--color C] [--view V]`: draws a frame around nodes that already stand together and prints `id group label viewId members`, with an `also id kind title` line per node that was not named but ended up inside the frame. The frame is the box those nodes occupy plus the room and the title band a person's own grouping gives it, from `groupFrame` in `packages/contracts`, which the client's `groupSelection` runs as well, so the two ways to group cannot drift. `--color` is one of the node accents (the same closed set the client's swatches come from, `NODE_ACCENT_NAMES` in contracts) and a value that is not one is refused with all of them. A group is never one of `--nodes` (`not-groupable`), the way the client leaves one out of a selection, and every node has to stand in the same place already, all on the canvas or all inside one and the same group (`different-groups`, which names both nodes and where each of them stands). Inside a group that is folded shut the new frame joins its `memberIds`, since nothing reads geometry while it is collapsed.
- `arrange --nodes A,B [--layout grid|row|column] [--cols N] [--view V]`: lays those nodes out without overlap, in the order they were named, and prints `id x y` per node. The block starts at the top left of the box they already occupy, so a canvas is straightened where it stands and nothing jumps out of sight; one node therefore never moves at all. A column is as wide as the widest node in it and a row as tall as the tallest, 40 px apart like everything else the daemon places, and nothing is resized. Without `--layout` it is a grid as square as the count allows (`gridColumns`); `--cols` only means something there and is refused on a row or a column (`flag-not-for-layout`), as is a number past the count (`too-many-columns`, which names both). A group carries whatever stands inside it, so it is not something to arrange (`not-arrangeable`). Nodes that already stand where this would put them are reported and nothing is written. The layouts themselves are `arrangeRects` in `src/canvas/placement.ts`, beside the other placing.
- `rename --node N --title T [--view V]`: renames one node and prints `id kind title`. It sets `titleSource: 'user'`, like `view rename` does for a row in the sidebar, so the session the node holds never renames over it again. One node per call, by id, and a rename to the title it already carries writes nothing.
- `open <viewId>`: shows a view to whoever has this project on screen. It prints `showing id kind name` and then `sent yes ...` or `sent no ...`, and it is the one verb that writes nothing: making is shared and lands in `project.json`, looking is one person at one screen. So it is an event, `project.showView { projectId, viewId, by }`, rather than a change to the document; `by` is the caller's id, never a title, so a client that wants to name the agent reads the name out of the document it already holds. It goes only to the clients that have that project open, which is the one event that is aimed rather than broadcast: `project.changed` reaches every socket because a client that let go of a project may still hold its document, while being shown a view is something that happens to a person. The store keeps that per socket (`addViewer` on `project.open`, `removeViewer` on `project.release` and `project.close`, everything dropped when the socket goes). Nobody watching is not a failure, which is what the `sent no` line says: nothing is held for later, and the same call a minute later shows the view to whoever is there then. A separator never opens (`never-opens`) and an id the project does not have is refused with the views it does (`unknown-view`). No `--dry-run`, since there is nothing to undo.


What a client does with `project.showView` is the client's own: by default nothing moves and the request waits in the banner over the views, naming the agent and the view with a "Go there" button. A client setting turns that into following, where the view takes the place of the one in the cell that has the focus, a view already standing in another cell takes the focus instead of appearing twice, and the same banner names the agent and the view with a way back. A client that does not have the project open ignores the event altogether. That is the whole of why this is a verb a person can refuse to follow: the daemon executes and never asks, but showing is the one thing that was never the daemon's to decide.

Every view an agent makes carries `createdBy` with the caller's id in `project.json`, a separator included, and that is the whole of the delete rule. It is in the shared file rather than beside the node like a depth, because a maker is a fact both sides read and nothing has to be defended with it: a person deleting a view of their own is not what the rule is about. A node's maker is the other way round, in the lineage beside the project (below): a node is made by a verb and by a person's own drag, the client never sends a maker, and an agent with a shell in the project folder could write itself into `project.json` as the maker of anything. Deleting a canvas takes its nodes with it, so the daemon ends their sessions first, under the same lock the write takes and before the new document is handed back: `SessionManager.kill` for a terminal and `ChatManager.kill` for a chat, an id neither knows counting as already ended. That is what makes the verb work with no client connected, where a project closing in the client is the same rule run from the other side. The prompt and the lineage record of a node that went are pruned by the `ProjectIndex.onPlaces` hook the write already fires.

The operations themselves are pure functions in `packages/contracts/src/project-views.ts` (`withView`, `withRenamedView`, `withViewIcon`, `withMovedView`, `withDuplicatedView`, `withoutView`, `withNodeAsView`, `withViewAsNode`, `withNodeOnView`, `sessionNodesOfView`), which the client's document store runs as well, so the sidebar and the verb cannot drift on what a view id, a separator, a cross-view edge or the last view of a project means. What only the client knows stays there: the camera, the focus and the split layout.

`--prompt` is what the new agent starts working on, and it never reaches `project.json`: the daemon holds it against the node id under `$RUIMTE_HOME/prompts/<nodeId>.json` and delivers it once, the moment the session or the chat for that id is made (`src/agents/pending-prompts.ts`). That is the only place where "exactly once" can be promised, since a project open in two windows would otherwise send it twice, and it is on disk because the node may well be made on a daemon that restarts before any client mounts it. A terminal agent gets the prompt on the line the daemon types into its shell, as the CLI's own prompt argument (`firstPromptArgs` per provider: a positional for `claude` and `codex`, `-i` for `gemini`, `-p` for `copilot`), because nothing can tell when a CLI is ready for typed input and the line is built at `session.create` anyway; the person then sees the prompt in the shell as a line they could have typed. A chat agent gets it as the first message of its thread, which is what spawns its process. A prompt is at most 2000 characters: the launch line waits in the tty's canonical buffer until the shell reads it, and a longer line is cut off there without a word. `--prompt-file` reads the same prompt from a file, resolved against the project folder and, like `--cwd`, refused outside the folder and the worktrees of its repository. A node deleted before anyone ran it takes its prompt with it (`ProjectIndex.onPlaces`).

An agent that opens agents is capped by how deep the chain already runs (`src/canvas/depth.ts`). A node a person opened is depth 0 and a node an agent verb opens is one deeper; `agent` opens up to depth 2, `team` up to depth 1, so a person's agent may open a team while the agents in that team may not open another one, and a hand-made chain of single agents still gets two links. Both refusals (`too-deep`) name the depth the caller sits at and the depth each verb reaches. Every node a verb makes is written down beside the project under `$RUIMTE_HOME/lineage/<nodeId>.json` (`src/agents/lineage.ts`): who made it, how deep it sits and whether it is an agent node. The depth and the per-caller cap are about the agent ones only, so a caller that makes twenty notes still has its room for agents; the maker is what `node delete` asks for, which is why a note is written down at all. A record from before that (no `agent` field) is read as an agent node. It is not a field on the node: an agent has a shell in the project folder and could rewrite `.ruimte/project.json` to call itself depth 0, and a field the client does not know is stripped by zod on the way through anyway. On disk, because a restart is exactly when a loop would otherwise start counting over. The same record caps one caller at 16 agent nodes open at a time (`too-many-agents`), which is the narrow limit under the canvas's own 500; a node the person removes frees the count, through the same `ProjectIndex.onPlaces` that prunes a pending prompt.

`--dry-run` is on `node`, `agent` and `team` only. It runs every check under the same lock a write takes and then writes nothing; the answer is the same columns with `dry-run` in the first field, and where a real call would draw an edge the last column names its ends (`term-1 -> <new node>`) rather than the bare word, so the direction can be read before anything is made. A team names the role in the place of that placeholder (`term-1 -> <Lexer>`), since a dry run of eight roles is a plan and two roles of one provider are otherwise the same row twice. Every other verb refuses the flag by name (`no-dry-run`) and lists the verbs that take it, so a dry run is never a silent nothing.

A name on the canvas is at most 120 characters, whether it arrives as `--title`, as a team's `--label`, as a role's `title` or as the label of a line (`titleField` in `src/canvas/verb.ts`). It is never unique: two nodes may carry the same title and two groups the same label, because an id is what names a node and a title is what a person reads. Every refusal that counts says both numbers, the one that came in and the one that fits, since a caller that only hears the limit has to count its own JSON: `--roles has 9 roles and a team takes at most 8`, `The prompt is 2001 characters and at most 2000 fit`, `Board holds 500 nodes and this would add 2 more`.

`--text` is read for the escapes `\n`, `\t` and `\\`, and nothing else (`src/canvas/text-escapes.ts`), since a shell hands `--text "a\nb"` to the daemon with the backslash still in it. For a body with exact bytes there is `--text -`, which is the CLI's own step: it reads stdin, escapes it back and sends one `--text=` argument, so the daemon only ever sees the final string and a heredoc arrives as it was typed.

The caller is the session or chat its token belongs to, looked up in every project the daemon knows (`ProjectIndex.locate`), open or released; one that no project places gets nothing. A verb that works on a canvas takes `--view` or the canvas the caller is a node on, and a caller that is a view of its own must pass `--view`. Selectors are ids, never titles. A change is applied by `ProjectStore.mutate` to the file on disk under the lock `project.save` takes, at `rev + 1`, and reaches every connected client as `project.changed`.

Answers are `text/plain`, one tab-separated line per result. A refusal is a 422 (a 404 for an unknown verb) whose first line is `refused	<code>	<message>`, followed by what the caller can pick instead wherever the set is closed: the verbs after an unknown verb, the canvases after a `--view` that is not one, the drawings after a bad `--source`, the flags of the kind after a missing or misplaced one, the nodes of the canvas after a `--beside` that names none (over twenty of them it points at `ruimte-context nodes` instead), and everywhere a list is offered it holds only what that same call would take: no group under a `group --nodes` or `arrange --nodes` that names none, not the node a `link --to` would start from, and under `node delete` only the nodes it would really remove, the groups of the canvas after a `--group` that names none, the CLIs that are installed after one that is not, the CLIs with a chat backend after a `--chat` on one without, the shape of a role after `--roles` that does not parse, the depths each verb reaches after one that is too deep, the verbs that take `--dry-run` after the flag on one that does not, the views of the project after an id that names none, the Lucide names after a mark that is not one, the node accents after a `--color` that is not one, and the project folder with the worktrees of its repository after a `--cwd` or a `--prompt-file` outside all of them. A closed set that happens to be empty is a `note` row saying so (a canvas with no groups on it, a project with no drawing views), never an empty list, which would read as a daemon that lost them. Where nothing can be listed, a URL, a path, a directory that is not there, the sentence itself says what is allowed and no list is invented. An unknown verb whose name holds a space, which is a caller that quoted the whole line, gets a `note` saying a verb and its arguments are separate words. Arguments a verb could not parse end with `detail	ruimte-context help <verb>`. The codes: `unknown-verb`, `unknown-subcommand`, `not-a-canvas-verb`, `bad-request`, `unknown-flag`, `missing-value`, `duplicate-flag`, `bad-arguments`, `not-in-project`, `view-required`, `not-a-canvas`, `flag-not-for-kind`, `missing-flag`, `bad-url`, `bad-path`, `bad-cwd`, `no-folder`, `cwd-outside-project`, `not-a-drawing`, `unknown-node`, `canvas-full`, `unknown-group`, `two-places`, `no-chat-backend`, `cli-not-installed`, `bad-roles-json`, `bad-roles`, `too-deep`, `too-many-agents`, `prompt-twice`, `empty-prompt`, `prompt-too-long`, `bad-prompt-file`, `prompt-file-outside-project`, `self-link`, `too-many-links`, `self-notify`, `not-on-a-canvas`, `not-an-agent`, `not-linked`, `no-dry-run`, `unexpected-value`, `unknown-view`, `too-many-views`, `unknown-icon`, `not-markable`, `not-yours`, `deletes-caller`, `unknown-color`, `not-groupable`, `different-groups`, `not-arrangeable`, `flag-not-for-layout`, `too-many-columns`, plus `project-missing` and `project-invalid` when the file is gone or broken, and `unknown-source` from the CLI's own `read`. The CLI prints an answer to stdout and a refusal to stderr, and exits 0 on success, 1 when the daemon cannot be reached or fails, 2 outside a live session (no token, or a 401 for a token the daemon does not know, such as one from a session that ended) and 3 on a refusal.

How an agent hears that the CLI exists depends on where it runs:

- Every chat process starts with one sentence about the verbs (`VERBS_NOTE`): Claude Code in its system prompt (`--append-system-prompt`), Codex in front of the first prompt, since the app-server protocol has no system prompt. A chat that has links at that moment gets a second sentence about them in the same place. When the set of links changes between two turns (added or removed, matched by id), the daemon puts a note in front of the next prompt naming what came and went (`src/context/context-note.ts`, `contextChangeNote`) and shows it in the thread as an info note. A slash command is sent untouched; the note waits for the next real prompt.
- A shell that has links the moment it is created shows one dimmed line above its first prompt (`contextHint`), written to the screen only, never to the PTY, with anything `notify` left for that node under it. A link made while the shell runs is not announced on the screen; the terminal node's header shows a "context" chip, and a Claude Code agent inside the shell hears what changed at its next turn through its prompt hooks (above).

A Codex chat (`provider: 'codex'` on `chat.create`) is `codex app-server`, JSON-RPC over stdio (`src/chat/codex-transport.ts`, `codex-backend.ts`, `codex-protocol.ts`). The first send spawns it and handshakes: `initialize`, `initialized`, then `thread/start` with cwd, model, approval policy and sandbox, or `thread/resume` with the stored thread id (a thread Codex no longer has falls back to a fresh one with a warning on the thread). Every message is a `turn/start`; the notifications fold into the same thread items, so the client does not know the difference:

- `agentMessage` items stream through `item/agentMessage/delta` into assistant items; `plan` items are assistant text too. Reasoning items are not shown.
- `commandExecution` is a `Bash` tool item (the `/bin/zsh -lc` wrapper stripped, `aggregatedOutput` as output) whose partial output streams in through `item/commandExecution/outputDelta` while it runs, `fileChange` an `ApplyPatch` tool item with the unified diffs in `changes`, `mcpToolCall` and `dynamicToolCall` tool items under their own names, `collabAgentToolCall` (Codex's own multi-agent calls) a tool item too, except `spawnAgent`, which is a subagent item, `contextCompaction` a compaction marker.
- `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` are approval items. `allow` answers `accept`, `allow-always` the execpolicy amendment Codex proposed (or `acceptForSession`), `deny` answers `decline`; Codex takes no reason with a decline, so `message` stays on the daemon. `serverRequest/resolved` cancels an approval that Codex withdrew.
- `item/tool/requestUserInput` (blocking) is a question item answered by Codex's own question ids. An agent message that carries `questions` (Codex asking without blocking, it polls with `sleep` until the person answers) is a question item too, marked `async`; `chat.answer` sends the chosen labels with `turn/steer` into the running turn, and `chat.dismiss` drops it locally so the person can ignore it.
- `chat.cancel` is `turn/interrupt` (the turn ends `interrupted`, shown as aborted), `chat.compact` is `thread/compact/start`, which Codex runs as a turn of its own.
- Usage comes from `thread/tokenUsage/updated` (`last.totalTokens` as the context in use, `modelContextWindow` as the window). Codex reports no cost, so `costUsd` stays zero and the turn fold only shows the duration. Slash commands stay empty.
- `item/permissions/requestApproval`, MCP elicitations and any other server request the daemon does not understand are refused with a JSON-RPC error, so Codex never waits on an answer that will not come.
- The thread id is what a terminal resumes with `codex resume <id>`, and "Open in chat" on a terminal that ran Codex opens a chat on the same thread.

## Usage

`src/usage` answers what both CLIs cost and what is left of their plans. Nothing here calls an API and nothing reads a credential.

The scanner walks `CLAUDE_CONFIG_DIR ?? ~/.claude` plus `/projects` and `CODEX_HOME ?? ~/.codex` plus `/sessions` (the same variables the hooks installer reads) for `*.jsonl`, prefilters every line on the words that can carry counts before it parses one, and remembers each file by size, modification time, byte offset and, for Codex, the parser state (`readers/`): unchanged is skipped without opening the file, grown is read from the offset on top of what is there, anything else is read again from the start. The line at the end of a file that is still being written is parsed but not counted towards the offset, so it is read once when it is finished. Claude repeats one message over several lines and copies finished ones into a resumed transcript, so the largest value per field per `message.id` wins; Codex reports a cumulative total per turn, so a call is the difference with the line before it, falling back to `last_token_usage` when a compaction makes that difference negative, and the burst a forked or spawned thread replays at its start is dropped. The index is at `$RUIMTE_HOME/usage/index.json` as interned tuples: throwing it away costs one cold scan (2.2 s over 1,400 transcripts on an M-series Mac; a warm pass is 50 ms), and a file that Claude Code has since cleaned up keeps its records.

Prices come from LiteLLM's `model_prices_and_context_window.json` with a 24 hour lifetime and a 10 second timeout, kept at `$RUIMTE_HOME/usage/prices.json`, with a snapshot bundled in the repo as the offline fallback (`bun run --cwd apps/server snapshot-prices` refreshes it). A model matches exactly, then without its date suffix, then on the longest family before a dash; a bare family name (`opus`, `gpt`) prices nothing and travels as `costUsd: null`, which every consumer shows as a question mark rather than as free. Missing cache rates default to 10% of input for a read, 125% for a write and twice input for the one hour kind. A Claude line whose model is `<synthetic>`, and one whose four counts are all zero, never reached the API and is not counted as a call. `usage.summary` scans when the last pass is over a minute old and aggregates in the time zone the request carries; `usage.subscribe` keeps that pass running once a minute while a client has the page open and announces a change with `usage.changed`.

Every price is in dollars. Beside the price table the daemon asks frankfurter.app for the ECB reference rate of the day (`from=USD&to=EUR`), on the same 24 hour lifetime and the same 10 second timeout, kept at `$RUIMTE_HOME/usage/exchange-rate.json` and travelling on `usage.summary` as `rate`. `--no-price-fetch` turns both off. Without a rate the page stays in dollars rather than putting a euro sign in front of a dollar amount; the conversion itself is the client's, so two people looking at one daemon can read it in different money.

`usage/limits` asks the CLIs what is left of the plan. Claude Code gets a `claude -p` on the stream-json protocol, an `initialize` control request (without it the process waits and answers nothing) and then `get_usage`; Codex gets a `codex app-server`, the usual handshake and `account/rateLimits/read`. Both processes end as soon as they have answered. A pass runs every five minutes, doubles to an hour after a failure and leaves the last good numbers up; a CLI that is not installed is reported as such. In between, the `rate_limit_event` frames of a running Claude turn and the `account/rateLimits/updated` notifications of a Codex one fold onto the same windows by id, keeping the reset and the length the event leaves out. `usage.limits` reads the snapshot, `usage.refreshLimits` forces a pass, `usage.limitsChanged` announces one.

## Smoke test

With a daemon running:

```sh
bun run --cwd apps/server smoke            # or: smoke ws://host:port/ws
```

It creates a session, runs `uname`, prints the streamed output and the screen a reattach would receive, then kills the session.

## A remote daemon in Docker

`docker/` builds a second daemon on Linux, reachable from this machine on `127.0.0.1:4310`, with two
git repositories of its own under `/work`. It is how the pairing, the handshake, the credential on
the socket and the `lan` reachability get tested against a machine that is really not the client's.
`bun run --cwd apps/server docker:up` starts it, `docker:pair` prints a pairing URL, `docker:test`
runs the suite against a fresh container of its own; the tests skip themselves unless
`RUIMTE_DOCKER=1` is set. The machine keeps its home and its `/work` in two named volumes across a
`docker:down`, and `docker:reset` is what empties them. See `docker/README.md`.
