# Agent verbs

`ruimte-context help` is the reference for every verb.

- `verbs.ts` is the one registry for parsing and `help`. No aliases for old spellings. A refusal is a 422 whose first line is `refused\t<code>\t<message>`, followed only by what that call would accept.
- The action handlers (`src/actions`, catalog from `@ruimte/actions`) enforce the checks, so a person, Voice and an agent meet the same ones. Selectors are ids, never titles. Every write goes through `ProjectStore.mutate`.
- Depth and the per-caller count live in the lineage under `$RUIMTE_HOME/lineage` (`depth.ts`), never on the node. A person's node is depth 0; `agent` opens up to depth 2, `team` up to depth 1. A caller holds at most `MAX_OPENED_PER_CALLER` agent nodes at a time.
- `fork` takes only a chat the caller opened, as its child under the same bounds as an `agent` child (`src/actions/fork-actions.ts`). `task new` gives work only to an agent the caller opened, by lineage, never by a canvas line.
- The mode ceiling (`mode.ts`) is read when the verb runs, carried on the `start-agent` entry and the lineage, and applied again at every start (`SessionManager.create`, `ChatManager.create`). A terminal agent no agent opened keeps the mode a person's save gave it (`src/sessions/mode-approvals.ts`), else `supervised`.
- Every start of a node an agent made checks its folder again (`startCwdGuard` in `project-paths.ts`), since a path may since have become a symlink.
- A first prompt never reaches `project.json`. It waits in `$RUIMTE_HOME/prompts/<nodeId>.json`, is delivered once (`src/agents/pending-prompts.ts`), and is capped, since the tty silently cuts a terminal agent's launch line.
- Delete verbs remove only what the caller made (a view's `createdBy`, a node's lineage), unless the machine's `agentsDeleteAnyView` allows more, and never the caller's own node or view. A terminal or chat node ends before the write.
- A verb never approves a command, launch, routine or mode; a command it sets in a routine or launch waits for a person. `--dry-run` runs every check under the write's lock and writes nothing; a verb that cannot preview refuses the flag by name.
- A verb into a feature follows that feature's rules beside its code: `launch-verb.ts` (`src/launches`), `routine-verb.ts` (`src/routines`), `browser-verb.ts` (`src/browser`), `device-verb.ts` (`src/devices`), `computer-verb.ts` (`src/computer`), `database-verb.ts` (`src/database`).
- No verb reads, writes in or operates a node bound to another machine: `read`, `node edit`, `node color`, `device`, `browser`, `link new` and `notify` refuse with `node-on-other-machine` (`remote-node.ts`).
- `--machine` on `agent` and `team` gives a task to an agent on a linked machine this one can work in (else `machine-not-linked`). It needs `--task` and refuses `--cwd`, `--reads`, `--model`, `--effort` and `--base`. The node goes on a private canvas only, bound through `ProjectMutation.bindMachines`, with no line. Ceiling and depth ride on `start-remote-agent`, and that machine takes the narrowest of them and its link's bounds (`remote-agent.ts`). `task new` to such a node refuses with `task-on-other-machine`.
- `--project <id>` is taken out of argv by the route (`canvas-route.ts`, `reach.ts`), never by a verb. Only `view list`, `node list`, `link list`, `read`, `notify`, `agent`, `team` and `task new` take it; the rest refuse `cross-project-refused`. Every call checks again that the machine's `reachOpenProjects` is on and that the project is open in a client and is not the caller's own. The action then works in that project's place, while `ServerActionContext.origin` keeps the caller's own, which is what judges the caller (a chat, its mode, its depth).
- An agent started with `--project` stands on a canvas of that project named with `--view`, never hidden and never on another machine, with no line to its opener. Its task lives in that project, and its parent elsewhere is no orphan there (`outbox/wiring.ts`, `outbox/end-children.ts`). Closing that project in its last window fails the task first (`tasks/closed-project.ts`).

## Product rules

Decisions the code cannot show. Do not reverse one without asking Bas.

- A node on a canvas reads, writes in and operates another node only over a line or a `#` reference, and keeps to them exactly. The one exception is `notify`: by Bas's choice it reaches every terminal and chat of the caller's project, with no line, so an agent can always answer the one that wrote to it. The wake rule for messages (`src/outbox`) keeps that from looping.
- A chat reads and writes in every view or node of its project a person referenced with `#` in one of its messages, as along a line (`apps/server/src/context/references.ts`). The reference is checked again at every call, so one that went or left the project is closed again.
- A referenced terminal stays read-only: no agent types into it. A referenced chat never gets `task new`. A `#` to a whole canvas reads everything on it and adds nodes, but writes only in a node with a `#` or a line of its own. Every other node still needs a line.
- An AI chat that is a view of its own arranges a canvas the way a person does (`chat-view.ts`). No line can run to a view, so with `--view <canvas>` it adds, edits, renames, arranges and groups that canvas's nodes, draws lines between them, and reads and operates every node there without a line (`read`, `node edit`, `browser`, `device`). A node it adds gets no line to it. Without `--view` those refuse with `view-required`.
- The rest holds for a chat view too. It never types into or closes another session, and the mode ceiling, `--cwd`, launch approvals and the database and computer use grants keep their own checks.
