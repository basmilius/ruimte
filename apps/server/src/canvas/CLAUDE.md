# Agent verbs

`ruimte-context help` is the reference for every verb. What a chat may reach through `#` and through `--view`, and what each feature's verb may do, are product rules in the root `CLAUDE.md`.

- `verbs.ts` is the one registry: the parser dispatches from it and `help` renders from it, so defining a verb documents it. No aliases for old spellings. A refusal is a 422 whose first line is `refused\t<code>\t<message>`, followed only by what that same call would accept.
- The action handlers (`src/actions`, catalog actions from `@ruimte/actions`) enforce what a verb checks, so a person, Voice and an agent meet the same checks. Selectors are ids, never titles. Every write goes through `ProjectStore.mutate`.
- Depth and the per-caller count live in the lineage under `$RUIMTE_HOME/lineage` (`depth.ts`), never on the node. A person's node is depth 0; `agent` opens up to depth 2 and `team` up to depth 1. One caller holds at most `MAX_OPENED_PER_CALLER` agent nodes at a time; other nodes do not count.
- `fork` takes only a chat the caller opened. The fork is the caller's child under the same depth, count and mode ceiling as an `agent` child (`src/actions/fork-actions.ts`).
- `task new` gives work only to an agent the caller opened, read from the lineage, not from a canvas line. Two agents that read each other have lines both ways and would set each other to work endlessly; lineage is a tree.
- The mode ceiling (`mode.ts`) is read when the verb runs, carried on the `start-agent` entry and the lineage record, and applied again by `SessionManager.create` and `ChatManager.create` at every start. A child on another machine (`--machine`, `remote-agent.ts`) is bounded there too: ceiling and depth ride on the `start-remote-agent` entry, and that machine takes the narrowest of them and its own link's ceiling, depth bound and folder. A terminal agent no agent opened keeps the mode a person's save gave it (`src/sessions/mode-approvals.ts`), or `supervised` with no client to say otherwise.
- Every start of a node an agent made checks its folder again (`startCwdGuard` in `project-paths.ts`), since a path the verb checked may be a symlink pointing elsewhere by then.
- A first prompt never reaches `project.json`. It waits in `$RUIMTE_HOME/prompts/<nodeId>.json` and is delivered once when the session or chat is made (`src/agents/pending-prompts.ts`). It is capped because a terminal agent's prompt rides on the launch line, which the tty cuts off silently.
- A view's maker is `createdBy` in the shared file; a node's maker is in the lineage. Delete verbs remove only what the caller made, unless the machine's `agentsDeleteAnyView` allows more, and never the caller's own node or view. A terminal or chat node ends before the write, so no shell outlives its node.
- A verb never approves a command, launch, routine or mode. It sets a command only in a routine or launch, which then waits for a person to approve it as it stands. `--dry-run` runs every check under the write's lock and writes nothing; a verb that cannot preview refuses the flag by name.
- A node on a canvas reads, writes in and operates another node only over a line or a `#` reference (`src/context/references.ts`). A chat view uses `--view` instead (`chat-view.ts`).
- A verb into a feature follows that feature's product rules, beside its code: `launch-verb.ts` (`src/launches`), `routine-verb.ts` (`src/routines`), `browser-verb.ts` (`src/browser`), `device-verb.ts` (`src/devices`), `computer-verb.ts` (`src/computer`) and `database-verb.ts` (`src/database`).
- No verb reads, writes in or operates a node bound to another machine (`ProjectStore.machineOfNode`). `read`, `node edit`, `node color`, `device`, `browser`, `link new` and `notify` refuse it with `node-on-other-machine` (`remote-node.ts`), since a line here never reaches it.
- `--machine` on `agent` and `team` gives a task to an agent on a machine the project is linked to and this machine can work in (else `machine-not-linked`). It needs `--task` and refuses `--cwd`, `--reads`, `--model`, `--effort` and `--base`. The node goes on a private canvas only, bound to the machine through `ProjectMutation.bindMachines` (the daemon's own path), with no line drawn to it. The start is owed in a `start-remote-agent` entry that waits for the link and never fails for its absence. The result comes back through `take-remote-result`; ending the node owes a `stop-remote-agent` (`remote/remote-tasks.ts`). `task new` to such a node refuses with `task-on-other-machine`, since it takes only the one task it was given.
