# Voice run by the daemon

The invariants of this folder. The repository root's `CLAUDE.md` has the map and the rules that hold everywhere; `apps/server/README.md` ("Voice for a phone") says what the route does.

- The matrix is the limit. Voice runs only what `DAEMON_VOICE_ACTIONS` (`packages/voice/src/matrix.ts`) names, with the fields `VOICE_FIELD_RULES` (`action-policy.ts`) allows, checked by `tool-executor.ts` before the registry sees a call and again before a confirmation is answered. A daemon handler for Voice refuses any other actor (`voiceOf` in `src/actions/voice-actions.ts`), and `action-policy.test.ts` fails when an action becomes reachable for Voice without a choice for or against it.
- Who Voice acts for is the daemon's: the session, owner (connection and scene) and time zone are set at `voice.start` (`VoiceCaller`), never by the model or the phone. The actor id is `voice:<sessionId>`. A request after the start is honored only from the connection and scene that started the session, and `voice.status` and `voice.activity` go only there. Owning a session is not owning the machine: the key stays the local secret's.
- A session works in one current project at a time and holds only that one. The phone may name where it starts; without that it starts in the project opened last, or in none. Only `project.switch` moves it, and only to a project in use on this machine (`openProjects`): the session lets go of the old project before it holds the new one, and tells the phone in `voice.status` and the model in a new context. Another machine is never where Voice acts. Every handler reads the current project when it runs, and one that needs a project refuses with `no-project` while there is none. A switch writes nothing.
- Audio is never kept or logged: the sideband drops every echoed audio event before anything sees it (`isAudioEvent`), and no line of the timeline holds what a chat said, raw tool arguments, a transcript or a key. An unexpected error reaches the model as `tool-error`, never with its message.
- A chat Voice started is no orphan. Its lineage names the session as its opener, which no project places, so `outbox/end-children.ts` passes it over when the project is indexed again, and ending the session ends nothing it started. Its ceiling is `supervised` whatever the host reports, it is depth 1, and the start claim is `voice:<sessionId>:<call_id>`, set by the executor over whatever the model gave.
- A start from Voice is an AI Chat, never a terminal, and refuses a CLI without a chat. Voice is no node and gives no `cwd`, so the folder of its session is checked against the untrusted folders (`refuseUntrustedStart`); a CLI that cannot be kept from a folder another machine made is refused there.
- Following is by turn id, never by the next turn that happens to end: the ticket is taken before the prompt or the start, and bound to the turn the chat names (the first turn of a new chat). Idle is never done. The follower only notes, like the push service: it wakes no chat and answers no request.
- What a chat says is data. The prompts say so to both models, a report quotes it as such, and no confirmation follows from it: the executor answers only a token the registry gave this session, rechecks first that the current project and its revision are still those it was asked in, and the registry forgets every token of a session that ended (`ActionRegistry.forget`).
- Voice writes only by prompting a chat (`chat.send`), starting one (`agent.start`) or clearing one (`chat.clear`), the way desktop Voice does; a start keeps the per-field bounds above whatever the model asks. A clear asks the person first, every time, as desktop Voice does by default: the line of the call carries the question and its token to the owner's scene in `voice.activity`, so the phone answers it with `voice.confirm` as the model does with its control tool, and the handler runs its checks again on the answer. A clear lets go of what the follower followed in that chat.
- The key is a person's and the daemon only passes it on. It comes from the desktop app's settings (the shell hands it over on `POST /machine/voice-key`), `ruimte voice key set` or `voice.setKey`, all of them the local secret's, is read from `key-store.ts` at every start, and rides only in the `Authorization` header to OpenAI: never in a URL, a log line, an error, an event or anything the phone gets.
- How Voice talks (language and voice) is the machine's, in `preferences-store.ts`, and no secret: any client but another machine reads and sets it, and every client hears the change. A session takes the stored choice first and what its start names only while none is stored, so two devices that start Voice on one machine speak alike.
- Every timer runs on the injected `VoiceClock`, ends with the session and wakes no chat: the start deadline, the minute clock, the context debounce and a new chat's first-turn deadline.
