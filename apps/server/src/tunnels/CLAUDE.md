# Tunnels

Tunnels put two things in reach from outside, through a tunnel on the person's own Cloudflare account: Ruimte's MCP and dev servers. Ruimte manages the tunnel with an API token and runs `cloudflared` for it. The same folder holds the listener an external MCP client talks to, its credentials and the OAuth consent. The guide page is "Tunnels" in `apps/site`, and a scene of the section is drawn beside it.

- `tunnel-service.ts` is the screen's state machine (install, token, tunnel, hostnames, child process). It runs only behind owner requests (`handlers/tunnels.ts`); `tunnel.state` is the one request a client let in may read. State is `$RUIMTE_HOME/tunnels/tunnels.json` (the tunnel and its rows, with the zone and DNS record of each), the token is `cloudflare-token` beside it, a downloaded build lives in `bin/`, and none of it is in a project file. A `tunnels.json` of the `cloudflared login` version reads as empty, keeping only whether the external MCP was on.
- `cloudflare-api.ts` is the only code that calls Cloudflare (`api.cloudflare.com/client/v4`, no redirect, no other host), through a fetch the wiring hands in; a test hands in `FakeCloudflare`. Every failure is a sentence that says what Ruimte was doing and why Cloudflare refused, built from the status and Cloudflare's own message with the token cut out.
- One dashboard-managed tunnel per machine (`config_src: cloudflare`). Ruimte makes one named `ruimte-<machine>-<4 hex of the machine id>`, so two machines with one name get a tunnel each, or a person picks one already on the account (`tunnel.list`, `tunnel.link`); only a dashboard-managed one qualifies. `tunnels.json` keeps whether Ruimte made it (`created`). Its ingress lives in Cloudflare, so the dashboard shows what Ruimte shows, and a change reaches the running `cloudflared` without a restart. Ruimte owns only the rule without a path for each hostname of a row; every other rule, a catch-all and the settings beside the ingress (`warp-routing`, `originRequest`) stay as they were and in their order, and a sync that changes none of Ruimte's rules writes nothing (a tunnel Ruimte did not make gets no catch-all of Ruimte's either). Cloudflare takes the first rule that matches, so a rule of Ruimte's goes before the first other rule that could catch its hostname: a wildcard, a rule for `*` or a rule without a hostname. A person's rule with a path on the hostname itself keeps serving its path while the row is on (`^/api` stays where it is); the 404 of a row that is off or leaving goes before such a rule when its path matches `/`. A hostname of a row that serves nothing (off, or refused on add) gets a rule `http_status:404` of its own in that place, also where what would catch it answers 404 already, since its proxied record stays and another writer may make that catch-all serve; Remove and unlink take it off after the record. A row refuses a hostname that already has a rule without a path. The state lists the other rules read-only (`others`). A change to a row is saved only once Cloudflare took it.
- Intent and observation are kept apart. A stored row's `enabled` is what the person asked, and only their actions change it: add, update, Remove, unlink, and the row's come-back setting at boot. Off and leaving are saved before Cloudflare took them, so no later write serves the row again; on, a new port and new origin settings are saved only once Cloudflare took them, so Try again never publishes a change that failed. What Cloudflare may serve is an observation in memory (`serving`, with `unsure` while a write may have landed unread), never saved: after a write that failed, whose answer got lost or that another writer undid twice, `settle` reads the configuration back and notes each row Cloudflare serves, with its port and origin; every other read of the configuration (before a write, or an add's check) notes the same (`observe`). The screen shows a row on while it is meant on or may be served (showing on while it is off is the safe side), and the child runs for the same rows: every job ends by stopping it when none is left, also a job that failed halfway. A write that held clears the observation. At boot every row may be served until Ruimte read Cloudflare. When the read fails too, a row the write would have turned on may be served as well, the screen says why, and the next change, Try again or the network coming back reads Cloudflare before anything else.
- Every write enforces intent: an off or leaving row gets its own 404, never a serving rule. Whether Cloudflare serves a hostname is decided the way Cloudflare does (`servedFor`): the first rule in order that takes the root path of the hostname (its exact hostname, a wildcard like `*.example.com` over it, `*` or no hostname, with a path that matches `/`), and only a status serves nothing; a rule for `*` without a path is a catch-all like one without a hostname. Every write is read back, and written once more when another writer changed a rule of Ruimte's in between or put a rule before a 404 of Ruimte's that serves the name (a wildcard, say), with the 404 placed before it again. A round that finds nothing to write still checks the held rows, so one Cloudflare serves while meant off stays shown on.
- Remove and unlink save `leaving: true` on their rows before they delete anything, and unlink saves it on the tunnel too. Leaving takes the 404 first, then the record, then the rule, and drops a row once Cloudflare holds neither. A bring-up (Try again, boot, the network back) finishes what a Remove left halfway and never records or serves a leaving row; on a leaving tunnel it finishes the unlink instead of bringing the tunnel up. Turning a leaving row on keeps it after all; a leaving tunnel refuses changes until the unlink is finished.
- `tunnel.unlink` takes Ruimte's rules off, deletes the records it made, stops its child and forgets the tunnel, only once the read back shows none of Ruimte's rules left; otherwise it keeps the tunnel and the rows that still have a rule, says so, and Try again finishes it. It never deletes a tunnel at Cloudflare, also one Ruimte made; nothing in `cloudflare-api.ts` can.
- Before it starts a child, Ruimte asks Cloudflare whether the tunnel has connections. If something else runs it (the person's own service, here or on another computer), Ruimte starts nothing and the state says `runner: 'other'`. It looks again on bring-up (boot, a new token, the network back), on Try again and when a row turns on; there is no timer for it. A hostname points at loopback of whatever computer runs the tunnel.
- A row picks a zone from the list and takes a label or a full hostname inside that zone. Adding writes a proxied CNAME to `<tunnel-id>.cfargotunnel.com` with the comment "Managed by Ruimte · <mark>", the mark being the 4 hex of the machine id that end its tunnel's name, only after Cloudflare took the 404 that holds the name, and then the rule that serves it. The row is saved off before the 404 goes out and dropped again only when Cloudflare turns the 404 down, so Remove cleans up after a failure at any step, also one whose answer got lost. A row whose record failed keeps only its 404. Turning a row on first writes its 404 (an add whose write failed never landed it), and then, also when it comes back on, looks up this machine's record by name, whatever the row says its record is, makes it when it is missing, and leaves the row off while that fails. A row that comes back on goes off (as an intent, through `intend`) only when the record is refused, by Ruimte or by Cloudflare with a 4xx other than 401 and 429 (a refused token is no refusal of the row); on any other failure it stays meant on, and the network coming back or Try again tries the record again. A record Ruimte made is a CNAME to this tunnel with this machine's comment; any other record under the name refuses the row, one of Ruimte on another machine with a sentence of its own, so two machines on one tunnel never take over each other's records. Removing deletes the rule, then every record under the name that is still such a record, whatever id the row kept, since a create whose answer got lost may have made one it never heard of; a deleted record is saved as gone at once, so a row turned on after a Remove or unlink that failed later makes its record again. Ruimte touches no other tunnel and no other record.
- On a tunnel Ruimte did not make, `isOurs` holds the same way: a record is Ruimte's only with its comment, and a rule only for a hostname of a row, so the person's own hostnames and records on that tunnel are never Ruimte's.
- `tunnel-service.property.test.ts` runs seeded sequences of a person's steps, restarts, token changes and other writers, with faults drawn per Cloudflare call, and checks the invariants above after every step. Ruimte is judged by the configuration it last read (the known limit below), and only a hostname with a record of Ruimte's counts as served. A failure names its seed, `RUIMTE_SEED=<seed>` runs it alone, and a defect it finds gets a focused test with that seed.
- `cloudflared` is a seam (`cloudflared-runner.ts`): a test hands in `FakeCloudflared`, and only an integration test may run the real binary. The installer finds it on the path, else downloads the official build only after its sha256 matched the one pinned in `cloudflared-pins.ts`, which a bump recomputes from the downloaded asset. It always runs as `tunnel --no-autoupdate run`.
- At most one `cloudflared` per machine, a child of the daemon, running while a hostname is on and nothing else runs the tunnel. A child that will not stop gets a warning and no signal of ours.
- A dev row and a port grant (`apps/server/src/ports`) are separate choices: a hostname makes no grant, a grant makes no hostname, and removing one leaves the other. The splash of a browser node offers the public address of a port that has a running row.
- A dev row may carry origin settings (`origin`): https instead of http, a `Host` header, and with https Skip TLS check and a server name. They go into the `originRequest` of that row's rule alone, never into the tunnel-wide `originRequest` or a rule of someone else's; `tunnel.update` replaces them whole. The MCP row takes none.
- A dev row points at one literal loopback port. The deny list holds Ruimte's own ports (the API, the door on the local network and the external listener); the ingress builder refuses them again, and only the MCP row may name the listener.
- After a restart each row has its own setting. The MCP row defaults to come back on, a dev row to stay off. The deny list is checked again when a row comes back. A row that stays off is saved off at boot and shows on while a failed bring-up leaves it served.

## Known limits

- Cloudflare's configuration has no version to write against, so a write of Ruimte's is a read, a change and a PUT. A writer on a shared tunnel (another machine, the dashboard) can put back a rule Ruimte just changed. Ruimte reads every write back and writes once more; when the other writer undoes that one too, the rows show what Cloudflare serves, and a write that lands after the read back stays unseen until Ruimte next reads the configuration.
- Cloudflare may still list connections for a short while after Ruimte's own `cloudflared` stopped or crashed, and names no connector Ruimte could recognize as its own. Until the next bring-up or Try again, such a tunnel reads as running elsewhere and Ruimte starts nothing.

## Product rules

Decisions the code cannot show. Do not reverse one without asking Bas.

- Ruimte talks to Cloudflare only through an API token a person typed into Ruimte (Zone read, DNS edit, Cloudflare Tunnel edit). It is set only with the local secret, kept 0600 under `$RUIMTE_HOME/tunnels`, sent only to `api.cloudflare.com`, and never in a log, an error, an event or the wire. Ruimte reads no other Cloudflare credential: no `cert.pem`, no credentials file of `cloudflared login`. The tunnel token it fetches with the API is held in memory and handed to `cloudflared` in its environment (`TUNNEL_TOKEN`), never on its command line. `tunnel-service.test.ts` holds this against the source.
- Nothing reaches a tunnel through the broker, and Ruimte relays none of its bytes. `cloudflared` dials from the machine to the dev port or to the listener.
- The listener (`external-listener.ts`) is on `127.0.0.1` with a port of its own (`--external-port`, the API port plus 20), off by default, and only the local secret turns it on. It answers `/mcp` and the fixed OAuth paths (`oauth.ts`), which serve no data. Every other path is a 404. It refuses any `Origin` with 403, takes neither a session token nor the local secret as a credential, and the API port refuses `Cf-Ray` and `Cf-Connecting-Ip` (`refuseTunnelled`). Those headers and `Host` prove nothing and only ever refuse.
- A credential is on every request. The source address, `Host`, `Cf-*`, `local.key` and an account token are no proof. A bearer works on loopback, and on the public hostname only if its credential allows that (off by default). Failures are rate limited, and the answer is a bare 401.
- `credential-store.ts` keeps hashes only, 0600 under a 0700 folder. A secret exists in the clear once, in the answer that makes it, and never in a log, an error, an event or the wire again. A revoke deletes the record, so it counts from the next request. A reused refresh token revokes its credential.
- A hosted client defaults to all projects, tier Work, `supervised` and no expiry until a person revokes it. Narrower is an explicit choice, and only a person in the app makes it. A credential cannot change its own tier, scope, ceiling or box.
- Consent happens in Ruimte (`consent-book.ts`, the consent window of the client), never on the public page. The page and the window lead with the host of the client's address, show the name its document gives only after that and as unverified, and show a code; the page waits. Pending requests are capped in all, per source address and per client address, and the window shows one at a time; the client metadata document is fetched from a public https address only (`client-metadata.ts`), and a redirect must be listed in it exactly. There is no `/register`.
- The approvals box (`approvals.ts`) is off by default and adds `approval_list` and `approval_answer`. With it on, the client answers a chat's runtime approvals and approves a command, launch, routine or mode as the person, a mode never wider than its ceiling. It never types into a terminal. The box lets the client run shell commands, and the app and the guide say so in those words. An id from `approval_list` carries a digest of the command (a held command), of the command, folder and environment (a launch), or of the routine, and is checked again where the approval is given, so a yes approves what was listed and nothing that changed since.
