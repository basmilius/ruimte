# Agent tools

Every tool an agent calls is an MCP tool (`src/mcp`). This folder is only the adapter: the rules (nodes, placement, paths, depth, tasks, worktrees) and the fields of `CanvasHost` every tool stands on are in `src/canvas`, and `src/actions` runs them, so nothing here is imported by `actions` or `canvas`. A toolkit file (`node-tools.ts`, ...) defines its tools with a zod `input` in the field names agents see, a description and its annotations (`tool.ts`, `@adecore/agents/context`); the agent feature of the toolkit (`src/agent-features`) lists it, and `mcp/catalog.ts` serves them with `guide`. The MCP schema is read off that input (`toolInputSchema`), and `runTool` checks the JSON input, answers `project` and `revision`, and runs the tool. A format a field takes as text is a guide topic kept beside its tools (`Toolkit.guides`).

- A new tool of an existing feature is its tool in the toolkit file, its handler in the feature's action file (and its schema in `packages/actions/src/catalog/<domain>.ts`); a method it needs from the daemon goes on the feature's port type, in the feature's folder (`launches/agent-host.ts`, `routines/agent-host.ts`, ...), and in the builder of its descriptor. A new feature is a file in `src/agent-features` that calls `defineAgentFeature` (name, toolkit, actions, previews, and `host` building the fields it fills) and a line in `agent-features/list.ts`. A feature declares the fields it adds to `CanvasHost` in its descriptor with `declare module '../canvas/host.ts'`, and a type that only that descriptor names stays in it. Code in `canvas` reads only the fields `canvas/host.ts` itself declares, since a program that loads `canvas` without the descriptors (the client's tests import the session manager) does not see the others. An action that previews (honors `dryRun`) lists itself in the `previews` of its action file, never in a registry. A test makes its host from the fakes of `canvas-fixture-test-helpers.ts` (`canvasFixture()` in `beforeEach`, `dispose()` in `afterEach`); a new part of the host is one entry in its `PARTS`.
- `mcp/tool-list.test.ts` holds every tool's name, fields, types, required flags, annotations and callers to a fixture, and `mcp/context-budget.test.ts` holds the bytes of the tool list and the instructions. Regenerate the fixture (`RUIMTE_WRITE_TOOL_FIXTURE=1`) only for a change Bas asked for, and never let the budget grow without asking him.
- No aliases for old spellings. A refusal is a `ToolRefusal` with a code, a message that names the field, and only what that call would accept, which the MCP route returns as an error result. Texts arrive as sent, and nothing rewrites a refusal on its way out.
- A toolkit counts its calls under its name (`countToolCall`), which is the usage counter and the name the client draws a call by (`CONTEXT_VERBS` in `@ruimte/contracts`); a tool that counts elsewhere says so with `counter`.
- The action handlers (`src/actions`, catalog from `@ruimte/actions`) enforce the checks, so a person, Voice and an agent meet the same ones. Selectors are ids, never titles. Every write goes through `ProjectStore.mutate`.
- Depth and the per-caller count live in the lineage under `$RUIMTE_HOME/lineage` (`canvas/depth.ts`), never on the node. A person's node is depth 0; `agent_start` opens up to depth 2, `agent_team` up to depth 1. A caller holds at most `MAX_OPENED_PER_CALLER` agent nodes at a time.
- `agent_fork` takes only a chat the caller opened, as its child under the same bounds as an `agent_start` child (`src/actions/fork-actions.ts`). `task_new` gives work only to an agent the caller opened, by lineage, never by a canvas line.
- The mode ceiling (`canvas/mode.ts`) is read when the tool runs, carried on the `start-agent` entry and the lineage, and applied again at every start (`SessionManager.create`, and `ChatCore.create` through its `runtimeModeFor` hook). A terminal agent no agent opened keeps the mode a person's save gave it (`src/sessions/mode-approvals.ts`), else `supervised`.
- Every start of a node an agent made checks its folder again (`startCwdGuard` in `canvas/project-paths.ts`), since a path may since have become a symlink.
- A first prompt never reaches `project.json`. It waits in `$RUIMTE_HOME/prompts/<nodeId>.json`, is delivered once (`src/canvas/pending-prompts.ts`), and is capped, since the tty silently cuts a terminal agent's launch line.
- Delete tools remove only what the caller made (a view's `createdBy`, a node's lineage), unless the machine's `agentsDeleteAnyView` allows more, and never the caller's own node or view. A terminal or chat node ends before the write.
- No tool approves a command, launch, routine or mode; a command it sets in a routine or launch waits for a person. `dry_run` runs every check under the write's lock and writes nothing; a tool that cannot preview has no `dry_run` field.
- A tool into a feature follows that feature's rules beside its code: `launch-tools.ts` (`src/launches`), `routine-tools.ts` (`src/routines`), `browser-tools.ts` (`src/browser`), `device-tools.ts` (`src/devices`), `computer-tools.ts` (`src/computer`), `database-tools.ts` (`src/database`).
- No tool reads, writes in or operates a node bound to another machine: `context_read`, `node_edit`, `node_update`, the `device_*` and `browser_*` tools, `link_new` and `notify` refuse with `node-on-other-machine` (`canvas/remote-node.ts`).
- `machine` on `agent_start` and `agent_team` gives a task to an agent on a linked machine this one can work in (else `machine-not-linked`). It needs `task` and refuses `cwd`, `reads`, `model`, `effort` and `base`. The node goes on a private canvas only, bound through `ProjectMutation.bindMachines`, with no line. Ceiling and depth ride on `start-remote-agent`, and that machine takes the narrowest of them and its link's bounds (`canvas/remote-agent.ts`). `task_new` to such a node refuses with `task-on-other-machine`.
- `project` is answered by `runTool` (`tool.ts`, `canvas/reach.ts`), never by the tool itself. Only `view_list`, `node_list`, `link_list`, `context_read`, `notify`, `agent_start`, `agent_team` and `task_new` take it; any other tool refuses it as a field it does not have. Every call checks again that the machine's `reachOpenProjects` is on and that the project is outside Recent (`closedAt == null`), is not Chats and is not the caller's own. Switching away or losing a socket keeps the project reachable. The action then works in that project's place, while `ServerActionContext.origin` keeps the caller's own, which is what judges the caller (a chat, its mode, its depth).
- An agent started with `project` stands on a canvas of that project named with `view`, never hidden and never on another machine, with no line to its opener. Its task lives in that project, and its parent elsewhere is no orphan there (`wiring/outbox.ts`, `outbox/end-children.ts`). Closing that project in its last window fails the task first (`tasks/closed-project.ts`).

## Product rules

- An extension whose manifest names `browser.control` or `devices.control` drives a page or device without a line (`ServerActionContext.extension`, set with the `extension` actor by `extensionActionCall`). Only `ExtensionHost.runAction` reaches it, within `EXTENSION_ACTIONS`.

Decisions the code cannot show. Do not reverse one without asking Bas.

- A node on a canvas reads, writes in and operates another node only over a line or a `#` reference, and keeps to them exactly. Two exceptions, by Bas's choice. `notify` reaches every terminal and chat of the caller's project, with no line, so an agent can always answer the one that wrote to it; the wake rule for messages (`src/outbox`) keeps that from looping. And a device needs no line: an agent names it by its device id or a device node and holds it alone while it works (`src/devices/CLAUDE.md`).
- A chat reads and writes in every view or node of its project a person referenced with `#` in one of its messages, as along a line (`apps/server/src/projects/references.ts`). The reference is checked again at every call, so one that went or left the project is closed again.
- A referenced terminal stays read-only: no agent types into it. A referenced chat never gets `task_new`. A `#` to a whole canvas reads everything on it and adds nodes, but writes only in a node with a `#` or a line of its own. Every other node still needs a line.
- An AI chat that is a view of its own arranges a canvas the way a person does (`canvas/chat-view.ts`). No line can run to a view, so with `view` naming a canvas it adds, edits, renames, arranges and groups that canvas's nodes, draws lines between them, and reads and operates every node there without a line (`context_read`, `node_edit`, the `browser_*` tools). A node it adds gets no line to it. Without `view` those refuse with `view-required`.
- The rest holds for a chat view too. It never types into or closes another session, and the mode ceiling, `cwd`, launch approvals and the database and computer use grants keep their own checks.
