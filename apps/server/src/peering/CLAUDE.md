# Peering (this machine as the one that is worked in)

"A" is the machine whose person works on another machine; "B" is this one.

## Links and admission

- B decides what A may do here. Nothing is granted without a link a person made on B (`links.ts`, `$RUIMTE_HOME/peers/<machineIdA>.json`). A link names one project of B per machine A and a mode ceiling, `supervised` until a person chooses another. Only a client acting as a person changes it (`peer.bind`, `peer.setCeiling`, `peer.unbind`); an agent has no socket.
- A machine gets in as a peer on a statement the address book signed for it (`checkPeerStatement`, ten minutes, its own signing prefix). Its record in `auth.json` has `origin: 'peer'`, never `statement`, so an older daemon drops it instead of keeping a machine as a client. A peer gets no ticket (`Handshake.redeemChannel`, and `ticketAccess` refuses a peer's session) and subscribes to no event (`connectionOpener`).
- A peer is vouched for for 30 days after its last statement (`PEER_ATTESTATION_TTL_MS`, `attestedAt` on its record). Past that it is not paired, but the record stays under the same session, so a new statement brings it back with its links. `peer.list` says until when (`attestedUntil`). The window of the machine that works here renews it silently while a person uses the link (`apps/client/src/project/peer-renewal.ts`). A peer statement in the offer of a key still let in renews it (`SignalGate`), so the other machine sends one over its own open link (`RemoteConnections.connectWithStatement`). The machine that works here forgets its peer key, known machines and statements when it leaves its account.
- Unlinking ends that machine's nodes here (`end-children` on the hidden canvas's nodes) and removes the canvas and the link. Revoking a machine's session closes its channels and puts its peer key on the revoked keys, which no later statement undoes.

## What a peer may ask

- A peer is never an owner. What only the local secret may do stays with it. No `fs.*`, `bytes.read`, `session.*`, `chat.*`, `launch.*`, `project.*`, `device.*`, `browser.*`, `database.*`, `computer.*` or `auth.ticket` request is on a peer's list, and a peer never gets an HTTP ticket.
- The list: `endpoint.info`, `server.ping`, `peer.taskStart`, `peer.taskStop`, `peer.result`, `peer.bundlePut`, `peer.bundleRead`, `peer.close` (`handlers/peer-tasks.ts`, `peer-tasks.ts`) and `peer.artifactList`, `peer.artifactGet`, `peer.artifactRead` (`handlers/peer-artifacts.ts`).
- The dispatcher (`apps/server/src/dispatcher.ts`) refuses a peer every request outside `{ peer: true }` as `forbidden`, before parsing the payload, and `register` throws on `owner` together with `peer`. Add a request to the list only after asking what a lying machine could do with it. `endpoint.info` names only the peer requests; `server.ping` is listed so the channel can be pinged.
- Every `peer.*` request a peer may ask starts with `requirePeerLinks`; without a link a person made here the answer is `peer-not-linked`.
- The three artifact requests read the Output of the one project a link names (`linkOf` with the request's project, else `peer-not-linked`; another project's artifact is `not-found`). They are read-only, in pieces of at most `PEER_ARTIFACT_PIECE_BYTES` (256 KiB), with no event and no ticket. `artifact.importFrom` on the other machine asks them when a person there copies a version. A link already lets that machine's agents read the project folder here, Output is less, and nothing here writes on a peer's word. The other way round, a lying machine offers only bytes: the copy checks every file against the size and sha256 in its manifest before the store commits it (`artifacts/artifact-import.ts`).
- Whatever another machine answers is read with the request's schema (`remote/peer-reply.ts`), and the result text kept and woken with is cut to `MAX_RESULT_LENGTH`, so a lying machine gets no more than a refusal or a clipped line.

## Tasks a peer gives

- The folder, mode and depth are B's own. The project is the one the link names. `--cwd` stays inside that folder or its worktrees (`startCwdGuard` at every start). The mode is the narrowest of what A asks, A's ceiling and the link's ceiling. The depth is `max(1, depth A gives)`, refused above B's maximum. B takes what A states only when it is narrower than its own bounds.
- Everything a peer starts runs as `actor: 'agent'` with B's own `start-agent` entry and lineage record (`openedBy` = `peer:<A>:<parentNodeId>`). A launch in such a chat stays held until a person approves it through B. Worktrees go under B's worktree folder. A peer drives no device: a device action refuses a caller on a hidden canvas or of peer lineage (`peer-no-device`), and `peer.placeNodes` drops any line it is sent to a device or a task node.
- A's nodes that live on B sit on one hidden, private canvas per machine A, `peer-<machineIdA>` (`peerCanvasId`), with A's node ids, so session and chat ids match on both sides. Hiddenness follows from a link and is laid over the document (`withHiddenCanvases`), like a node's machine. It is written to neither project file, and a hidden canvas cannot be shared. That machine's window mirrors its nodes onto the canvas with `peer.placeNodes` and manages only the ids it placed (recorded in the machine's file under `peers`). It never rewrites or ends a task node (peer lineage) or one a person placed, and `peer.taskStart` takes over only a node that window placed or a new one. Where a task runs here is recorded beside it, and the result is read from that record, never the project file.
- A peer task is a task of this machine's `TaskStore` whose parent is the hidden canvas (`peerCanvasId`), since the real parent is a chat on the other machine. The outbox keeps it through `parents` while the canvas stands, `wake-parent` skips it, and the lineage record carries `peer`, so the end-children cascade does not take its opener for a deleted one. Its result is owed in a `deliver-remote-result` entry (target `peer:<machineId>`, outliving any node) until the machine acknowledges with `peer.result { ack: true }`. The machine is told over its own link (`peer.taskSettled`) and asks again when it reconnects, so nothing here runs on a clock.
- Limits per machine: at most `PEER_MAX_OPEN_TASKS` (4) open tasks, and the fifth is `peer-busy`, which makes the other machine wait rather than fail the task. At most `PEER_MAX_BUNDLES` (2) transfers and `PEER_MAX_BUNDLE_BYTES` (512 MiB) in its bundle store, finished ones included; results have their own limit (`PEER_MAX_RESULT_BUNDLES`; an acknowledging `peer.result` makes none). At most `PEER_MAX_WORKTREES` (8) worktrees from its tasks, which a person removes and nothing here does. A branch it names is at most `PEER_MAX_BRANCH_LENGTH` (100) characters (`branch-too-long`), and its folder is recorded as untrusted before git makes it. A start is judged in the machine's own queue, so the count is true when the next one comes.
- Only the daemon starts the chat of a peer task: `chat.create` for such a node refuses (`peer-task-starting`) while its `start-agent` entry is owed, since a window would start it in the project folder instead of the worktree.
- A task holds its project under the channel that started it, so the agent keeps the project loaded. The hold goes when that machine's last open task settles, when the channel closes and on `peer.close`, so a person here can still close the project.
- Every end of a peer task the machine did not ask for is told to it with `peer.taskSettled`: a result owed in `deliver-remote-result`, a task a person stopped or removed here, and the open tasks of an unbound link. A task the machine stopped itself (`peer.taskStop`) is not.

## Bundles and untrusted folders

- A bundle from A is data. It passes `git bundle verify`, and only its one `refs/ruimte/handoff/*` ref is fetched, into `refs/ruimte/received/<id>`, with hooks off in every following git call (the fetch, `update-ref`, `worktree add`). That ref is deleted once the worktree or the `refs/remotes/ruimte-<machine>/<branch>` ref exists. Nothing a bundle carries moves a branch a person has checked out.
- A peer's bundles sit in a store of their own per machine under `bundles/peers`, so no machine can fetch or read another's. A result bundle is offered only to the machine whose task it came from (`bundleRead`) and goes once read to its last byte.
- A folder that came from another machine, either way, is untrusted and recorded before git makes it: the worktree of a task it gave here, the worktree a result came back into there, and any worktree cut from a branch such work arrived on.
- A person's own handoff is the one vouched-for transfer. The checkout a person's client sends from the dialogs (`git.bundle` there, `git.fetchBundle` with `into: 'worktree'` here) and a worktree it starts here from origin are trusted, since that client may already write files and start terminals here. What the sending machine never vouched for stays untrusted (`untrusted` on its bundle, carried on `git.fetchBundle`, which can only narrow), and so does anything cut from a foreign tip here. Work brought back into a project's own machine keeps its `refs/remotes/ruimte-*` mark and is untrusted whoever asked, since that mark keeps every later branch cut from it untrusted. Origin is outside these records: what a person pushed there is trusted like any fetch.
- A peer task's CLI never loads the configuration of the folder A sent (settings, hooks, permission rules, MCP servers), so only the person's own settings on B apply (`projectConfigFor` in `chat/chat-manager.ts`). `peer.taskStart` refuses up front, before a task or worktree exists, a provider that cannot be kept from it (`ignoresProjectConfig` not `true`) and a terminal agent.
- `UntrustedFolders` (`untrusted.ts`) decides what is untrusted: a node that machine gave a task, or one an untrusted node opened (it walks the `openedBy` chain and forks; `peer` is never copied to the child), and any node whose cwd lies in a folder made from that machine's work (recorded under `$RUIMTE_HOME/peer-worktrees`, which outlives the link). Such a node loads no project configuration and never runs the after-settle task. `agent` and `team` from it, or with such a `--cwd`, refuse the providers and terminals `peer.taskStart` refuses (`untrusted-folder`).
- A one-shot CLI run (AI commit message, conflict help, a Codex chat title) in such a folder works in an empty daemon folder, `$RUIMTE_HOME/oneshot` (`OneShotPlace`, `one-shot-place.ts`), because a CLI loads the hooks of the folder it starts in. The prompt carries everything those runs read, and none lets the CLI read files itself.
