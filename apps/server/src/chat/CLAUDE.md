# Chats, forks and plans

The invariants of this folder. The repository root's `CLAUDE.md` has the map, the wire protocol and the rules that hold everywhere.

- A fork (`chat.fork`, `apps/server/src/chat/fork.ts`) copies the CLI's conversation at the click: a Claude transcript cut at the turn's `native.lastUuid` (format checked against Claude Code 2.1.273, refused otherwise) or Codex `thread/fork` with `native.turnId`. Its record is written before its node, its agent's note waits in the record's `preambles` (never on the wire), and its lineage entry has `relation: 'fork'`, so ending, capping or orphaning the original never touches it. A chat view forks into a chat view listed right after it (a node into a node, or a view after its canvas with `asView`), and a fork and its original with no canvas in common read each other through that lineage entry instead of an edge (`apps/server/src/context/fork-origin.ts`). A fork in a worktree puts its files to the tree its turn settled with (`checkpointAfter`) only in that new worktree, never in a shared folder; a fork into another CLI, or into an account whose folder does not hold the original's transcripts, copies no conversation and gets a handoff preamble instead (`chat/handoff.ts`), in a mode no wider than the original's. A fork stays on the original's account unless it names another; a fork into another CLI starts on that CLI's default account. A fork's summary is a turn of the fork with `summaryFor`; `SummaryCoordinator` only owes a `deliver-summary` outbox entry, whose handler draws the line back first and then writes the note (id `summary-<turnId>`, so it lands once) and a preamble in the original. A fork node deleted before anyone wrote in it takes its record and transcript copy along, never its worktree.
- A plan belongs to a chat, never to a project: `$RUIMTE_HOME/chats/<chatId>.plans.json` beside the record (`apps/server/src/plans/plan-store.ts`), gone with the chat or a clear of it and copied by a fork. It is written as operations on item ids at the latest rev, without a base rev: every operation names an id and is refused when that id is gone, and the daemon is its only writer. An agent never overwrites a status a person set, and nothing about a plan wakes an agent or schedules work.
- A bookmark belongs to a chat as well: `$RUIMTE_HOME/chats/<chatId>.bookmarks.json` (`chat/bookmark-store.ts`), hung on an item id of the chat's own thread (a message of the person or a reply of the agent, never a subagent's), gone with the chat or a clear of it. A fork copies the ones on the items it copied, so nothing past the cut. Every change sends the whole list as `chat.bookmarks` to the clients attached to that chat, and `chat.attach` carries it; a client that is not reading the thread has nothing to point one at.
- A question or an approval ends with its turn only when the CLI takes it back (`control_cancel_request`, or a Codex turn completing), when the process goes, or when a person stops the turn. One asked by work the CLI runs beside its turns (a background subagent, a workflow member; Claude Code 2.1.282 names the agent in `agent_id`) outlives the turn that was running: it stays pending, the chat reads `needs-you` between turns, and its answer goes back over the same `control_response`. A stop turns down what the CLI still holds (`declineRequest`), so that work goes on instead of waiting on an answer nobody can give.
- A chat whose last turn stopped on a limit goes on under another account of its CLI only when a person asks (`chat.continueOn`, `chat/continue-on.ts`), never on its own. An account that reads the chat's transcripts (Codex accounts over one home, shadow homes included) takes the chat over in place, the way `chat.configure` switches it, and a turn opens at once that carries what the limited turn answered; any other account gets a fork cut after the limited turn, with the conversation handed over, and that fork's first turn opens at once. Either way the original's owed `resume-limit` lapses, so the limited turn is taken up once. After a fork the original keeps a note under that turn (`continued-<turnId>`), and no switch turned on later owes that turn a resume there again.
