# Chats, forks and plans

- A fork (`chat.fork`, `fork.ts`) copies the CLI's conversation at the click: a Claude transcript cut at the turn's `native.lastUuid` (format checked against Claude Code 2.1.273, refused otherwise), or Codex `thread/fork` with `native.turnId`.
    - Its record is written before its node. Its agent's note waits in the record's `preambles`, never on the wire. Its lineage entry has `relation: 'fork'`, so ending, capping or orphaning the original never touches it.
    - A chat view forks into a chat view listed right after it; a node forks into a node, or into a view after its canvas with `asView`. A fork and its original with no shared canvas read each other through that lineage entry instead of an edge (`apps/server/src/context/fork-origin.ts`).
    - A fork in a worktree puts its files to the tree its turn settled with (`checkpointAfter`) only in its new worktree, never in a shared folder.
    - A fork into another CLI, or into an account whose folder lacks the original's transcripts, copies no conversation and gets a handoff preamble (`handoff.ts`), in a mode no wider than the original's. A fork stays on the original's account unless it names another; a fork into another CLI starts on that CLI's default account.
    - A fork's summary is a fork turn with `summaryFor`. `SummaryCoordinator` only owes a `deliver-summary` outbox entry. Its handler draws the line back first, then writes the note (id `summary-<turnId>`, so it lands once) and a preamble in the original.
    - A fork node deleted before anyone wrote in it takes its record and transcript copy along, never its worktree.
- An agent forks only a chat it opened (`ruimte-context fork`, `forkForAgent`), after its last finished turn, on the original's CLI, account and model. That fork is the agent's child, not a sibling: its lineage entry names the agent with no `relation`, one level deeper, with the agent's mode as ceiling. So it counts toward depth and the per-caller cap, ends with the agent, and takes work only through `task new`, whose result wakes the agent once. A hidden agent's fork is a hidden agent of the forking one.
- A plan belongs to a chat, never a project: `$RUIMTE_HOME/chats/<chatId>.plans.json` beside the record (`apps/server/src/plans/plan-store.ts`). It goes with the chat or a clear and is copied by a fork. The daemon is its only writer, as operations on item ids at the latest rev, without a base rev; an operation whose id is gone is refused. An agent never overwrites a status a person set, never removes or retitles a step only a person checks or one a person checked, and never deletes a plan holding such a check. Nothing about a plan wakes an agent or schedules work.
- A bookmark belongs to a chat: `$RUIMTE_HOME/chats/<chatId>.bookmarks.json` (`@adecore/agents/chat/bookmark-store.ts`), on an item id of the chat's own thread (a person's message or the agent's reply, never a subagent's). It goes with the chat or a clear. A fork copies those on the items it copied, nothing past the cut. Every change sends the whole list as `chat.bookmarks` to the attached clients, and `chat.attach` carries it.
- A visual belongs to a chat: its list is `$RUIMTE_HOME/chats/<chatId>.visuals.json`, each page `attachments/<chatId>/<visualId>.html` (`@adecore/agents/chat/visual-store.ts`). The attachment route and `bytes.read` serve it by id, never inline on the daemon's origin. Only an agent's `visual show` adds one, to its own chat; a person or agent can remove one. It goes with the chat or a clear. A fork copies those its copied turns showed, plus those shown between turns until the end of the cut turn, each with its own page. Every change goes as `chat.visuals` to attached clients, and `chat.attach` carries the list.
- An image or 3D model an agent attaches belongs to a chat. `ruimte-context chat attach` (`src/canvas/chat-verb.ts`) reads the file in the agent's own process; the daemon never opens a path. It accepts PNG, JPEG, GIF, WebP, HEIC and HEIF (10 MiB each) and binary glTF, USDZ and STL (50 MiB each), typed by their bytes (`attachment-type.ts`). They are stored as `attachments/<chatId>/agent-<uuid>~<name>.<ext>` (`agent-images.ts`, 64 per chat in total) and found by id with no index, so a clear, a deletion or an id-keeping move takes them along; a fork copies them under the same ids. Only an AI chat attaches, to its own thread.
- A question or approval ends with its turn only when the CLI takes it back (`control_cancel_request`, or a Codex turn completing for a blocking request), when the process goes, or when a person stops the turn. One asked by work beside the turns (a background subagent, a workflow member; Claude Code 2.1.282 names the agent in `agent_id`) outlives the running turn. It stays pending, the chat reads `needs-you` between turns, and the answer goes back over the same `control_response`. Optional Codex questions also outlive a successful turn; an answer joins the running turn or starts a new one in the same chat, and an explicit withdrawal still closes the card. A stop declines what the CLI still holds (`declineRequest`), so that work goes on instead of waiting on an answer nobody can give.
- A chat whose last turn stopped on a limit moves to another account of its CLI only when a person asks (`chat.continueOn`, `continue-on.ts`), never by itself.
    - An account that reads the chat's transcripts (Codex accounts over one home, shadow homes included) takes the chat over in place, as `chat.configure` switches it. A turn opens at once carrying what the limited turn answered. It refuses with `chat-busy` while the CLI runs background work or waits on a request, since another account needs another CLI.
    - Any other account gets a fork cut after the limited turn, with the conversation handed over, and its first turn opens at once.
    - Either way the original's owed `resume-limit` lapses, so the limited turn is taken up once. After a fork the original keeps a note under that turn (`continued-<turnId>`), and no switch turned on later owes that turn a resume there again.
- A chat leaves Chats only through `chat.move` (`apps/server/src/projects/move-chat.ts`).
    - It refuses what the Chats write (`onPlaces`) would end or orphan (`move-refusal.ts`), and decides every refusal before it makes a folder, repository or project.
    - It changes the chat's folder only once its CLI is gone (`ChatCore.relocate`). It writes the target before Chats, so a project places the chat at every moment, and rehomes a fork's lineage between the two writes, since `forksLeaving` on the Chats write would drop an unspoken fork's record and transcript.
    - Each step has an undo; a failure puts back the ones before it. A running move is recorded in `$RUIMTE_HOME/chat-moves`, and a stop in between is finished at the next start before the outbox runs (`move-repair.ts`), so Chats and a project never place the chat for long.
- An agent in Chats only suggests that its chat become a project (`ruimte-context project propose`, `projects/project-proposals.ts`). The verb makes nothing and refuses outside Chats. Its card holds the chat at `needs-you`, which the move's own `working` check ignores for that one card (`wiring/chat-move.ts`). The move releases that hold before it makes anything (a held chat does not relocate) and restores it if the move fails, so a person can review it. Any other wait still refuses the move.
