# The outbox, tasks and lineage

The invariants of this folder. The repository root's `CLAUDE.md` has the map, the wire protocol and the rules that hold everywhere, including when a task settles, what wakes a chat and when the daemon works on a clock.

- The daemon, not a client, starts the agents a verb creates: through a durable entry in `$RUIMTE_HOME/outbox` that survives a restart. The store and its worker are `@adecore/agents/outbox`; the kinds of entry Ruimte owes and what each holds are in `outbox/outbox.ts`, the handlers beside it, and those of tasks in `@adecore/agents/tasks` (bound in `tasks/wiring.ts`) and of a message in `@adecore/agents/messages`. Lineage (`AgentLineageStore`) and the mode ceiling are `@adecore/agents/lineage.ts` and `modes.ts`. A running turn is resumed from the outbox too (`resume-run.ts`). Session and chat managers create one id at a time.
- Tasks settle through chat observers (`@adecore/agents/tasks/task-coordinator.ts`), never a clock. The only entries due later are `resume-limit` (`@adecore/agents/chat/limit-resume.ts`), `background-limit` (`@adecore/agents/tasks/background-limit.ts`) and `deliver-waiting` (`@adecore/agents/tasks/waiting-child.ts`). `connect-peer` (`remote/connect-peer.ts`) is due later too: the reconnect of the link to another machine, owed only while work for it waits, one entry at most per machine under the target `peer:<machineId>`. Each failure writes a fresh entry with the wait doubled from a minute to ten, and a restart makes it due at once. After 7 days without an open link it gives up, and at once when that machine refuses this one's key or statement (another version of Ruimte is waited out instead): the tasks still owed to that machine fail (`RemoteTasks.giveUp`), an agent that ran there, or whose start may have reached it, is owed a stop that is asked once over a link that happens to be open and never opens a window (`once`), and new work starts a window of its own. `deliver-pr-watch` (`outbox/outbox.ts`, handled in `wiring.ts`) is due at once and written only by the PR-watch (`github/pr-watch.ts`), which owns the clock and the 7 days; it opens one turn in the watching chat, and the turn wakes nobody. `run-after-settle` is due at once and written only when a chat in a worktree settles (`launches/after-settle.ts`); it starts the project's chosen task there, never twice for one turn, and only notes in the chat. Work due later holds no lane, so nothing owed after it waits for it.
- While a `resume-limit` is owed, nothing else the outbox owes that chat opens a turn (`@adecore/agents/chat/wake-chat.ts`): a turn before the reset would stop on the same limit and spend a try.
- The tasks of one `team --task` call (`batchId`) wake the parent once, when all of them settled. A wake that finds its chat in a turn answers `wait` and runs again when `OutboxWorker.wake` names that chat.
- After a restart a `background-limit` entry is made due at once (`restarted`), since the commands it waited on went down with the CLI.
- Stopping or deleting a node ends its descendants through an `end-children` entry (`@adecore/agents/tasks/end-children.ts`, bound to Ruimte's chats, terminals and kinds in `end-children.ts`), written before the node goes so a restart still ends them; their threads and screens stay. A node whose opener no project places is no orphan when the project is indexed again: one another machine's agent opened (`peer` on its record) and a chat a Voice session started (`openedBy` = `voice:<sessionId>`), which keeps running after that session ends.
- A task whose child runs on another machine (`machine` on the task) is settled by no observer here: the machine says so, and `settleFromElsewhere` settles it through the usual path, waking the parent once. Four kinds of entry carry that work, all counted as owed to the machine by `connect-peer`: `start-remote-agent` (target the node; waits for the link and for a place on the machine, and neither ever fails the task), `take-remote-result` (target the node; waits for the machine's word, then takes the result and the branch in and acknowledges), `stop-remote-agent` (target `peer:<machineId>`; outlives the node) and, on the machine that does the work, `deliver-remote-result` (target `peer:<machineId>`; stays until the other machine acknowledges). A node that is ended drops its `start-remote-agent` and owes a stop only for an agent that started (`remote/remote-tasks.ts`).
