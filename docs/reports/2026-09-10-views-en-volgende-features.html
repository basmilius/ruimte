Views per project en de volgende features

Een project wordt een map met een lijst views. Een view is een canvas, een chat, een terminal of een browser. Een losse view is een node zonder positie, met dezelfde id als zijn sessie, dus een node van het canvas naar de sidebar tillen kost geen herstart. Daarnaast liggen er uit nodeterm en T3 Code zeven kleine features klaar die samen minder dan een week kosten.

Voorstel, nog niet besloten

Bron: Ruimte op commit 8b7c11d (main, 10 september 2026), de nodeterm-fork op 323931ea (9 september), T3 Code op d29c56a (10 september). Gedrag gelezen, nooit code overgenomen. De git-panelsessie (worker) loopt parallel en is hier buiten beschouwing gelaten.

Samenvatting

Vandaag is een project hetzelfde als een canvas. De canvasstore is een singleton, de sidebar toont de nodes van dat ene canvas, en het woord "Canvas" in de breadcrumb is een vaste string. Het voorstel breekt dat op in drie besluiten.

  • Eén bestand, versie 2. project.json houdt naam, kleur en icoon en krijgt een lijst views. Een canvasview draagt nodes, texts, edges en layouts, precies wat het project nu draagt. Een migratie van versie 1 wikkelt de bestaande inhoud in één canvasview met de vaste id main, zodat twee machines die hetzelfde gecommitte bestand openen op dezelfde id uitkomen.
  • Een losse view is een node zonder positie. Een chat-, terminal- of browserview is dezelfde ProjectNode minus x, y, w en h. De id is de sessie-id, net als bij een node, dus "Open as view" en "Put on canvas" verplaatsen alleen waar iets gehost wordt. De daemon merkt er niets van.
  • De sidebar wordt de lijst met views. Boven de lijst blijft een sectie "Needs you" die over het hele project kijkt. Het actieve canvas klapt uit naar zijn agentnodes. Cmd+1 tot en met Cmd+9 wisselen van view.

7kleine features uit de concurrentie, samen onder een week

Van de concurrentie zijn dit de aanraders, in volgorde van waarde per uur: een notitie tot agentsessie maken, een weggevallen CLI-sessie herkennen en hervatten, de titel van een node uit de eerste prompt, projectscripts in project.json, prompt-terughalen met pijl omhoog, "Recently closed" met heropenen op Cmd+Shift+T, en settle en snooze voor views. Nodeterm heeft geen meerdere canvassen per project. Het lost dat op met tabs per project en een kanbanbord. T3 Code heeft geen canvas maar wel precies de sidebar die Ruimte voor views nodig heeft.

Het schema, versie 2

// packages/contracts/src/project.ts, nieuw
const ViewBaseSchema = z.object({
    id: z.string().min(1),
    name: z.string().min(1)
});

export const ProjectViewSchema = z.discriminatedUnion('kind', [
    ViewBaseSchema.extend({
        kind: z.literal('canvas'),
        nodes: z.array(ProjectNodeSchema),
        texts: z.array(ProjectTextSchema),
        edges: z.array(ProjectEdgeSchema),
        layouts: z.array(ProjectLayoutSchema).default([])
    }),
    // Een losse chat, terminal of browser is een node zonder plek op een canvas. De id is de sessie-id, zoals bij een node.
    ViewBaseSchema.extend({ kind: z.literal('chat'), node: StandaloneNodeSchema }),
    ViewBaseSchema.extend({ kind: z.literal('terminal'), node: StandaloneNodeSchema }),
    ViewBaseSchema.extend({ kind: z.literal('browser'), url: z.string() })
]);

// ProjectNodeSchema zonder id, kind, title, x, y, w, h en zonder de groep- en notitievelden.
const StandaloneNodeSchema = ProjectNodeSchema.pick({
    cwd: true, command: true, resume: true, provider: true, providerFixed: true, runtimeMode: true, accent: true
});

export const ProjectContentSchema = z.object({
    name: z.string().min(1),
    color: z.string(),
    icon: ProjectIconChoiceSchema.optional(),
    // In sidebarvolgorde. Nooit leeg: wie de laatste view verwijdert krijgt een leeg canvas terug.
    views: z.array(ProjectViewSchema).min(1)
});

export const ProjectDocumentSchema = ProjectContentSchema.extend({
    version: z.literal(2),
    rev: z.number().int().nonnegative()
});

// Machine-lokaal: welke view open stond en per view de camera en de focus.
export const ProjectLocalSchema = z.object({
    activeViewId: z.string().nullable(),
    views: z.record(z.string(), z.object({
        camera: CameraSchema.nullable(),
        focusedNodeId: z.string().nullable()
    })),
    panels: ProjectPanelsSchema.optional()
});

Twee invarianten die de daemon bij het parsen afdwingt. Alle view-ids en alle node-ids over alle views heen zijn uniek binnen het project, omdat ze samen de sleutels van de globale sessiemap van de daemon zijn. En een edge verwijst altijd naar twee dingen in dezelfde canvasview. Een edge over een viewgrens wordt bij het lezen weggegooid.

Migratie

De daemon leest versie 1 en 2 en schrijft alleen versie 2. Versie 1 wordt bij het lezen { views: [{ kind: 'canvas', id: 'main', name: 'Canvas', nodes, texts, edges, layouts }] }. De vaste id main is bewust: het bestand kan gecommit zijn, en twee machines die het onafhankelijk migreren moeten op dezelfde id uitkomen, anders levert de tweede save een spookview op. Het lokale bestand migreert net zo: de oude camera en focus komen onder views.main, activeViewId wordt main. De eerste save na het openen schrijft versie 2 terug, dus een project dat alleen gelezen wordt blijft leesbaar voor een oudere build.

Nodeterm heeft precies deze afweging al gemaakt en gekozen voor tabs per project met één canvas per project. T3 Code heeft geen canvas. Geen van beide heeft dus een voorbeeld voor "meerdere canvassen per map"; het ontwerp hierboven is van ons.

Wat een losse view betekent voor de agent

Een chatview heeft geen edges, dus ruimte-context geeft leeg terug, zoals bij een node zonder lijnen. "Put on canvas" zet de node terug met dezelfde id, en vanaf dat moment werken lijnen weer. "Open as view" laat de edges van de node vallen. Dat verdient een bevestiging als er lijnen zijn, en anders niets. De canvasverbs van fase 18 (list, open, note, link, group) krijgen een viewargument, met de view van de aanroepende sessie als standaard.

Wat een rij doet

  • Klik wisselt van view; op een node in het actieve canvas gaat de camera ernaartoe, zoals nu. Een node in een ander canvas wisselt eerst van view en gaat dan naar de node.
  • Een canvasrij toont het zwaarste status van zijn nodes en een teller. Alleen het actieve canvas staat uitgeklapt; een ander canvas klapt uit op de pijl.
  • Dubbelklik en F2 hernoemen, zoals nu bij nodes. Slepen herschikt. De volgorde staat in het bestand en is dus gedeeld.
  • Contextmenu: Rename, Duplicate (alleen canvas), Put on canvas of Open as view, Delete. Delete met een draaiende sessie vraagt een bevestiging, zoals een node.
  • "Needs you" verschijnt alleen als er iets is en verdwijnt daarna. De statusgroepering "running" en "idle" van nu vervalt: de volgorde is de volgorde van het project, en de dock houdt de tellers.

Een losse chat of terminal op het scherm

De hoofdkolom toont een ViewHost dat op de soort van de actieve view schakelt: het canvas, of het lichaam van een chat-, terminal- of browsernode zonder frame. De body's van ChatNode en TerminalNode zitten nu in NodeFrame; die krijgen een frameloze variant, met de header van de node als de toolbar-breadcrumb. De composer draagt al provider, model en modus, dus een chatview mist niets. Een terminalview mist de cwd-chip en de moduschip uit de header. Die gaan in de toolbar naast de viewnaam.

Focus blijft expliciet. Een losse view zet bij het wisselen de focus in zijn body, alsof je Enter op een node drukt. Cmd+Escape (terminal) of Escape (chat) verlaat de body naar de sidebarrij van die view, want er is geen canvas om naar terug te vallen. De moduschip in de dock zegt "Chat" of "Terminal" in plaats van "Node".

Een browserview is dezelfde <webview> als een browsernode, maar niet in wereldcoördinaten: het viewhost plaatst hem schermvullend in de hoofdkolom, met de navigatiebalk van de node (terug, vooruit, adres, herladen) in de toolbar. Het element blijft, net als bij een node, eigendom van de registry op node-id, dus een pagina die je naar het canvas terugzet houdt zijn sessie en scrollpositie. Net als browsernodes werkt een browserview alleen in de desktop-app; in de browserclient toont de view de bestaande "alleen in de desktop-app"-melding.

Eén view tegelijk, nooit een gesplitst scherm. Twee dingen naast elkaar is wat het canvas is.

Toolbar, palette, dock en sneltoetsen

  • Breadcrumb wordt machine / Project / View. Het viewsegment is een menu met de views en "New view"; het vervangt het vaste woord "Canvas".
  • Palette: "Jump to" spant alle views, met de viewnaam als hint bij een node uit een ander canvas. Nieuwe sectie "Views". Acties: New canvas view, New chat view, New terminal view, New browser view, Rename view, Delete view, Move node to view, Open as view, Put on canvas.
  • Dock: de statustellers gaan over het hele project. Klik op "Needs you" springt naar de eerste node die aandacht vraagt, ook in een andere view.
  • Sneltoetsen: Cmd+1..9 de n-de view, Cmd+Shift+[ en Cmd+Shift+] vorige en volgende view, Cmd+T de "New view"-keuze. Fase 20 houdt Cmd+pijl voor gerichte focus, Cmd+Shift+Enter voor maximaliseren en Cmd+[ en Cmd+] voor camerahistorie. Elk chord heeft een modifier, zoals afgesproken.
  • Projectmenu: "New canvas" heet voortaan "New project". Een nieuw project begint met één canvasview "Canvas".
  • Panelen: Files, Git en de preview blijven per project. Ze gaan over de map, niet over een view, en ze blijven staan als je van view wisselt.

Views: de stappen

Twee leveringen. A geeft meerdere canvassen per project en de nieuwe sidebar. B voegt de losse chat en terminal toe. A alleen is al bruikbaar en verandert de daemon nauwelijks. Groottes zijn schattingen.

  1. Contracts versie 2 en de migratie (halve dag)

    ProjectViewSchema, ProjectContentSchema met views, ProjectLocalSchema per view, een migrateDocument en migrateLocal met tests op een versie-1-bestand uit de repo.

    Klaar als een versie-1-bestand na lezen precies één canvasview main oplevert en de tweede lezing van het geschreven bestand identiek is.

  2. Daemon: lezen, migreren, schrijven (halve dag)

    project-files.ts migreert bij het lezen, toPortable en fromPortable lopen over alle views. project.changed, de watcher en rev blijven ongewijzigd. Bij het parsen: unieke ids over alle views, edges binnen één view.

    Klaar als de bestaande project-store-tests slagen op versie 2 en een bestand met een dubbele node-id met een leesbare fout wordt geweigerd.

  3. Client: documentstore en de canvas als editor (1 tot 2 dagen)

    Een nieuwe store useDocument met alle views en activeViewId. useCanvas.loadDocument laadt één canvasview; een viewwissel schrijft de actieve canvasview terug in het document en laadt de volgende. Undo reset per wissel, zoals bij een projectwissel. project-client.ts bewaakt dirty en autosave op het document in plaats van op de canvasstore, en schrijft per view camera en focus in het lokale bestand.

    Klaar als je met twee canvassen kunt wisselen zonder dat een node beweegt, de camera per view terugkomt na een reload en de conflictbanner nog steeds werkt.

  4. Levenscyclus uit het document (halve dag)

    terminal/lifecycle.ts leidt de levende set af uit alle views van het document: elke node op elk canvas plus elke losse view. Een sessie sterft als zijn id uit het document verdwijnt, niet als hij van het scherm gaat. De loading-uitzondering blijft voor een projectwissel. Meteen oplossen: useSessions.byNodeId en useChats.byNodeId worden bij een projectwissel leeggemaakt, want die houden nu stale rijen vast.

    Klaar als een viewwissel geen enkele session.kill stuurt en het verwijderen van een view de sessies van al zijn nodes beëindigt.

  5. Sidebar als boom (1 dag)

    sidebar-rows.ts wordt een pure module die uit het document een rijlijst bouwt: "Needs you" over het project, dan views in volgorde, met de nodes van het uitgeklapte canvas. Roving tabindex, F2, aria-current en het contextmenu blijven. Slepen herschikt views en schrijft de volgorde in het document.

    Klaar als de bestaande sidebar-tests op de nieuwe module slagen en een agent die aandacht vraagt in een ander canvas bovenaan verschijnt.

  6. Webviews parkeren (halve dag)

    Een WebviewParking-laag buiten de canvastransformatie houdt de elementen van browsernodes uit verborgen views vast met visibility: hidden; de registry adopteert ze terug zodra hun view mount. Het WebGL-budget blijft zoals het is: alleen gemonteerde terminals doen mee.

    Klaar als een pagina in een browsernode zijn scrollpositie en ingelogde staat houdt over een viewwissel heen.

  7. Breadcrumb, commando's, sneltoetsen, palette (halve dag)

    Het viewsegment als menu, de nieuwe entries in commands.ts, Cmd+1..9, Cmd+Shift+[ en ], Cmd+T, de sectie "Views" in de palette en "Jump to" over alle views. Het shortcuts-overzicht in Settings groeit mee.

    Klaar als elke actie via de palette en via zijn chord hetzelfde doet en de dock-tellers over het project gaan. Hiermee is levering A rond.

  8. ViewHost met frameloze chat, terminal en browser (1 tot 2 dagen)

    De body's van ChatNode, TerminalNode en BrowserNode uit NodeFrame lichten tot een ChatBody, TerminalBody en BrowserBody die het frame en het viewhost delen. De toolbar toont voor een terminalview de cwd- en moduschip en voor een browserview de navigatiebalk. De webview van een browserview staat buiten de canvastransformatie, in de hoofdkolom; de parkeerlaag uit stap 6 geeft hem af en neemt hem terug. Focus en Escape zoals hierboven beschreven.

    Klaar als een chatview een gesprek kan voeren met attachments, mentions en skills, een terminalview Claude Code kan draaien met werkende hooks, en een browserview zijn pagina houdt over een wissel naar een ander canvas en terug.

  9. Open as view en Put on canvas (halve dag)

    Twee documentmutaties die een node (chat, terminal of browser) tussen een canvasview en een losse view verplaatsen met behoud van id. De geplaatste node komt in het midden van de camera van het doelcanvas. Edges vallen bij promoveren weg na bevestiging.

    Klaar als een draaiende chat heen en terug kan zonder dat het proces herstart. Hiermee is levering B rond.

  10. Documentatie

    HANDOFF: de view als begrip, de invarianten, de migratie. PLAN: een fase voor views. README: het principe "One canvas, many kinds of things on it" verdient een zin over views (zie open vragen). CLAUDE.md van het project: de regel over project.json.

Ideeën uit nodeterm

Nodeterm heeft één canvas per project en zet projecten in tabs. Wat het boven de node heeft zijn benoemde layouts (die Ruimte al heeft), de kanbanweergave (bewust overgeslagen), een omni-bord over projecten en groepframes met een worktree. Sinds augustus beweegt het richting teams, scheduling en een tracker. Dat is de lijst die Ruimte overslaat. Wat overblijft, gerangschikt op waarde voor iemand die alleen werkt met meerdere agents tegelijk. Wat Ruimte al heeft (layouts, stash, attachments, de contextmeter op chats) staat er niet in.

Wat nodeterm slecht doet en wat we daarvan meenemen

  • Toestemming voor de agentconfig. Nodeterm schrijft bij het opstarten in globale instructiebestanden van agents zonder te vragen. Er kwam een uninstall-script voor. Ruimte's daemon installeert hooks bij het starten (--no-hooks): zeg één keer wat er is geschreven en bied verwijderen aan.
  • Notificatieruis. Elke subagent die terugmeldt liet de chime afgaan. Fase 18: één chime per node per beurt, nooit per event.
  • Focus die de muis volgt. Een hover van 600 ms focust de terminal en mouseleave blurt hem. Op twee schermen is de focus al weg voor je Cmd+Tab drukt. Ruimte's expliciete focus is het antwoord. Wel: onthoud de laatst gefocuste node over het activeren van het venster heen.
  • De camera die uit zichzelf beweegt. Canvasverbs van een agent op de achtergrond trokken de view weg. "Een agent beweegt de camera nooit" hoort in de eerste commit van fase 18, niet in een fix.
  • Gegevensverlies bij meerdere schrijvers. Een SSH-spiegel bracht 16 verwijderde nodes terug omdat een write-ack als bewijs over de inhoud gold, en een conflictbalk die autosave pauzeerde bleef daardoor staan. Voor onze rev en watcher: een conflictbanner mag het opslaan nooit stoppen, en het binden van een map op een bestaand projectbestand van iemand anders weigeren.
  • Prompts door een PTY. Afkappen op 1024 bytes en toch verzenden, bracketed-paste-markers als tekst. Bevestigt het besluit om agent-naar-agent-berichten door de PTY over te slaan.

Ideeën uit T3 Code

T3 Code kent geen canvas. Zijn model is omgeving, project, thread, beurt. De sidebar is één inbox van threads over alle projecten met een projectfilter, in vier secties: Pinned, Active, Snoozed, Settled. Slepen tussen secties is de actie, de volgorde staat op de server, en activiteit herschikt nooit de lijst. Dat laatste is een regel die Ruimte's viewlijst overneemt. Vijftien releases in drie maanden gaan over meer providers, remote en mobiel, de PR-workflow in de app en, in versie 0.0.39, ruim honderd performance-PR's. Van die vier lijnen slaat Ruimte er drie bewust over; de vierde komt vanzelf.

Wat T3 Code slecht doet en wat we daarvan meenemen

  • Performance is de vaste klacht. Een issue met 28 stemmen zegt dat dezelfde taak 20 minuten duurt tegen 3,5 in kale Codex. Lange threads maken de UI traag en replay bij heropenen is kwadratisch. T3 begrenst nu terminalhistorie in bytes en houdt maar drie sidebarrijen live. Fase 16 richt hier al op. De viewlijst maakt het urgenter, want elke rij met een live status is een abonnement.
  • Vastzittende status. "Working..." nadat de CLI klaar is, en een thread die na een interrupt op running blijft. Status uit hooks is de goede keuze. Een settle-timeout als vangnet erbij hoort samen met de weggevallen-sessie-detectie hierboven.
  • Harde timeouts die een heel paneel laten falen. Een scan van 15 seconden doodt het bestandenpaneel zonder deelresultaat. Stream deelresultaten. Het git-paneel van fase 17 streamt de status al.
  • PATH uit een GUI-start. T3 hydrateert PATH uit de loginshell omdat een app uit de dock die niet meekrijgt. Ruimte doet dat nog niet. Voor de gepakte desktop-app van fase 25 is dit nodig.
  • Een gecachte branchchip die achterbleef nadat de sessie van worktree wisselde. Afleiden, nooit cachen.
  • Twee sidebars. De oude staat achter een vlag. Eén vorm kiezen en de oude weghalen.

Wat we niet doen

  • Geen inbox over alle projecten, zoals T3 Code. Ruimte houdt één project tegelijk open: de daemon watcht per open project, Files, Git en de preview zijn per map, en één transport wijst naar één endpoint. De sidebar toont de views van het open project. Projectwisselen blijft in de breadcrumb en de palette.
  • Geen tabstrip in de toolbar. De band van 48 pixels is vol, en de sidebar is al de wisselaar. Nodeterm's tabs zijn projecten, niet views.
  • Geen gesplitst scherm met twee views naast elkaar. Twee dingen naast elkaar is het canvas.
  • Geen node in twee views. Een positie per node, edges binnen één view.
  • Geen kanban, ook niet als "Settled" een kolom lijkt. Settle is een gevouwen sectie onderaan de lijst, zonder kaarten en zonder slepen tussen statussen.
  • Ongewijzigd uit PLAN: geen scheduler, geen minimap, geen teamfuncties, geen PR-client, geen mobiel.

Voorstel voor de volgorde

Views horen vóór fase 18, want de canvasverbs voor agents hebben een view als doel nodig en het is duurder ze later een argument te geven. Het git-paneel van de worker loopt door; views raken de panelen niet.

  1. Fase 17b, Views A: stappen 1 tot en met 7. Meerdere canvassen, de nieuwe sidebar, sneltoetsen. Drie tot vier dagen.
  2. Kleine winsten, tussendoor of ernaast: notitie tot agent, weggevallen sessie, autotitel plus CLI-naam, prompt terughalen. Samen anderhalve dag, elk apart commitbaar.
  3. Fase 17c, Views B: stappen 8 en 9, de losse chat, terminal en browser. Twee dagen.
  4. Na views: Recently closed met Cmd+Shift+T, settle en snooze, projectscripts. Drie dagen.
  5. Na het git-paneel: fetch en auto-pull, de diff-badge op een klare node. Een dag.
  6. Fase 18 en verder zoals in PLAN, met de viewargumenten op de verbs en de lessen uit nodeterm (camera, chime, toestemming voor hooks) als regels in de eerste commit.

Open vragen voor Bas

  1. Het principe in de README. "One canvas, many kinds of things on it" klopt straks per view, niet per project. Voorstel: "One canvas per view, many kinds of things on it. A view is also a chat, a terminal or a browser on its own." Akkoord met die verschuiving?
  2. Cmd+1..9 voor views in plaats van voor nodes, zoals fase 20 nu zegt. Nodes krijgen dan alleen Cmd+pijl en Tab.
  3. De statusgroepering in de sidebar vervalt ten gunste van projectvolgorde plus een "Needs you"-sectie bovenaan. Of moet "Running" ook een eigen sectie houden?
  4. Settle en snooze: gewenst, of voelt het als kanban?
  5. Losse views in het gedeelde bestand. Een chatview staat in project.json en gaat dus mee in git, net als een chatnode nu. De thread zelf blijft onder ~/.ruimte/chats. Dat is consistent met nu; bevestigen dat dat de bedoeling blijft.
  6. Levering B meteen of later. A is op zichzelf bruikbaar; B is het deel dat de app een "T3-modus" geeft. Samen in één fase, of B pas na de kleine winsten?
