Fase 3: taalservers op de machine

De editor kent één bestand tegelijk. Monaco's eigen taalservices zien geen tsconfig.json, geen node_modules en geen ander bestand van het project. Een import is voor ze een onbekende, en een typefout die een ander bestand veroorzaakt bestaat niet. Dit rapport ontwerpt de volgende stap. De daemon draait echte taalservers, één per project en taal, en de editor vraagt ze over de wire wat ze weten.

Ontwerp, nog niets gebouwd. Wel gemeten tegen de TypeScript-server van deze repository.

De kern

De daemon wordt LSP-client. Hij start per project-root en taal één taalserver, de eerste keer dat iemand een bestand van die taal bewerkt. Elke client die het project open heeft deelt die server, en hij stopt als de laatste het project loslaat. De client praat nooit rechtstreeks met de server. Hij stuurt getypeerde requests uit packages/contracts, en de daemon vertaalt ze naar LSP en weer terug.

  • Eerste snede. Diagnostiek over het hele bestand met kennis van het project, aanvullen, hover, signature help, en naar de definitie, ook als die in een ander bestand staat. Referenties, hernoemen, formatteren en code actions komen later. Die vier schrijven in bestanden die niemand open heeft, en dat verdient een eigen ontwerp.
  • Eerste taal. TypeScript en JavaScript, met de eigen TypeScript van het project. Vanaf versie 7 is tsc --lsp --stdio zelf een taalserver. Ik heb dat in deze repository gedraaid. Hover kostte 30 ms, het proces 142 MB geheugen. Python, Go, Rust, PHP en Swift zijn daarna elk een regel in een tabel plus een integratietest. CSS, HTML en JSON houden Monaco's workers.
  • Niets installeren. De daemon zoekt in de node_modules van het project en op zijn eigen PATH. Vindt hij niets, dan zegt de editor welke server ontbreekt en werkt hij verder zoals nu.
  • Eén keer toestemming per project. Een taalserver voert code van het project uit: de binary in node_modules/.bin, build scripts, macro's, go list. Een persoon zegt één keer per project ja. Dat antwoord staat onder $RUIMTE_HOME, zoals alles wat de daemon tegen een agent afdwingt, en nooit in project.json of .ruimte/settings.json. Een agent heeft geen werkwoord dat een server start.
  • Eén document per pad. Elke client heeft per bestand één draft, en de server kent per pad één tekst. De daemon houdt per client een spiegel van die draft bij. De server krijgt de tekst van de client die als laatste iets veranderde of vroeg. Elk request noemt de seq van de tekst waar het over gaat, dus een antwoord valt nooit op tekst die al verschoven is.

Ik raad monaco-languageclient af. Die library vervangt monaco-editor door een eigen build, brengt een tweede tokenizer naast Shiki mee en verwacht een ondoorzichtige JSON-RPC-lijn naar de server. Dat zijn drie dingen die dit ontwerp juist niet wil.

Welke servers, en hoe de daemon ze vindt

De daemon zoekt op twee plekken en verder nergens. Eerst in het project zelf: node_modules/.bin en .venv/bin onder de root, want dan draait de versie die het project vastlegt. Daarna op het PATH van de daemon, dat de service van de login-shell heeft. Nooit npx of bunx, die iets ophalen als het er niet is, en nooit een eigen download. Als er niets is, zegt de status welke server ontbreekt en hoe die meestal geïnstalleerd wordt. De persoon beslist.

De root is de dichtstbijzijnde map boven het bestand met de marker van die taal, en nooit hoger dan de checkout waar het bestand in staat (git/repos.ts). Een worktree is een eigen checkout en krijgt dus een eigen server, met zijn eigen node_modules.

Levensloop

Starten

Een server start bij het eerste lsp.open voor een bestand van zijn taal onder een root waar hij nog niet draait. Er gaat altijd een persoon aan vooraf. Iemand opende dat bestand, en het project heeft toestemming (zie veiligheid). Een tweede client op hetzelfde project krijgt dezelfde server. Starten gebeurt nooit bij het openen van het project, want een project met vijf talen zou dan vijf servers starten voor één blik op de canvas.

Stoppen

De server hoort bij de projecthold, net als de watcher. Roept ProjectStore.release de laatste hold af, dan stopt de daemon de servers van dat project. Eerst shutdown en exit volgens het protocol, na vijf seconden SIGTERM. Omdat een hold ook vervalt als een socket wegvalt, wacht de daemon eerst twee minuten. Een client die binnen die tijd terugkomt vindt een warme server. Voor TypeScript 7 maakt dat weinig uit, want starten kost milliseconden. Een Rust-workspace kan bij het starten minuten indexeren (niet gemeten).

Hoe verhoudt dit zich tot de regel dat een vastgelopen proces een waarschuwing krijgt en nooit een signaal waar niemand op drukte? Die regel beschermt werk, zoals een agent midden in een beurt of een shell met een build. Een taalserver heeft geen werk van iemand in handen, alleen een cache. Hem stoppen met het project kost opwarmtijd en verder niets. Een server stoppen omdat hij een tijd niets deed, stel ik niet voor. Dat is de daemon die oordeelt over een proces terwijl het project open is, en daar gaat de regel precies over. Een server die veel geheugen houdt ziet een persoon in het processenpaneel, waar de 2 GB-waarschuwing en de knop al zitten.

Crashen, herstarten, hangen

  • Crash. Stopt de server zonder dat de daemon erom vroeg, dan start het volgende request hem opnieuw, en de daemon stuurt de open documenten weer met didOpen. Na drie crashes binnen drie minuten stopt het herstarten. De status wordt failed en er komt een knop Opnieuw starten (lsp.restart). De laatste regels van stderr gaan mee in de status.
  • Een traag antwoord. Elk request heeft een termijn op de daemon, vijf seconden voor aanvullen en tien voor de rest. Daarna antwoordt de daemon de client met timeout en stuurt hij $/cancelRequest naar de server. De server blijft draaien.
  • Hangen. Drie termijnen achter elkaar zonder één antwoord maakt de status unresponsive. De editor toont een waarschuwing met Opnieuw starten, en alleen die knop stopt het proces. Dit is de regel van het processenpaneel, toegepast op een taalserver.
  • Indexeren. $/progress van de server wordt indexing in de status, met een percentage als de server er een geeft.

Wat een persoon ziet

Een kleine chip in de toolbar van het bestand, via het slot dat daar al is. De chip toont de naam van de server en zijn toestand (starting, indexing 40%, ready, not found, failed, unresponsive). Een klik opent een menu met de versie, de root, de laatste fout en Opnieuw starten. Is er geen server, dan zegt het menu wat de machine zocht en waar. De status reist als event lsp.status naar elke client die het project vasthoudt, alleen bij een verandering, zoals chat.status. Een client vraagt bij elke verse socket lsp.list voor de stand.

Het proces zelf staat in het processenpaneel in de groep daemon, zonder dat daarvoor iets verandert. Een nieuwe waarschuwingssoort in ProcessAlertKindSchema voeg ik niet toe. Dat zou een nieuwe enum-waarde zijn in een payload die oude clients valideren. Een client laat een event dat niet door zijn schema komt vallen (dispatchEvent in link-transport.ts), en de wire krijgt alleen optionele velden, requests en events.

Documenten

LSP kent per URI één open document met één tekst. De specificatie is daar streng over: "An open notification must not be sent more than once without a corresponding close notification" (didOpen). Ruimte heeft per client één draft per pad. Twee clients met elk een eigen draft zijn twee teksten voor één URI. Een eigen URI per client zou dat oplossen, maar dan ziet de server een bestand dat niemand importeert en werkt niets over bestanden heen.

De regel

  1. De client meldt een pad aan met lsp.open { path, seq, text } zodra een editor op dat pad een draft vasthoudt, en af met lsp.close als de draft wegvalt. Meer oppervlakken op één pad zijn één draft en dus één aanmelding.
  2. De client volgt de draft, niet de editor. Editor.onChange zwijgt bij een herlading, de draft niet. Bij elke verandering berekent de client het verschil met de vorige gestuurde tekst (changedSpan uit text-span.ts bestaat al) en stuurt lsp.change { path, seq, changes }.
  3. De daemon houdt per client en pad een spiegel. De server kent per pad één document, met een versie die de daemon telt.
  4. Is de spiegel van de client die verandert of vraagt dezelfde tekst als wat de server heeft, dan gaat de wijziging incrementeel door. Is het een andere tekst, dan krijgt de server eerst die hele tekst met één didChange. Wie het laatst typte of vroeg, bepaalt wat de server ziet.
  5. Elk feature-request noemt de seq van de draft waar het over gaat. De daemon wacht tot de spiegel op die seq staat. Ligt de spiegel al verder, dan antwoordt hij stale en vraagt Monaco opnieuw.
  6. Diagnostiek gaat alleen naar de clients waarvan de spiegel gelijk is aan de tekst die de server controleerde, met hun eigen seq erbij. Een client met een andere tekst krijgt geen fouten op verkeerde regels.
  7. De laatste client die een pad afmeldt, of wiens socket wegvalt, laat de daemon didClose sturen. Vanaf dan leest de server de schijf.

Het wisselen in stap 4 gebeurt zelden. Een draft slaat zich binnen een seconde op, dus twee clients hebben meestal dezelfde tekst. Alleen twee mensen die tegelijk in hetzelfde bestand typen laten de server heen en weer gaan. Dat kost dan een volle tekst per wissel, maximaal 2 MiB, en ook dan blijft elk antwoord juist.

Schijf, fs.changed en fs.write

  • Een open bestand verandert op schijf. De draft herlaadt al vanzelf als hij niet dirty is (weigh), en de sync volgt de draft. Is hij dirty, dan houdt de server de tekst van de draft. Dat is wat de persoon ziet.
  • Een bestand dat niet open is verandert. Een agent schrijft types.ts, en de fouten in het open main.ts moeten meebewegen. Servers vragen daarvoor met client/registerCapability om workspace/didChangeWatchedFiles. TypeScript 7 deed dat in de meting. De daemon ondersteunt het met een eigen recursieve watch per server, via de seam van watch-seam.ts. Een watch van FolderWatcher hoort bij een client en meldt mappen, maar LSP wil bestandsnamen.
  • Opslaan. fs.write loopt al door de daemon. Na een geslaagde write van een pad dat open staat in een server stuurt de daemon didSave. Rust-analyzer draait zijn cargo check bij opslaan, dus daar hangt de volledige diagnostiek aan. Er komt niets bij op de wire.

De wire

LSP doorgeven afgewezen

Eén request lsp.rpc { server, message } met de JSON-RPC ongezien erin. De client doet dan zelf LSP, en de daemon is een pijp.

  • Het bericht is z.unknown(). Dat is een gat in de regel dat elke vorm in packages/contracts staat en aan beide kanten gevalideerd wordt.
  • De client ziet file://-URI's van de machine en kan elke methode sturen, workspace/executeCommand incluis.
  • Een aanvullijst gaat onbewerkt over de lijn: 424 KB in de meting.

Getypeerde requests voorstel

Per functie een request met een zod-schema, in de vorm die de editor gebruikt. Posities zijn nul-gebaseerd in UTF-16, paden zijn absolute paden op de machine, zoals bij fs.read.

  • De daemon beslist welke methodes bestaan. Een nieuwe functie is een nieuw request, dus nooit een PROTOCOL_VERSION-bump.
  • De daemon filtert en snoeit een aanvullijst voordat die de lijn op gaat.
  • Een LSP-server die zich vreemd gedraagt wordt op de daemon gevangen, niet in elke client.

Gemeten: hoe groot is een antwoord

Ik heb tsc --lsp --stdio van TypeScript 7.0.2 uit deze repository gestart met een klein script over stdio, en het packages/editor/src/index.ts gegeven. Dit is één run op deze Mac, geen reeks.

Wat daaruit volgt:

  • De daemon filtert de aanvullijst. Hij kent de tekst en dus het woord voor de cursor. Hij houdt de items die daar fuzzy op passen, in de volgorde van sortText, en stopt bij 200. Is er meer, dan staat incomplete op true en vraagt Monaco bij de volgende letter opnieuw. Per item gaan alleen label, soort, detail, sortText, filterText en de invoegtekst mee. Mijn schatting is 20 tot 30 KB per antwoord, gemeten is dat nog niet. Zonder die snoei zit een antwoord van 400 KB op het geordende DataChannel voor de terminaluitvoer.
  • De daemon biedt alleen utf-16 aan. Dat is de standaard die elke server moet kunnen (PositionEncodingKind), en het is wat een JavaScript-string en Monaco tellen. Dan hoeft niemand om te rekenen.
  • De daemon zet URI's om naar paden. De wire kent alleen absolute paden, zoals fs.read. %40 wordt weer @ voordat de client het ziet.

Afbreken

Monaco geeft elke provider een cancellation token. De client kiest per request een requestId, zoals git.cancel dat met actionId doet. Bij een afgebroken token stuurt hij lsp.cancel. De daemon stuurt $/cancelRequest naar de server en antwoordt het oorspronkelijke request met cancelled. De server moet volgens de spec ook dan antwoorden (cancelRequest, code -32800). De daemon vangt dat antwoord en gooit het weg. Een antwoord dat de client toch nog bereikt nadat de tekst verschoof, valt af op de seq.

Diagnostiek als event

Diagnostiek is een event en geen antwoord, want de server stuurt ze wanneer hij klaar is, ook na een wijziging in een ander bestand. lsp.diagnostics gaat alleen naar clients die het pad open hebben (zie de regel hierboven), en vervangt telkens de hele lijst voor dat pad. Pull-diagnostiek (textDocument/diagnostic, sinds 3.17) gebruik ik niet. Push werkt bij elke server in de tabel, en de daemon kan het event hetzelfde houden.

Editor en client

De interface groeit met één object

De client geeft bij het mounten een LanguageFeatures mee, een object met functies. De package vertaalt die naar Monaco-providers. De client importeert Monaco nog steeds niet, en de fake engine in fake.ts kan dezelfde functies in een test aanroepen.

Monaco registreert providers per taal en voor de hele pagina. De adapter registreert er daarom één per taal, één keer, en zoekt bij elke aanroep via het model de LanguageFeatures van de editor op. setFeatures bestaat omdat een server later klaar kan zijn dan de editor, of kan uitvallen. De omzetting tussen Monaco's eengebaseerde regels en kolommen en LSP's nul-gebaseerde posities zit in de adapter, met een test.

Een definitie in een ander bestand loopt via monaco.editor.registerEditorOpener. Die bestaat in de meegeleverde monaco.d.ts: "Callback that is invoked when a resource other than the current model should be opened (e.g. when "go to definition" is called)". De opener roept features.open aan, en de client doet useFiles.open met de regel. De peek-weergave zet de adapter uit, want die wil een model van het doelbestand. Of gewoon naar de definitie gaan zonder dat model werkt, heb ik niet geprobeerd. Dat gaat in de spike.

Naast Monaco's workers

De TypeScript-worker registreert zijn providers voor de taal-ids typescript en javascript, voor elk model met die id. Twee bronnen voor hetzelfde model geven dubbele aanvullingen en twee hovers boven elkaar. Zijn instellingen (setModeConfiguration) gelden voor de hele pagina, dus uitzetten raakt ook het bestand buiten het project dat geen server heeft.

Mijn voorstel: een model dat een server bedient krijgt een eigen taal-id, bijvoorbeeld ruimte-typescript, met dezelfde Shiki-grammatica en dezelfde haakjes- en commentaarregels. De worker ziet dat model dan niet, en een ander bestand houdt hem gewoon. Zegt lsp.open served: false, of valt de server uit, dan gaat het model terug naar typescript. De woordsuggesties gaan uit voor een bediend model, zodat ze niet tussen de antwoorden van de server staan. Voor Python, Go en de rest is er geen worker en registreert de adapter gewoon onder de Shiki-id.

Paden, worktrees en bestanden buiten het project

  • Een bestand in een worktree heeft zijn eigen root en dus zijn eigen server. Een definitie wijst binnen die worktree, want die server kent alleen die checkout.
  • Een bestand buiten de projectmap en zijn worktrees krijgt geen server. editBlockOf maakt het al alleen-lezen, en de daemon weigert lsp.open met outside-project, dezelfde grens als fs.write. Monaco's worker blijft daar.
  • Een definitie die buiten de projectmap valt (een SDK, een Go-module in $GOPATH/pkg/mod) opent als alleen-lezen bestand. Dat regelt de bestaande bewerkgrens. Een definitie in node_modules valt binnen de projectmap en is dus bewerkbaar. Dat is zo vandaag ook al, en ik laat het zo in de eerste snede.

monaco-languageclient

Versie 10.7.0 op npm heeft 33 dependencies (registry). Daaronder zitten @codingame/monaco-vscode-api (36 MB uitgepakt), veertien taalpakketten en een override van de tokenizer-service. De README van die API zegt dat het pakket "is installed as an alias to monaco-editor". De library vervangt dus de editor die we hebben, zet een tweede tokenizer naast Shiki, en neemt aan dat de browser JSON-RPC met de server spreekt. Wat Ruimte nodig heeft is vier providers en een marker-lijst. Dat schrijf ik liever zelf in de adapter, geschat op een paar honderd regels.

Aan de daemonkant geldt hetzelfde als voor de CLI's in een chat. LSP over stdio is een header met Content-Length en JSON. Een eigen lsp/rpc.ts met framing en request-ids, plus lsp/protocol.ts met zod-schema's voor het deel dat de daemon leest, zijn puur en te testen zoals claude-protocol.ts. Geen SDK.

Veiligheid

Een taalserver starten is code van het project uitvoeren. Soms is het de binary zelf (node_modules/.bin, .venv/bin, vendor/bin), soms wat die binary aanroept: tsserver-plugins, build.rs en proc macros, go dat go list draait, een Python-interpreter die pyright start. Dit is een groter recht dan fs.write, en het vraagt een eigen grens.

Wie mag een server starten

  • Alleen een client, alleen voor een project dat hij vasthoudt. lsp.open hanteert de grens van fs.write, dus de heldFolders van die client plus de worktrees onder $RUIMTE_HOME/worktrees, vergeleken op echte paden.
  • Pas na toestemming voor dat project. De eerste keer toont de editor een balk boven het bestand: "Language servers run code from this project, such as its build scripts. Run them on this machine?" met Allow en Not now. Allow stuurt lsp.allow. Tot dan werkt de editor zoals nu.
  • De toestemming staat onder $RUIMTE_HOME. In een nieuw bestand $RUIMTE_HOME/language-servers.json (0600), per echt pad van de projectmap. Niet in project.json of .ruimte/settings.json, want die kan een agent met een shell herschrijven. Dit volgt de regel dat wat de daemon tegen een agent afdwingt onder $RUIMTE_HOME leeft.
  • Een agent start niets. Er komt geen ruimte-context-werkwoord voor taalservers, en lsp.* is alleen voor clients. Een agent kan wel een file node op de canvas zetten, en een client die die toont meldt het pad aan. Dan draait er een server zodra het project toestemming heeft. Dat vind ik aanvaardbaar: de toestemming gaat over de code van het project, niet over wie het bestand liet zien.

Wat de server meekrijgt

  • De omgeving van de daemon, dus het PATH van de login-shell, maar zonder ruimte-context op dat PATH en zonder RUIMTE_CONTEXT_URL. Een build script dat een taalserver aanroept, kan zich zo niet voordoen als een agent die werkwoorden gebruikt.
  • De root als werkmap. Geen argumenten die uit het project komen. De initializationOptions komen uit de tabel in de daemon, niet uit een bestand in het project.

Deze grens houdt een draaiende server niets tegen. Hij is een proces van dezelfde gebruiker als de daemon. Hij kan alles lezen wat die gebruiker kan, $RUIMTE_HOME/local.key incluis. De grens gaat over wie een server laat starten, niet over wat hij daarna kan. Dat is hetzelfde als een persoon die in dat project een build draait.

Worktrees van agents

De toestemming van een project geldt ook voor zijn worktrees onder $RUIMTE_HOME/worktrees. Het is dezelfde repository, en fs.write behandelt ze ook zo. Er zit een scherpe kant aan. Een agent in een beperkte modus schrijft een build.rs in zijn worktree. Opent een persoon daar een Rust-bestand, dan voert rust-analyzer dat script uit met de rechten van de daemon, buiten de sandbox van de agent. De persoon opent het bestand, maar weet niet wat erin staat. Voor de eerste snede (alleen TypeScript) speelt dit nauwelijks. Bij Rust wil ik build scripts en proc macros uitzetten in een worktree van een agent. Zie de open vragen.

Tests

  • Een nep-server in de standaardrun. FakeLanguageServer achter dezelfde seam als ChatProcess: stdin en stdout als streams, LSP-framing, vooraf ingestelde antwoorden, en een knop om te crashen of te zwijgen. Daarmee: framing (een header in twee chunks, Content-Length in bytes bij multibyte-tekst), de documentregel met twee clients en een wissel, seq en stale, afbreken, termijnen met een ingespoten klok, het herstartbudget, stoppen bij de laatste hold na de wachttijd, en de weigering zonder toestemming of buiten het project.
  • Pure delen los. Het filteren en snoeien van een aanvullijst, URI naar pad (%40), de root-marker-zoektocht op een nep-bestandssysteem, en het kiezen van een server uit de tabel.
  • De client. De sync van draft naar lsp.change tegen een FakeTransport, en de LanguageFeatures tegen de fake EditorEngine zonder DOM.
  • Echte servers alleen in *.integration.test.ts. TypeScript 7 staat altijd in deze repository, dus lsp/typescript.integration.test.ts draait altijd, op een fixture-map die één keer per bestand gebouwd wordt, zoals git/test-repo.ts. Een test voor gopls, rust-analyzer, pyright of sourcekit-lsp slaat zichzelf over als de server er niet is, en ruimt zijn proces op.
  • Geen test in de standaardrun wacht op de wandklok of op een echt proces.

Open vragen voor Bas

  1. Toestemming per project, of niet? Voorstel: één keer per project vragen, bewaard onder $RUIMTE_HOME, in te trekken in de projectinstellingen. Het alternatief is geen vraag en alleen starten na een toetsaanslag van een persoon in de editor. Dat is minder gedoe, maar dan start een server ook voor een project dat net gekloond is en nog niet bekeken.
  2. TypeScript 6 en lager? Die hebben typescript-language-server nodig, en dat heeft bijna niemand in node_modules. Voorstel: niet meeleveren in de eerste snede. De status zegt wat er ontbreekt. Blijkt het veel voor te komen, dan kan Ruimte die server zelf meenemen, want hij draait tegen de tsserver van het project.
  3. Hoe lang wacht een server na de laatste hold? Voorstel: twee minuten, zodat een wegvallende socket geen koude start kost. Het alternatief is direct stoppen, zoals de watcher.
  4. Build scripts in de worktree van een agent? Voorstel: bij Rust cargo.buildScripts.enable en procMacro.enable uit in een worktree onder $RUIMTE_HOME/worktrees, en een regel in de status die dat zegt. Voor de eerste snede met alleen TypeScript is dit nog niet nodig.
  5. Kale F-toetsen in de editor? F2, F8 en F12 zijn nu al gebonden. Voorstel: weghalen, Mod+klik voor de definitie houden, en de rest met een modifier binden of weglaten tot de functie er is.
  6. Diagnostiek zichtbaar buiten de editor? Een foutenteller op de tab, de sidebar-rij of de node-plaat. Voorstel: eerst alleen in de editor. Een teller vraagt diagnostiek voor bestanden die niet open zijn, en daar vraagt dit ontwerp niet om.

Nagegaan in bronnen: de LSP-regels over didOpen, didClose, afbreken en positiecodering, de standaardwaarden van rust-analyzer, dat gopls het go-commando van het PATH draait, dat pyright een interpreter kan starten, wat sourcekit-lsp nodig heeft, en de dependencies van monaco-languageclient op npm.
