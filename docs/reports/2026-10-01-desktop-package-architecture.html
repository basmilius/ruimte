Begin met gedrag dat beide apps al hebben

De beste kandidaten voor @adecore/shell zijn de volledige navigatiebescherming, het ophalen van de login-shell-PATH en de conversie van sneltoetsen naar native accelerators. Ruimte en AfterMotion implementeren deze nu ieder zelf. Voor @adecore/ui is selectie in een zoeklijst de sterkste kandidaat: de command palette, modelpicker en composer-suggesties herhalen hetzelfde interactiegedrag.

De modules voor windows, theme, menu en updates bestaan al in Desktop Shell. Bouw daarop voort. De huidige UI-primitieven, formatters, shortcuts, lazy-loading en settingsdialog hebben hun plek al in Desktop UI. De winst zit in het verbergen van extra kennis die aanroepers nu nog zelf moeten hebben.

Direct voorbereiden

Maak Ruimtes volledige desktopbridge één contract. Werk daarna de gedeelde navigatiebescherming uit, met de twee apps als concrete adapters.

Daarna verdiepen

Consolideer native sneltoetsen en zoeklijstinteractie. Pak workspace-persistence en de publieke chatinterface op als afzonderlijk werk in Ruimte.

Dit rapport beschrijft voorstellen. De genoemde nieuwe modules en methoden zijn nog geen bestaande exports. De bevindingen zijn gebaseerd op broncode-inspectie; er zijn geen functionele bugs of prestatieverbeteringen gemeten.

Wat gaat naar welke package?

De modulegrens hoort op de plek waar iets werkelijk varieert. Desktop UI verbergt de interactie met een lijst; de app bepaalt wat erin staat. Desktop Shell verbergt de verschillen tussen Electron-events; de app bepaalt welke adressen toegestaan zijn. Een kleine interface neemt zo veel werk over, terwijl het appbeleid lokaal blijft.

Desktop Shell: drie verplaatsingen en één contract

De package heeft al factories voor windows, bounds, theme, menucommands en updates, plus pure web guards. Daarmee is de basis aanwezig. De voorstellen hieronder vullen aantoonbaar gedeeld gedrag aan. [S01]

Geverifieerde doublureEerste library-refactor

1. Een complete module voor navigatiebescherming

De pure beslissingen leven al in Desktop Shell. Beide apps schrijven de eventafhandeling opnieuw: bij een gekozen externe navigatie wordt de systeem-browser geopend, bij een redirect wordt alleen tegengehouden en bij een subframe wordt een afzonderlijk beleid toegepast. [S02] [S03]

Voeg bijvoorbeeld protectPage(contents, policy) toe in packages/desktop-shell/src/page-navigation.ts. De module registreert en verwijdert de listeners, onderscheidt hoofdframe en subframe en past iedere beslissing op het juiste event toe. De app levert alleen haar navigatieregels aan.

const releaseGuard = protectPage(contents, {
    main: (url) => appWindowNavigation(url, appOrigin),
    subframe: (url, from) => appSubframeNavigation(url, appOrigin, from),
    openExternal: (url) => shell.openExternal(url)
});

Ruimte levert haar HTTP-origin en beperkingen voor subframes. AfterMotion levert haar custom scheme en de regel dat een sandbox-frame in zijn sandbox blijft. Die regels hebben verschillende betekenissen en blijven daarom bij de apps. Ruimtes browser- en previewpartitions, guestpermissions en het parkeren van webviews blijven eveneens in Ruimte. [S04] [S05]

Acceptatie. Beide apps gebruiken dezelfde eventimplementatie. Gekozen externe links, externe redirects, about:blank, about:srcdoc en AfterMotions sandbox hebben het huidige gedrag. Loslaten verwijdert de geregistreerde listeners. Tests gebruiken een fake event-emitter; de app registreert haar IPC nog steeds zelf.

Geverifieerde doublureKleine, zelfstandige stap

2. Login-shell-PATH als afgerond gedrag

Ruimte en AfterMotion starten een login-shell met een marker rond de PATH en een timeout. Een desktopapp die via de Dock start, krijgt zo de omgeving waarin de agent-CLI's beschikbaar zijn. Ruimte bewaart de uitkomst voor later gebruik. [S06] [S07]

Verplaats ophalen en parsing naar packages/desktop-shell/src/login-path.ts, met een functie zoals readLoginPath. Lever de procesexecutor aan voor tests en houd het resultaat een string of null. De app bepaalt wanneer zij leest, hoe zij cachet en welke procesomgeving zij ermee bouwt.

Ruimtes Bun-daemon, launchd/systemd-definitie en homefolder blijven Ruimte. AfterMotions utility process en extra omgevingsvariabelen blijven AfterMotion. De gedeelde module hoeft die processen niet te kennen.

Acceptatie. Beide apps gebruiken dezelfde begrensde uitlezing. Tests dekken ontbrekende shell, Windows, timeout, mislukte start en extra uitvoer uit shellconfiguratie. De fallback-PATH en het aantal reads per app blijven zoals bedoeld.

Geverifieerde doublureBrowserveilig entry point

3. Native shortcut-encoding bij Desktop Shell

Beide menumodellen bevatten dezelfde ELECTRON_KEYS en toAccelerator. De conversie kent de Electron-spelling voor onder meer pijltjes en de plus-toets. Op macOS worden toetsen zonder Cmd/Ctrl niet als accelerator aangeboden, zodat het menu ze niet uit tekstvelden neemt. [S08] [S10]

Begin met één pure acceleratorOf in packages/desktop-shell/src/bridge/shortcut.ts. Exporteer die via /bridge. Laat de functie een structureel compatibele shortcutwaarde aannemen, zodat de shell geen runtime-import van Desktop UI nodig heeft.

Parsing van Mod+K, keyboardmatching en het tekenen van keycaps blijven bij Desktop UI. Welke commands bestaan en wanneer ze beschikbaar zijn blijven bij de apps. De conversie naar het native doel en het voorkomen van dubbele native uitvoering zijn Desktop Shell-gedrag; dat laatste zit al in createMenuCommands. [S11] [S29]

Acceptatie. De twee lokale converters verdwijnen. De bestaande menutests blijven dezelfde accelerators opleveren voor Cmd/Ctrl, Meta, pijltjes en Plus. macOS, Windows en Linux behouden hun gedrag bij een page-key en een native-menucommand.

Een declaratief shortcut-veld in MenuSpec kan later nog meer kennis verbergen. Het huidige plan houdt de accelerator-string intact. Daarmee vraagt de eerste migratie geen nieuw preloadprotocol van een shell die al draait.

Twee bestaande contractenAdditief ontwerpen

4. Deel de gemeenschappelijke bridge, behoud app-extensions

AfterMotion heeft zijn volledige AftermotionDesktop-type al in de eigen bridgepackage. Ruimtes volledige DesktopBridge staat nog in de client. Menu-, theme- en update-shapes worden al via Desktop Shell gedeeld. [S12] [S13] [S09]

Maak eerst het Ruimte-contract compleet in @ruimte/desktop-bridge. Ontwerp daarna in @adecore/shell/bridge een kleine gemeenschappelijke interface voor de overeenkomende delen: folderdialog, externe links, menu, theme, windowclaim en updates. Een generiek menu-actiontype houdt de eigen shellcommands van iedere app mogelijk.

Metadata verschilt nu ook: AfterMotion heeft appversie en devstatus, Ruimte geeft systeemlocale en talen door. Deel de overeenkomende velden en maak die verschillen bewuste extensions. Neem de bestaande optionaliteit voor oudere preloads over.

ruimteDesktop en aftermotionDesktop blijven eigen globals. Ruimtes Speech, OpenAI Live, Pulsar, lokale secret en achtergrondservice blijven eigen contracten. AfterMotions server-MessagePort blijft zijn eigen contract. Een gedeelde interface mag deze functies niet vereisen.

Acceptatie. De twee preloads worden op hun eigen samengestelde type gecontroleerd. De bridge blijft importeerbaar zonder Electron-runtime. Een client met een oudere preload biedt alleen aanwezige functies aan, inclusief de bestaande keep-awake-fallback. [S14]

Desktop UI: verberg de interactie met zoekresultaten

Herhaald gedragDomeinvrije UI-module

De command palette, modelpicker en composer-suggesties beheren actieve indices en toetsen zelf. Palette en modelpicker regelen ook het scrollen naar de actieve rij. De modelpicker wordt door AfterMotion gebruikt; dit gedrag heeft dus meerdere concrete aanroepers. [S15] [S16] [S17] [S18]

Desktop UI neemt over

  • Selectie met toetsen en pointer.
  • Een geldige actieve rij na veranderende resultaten.
  • Scroll naar de actieve rij zonder de invoerfocus kwijt te raken.
  • De relaties tussen invoer, lijst en opties voor toegankelijkheid.
  • Het standaardgedrag bij een lege lijst.

De aanroeper houdt

  • Zoeken op de machine en omgaan met de verbinding.
  • Matchen, rangschikken en groeperen van resultaten.
  • Modellen, accounts, bestanden en projectspecifieke labels.
  • Grep-, browse- en machinekeuzemodi.
  • Wat Enter of Tab doet met een gekozen domeinresultaat.

Een kleine interface, met echte adapters

Werk bijvoorbeeld een Results-module uit met compound parts voor input, lijst en item. Een aanroeper geeft items, hun stabiele identiteit en een onChoose-callback aan. De module levert focus- en selectiegedrag. Controleer eerst welke bestaande Base UI-primitief dit al ondersteunt; bouw de librarymodule daarop.

<Results.Root items={items} itemKey={keyOf} onChoose={choose}>
    <Results.Input value={query} onValueChange={setQuery} />
    <Results.List>
        {(item) => <Results.Item item={item}>{labelOf(item)}</Results.Item>}
    </Results.List>
</Results.Root>

Dit is een ontwerpillustratie. Props en partnamen worden tijdens het ontwerp op beide apps getoetst. Een gewone input en CodeMirror hebben verschillend eventgedrag; voeg een headless interface pas toe wanneer de composer die daadwerkelijk nodig heeft.

De grens zit bij de interactie met de resultaten. Als de aanroeper zelf nog indices begrenst, pijltjes afhandelt, ARIA-relaties opbouwt en scrollt, verbergt de nieuwe module te weinig. Een wrapper om de bestaande listbox-markup neemt dat werk nog niet over.

Acceptatie. Migreer eerst de modelpicker, daarna de palette en vervolgens de composer. Tests controleren kiezen met het toetsenbord, een lege lijst, verdwijnende resultaten, pointerselectie en focusbehoud. De bestaande appgedragingen voor Tab, grepresultaten en modelkeuze blijven zichtbaar getest.

Wat al goed in Desktop UI zit

Behoud de huidige ownership van formatters, shortcutmatching, keycaps, settingsdialog, menus, lazy-loading, prefetching en de algemene controls. Ruimtes Panel, CommandPalette en canvasdock blijven appmodules: zij weten welke panels, commands en editors bestaan. Ze gebruiken de algemene controls van Desktop UI. [S30] [S19]

Een plan met afzonderlijk reviewbare stappen

Begin additief. Elke librarywijziging krijgt een concrete aanroeper in beide apps, een acceptatievoorwaarde en een eigen release/adoptiestap. De apps gebruiken nu gepubliceerde npm-versies; een wijziging in de desktop-repository bereikt Ruimte pas nadat Ruimte haar dependency bijwerkt.

  1. Ruimtes desktopcontract compleet maken

    Ruimte Verplaats de volledige DesktopBridge en bijbehorende client-only bridge-shapes naar packages/desktop-bridge/src/desktop.ts. Laat client en preload hetzelfde contract gebruiken. Houd methods, globals en kanalen gelijk.

    Resultaat. Een typecheck van de preload op het gedeelde contract, plus fixtures voor de bestaande oudere bridgevarianten. Ruimtes webclient en oude shell blijven hun huidige capabilities houden.

    Geen dependency op een nieuwe desktop-release. Dit bereidt de gedeelde contractstap voor.

  2. Navigatiebescherming en PATH in Desktop Shell onderbrengen

    Desktop Shell Werk twee zelfstandige voorstellen uit: protectPage en readLoginPath. Leg per voorstel de huidige aanroepers en het afwijkende appbeleid vast. Migreer Ruimte en AfterMotion naar de nieuwe exports.

    Resultaat. Twee afgeronde modules met de acceptatievoorwaarden uit navigatie en PATH. De twee apps slagen voor hun bestaande checks; Desktop Shell houdt haar eigen tests en build.

    Deze twee voorstellen kunnen onafhankelijk worden uitgewerkt. Ze veranderen geen rendererprotocol.

  3. Browserveilige shortcutconversie en gedeelde bridge-shapes toevoegen

    Desktop Shell /bridge Consolideer toAccelerator eerst zonder de menuwire te veranderen. Deel daarna de werkelijk overeenkomende bridge-shapes, met Ruimte- en AfterMotion-extensions erboven.

    Resultaat. Eén native shortcutconversie; geen React-runtime in Desktop Shell en geen Electron-runtime in de bridge. Beide preloads worden gecontroleerd op hun samengestelde contract. Het Ruimte-contract uit stap 1 maakt de verschillen zichtbaar.

    Versie en migratienotitie worden op de uiteindelijke wijziging van de exports gebaseerd. Behoud accelerator-strings tijdens deze stap.

  4. Zoeklijstinteractie in Desktop UI verdiepen

    Desktop UI Kies een bestaande Base UI-primitief als basis en ontwerp de Results-interface op de modelpicker en palette. Migreer de modelpicker als eerste concrete aanroeper. Controleer AfterMotion, dat deze picker gebruikt. Pak daarna palette en composer aan.

    Resultaat. Aanroepers onderhouden geen eigen selectie-index en standaard arrow/scroll/ARIA-gedrag meer. Domeinzoekwerk en bijzondere acties blijven lokaal. Desktop UI documenteert de nieuwe export en neemt die bewust op in het exportsnapshot.

    Kan onafhankelijk van de Desktop Shell-stappen. CodeMirror-integratie volgt op een werkende gewone inputadapter.

  5. Workspace-persistence in Ruimte samenbrengen

    Ruimte client Geef de bestaande workspace-module eigenaarschap over gezamenlijk opslaan, vrijgeven en dispose. Laat windowverplaatsing en projectwissel dezelfde interface gebruiken.

    Resultaat. Opslagvolgorde staat op één plek. Tests met echte editorstores en een in-memory transportadapter dekken edits in meerdere cellen, een wissel tijdens opslaan en reconnect. ProjectSwitch behoudt zijn huidige rollbackgedrag.

    Onafhankelijk van de desktop-libraryreleases; een afzonderlijke domeinrefactor.

  6. De publieke chatinterface versmallen

    @ruimte/agents-react Bied een chatruntime en ChatView aan voor het gebruikelijke geval. Behoud bewuste slots en laag-niveau-exports waar de twee apps die nodig hebben. Maak geen extra transportlaag: gebruik de bestaande ChatTransport-seam.

    Resultaat. Een nieuwe aanroeper kan een chat opbouwen zonder handmatig clients, providers, subscriptions en diffpool te verbinden. Tests volgen attach/detach, reconnect, draftbehoud en hostactions via de nieuwe interface.

    Maak eerst een lijst van gebruikte publieke paden. Migreer beide apps via aliases voordat oude paden verdwijnen. De Results-module uit stap 4 kan de interne composer vereenvoudigen.

Hoe dit langs de repositories gaat

Voor Desktop UI en Desktop Shell volgt het werk de bestaande libraryworkflow: een issue per behoefte in basmilius/adecore, met het probleem, de gewenste ervaring en impact op AfterMotion. De libraryimplementatie gebeurt daar. Beide apps testen met een gelinkte checkout; daarna wordt de library gereleased en nemen de apps die versie afzonderlijk over. Dit rapport opent nog geen issues en voert het plan niet uit. [S27]

Gedragstests aan de nieuwe interface vervangen overlappende tests op helpers die verdwijnen. Houd security- en compatibiliteitsgevallen expliciet. Voer per repository de vereiste typechecks, lint, tests en builds uit zodra de betreffende code verandert.

Bewijs: navigatie heeft app-specifiek beleid

Ruimte staat app-URL's, about:blank en about:srcdoc in subframes toe. AfterMotion geeft een sandbox-frame een striktere regel en leest daarvoor ook de huidige frame-URL. De gedeelde module moet daarom de eventmechaniek verbergen en deze policy aangeleverd krijgen. [S04] [S05]

export const appSubframeNavigation = (url: string, appOrigin: string, from = ''): NavigationVerdict => {
    if (isSandboxUrl(from)) {
        return isSandboxUrl(url) ? 'allow' : 'refuse';
    }
    return isAppUrl(url, appOrigin) || isSandboxUrl(url) || url === 'about:blank' || url === 'about:srcdoc' ? 'allow' : 'refuse';
};
Bewijs: de publieke chatinterface volgt alle bronbestanden

De onderstaande test legt vast dat ieder bronbestand een eigen publiek pad krijgt. Dat is een bewuste bestaande conventie. Een versmalling vraagt dus een wijziging van die conventie en een migratie voor beide apps. [S24]

test('every source file is exported under its own path', () => {
    const manifest = JSON.parse(readFileSync(join(HERE, '../package.json'), 'utf8')) as { exports: Record<string, string> };
    const exported = new Set(Object.values(manifest.exports));
    const missing = sources().filter((path) => !path.endsWith('.test.ts') && !exported.has(`./src/${path}`));
    expect(missing).toEqual([]);
});
