Terugswipen in een browserpagina

Het kan, maar Electron geeft het niet cadeau. Chrome's twee-vinger terug en vooruit zit in de Chrome-laag boven Chromium, niet in de laag die Electron meelevert. Wij moeten het gebaar zelf herkennen uit de horizontale scroll-events in de pagina, en zelf tekenen wat eronder gebeurt. Dat is ongeveer een dag werk voor een versie die goed genoeg aanvoelt, en het werkt in de browsernode en de browserview tegelijk omdat beide dezelfde geparkeerde <webview> gebruiken.

Onderzocht, nog niet gebouwd

Bron: de werkboom van Ruimte op 10 september 2026 (5358501 plus ongecommit werk), Electron 44.3.0 uit bun.lock. Electron-feiten komen uit de typings in node_modules, de breaking-changes van het project en issue #2683 met de openstaande PR #53522, opgehaald op 10 september 2026.

Samenvatting

Het antwoord op de vraag is ja, met een kanttekening over hoe echt het aanvoelt. Vier dingen die het bepalen:

  • Electron heeft geen API voor het twee-vinger gebaar. BrowserWindow kent alleen een swipe-event voor drie vingers, en dat vuurt alleen als de gebruiker in Systeeminstellingen "Wissel tussen pagina's" op "Veeg met twee of drie vingers" heeft gezet. De scroll-touch-*-events die je hiervoor kon misbruiken zijn in Electron 23 verwijderd.
  • Zelf herkennen werkt wel. Een preload-script in de gastpagina telt horizontale wheel-deltas op, kijkt of er nog iets te scrollen valt en meldt een gebaar aan de host. Dat is dezelfde route die andere Electron-apps in issue #2683 gebruiken. De navigatie zelf is dan browserRegistry.back(nodeId), dat er al is.
  • De rubberband van Chrome kunnen we niet lenen. De pagina die met je vinger meeschuift komt uit macOS' eigen trackSwipeEventWithOptions:, waar wij zonder native code niet bij kunnen. Wat wel kan: een pijloverlay die met de accumulatie meebeweegt, getekend in de host waar de foutplaat nu ook al in staat.
  • Er ligt een PR bij Electron die dit oplost. #53522 voegt een swipe-gesture-event toe met richting, fase en genormaliseerde voortgang. Geopend op 4 september 2026, nog geen review. Als die landt, vervangt hij onze detectie en houden we de overlay.

Aanbeveling: bouw de eigen detectie, houd de laag ertussen dun genoeg om later op swipe-gesture over te stappen, en zet er sneltoetsen naast voor wie liever niet veegt.

Waarom het niet vanzelf gaat

In Chrome loopt het gebaar over AppKit. Zodra een horizontale scroll begint, vraagt Chrome met NSEvent.trackSwipeEventWithOptions: aan macOS om het gebaar te volgen. macOS levert dan per frame een voortgang tussen -1 en 1 en een fase, en Chrome tekent daarop de pagina die meeschuift en de pijl in de hoek. De code die dat doet heet HistorySwiper en zit in de Chrome-browserlaag, samen met de geschiedenisoverlay en de navigatie zelf.

Electron levert Chromium mee, niet Chrome. Dat verschil is precies de laag waar dit in zit. De auteur van PR #53522 schrijft het zelf op, na te hebben overwogen om HistorySwiper over te nemen:

"Chromium's HistorySwiper was evaluated for direct reuse. It is coupled to renderer input acknowledgements, overscroll state, Chrome's history overlay, and browser navigation. Those policies do not fit a window-level Electron event, particularly because a BaseWindow can contain zero or multiple WebContents."

Die laatste zin is ook onze situatie. Eén venster, een handvol pagina's ernaast op hetzelfde canvas: het venster weet niet welke pagina de veeg bedoelt. Wij weten dat wel, want de canvas houdt bij welke node focus heeft.

De Chromium-vlag TouchpadOverscrollHistoryNavigation die soms genoemd wordt, helpt op macOS niet. Die stuurt de overscroll-controller aan die op Windows en ChromeOS de navigatie doet; op macOS loopt het gebaar via AppKit en via Chrome's eigen code. niet getest, wel beredeneerd uit de PR-tekst hierboven

Het ontwerp

De pagina ligt in een <webview> in de parkeerlaag, dus het gebaar begint in de gast en moet naar de host. Die route bestaat al voor het contextmenu; deze is korter, want sendToHost gaat rechtstreeks naar het element in registry.ts.

1. Het preload-script in de gast

Registreren op de sessie die de browsernodes al delen, zodat we het preload-attribuut per element niet hoeven te zetten en een pad in de gepackagede app niet naar de renderer hoeft:

// apps/desktop/src/main.ts, naast de bestaande partitie-instellingen
session.fromPartition(BROWSER_PARTITION).registerPreloadScript({
    type: 'frame',
    filePath: join(__dirname, 'guest.cjs')
});

Het script zelf luistert in de capture-fase op window, zodat een pagina die wheel afvangt ons niet blokkeert. Passief, want wij houden niets tegen:

const THRESHOLD = 110;   // opgetelde pixels voordat het vuurt
const IDLE_MS = 120;     // stilte die het eind van een gebaar markeert

let sum = 0;
let spent = false;
let timer = 0;

window.addEventListener('wheel', (event) => {
    // Een muiswiel levert grove stappen en zelden een deltaX; dit is het trackpad.
    if (event.deltaMode !== 0 || Math.abs(event.deltaX) <= Math.abs(event.deltaY)) {
        return;
    }
    // Een pagina die zelf nog opzij kan, mag eerst.
    if (scrollableX(event.target, event.deltaX)) {
        return;
    }
    window.clearTimeout(timer);
    timer = window.setTimeout(reset, IDLE_MS);
    sum += event.deltaX;
    if (!spent && Math.abs(sum) > THRESHOLD) {
        spent = true;
        ipcRenderer.sendToHost('swipe', { direction: sum < 0 ? 'back' : 'forward' });
        return;
    }
    ipcRenderer.sendToHost('swipe-progress', { progress: Math.max(-1, Math.min(1, sum / THRESHOLD)) });
}, { capture: true, passive: true });

Het script exposeert niets via contextBridge en leest niets uit de pagina. Het draait wel in elke pagina die een browsernode opent, dus het moet klein en stil blijven.

2. De host luistert op het element

BrowserRegistry.listen heeft al een rij listeners; hier komt er één bij, in dezelfde stijl als page-favicon-updated:

element.addEventListener('ipc-message', (event) => {
    const message = event as unknown as { channel: string; args: unknown[] };
    if (message.channel === 'swipe') { ... this.back(nodeId) of this.forward(nodeId) }
    if (message.channel === 'swipe-progress') { ... patch({ swipe: progress }) }
});

De navigatie gaat alleen door als canGoBack() waar is; anders laat de overlay zien dat er niets achter zit en veert hij terug. De voortgang gaat in de bestaande BrowserState, zodat de node en de view hem allebei zien.

3. De overlay

Een halve cirkel met een pijl aan de rand van de pagina, die met de voortgang naar binnen komt en op vol vermogen even oplicht. Die hangt in dezelfde geparkeerde host waar BrowserErrorPlate nu zijn portal in zet, want dat is de enige plek die zowel de node als de browserview afdekt en die met de camera meeschaalt. Onder prefers-reduced-motion vervalt de beweging en blijft de pijl kort staan.

De pagina zelf laten meeschuiven zou een opname van het vorige scherm vragen. webview.capturePage() kan dat, maar dan onderhouden we per node een cache van schermen en een tweede lifecycle. Dat is een aparte beslissing, geen onderdeel van dit voorstel.

4. Sneltoetsen ernaast

Cmd+[ en Cmd+] horen bij een browser en zijn goedkoop, maar toetsen in een gefocuste pagina gaan naar de gast, niet naar onze renderer. Twee wegen: een item in het applicatiemenu met een accelerator, of before-input-event op de gast in main.ts, waar de contextmenu-hook al hangt. Het tweede past beter, want het applicatiemenu heeft nu geen browser-sectie.

Randgevallen

  • Pagina's die zelf horizontaal scrollen. Een kaart, een tabel, een carrousel. De scrollableX-check loopt de voorouders van het doel langs en laat het gebaar vallen zodra er nog ruimte is in die richting. Pagina's die scrollen met JavaScript in plaats van met overflow blijven een gok. Chrome heeft hier dezelfde klasse fouten, alleen met betere informatie.
  • Iframes van een andere origin. Een wheel in een ingesloten frame bereikt het hoofdframe niet. Omdat we het preload-script op de sessie registreren met type: 'frame', draait het ook in die frames. Of sendToHost vanuit een subframe aankomt is niet zeker; zo niet, dan gaat het bericht via ipcRenderer.send naar main en mapt nodeIdOfContents het terug. Die functie bestaat al voor het contextmenu. te meten bij de eerste test
  • Het canvas eronder. Alleen een node met focus geeft de pointer door aan zijn pagina; bij een node zonder focus pant het canvas op dezelfde horizontale deltas. Dat is bestaand gedrag en het botst niet, maar het betekent wel: veeg pas nadat je de node hebt aangeklikt. In een browserview speelt het niet, daar is de pagina de hele kolom.
  • Zoom. De host schaalt met scale(camera.zoom). De deltas die de gast rapporteert zijn CSS-pixels binnen de pagina, dus de drempel voelt bij uitgezoomd canvas anders aan dan bij 100%. Als dat stoort, deelt de host de drempel door de zoom.
  • Uitloop na het afvuren. Na een gebaar blijven er nog honderden pixels aan momentum binnenkomen. spent houdt die tegen tot de stilte van 120 ms voorbij is, anders navigeer je drie pagina's terug in één veeg.
  • Windows en Linux. Daar bestaat het gebaar op OS-niveau: Windows stuurt browser-backward als app-command naar het venster bij een drie- of vier-vinger veeg. Vijf regels in main.ts, zelfde doorgeefroute als het drie-vinger event op macOS.
  • Muizen met zijknoppen. Knop 3 en 4 komen als gewone mouseup binnen in de gast en kunnen mee in hetzelfde preload-script.

De stappen

  1. Het gebaar meten voordat we het bouwen

    Een tijdelijke wheel-logger in de gast, en dan zelf vegen: op een pagina die niet scrollt, op een pagina die wel horizontaal scrollt, en met een muiswiel. Wat we zoeken zijn de deltas per frame, de duur van de uitloop en of de systeeminstelling "Wissel tussen pagina's" er iets aan verandert. Daaruit komen de twee getallen die het gevoel bepalen.

  2. Preload en doorgeefroute

    apps/desktop/src/guest.ts, meegebouwd in build:main zoals preload.cjs, geregistreerd op de persist:ruimte-sessie. De registry krijgt de ipc-message-listener en BrowserState een veld voor de voortgang. Klaar als terug en vooruit werken zonder overlay.

  3. De overlay

    Een portal in de geparkeerde host, naar het voorbeeld van BrowserErrorPlate. Meebewegen met de voortgang, terugveren als er geen geschiedenis is, niets doen onder prefers-reduced-motion.

  4. De goedkope extra's

    Het drie-vinger swipe-event, app-command voor Windows, de zijknoppen van de muis en Cmd+[ en Cmd+] via before-input-event. Allemaal via dezelfde ingang als het gebaar.

  5. Tests

    De detectie is een pure functie over een reeks deltas en tijdstempels: een *.test.ts naast het script dekt drempel, uitloop, richting en de rand-check af. Het gebaar zelf blijft handwerk, want een trackpad valt niet na te bootsen in bun test.

Nog open

  • Hoe ver moet een veeg gaan? Chrome vuurt rond een kwart van de vensterbreedte. Wij hebben nodes die smaller zijn dan een venster; een vaste 110 px voelt op een kleine node anders dan op een brede. Vast getal of een deel van de breedte van de node?
  • Alleen op een gefocuste node, of ook onder de muis? Focus is de simpele regel en sluit aan bij het scrollen dat er nu is. De pagina onder de cursor laten reageren zou consistenter zijn met een echte browser, maar botst met het pannen van het canvas.
  • Wachten we op #53522? Als je het gebaar pas over een paar maanden nodig hebt, is niets bouwen de goedkoopste optie en kunnen we de PR volgen. Wil je het deze week, dan is route A het.
