Wat Windows-ondersteuning kost

De Electron-shell en de client zijn al grotendeels op Windows voorbereid. Het werk zit in de daemon. Bun heeft op Windows geen PTY, CLI's starten er via .cmd-shims en git geeft paden terug met forward slashes. Daarna komt een release-pipeline die nog geen Windows kent.

Nog niet begonnen. Eerst een Windows-VM om op te testen.

Issue #15, gemeten op main bij ba18ffa5. Scope is de daemon, de desktop-shell, de client, build, CI, npm en docs. iOS valt erbuiten.

Zonder een PTY op Windows draait er geen terminal, en zonder terminal heeft de rest weinig zin. Die vraag gaat daarom voor. Veel van het overige werk hangt niet van Windows af. Denk aan PATH met path.delimiter, git-paden normaliseren, ruimte-context en de hooks via de binary laten lopen, en stoppen zonder SIGTERM. Dat kan meteen op de Mac, met tests.

Op één plek zit een beveiligingsrisico. Windows negeert de mode 0o600, dus local.key leunt op de ACL's van de map waar hij staat. Onder %USERPROFILE% is dat goed genoeg. Onder een RUIMTE_HOME als C:\ruimte kan elke gebruiker hem lezen.

De PTY blokkade

BunPtyAdapter start een shell met Bun.spawn({ terminal }). De typings van Bun 1.4.2 zeggen daarover letterlijk "Only available on POSIX systems (Linux, macOS)". De seam om dat te vervangen is er al. PtyAdapter in apps/server/src/pty/pty.ts is precies één methode, spawn.

node-pty onder Bun

Het minste eigen code. Het gebruikt ConPTY, dezelfde laag als Windows Terminal. Ik weet niet of het werkt in een bun build --compile-binary. Het native addon moet laden, en conpty.dll en OpenConsole.exe moeten naast de binary meereizen.

Een Rust-helper

Een klein programma op portable-pty dat over stdin en stdout met de daemon praat. Het past bij ios-device-bridge en speech-bridge, die al zo werken. Het kost een extra binary in de build en een protocol om te onderhouden.

Mijn voorkeur is een spike van een dag. Probeer eerst node-pty in een gecompileerde binary op de VM. Werkt dat niet schoon, dan wordt het de Rust-helper.

Met de PTY komen drie kleinere dingen mee.

  • defaultShell kiest $SHELL of /bin/bash. Windows heeft geen van beide, en basename('bash.exe') valt buiten LOGIN_CAPABLE.
  • sessions/session.ts:110 schrijft een startcommando met \n. Via ConPTY verwacht de shell \r.
  • providers/launch.ts quote een resume-commando op POSIX-manier met '\''. PowerShell en cmd lezen dat anders, en er gaat prompttekst doorheen.

Processen en signalen middel

  • daemon.ts:891 vangt SIGINT en SIGTERM. Windows stuurt geen SIGTERM, dus een stop vanuit de desktop (main.ts:216) is TerminateProcess en slaat de shutdown-flush over. Er is een stopverzoek over HTTP of IPC nodig.
  • Een kill() op een .cmd-shim stopt alleen cmd.exe, en de node.exe eronder blijft als wees draaien. Dat geldt voor de chat-backends, de probe en git/run.ts. Kinderen binnen ConPTY overleven ook. De oplossing is taskkill /T of een job object.
  • packages/npm/src/bin.ts:54 stuurt SIGHUP en SIGQUIT door. Op Windows doet dat niets.

Beveiliging security-grens

fs.ts:18 schrijft standaard met 0o600, net als auth/local-secret.ts:38, endpoint-id.ts:206 en auth-store.ts:305. Windows negeert die bits. Nodig zijn expliciete ACL's bij het aanmaken van RUIMTE_HOME, of een daemon die weigert te starten als de ACL's te ruim zijn.

Kleiner

  • git/diff.ts:134 en git/status.ts:123 gebruiken --no-index /dev/null. Git for Windows vangt dat waarschijnlijk op. Dat moeten we op de VM controleren.
  • Een recursieve watch houdt een handle op de map. Een git worktree remove van een map onder watch kan dan EBUSY geven.
  • project-files.ts:92 herkent zijn eigen writes aan LF. Met core.autocrlf=true ziet dat eruit als een externe wijziging.
  • fs/reveal.ts:15 geeft /select,C:\a b met quotes door, en Explorer leest dat verkeerd.
  • providers/claude.ts:21 staat Bash(ruimte-context *) toe, maar niet de PowerShell-tool van Claude Code.

Build, CI, release en npm groot

  • apps/server/scripts/compile.ts:28 vertaalt windows, terwijl Node win32 zegt. Daardoor faalt --target win32-x64. Het script kopieert ook het sh-script van ruimte-context mee.
  • electron-builder.yml heeft geen win-target. Auto-update via electron-updater vraagt om NSIS, want alleen dat levert latest.yml.
  • release.yml draait op macOS en Ubuntu. Er is een windows-latest-job nodig die de client bouwt, de daemon compileert en electron-builder --win draait.
  • Authenticode-signing ontbreekt. Zonder signing blokkeert SmartScreen de installer, en de publisher-check van de updater faalt.
  • ci.yml draait alleen op macos-latest. Een windows-latest-job vangt padregressies af.
  • packages/npm/src/targets.ts mist win32-x64. launcher.ts:23 weigert Windows met "Ruimte does not run on Windows yet", en launcher.ts:43 zoekt naar bin/ruimte zonder .exe. Voor Trusted Publishing moet een placeholder-package eenmalig met de hand gepubliceerd worden.
  • Docs noemen alleen macOS en Linux. Het gaat om README.md:43, docs/RELEASE.md, docs/NEXT.md, apps/server/README.md en site/index.html. docs/research/windows.md gaat over app-vensters en niet over het besturingssysteem, en een notitie bovenaan voorkomt verwarring.

Ongeveer 51 testbestanden gebruiken hardgecodeerde POSIX-paden. De grootste zijn contracts.test.ts, stored-path.test.ts, service/manager.test.ts en cli/service.test.ts. Zo'n 16 leunen op sh, SIGHUP, mode bits of symlinks. Die hoeven niet allemaal meteen om. Een Windows-VM om op te testen

Op de Mac staat nog geen hypervisor. De opzet is Windows 11 ARM in een VM, met de OpenSSH Server van Windows zelf. Claude voert daarna alles uit met ssh win '...'. Dat gaat over tests, de daemon en de PTY-spike.

Parallels Desktop

Werkt het soepelst met Windows op ARM. prlctl capture maakt screenshots die Claude kan lezen. Het kost geld.

UTM of VMware Fusion

Allebei gratis en goed genoeg voor SSH en tests. Minder integratie, en screenshots gaan via een script in de VM.

  1. Hypervisor en Windows 11 ARM

    Download de ARM64-ISO bij Microsoft. Zonder activatie werkt Windows met een watermerk, en voor development is dat genoeg. Geef de VM minstens 8 GB geheugen en 80 GB schijf.

  2. Gereedschap in de VM

    Installeer Git for Windows, Bun, Node en de CLI's claude en codex, bijvoorbeeld met winget. Rust komt pas als de spike op de helper uitkomt.

  3. OpenSSH Server aanzetten

    In een PowerShell als admin:

    Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic

    Zet je publieke sleutel in C:\ProgramData\ssh\administrators_authorized_keys als je account admin is, anders in ~\.ssh\authorized_keys. Maak PowerShell de standaardshell van sshd, zodat commando's niet in cmd.exe landen.

  4. Verbinden vanaf de Mac

    Een Host win in ~/.ssh/config met het IP van de VM. Het werkt als ssh win 'bun --version; git --version' antwoordt. Clone de repo daarna in de VM. Een gedeelde map raad ik af, want bun install en symlinks gaan daarop vaak mis. Wijzigingen gaan erheen als patch of via een WIP-branch.

Twee dingen om van tevoren te weten.

  • Een programma dat via SSH start, draait in een sessie zonder bureaublad. Het Electron-venster verschijnt dan nergens. De app moet daarom starten via een geplande taak in de ingelogde sessie (schtasks /run). Klikken en visuele QA blijven mensenwerk.
  • Met een tunnel koppelt de Electron-app op de Mac aan de daemon in de VM: ssh -L 4212:localhost:4211 win. Zo test je terminals, shells en agents op Windows voordat de Windows-shell af is.

De VM draait ARM64. Bun kent bun-windows-arm64 als target, dus native testen kan. x64-specifieke problemen, zoals prebuilds van native modules, dekt de VM maar deels. De x64-build hoort in CI op windows-latest.

Volgorde

  1. VM opzetten

    Klaar als ssh win werkt en bun install slaagt in een clone in de VM.

  2. PTY-spike

    Probeer node-pty in een binary van bun build --compile op de VM, met de Rust-helper als terugval. Klaar als een PowerShell in een Ruimte-terminal typt, van grootte verandert en netjes afsluit, bekeken vanaf de Mac via de tunnel.

  3. Daemon-fundament

    Dit kan op de Mac en is met tests af te dekken. Het gaat om PATH met path.delimiter, CLI's vinden via PATHEXT, git-paden normaliseren, ruimte context en ruimte hook via de binary, een stopverzoek in plaats van SIGTERM, en ACL's op RUIMTE_HOME. Klaar als de bestaande tests op macOS groen blijven en de nieuwe tests Windows-paden als invoer gebruiken.

  4. Terminals en agents op Windows

    De standaardshell met de juiste args, \r, quoting per shell en het stoppen van procesbomen. Klaar als een chat met Claude Code in de VM start, een hook binnenkomt en ruimte-context antwoordt.

  5. Shell en client

    windowsHide, .ico, een Settings-ingang, de badge en de vijf padhelpers. Klaar na een visuele ronde in de VM.

  6. CI, release en npm

    Eerst tests op windows-latest, daarna de release-job met signing en NSIS, dan @ruimte/win32-x64. Als laatste de docs en de site bijwerken.
