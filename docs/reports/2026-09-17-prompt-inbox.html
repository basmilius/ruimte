Eén plek voor alles wat agents je vragen

Elk canvas krijgt een stapel promptkaarten boven de dock. De oudste ligt vooraan en is meteen te beantwoorden. De randen erachter laten zien dat er meer wacht. Een kaart ziet er precies zo uit als de prompt in een AI-chat nu, omdat chat en stapel dezelfde componenten gebruiken. Alles blijft in de client.

Samenvatting

Een prompt staat nu in de node die hem stelt. Een chat vervangt zijn composer door de prompt, en een terminal toont een strook onder de kop. Op een vol canvas mis je die snel.

Voortaan zijn prompts op een canvas op één plek te zien: een stapel kaarten boven de dock, gesorteerd op binnenkomst. De voorste kaart is altijd volledig in beeld. Er is geen lijst en geen ingeklapte pil. De prompt in de node wordt verborgen, maar de code blijft, zodat hij later met één schakelaar terug kan.

Voor dat uiterlijk wordt PendingDock opgeknipt in gedeelde componenten: een kaart, de inhoud van een toestemming, de inhoud van een vraag en de knoppen. De chat en de stapel bouwen er allebei mee. Een terminaltoestemming krijgt via een kleine adapter dezelfde kaart. De chat zelf verandert niet zichtbaar.

Een canvas dat niet in de splitsing staat, is niet gemount. Zijn prompts zie je pas als je ernaartoe gaat. De teller in de dock wijst daar nu al de weg, maar mist chats op zo'n canvas. Dat gat bestond al en valt buiten dit voorstel.

Schets van PromptSubject 
// What a prompt card draws, whatever asked it. The chat's items pass through unchanged.
export type PromptSubject =
    | { kind: 'chat'; chatId: string; item: ChatApprovalItem | ChatQuestionItem }
    // A terminal approval drawn as a chat approval: summary as the command, its choices as the buttons.
    | { kind: 'terminal-approval'; sessionId: string; request: ApprovalRequest }
    // Only its TUI can answer; the card offers the way there.
    | { kind: 'terminal-waiting'; sessionId: string; since: number };

// How a card's action reaches the machine: chat.approve / chat.answer / chat.dismiss or agent.answerApproval.
export function answerPrompt(subject: PromptSubject, action: PromptAction): Promise<void>;

Een terminaltoestemming in de chatkaart

Een ApprovalRequest heeft minder dan een chat-item: een toolName, een regel summary en een lijst choices met labels. De adapter doet het volgende:

  • De kop volgt de chat: "Run command" voor Bash, anders de toolnaam.
  • summary komt in hetzelfde verzonken vlak als een commando in de chat. Een diff of map is er niet, want die stuurt de daemon voor terminals niet mee.
  • De knoppen komen uit choices, in de volgorde en stijl van de chat: de remember-keuze als "Always allow", dan Deny, dan Allow als primaire knop. De labels komen van de daemon.
  • "Add a reason" bij Deny valt weg, omdat agent.answerApproval geen reden meeneemt.

ApprovalStrip blijft zoals hij is. Hij is op het canvas verborgen, en in een terminal als eigen view blijft de strook staan.

Architectuur

Aanname

aanname AgentInfo.updatedAt verandert op het moment dat de status needs-you wordt. Werkt de CLI daarna nog iets anders bij, bijvoorbeeld de titel, dan schuift de terminalkaart naar achteren. Dat controleer ik in stap 3; klopt het niet, dan onthoudt de client zelf wanneer hij de status voor het eerst zag.

Plan

  1. Gedeelde promptcomponenten

    Knip PendingDock op in PromptCard, ApprovalBody, QuestionBody, PromptActions en PromptView. Verplaats de toestand uit PromptComposer naar usePromptSession. De chat gebruikt de nieuwe onderdelen. Dit is een aparte refactor:-commit.

    Klaar als de chat er pixel voor pixel hetzelfde uitziet (screenshots van toestemming met diff, commando, vraag met meerdere vragen en een fout, voor en na) en de bestaande tests slagen.

  2. Onderwerpen en antwoorden

    PromptSubject, de adapter voor ApprovalRequest en answerPrompt in prompts/logic/subjects.ts, met tests.

    Klaar als tests laten zien dat een terminaltoestemming de knoppen in chatvolgorde krijgt en elk onderwerp het juiste request stuurt.

  3. Het promptmodel per canvas

    canvasPrompts in apps/client/src/canvas/prompts.ts, met tests.

    Klaar als tests laten zien dat prompts van vier soorten op tijdstip staan, dat nodes van een ander canvas wegvallen en dat een beantwoorde prompt verdwijnt.

  4. PromptStack

    canvas/PromptStack.tsx, getekend per canvascel boven de plek van de dock. PromptView vooraan met de bronregel, hooguit twee randen, "1 of N" met pijltjes, Mod+Shift+P. Met een ErrorBoundary.

    Klaar als vier prompts op één canvas op volgorde te beantwoorden zijn zonder te navigeren, ook met de dock verborgen.

  5. De prompt in de node verbergen

    Achter PROMPTS_IN_NODES tekent een chatnode op het canvas de regel "Waiting for your answer below" in plaats van de prompt, en tekent een terminalnode geen ApprovalStrip. Views zonder canvas blijven zoals ze zijn.

    Klaar als de oude weergave terugkomt door de constante op true te zetten.

  6. Nalopen in de Electron-app

    Splitsing met twee canvassen, verborgen dock, antwoorden in de TUI en in een tweede venster, een verlopen terminaltoestemming, een vraag met meerdere vragen en een concept dat blijft staan na doorbladeren.

    Klaar als bun run format en bun run check slagen en jij het getest hebt.

Open punten

  1. Een chat of terminal als eigen view houdt zijn prompt in de view, want daar is geen stapel. Is dat goed?
  2. De chat zet nu toestemmingen en blokkerende vragen vóór een async vraag (nextPrompt). De stapel volgt strikt de binnenkomst, dus een async vraag kan een toestemming erachter tijdelijk afdekken. Mag dat, of volgt de stapel de regel van de chat?
