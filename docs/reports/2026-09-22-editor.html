Bestanden bewerken in drie fases

Ruimte laat een bestand zien op drie plekken en kan het nergens wijzigen. Dit rapport zet uit wat er ligt, wat een editor moet kunnen, hoe de file preview eerst een view wordt zodat de editor daarna op één plek gebouwd wordt, en waarom de editor Monaco wordt met de kleuren van Shiki, achter een interface van onszelf.

De kern

Drie beslissingen, één per fase.

  • Fase 0. De editor is monaco-editor met @shikijs/monaco voor de kleuren, zodat de viewer en de editor dezelfde tokens onder hetzelfde thema tekenen. Beide zitten in een package van onszelf, packages/editor, achter een interface van een handvol methodes. De client kent Monaco niet, dus een andere engine is later een tweede adapter en geen verbouwing. Wat bewerkt mag worden is elk bestand dat fs.read als tekst teruggeeft en dat onder de leesgrens blijft. Opslaan is een nieuw request, fs.write, dat de mtime meestuurt die de client las en weigert als het bestand intussen veranderd is.
  • Fase 1. De preview stopt als kolom naast de canvas en wordt een view die niet in de sidebar staat. De tabs verhuizen naar de toolbar, via het slot dat een file view daar al heeft. Daarmee kan de preview in een split cel en verdwijnt een derde kolom uit de shell. Een bestand slepen naar de sidebar of naar een split blijft één file view opleveren.
  • Fase 2. De editor komt in CodeFile, en daarmee op elke plek die FileBody tekent: een preview tab, een file view en een file node op de canvas. Markdown en HTML krijgen een bronmodus naast hun weergave. Niets wordt gebouwd voordat fase 0 fs.write, het conflictgedrag en de interface van de package heeft vastgelegd.

Fase 1 gaat vóór fase 2, ook al is de editor het doel. Een editor in een kolom die niet in een split past, staat in de weg zodra iemand naast een chat wil typen. En de toolbar-verhuizing raakt dezelfde bestanden die de editor straks aanpast, dus twee keer door FileTabs en FileToolbar gaan is duurder dan één keer.

Hoe het nu zit

Een bestand komt op drie plekken op het scherm, en alle drie lezen via dezelfde laag. Dat is de reden dat een editor op één plek gebouwd kan worden.

Fase 0: de editor uitdenken

Drie vragen. Waarmee bewerk je, wat mag bewerkt worden, en hoe komt een wijziging op schijf.

Waarmee

De keuze is gemaakt na drie rondes. Wat de doorslag gaf is één ding: de viewer kleurt met Shiki en dat ziet er goed uit, dus de editor moet dezelfde tokens tekenen. Alles wat een tweede tokenbron introduceert valt daarmee af.

Shiki blijft de viewer

Shiki maakt statische spans en heeft geen cursor, selectie, undo of IME-invoer. Een textarea eroverheen werkt voor een snippet en gaat stuk bij wrap, bij samengestelde invoer en op een iPad. Shiki blijft waar hij is, in de viewer, de diff en de chat, en levert straks ook de tokens van de editor.

CodeMirror 6 afgewezen

Zit al in de client voor de composer en werkt met touch. Maar CodeMirror kleurt met lezer-grammatica's, een tweede tokenbron naast Shiki, met minder talen en andere grenzen. Shiki-tokens als decorations in CodeMirror leggen is te bouwen, maar dat is eigen werk met incrementeel tokenizen erbij, en daar bestaat geen onderhouden pakket voor.

Monaco + @shikijs/monaco gekozen

Monaco is de editor van VS Code en @shikijs/monaco is van het Shiki-team zelf: het vervangt Monaco's Monarch-tokenizer door Shiki, met dezelfde grammatica's en thema's die de viewer laadt. Twee onderhouders die allebei blijven. De prijs is bekend en wordt hieronder benoemd.

Ook bekeken: modern-monaco van esm.sh, dat precies deze combinatie kant-en-klaar biedt met lazy laden en een Workspace. Het is versie 0.4, ontworpen om vanaf een CDN te laden, en brengt een eigen bestandssysteem mee dat Ruimte niet wil. Het blijft een goede bron om af te kijken hoe zij de Shiki-koppeling en het lazy laden doen, maar geen dependency onder script-src 'self' in een app die offline moet werken.

Wat Monaco kost, en waar we van weten dat we het accepteren:

  • Geen touch. De station-client op een iPad kijkt alleen. Dat was al zo.
  • Layout-meting. Monaco meet zijn container zelf. Met automaticLayout gebruikt hij een ResizeObserver, wat in een split cel moet volstaan. De spike hieronder controleert dat.
  • Gewicht. De kern van Monaco is enkele megabytes en laadt daarom pas bij het eerste bewerken, zoals Shiki pas bij het eerste codebestand laadt. Geen TypeScript-, JSON- of CSS-taalservice: die brengen Monarch en eigen workers mee, en de kleuren komen toch van Shiki. Alleen de basisworker van de editor, via worker-src 'self' blob: dat de CSP al toestaat.
  • Eigen thema. Monaco heeft een thema-object en geen CSS-variabelen. @shikijs/monaco zet een Shiki-thema om naar dat object, dus de tokenkleuren komen mee. Wat overblijft (achtergrond, gutter, selectie, cursor) zet de adapter uit de tokens van styles.css.

De grens: een package van onszelf

De editor komt in packages/editor, de eerste package met DOM erin. De reden is niet hergebruik maar de grens. De client importeert de interface en een fabriek, nooit Monaco. Een andere engine later is een tweede bestand naast monaco.ts en verder niets.

export interface EditorOptions {
    text: string;
    /* Het Shiki-id dat fs.read meegeeft; zonder id is het platte tekst. */
    language?: string;
    theme: 'light' | 'dark';
    readOnly?: boolean;
    wrap?: boolean;
    /* Eén-gebaseerd, de regel waar de cursor opent. */
    line?: number;
}

export interface Editor {
    getText(): string;
    /* Een wijziging van buiten (herladen na fs.changed); wordt niet als change gemeld. */
    setText(text: string): void;
    onChange(listener: () => void): () => void;
    /* Cmd+S van binnen de editor; wat er dan gebeurt is aan de client. */
    onSave(listener: () => void): () => void;
    revealLine(line: number): void;
    setTheme(theme: 'light' | 'dark'): void;
    setReadOnly(readOnly: boolean): void;
    focus(): void;
    dispose(): void;
}

export interface EditorEngine {
    mount(element: HTMLElement, options: EditorOptions): Editor;
}

/* De enige plek die Monaco kent. De highlighter is die van de viewer, zodat een grammatica één keer laadt. */
export const monacoEngine = (highlighter: () => Promise<Highlighter>): EditorEngine => ...

Wat er bewust niet in zit: een bestandssysteem, tabs, opslaan, conflicten. Dat is allemaal van de client, die het al heeft of in fase 2 bouwt. De interface kent tekst, taal, thema, een cursor en wijzigingen, en meer niet. Een adapter die meer nodig heeft, vraagt om een interface-uitbreiding en niet om een import in de client.

De spike, één dag

Vier dingen die de documentatie niet beantwoordt en die de keuze definitief maken of terugdraaien:

  1. De bundel met alleen editor.api en de basisworker, gemeten na een Vite-build, en of hij pas laadt bij het eerste bewerken.
  2. Of Monaco draait onder de CSP van de client zoals die is, zonder een directive te verruimen.
  3. Een editor in een split cel die van maat verandert, en in een file node die op de canvas gezoomd wordt.
  4. Of de highlighter van de viewer één keer laadt en zowel CodeFile als @shikijs/monaco bedient.

Hoe het op schijf komt

Een nieuw request op de wire, dus geen PROTOCOL_VERSION-bump.

fs.write
  payload: { path, text, expectedMtime }
  result:  { mtime, size }
  error:   'stale'  (het bestand op schijf heeft een andere mtime dan expectedMtime)
           'too-large', 'not-text', 'outside-project'

De expectedMtime is de mtime die fs.read teruggaf. Schrijft een agent het bestand intussen (en dat gebeurt voortdurend), dan komt stale terug en beslist de persoon: opnieuw laden en de eigen wijziging kwijt, of overschrijven. Geen driewegmerge in de eerste versie. Die is later te bouwen op dezelfde fout.

Aanroepen mag elke client die fs.read mag doen, dus een gekoppelde sleutel of het lokale geheim. Een agent komt hier nooit langs. Die schrijft met zijn eigen CLI en dat verandert niet. Er komt geen ruimte-context-werkwoord voor.

Opslaan is expliciet, Cmd+S, met de dirty-stip in de tab die daar al voor gereserveerd is. Autosave zoals JetBrains het doet zou ik pas na een paar weken gebruik beslissen: in een canvas waar een agent tegelijk aan hetzelfde bestand werkt, is een halve regel die automatisch weggeschreven wordt eerder een bron van conflicten dan gemak. Dit is een van de open vragen hieronder.

Wat er nog bijkomt op de daemon: fs.changed noemt nu alleen mappen. Een editor met een open bestand wil weten of dát bestand veranderde. De simpelste weg is dat de client bij een fs.changed voor de map van het bestand een nieuwe fs.read doet en de mtime vergelijkt. Geen nieuw event nodig.

Wat fase 0 oplevert

  • De package packages/editor met de interface, de Monaco-adapter en de uitkomst van de spike.
  • Het schema van fs.write in packages/contracts, met tests, en de daemon-kant met de projectmapgrens en de stale-controle.
  • Een antwoord op de open vragen aan het eind, minstens die over autosave en buiten de projectmap. De enginevraag is beantwoord.

Fase 1: de preview als view, de tabs in de toolbar

Vandaag is de preview een derde kolom: sidebar, canvas, preview, panel. Hij heeft een eigen breedte, een eigen open-toestand en een eigen tabstrook. Het voorstel maakt er een view van die in een cel van de split grid staat, met de tabs in de toolbar van het venster.

Nu

  • De preview schuift open naast de canvas en neemt breedte van hem af.
  • Niet te combineren met een split: hij staat er altijd naast, nooit erin.
  • Eigen tabstrook, eigen breedte, eigen sneltoetsen in PreviewPanel.
  • Een file view en de preview tekenen hetzelfde bestand op twee manieren: de een met de toolbar van het venster, de ander met een eigen balk.

Voorstel

  • Een view van een eigen soort, files, die niet in de sidebar staat en niet in project.json. Zijn toestand (tabs, actieve tab) is al lokaal in state/files.ts en blijft dat.
  • Hij staat in een cel zoals elke view, dus naast een chat, onder een terminal, of alleen.
  • De tabs tekenen in de toolbar via de leads die ViewToolbar al voor een file view heeft. In een split krijgt de cel ze in zijn CellToolbar, zoals een browser daar zijn adresbalk krijgt.
  • De knoppen van een bestand gaan door het bestaande slot, de eigen balk in de preview vervalt.

Wat er precies verandert

  1. Een view die het document niet kent

    De layout is lokaal (exportLocal in state/document.ts), dus een cel kan een id dragen dat niet in views voorkomt. Eén vaste id, bijvoorbeeld files, die ViewSurface, CellToolbar, locateView en ViewMenu herkennen. Dat is de eigenlijke omvang van de fase, elke plek die aanneemt dat een cel een view uit het document is.

    Acceptatie: een project dat de preview in een cel had, opent na een herstart met die cel op dezelfde plek, en het shared bestand in git is niet veranderd.

  2. Een bestand openen

    Openen uit het files panel, het git panel of het palet doet nu useFiles.open en zet de preview open. Straks werkt het zo. Staat de files-view in een cel, dan wordt de tab daar actief. Staat hij nergens, dan neemt hij de gefocuste cel over als die geen canvas is, en anders splitst hij naast de canvas. Dat laatste is een keuze. Het alternatief is altijd vervangen, en dat verliest een chat die iemand open had.

    Acceptatie: Cmd+P op een bestand vanuit een chat-cel toont het bestand zonder dat de chat verdwijnt.

  3. Tabs in de toolbar

    FileTabs verhuist van de header van het panel naar een lead in ViewToolbar. De strook scrollt al horizontaal en heeft zijn contextmenu. Wat verandert is de hoogte (de toolbar is 48px) en de plek van de sluitknop. Bij één cel staan ze in de toolbar van het venster, bij meer cellen in de balk van de cel.

    Acceptatie: pinnen, sluiten, Ctrl+Tab en het contextmenu werken op beide plekken, en de tabs blijven leesbaar naast de breadcrumb.

  4. Slepen naar een split

    SplitGrid.zoneFor neemt alleen een view-drag. Een drag met PATHS_DRAG_TYPE uit het files panel moet er ook een zone krijgen, en op de drop newFileView aanroepen, zoals de sidebar dat al doet. Meerdere paden geven meerdere views, waarvan de eerste in de cel landt en de rest in de sidebar.

    Acceptatie: een bestand uit het files panel op de rechterrand van een cel laten vallen geeft een file view in een nieuwe kolom, en de sidebar toont hem.

  5. Opruimen

    PreviewPanel.tsx, preview en previewWidth in useUi, de legacy-sleutels ruimte.preview en ruimte.preview.width, en de eigen balk in de renderers. De toolbar hoeft previewOpen niet meer te kennen.

    Acceptatie: bun run check en de tests slagen, en het woord preview komt in state/ui.ts niet meer voor.

Wat dit aan bestaand gedrag raakt

  • De preview kon open zijn terwijl de canvas de hele breedte hield, omdat hij ernaast schoof. Straks neemt hij een cel. Bij één cel betekent openen van een bestand dus een split of een vervanging. Dat is de grootste gedragsverandering en de reden voor de keuze in stap 2.
  • De sneltoetsen in PreviewPanel.onKeyDown (Cmd+W sluit een tab, Ctrl+Tab wisselt) worden sneltoetsen van de cel. Cmd+W is nu ook closeCell; in een files-cel sluit hij de tab, en de cel pas als er geen tab meer is.
  • De lege preview (recente bestanden, zoeken, openen) blijft: dat is wat de view toont zonder tab.
  • Op iOS verandert niets. De iPhone-app kent geen split grid en geen preview-kolom.

Fase 2: de editor

Na fase 1 is er één plek waar een bestand getekend wordt en één toolbar-slot waar zijn knoppen terechtkomen. De editor komt in CodeFile en gaat daarmee vanzelf mee naar een tab, een view en een node.

Bouw

  • Lezen blijft de standaard. Een bestand opent zoals nu, gehighlight door Shiki in blokken. Een klik in de tekst, of een knop in de toolbar, zet de editor aan. Twee redenen: een viewer van 400 regels per blok is goedkoper dan tien Monaco-instanties op een canvas met tien file nodes, en een klik die per ongeluk een bestand van een agent aanpast is erger dan een klik extra.
  • De editor vervangt de viewer in dezelfde ruimte. Zelfde scroller, zelfde regelnummers, zelfde regelhoogte van 20px, zodat de overgang niets verplaatst. De inhoud komt uit de FsReadText die de viewer al had.
  • Talen. De language die de daemon meegeeft is een Shiki-id en gaat ongewijzigd door naar de adapter. Elke taal die de viewer kleurt, kleurt de editor, een onbekend id is platte tekst.
  • Kleuren. Dezelfde Shiki-highlighter en hetzelfde thema als de viewer, dus per constructie dezelfde tokens. Wat de adapter zelf zet (achtergrond, gutter, selectie) komt uit styles.css.
  • Markdown en HTML. De schakel weergave/bron in de toolbar. Een bestand met een dirty editor blijft in de bronmodus tot het opgeslagen is. De weergave toont wat op schijf staat.
  • Opslaan. Cmd+S roept fs.write aan met de mtime van de laatste read. Bij stale een balk boven de editor: "Het bestand is op schijf veranderd", met opnieuw laden of overschrijven. Sluiten van een dirty tab, view of node vraagt eerst.
  • Dirty-markering. De stip in de tab (het veld is er), een stip in de sidebar-rij van een file view en op de plaat van een file node. De laatste twee zijn nieuw.
  • Veranderingen van buiten. Een fs.changed voor de map van een open bestand leidt tot een nieuwe read. Niet dirty: stil herladen, zoals de viewer nu al zou moeten doen. Wel dirty: dezelfde balk als bij stale, maar dan vóór het opslaan.

Acceptatie

  • Een TypeScript-bestand openen, een regel wijzigen, Cmd+S: het git panel toont het bestand als gewijzigd binnen een seconde, zonder herladen.
  • Een agent schrijft hetzelfde bestand terwijl het dirty is: de balk verschijnt en opslaan overschrijft niets zonder een klik.
  • Een file node op de canvas met de editor aan: de sneltoetsen van de canvas blijven uit zolang de editor de focus heeft, en Escape geeft de focus terug.
  • Een markdown-bestand: weergave, bron, wijzigen, opslaan, weergave toont de wijziging.
  • bun run test zonder wandkloktiming: het conflictgedrag is een test op een FakeTransport die stale teruggeeft, en de tab- en dirty-logica draait tegen een fake EditorEngine zonder DOM.

Open vragen voor Bas

  1. Autosave of Cmd+S? Mijn voorstel is expliciet opslaan en autosave als latere instelling. Een JetBrains-gebruiker mist autosave vanaf dag één, dus dit is een echte keuze.
  2. Bewerken buiten de projectmap? Een file view mag erbuiten wijzen. Voorstel: eerst niet, dezelfde grens als --cwd.
  3. Eén files-view per venster, of meer? Eén is simpel en dekt "de preview in een split". Twee zou twee tabstroken betekenen die elk hun eigen tabs hebben, wat state/files.ts nu niet kan. Voorstel: één.
  4. Wat doet openen bij één cel? Splitsen naast de canvas, of de cel vervangen? Voorstel: splitsen als de cel een canvas is, vervangen als het al een files-view is, en anders splitsen. Vervangen van een chat verliest te veel.
  5. Klik-om-te-bewerken op een file node, of ook in een view en tab? Voorstel: overal dezelfde drempel, zodat een bestand op drie plekken hetzelfde doet. Een klik in de tekst zet de cursor en de editor aan. Een selectie slepen in de viewer selecteert alleen.
  6. De preview-kolom helemaal weg, of als optie behouden? Voorstel: weg. Twee manieren om hetzelfde bestand te tonen is precies wat deze fase oplost.

De bundelgrootte van Monaco, het touch-gedrag en de werking onder de CSP komen uit documentatie en niet uit een meting in dit project. De spike in fase 0 meet ze. Het rapport is gecontroleerd op ankers, licht en donker en op een smal venster in de bron. Het is niet in een browser gerenderd.
