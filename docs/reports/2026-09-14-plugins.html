Plugins in Ruimte

Een plugin kan veel in Ruimte, maar de vraag die alles bepaalt is waar zijn code vandaan komt. Begin met plugins die alleen data zijn: een manifest met verbs, commando's, web-panels en -nodes, thema's en link providers. Code die in de client zelf draait, kan elke gepairde machine bedienen, dus die komt pas later, geïsoleerd, of alleen van Ruimte zelf.

Advies

Bouw plugins in drie lagen en begin onderaan.

  1. Interne registries. Maak van de gesloten lijsten in de code tabellen waar je iets aan kunt toevoegen: panels, node- en view-kinds, verbs, bestandsrenderers, palette-commando's, instellingen. Dat is een refactor zonder zichtbaar gedrag, en de ingebouwde features worden er de eerste gebruikers van.
  2. Declaratieve plugins. Een map $RUIMTE_HOME/plugins/<id>/ met een ruimte-plugin.json, geïnstalleerd per machine. Het manifest voegt verbs toe die een commando uitvoeren, palette-commando's, een panel of node die een web-pagina van de plugin is, instellingen, thema's, Shiki-grammatica's en link providers voor terminals. Er draait geen plugin-JavaScript in de client.
  3. Geïsoleerde code. Pas als laag 2 laat zien dat er vraag is naar echte UI en logica: plugin-UI in een iframe of webview achter een broker met een geversioneerde API, en een daemon-helft als apart proces dat JSON over stdio spreekt.

Plugins die in de client zelf draaien, met echte React-nodes op het canvas, zijn het krachtigst en het gevaarlijkst. Houd dat model voor features van Ruimte zelf.

Alternatief Een smaller model staat onder Alternatief: plugins die alleen voeden. Daar leest een plugin alleen iets in, zoals een lijst Jira-issues, en geeft die als context aan een agent. Een plugin bestuurt niets en draait geen code op de daemon.

Vertrouwen bepaalt de architectuur

Code in de origin van de client heeft dezelfde macht als de client. Zo'n plugin kan op de lokale daemon zonder token shells starten, want loopback vraagt geen credential (apps/server/src/auth/access.ts:73). Hij kan de niet-extraheerbare ed25519-sleutel in IndexedDB gebruiken en via transportFor(id) elke gepairde machine bedienen. Ook window.ruimteDesktop uit de preload is voor hem bereikbaar. Geverifieerd

Pairen geeft de client macht over een machine, en niet andersom. Laat een client JavaScript draaien die van machine A kwam, dan draai je die richting om. Een gecompromitteerde A neemt de client over, en via de client ook B en C.

Een plugin-verb doet een agent code starten die niet van Ruimte is. Het sessietoken heeft geen scopes, dus elke agent op de machine kan elk plugin-verb aanroepen. Een schakelaar per machine, zoals agentsDeleteAnyView, is daarom het minimum.

Een manifest met permissies (canvas.write, context.read, net:<host>, shell) maakt die keuze leesbaar. De client of machine pint de hash bij het goedkeuren, trust on first use zoals bij pairen, en vraagt opnieuw als een update meer permissies wil. Een handtekening bewijst waar een update vandaan komt, niet dat die deugt. Hij vult de goedkeuring aan en vervangt haar niet.

Code laden

Wat de app nu toestaat

  • De CSP (apps/client/index.html:11, apps/server/src/daemon.ts:74) staat script-src 'self' 'wasm-unsafe-eval', frame-src 'none' en worker-src 'self' blob: toe. Een import() kan dus alleen van de eigen origin laden, iframes zijn dicht, en workers en WASM mogen. Geverifieerd
  • Electron laadt de client van de lokale daemon (apps/desktop/src/main.ts:811) en registreert geen eigen protocol. Er zijn twee partities: persist:ruimte voor browsers met een preload, en de verzegelde preview zonder permissies (main.ts:190). Die laatste is het model voor een plugin-partitie.
  • De Vite-build heeft geen externals. React en zustand zitten gehasht in de chunks, er is geen import map en geen host-object.

Daemon-code

Een daemon-plugin in hetzelfde proces draait met de volle rechten van de gebruiker. Hij kan de daemon laten crashen of blokkeren, en dat is het proces dat terminals en chats vasthoudt. Een apart proces per plugin, met JSON over stdio, houdt een crash buiten de daemon en maakt de API een protocol in plaats van interne objecten.

Geverifieerd Onder bun 1.4.0 laadt await import(pad) tijdens runtime zowel een .js- als een .ts-bestand buiten het project.

Niet vastgesteld: of een binary van bun build --compile, zoals de verpakte app die meeneemt, hetzelfde kan, en wat er met de node_modules van een plugin gebeurt. Op deze Mac werd elke ad-hoc gesigneerde gecompileerde binary vanuit de shell direct met SIGKILL gestopt, ook één die alleen "hello" print. De test zei dus niets over import(). Tot dat vaststaat is de veilige vorm: een plugin levert één gebundeld JS-bestand zonder node_modules. Dit is ook de eerste taak van de spike.

Panels toevoegen

shell/panels.ts:6 heeft al een halve registry (kind, label, icoon, minimale breedte), en de toggles worden daaruit getekend. De inhoud kiest Panel.tsx:25 nog met een switch. Het kind is een gesloten enum, z.enum(['files','git','processes']) (packages/contracts/src/project.ts:487). Wat een panel zelf moet onthouden, staat als vaste velden in het lokale schema (git, expandedDirs).

De val: project/client-local.ts:35 gooit met safeParse de hele rij in localStorage weg als één veld niet klopt. Een onbekend panel-id kost dan de camera, het raster en de panels van dat project, niet alleen het panel. Een oudere client heeft die enum al, dus een plugin-panel mag pas in de lokale staat komen als de versoepeling een release oud is.

Kleinste stap

  • render in PANELS in plaats van de switch, en de palette-regels uit commands.ts:268 genereren.
  • panel.kind wordt een string. Een client die het id niet kent valt terug op files.
  • Eigen staat per plugin in panels.plugins: record<string, unknown>, in plaats van nieuwe vaste velden.
  • Declaratief: een panel is een web-pagina van de plugin in een webview met partitie plugin:<id>, met de PanelHeaderSlot voor knoppen.

ruimte-context uitbreiden

Dit is de seam die het meest klaar is. VERBS (apps/server/src/canvas/verbs.ts:193) is een array van objecten met synopsis, zod-schema's en run, en help wordt uit dezelfde spec gerenderd. De CLI stuurt alles behalve list en read ongelezen als argv naar POST /canvas/<verb> (cli/context.ts:86), dus een nieuw verb vraagt niets van de CLI. Geverifieerd

Een plugin-verb

  • ruimte-context <plugin> <verb> past op defineVerbGroup, dat subcommando's en help al uit één tabel haalt. Een plugin-id die botst met een ingebouwd verb wordt geweigerd.
  • VERBS wordt een VerbRegistry met register(). dryRunVerbs is nu module-globaal en moet per registry. SCOPE_LINE somt de verbs met de hand op en moet gegenereerd worden.
  • Declaratief: het manifest noemt een argv-array (geen shell-string) met getypeerde parameters. De daemon valideert, voert uit en geeft de uitvoer door. Exit 3 blijft een weigering.
  • Met code: de plugin krijgt niet heel CanvasHost (dat kan sessies beëindigen en diagrammen schrijven), maar locate, read en een mutate die alleen nodes van zijn eigen kind raakt.

Een contextbron

ContextSourceSchema.kind is een gesloten enum (contracts/src/context.ts:6), deriveContextSources een if-keten, en ContextStore.read een exhaustieve switch. Voeg één bronkind plugin toe met pluginId, en in de daemon een Map<pluginId, reader> naast de switch. Declaratief kan een reader een commando zijn dat tekst print, of een bestand van de plugin.

Een contextbron moet op de daemon bestaan. De daemon leidt de bronnen af uit ProjectIndex, ook als er geen client openstaat. Een plugin die alleen in de client draait, kan een agent dus nooit iets laten lezen.

Een reader zit in het pad van de prompt-hook (changeSince). Hij heeft een timeout en een regellimiet nodig, zoals MAX_SCREEN_LINES die al heeft.

Eigen views en nodes

Het mechanisme ligt er al. readEntry (project.ts:52) leest elk onbekend kind als { kind: 'unknown', raw }, storedContentOf schrijft het ongewijzigd terug, en de opruiming van wezen telt het als levend. Een plugin-kind overleeft vandaag al een Ruimte die het niet kent, als een plaat die niet opent. Geverifieerd

Wat ontbreekt is tekenen en wijzigen:

  • Nodes lopen via ketens van node.kind === ... in NodeFrame.tsx:324 en via Record<NodeKind, …>-tabellen. Voorbeelden zijn NODE_SIZE, DEFAULT_TITLES, ICONS, ROW_ICON en ADD_NODE_SHORTCUTS.

Intern: een kind-registry

Een NodeKindDef met body, plaat, icoon, standaardmaat, titel, menu-items en readableOnly, naar het model van tldraw's ShapeUtil. De ingebouwde kinds verhuizen erheen. Culling (canvas/culling.ts) is al onafhankelijk van het kind. De ErrorBoundary rond de body vangt een plugin-kind vanzelf, met het plugin-id erbij in het label.

Op disk: één kind plugin

Een node of view { kind: 'plugin', plugin: '<id>', type: '<kind>', data }. Een client zonder de plugin tekent een plaat met de naam van de plugin. Plugin-data staat altijd in data en nooit als veld op een bekend kind, want zod verwijdert onbekende velden bij de eerste save. Grote data krijgt een eigen bestand onder .ruimte/plugins/<id>/.

Declaratief is de eerste plugin-node een web-pagina van de plugin, dus een browser-node in een eigen partitie. Die krijgt dezelfde z-order-beperking als elke webview (#13). Nodes die echt op het canvas thuishoren (native tekenen, zoomen, culling) vragen de broker of in-process code.

Nog open in dezelfde refactor: de drop-regels in canvas/drop.ts maken altijd een file-node, en er is geen hook op MIME-type of extensie. "Open een .excalidraw als node van plugin X" heeft die hook nodig.

Apart houden

  • Agent-providers. AgentKindSchema is gesloten (contracts/src/agent.ts:6). Hooks, usage, limieten en logo zijn per kind hard gecodeerd. Hoge waarde (een extra CLI-agent), maar diep.
  • Markdown en rehype in chats. Die draaien per blok bij elke delta. Een trage plugin maakt het streamen traag.
  • Vormen en tinten in drawings en diagrammen. Die zitten in het bestandsformaat en in de determinisme van layoutOf.
  • De guest-preload van browsers. Die draait in elke pagina van persist:ruimte. Daar hoort geen plugin-code.

Een observer die zich als nep-client abonneert, telt mee als iemand die approvals wil (sessions/manager.ts:187). Hij houdt dan elke PermissionRequest vast. De bus moet los staan van attach. onProcessChange en onPlaces hebben één slot en zijn al bezet door daemon.ts.

Wire, opslag en versies

  • Requests. REQUEST_SCHEMAS en EVENT_SCHEMAS zijn as const-tabellen. Voeg één plugin.request toe met { pluginId, type, payload: unknown } en één plugin.event. Die worden in twee stappen gevalideerd: eerst de envelop in contracts, dan de payload met het schema van de plugin. Contracts groeit zo niet per plugin.
  • HTTP. De routes zijn een if-keten van prefixes (daemon.ts:351). Eén prefix /plugins/<id>/ serveert de statische bestanden van een web-panel en de routes van een plugin. Elke route declareert zelf of hij client-auth (decideAccess) of een agent-bearer wil.
  • Eigen bestanden. DrawingStore en DiagramStore zijn twee kopieën van hetzelfde patroon: één regel per element, een rev, een watcher. Een generieke ViewFileStore<T> onder .ruimte/plugins/<id>/<viewId>.json geeft een plugin datzelfde, en ruimt de twee kopieën meteen op.
  • Versies. packages/contracts is intern en verandert vrij, dus het is geen plugin-API. Maak een apart @ruimte/plugin-api met het manifest-schema, het broker-protocol en een apiVersion. EndpointInfoSchema krijgt een optioneel plugins: [{ id, version, apiVersion }], zodat een client ziet wat een machine draait.

Drie architecturen

A. Declaratief

Dagen. Een manifest per machine: verbs als argv, palette-commando's, web-panels en -nodes in partitie plugin:<id>, instellingen als schema, thema's, grammatica's, link providers en een contextbron die een commando of bestand is.

Voor: past op wat er ligt (de verbs-registry, de verzegelde preview-partitie, het unknown-kind), en is veilig bij installatie op een machine op afstand. Tegen: geen native canvas-integratie, de webview-z-order (#13), en in de Server Edition een iframe.

B. Geïsoleerde code

Weken. Bovenop A: plugin-UI in een iframe of webview, met een postMessage-broker die een geversioneerde API aanbiedt (canvas.addNode, context.read, notify, thema-tokens), beperkt tot de eigen machine. De daemon-helft draait als apart proces met plugin.request en plugin.event.

Voor: code van machine A kan veilig draaien, permissies zijn af te dwingen, en een hostwijziging raakt alleen het protocol. Tegen: een broker-API om te onderhouden, geheugen per webview, en UI die minder als Ruimte voelt.

C. In-process, alleen vertrouwd

Een ESM-bundel via import(), met React en de stores gedeeld via een host-object, en echte nodes op het canvas zonder z-order-probleem. Een plugin krijgt dan alleen een PluginContext (endpointId, zijn eigen request, viewId of nodeId, data en updateData, opslag onder ${endpointId}:${projectId}:${pluginId}), nooit de module-singletons. Wie transport of projectClient importeert, praat met de actieve machine in plaats van die van zijn workspace (state/keys.ts:5).

Hij kan alles wat de client kan, dus alleen voor wat de persoon zelf in deze client installeerde, achter een waarschuwing. Het is vooral nuttig als interne vorm: de kind-registry uit laag 1 is precies dit, zonder het laden van buitenaf.

Alternatief: plugins die alleen voeden

Toegevoegd 14 september, nog niet uitgewerkt

Een plugin haalt iets op en toont het, en geeft die inhoud als context aan een agent. Hij heeft geen verbs, raakt het canvas niet en start geen sessies. Het voorbeeld: een panel met Jira-issues, waarna je tegen een agent zegt dat hij een issue daaruit moet inlezen.

Hiermee vallen laag 2 en 3 samen tot één smal model. Er is geen plugin-code op de daemon, dus het compile-importprobleem verdwijnt. Er zijn geen plugin-verbs die agents kunnen aanroepen. Je installeert niets per machine op afstand.

Context moet op de daemon staan

Een agent leest via ruimte-context, en de daemon beantwoordt dat ook als er geen client openstaat. Een plugin in de client stuurt zijn inhoud daarom naar de daemon, bijvoorbeeld met context.publish(nodeId, items). De daemon bewaart die snapshot en serveert hem als contextbron van kind plugin, met het tijdstip erbij zodat de agent ziet hoe oud hij is.

Snapshot

De plugin publiceert de lijst plus de details van elk issue. Dit werkt zonder open client en is prima voor tientallen issues. Het nadeel is dat de inhoud veroudert zodra niemand de plugin open heeft.

Op aanvraag

Voor ruimte-context read <node> ABC-123 vraagt de daemon een verbonden client met die plugin om het issue op te halen. Het resultaat is altijd vers, maar het faalt zonder client, en dan moet de agent dat duidelijk te horen krijgen.

Voorstel: een snapshot als basis, met ophalen op aanvraag als aanvulling.

"Niks besturen" vraagt isolatie

Plugin-code in de client zelf kan bij transport en dus bij elke gepairde machine (zie Vertrouwen). De grens houdt alleen stand als de plugin in een sandboxed iframe of worker draait, achter een broker met een handvol functies:

  • zijn eigen UI tekenen;
  • instellingen en een geheim, zoals het Jira-token, lezen;
  • fetch naar de hosts uit zijn manifest;
  • context publiceren.

Die kleine API is het voordeel: er is weinig te onderhouden en weinig dat breekt.

Een edge vraagt een node

Een panel staat niet op het canvas, dus je kunt er geen lijn van trekken. Het panel toont de lijst, en je sleept een issue of de hele lijst op het canvas. Daar wordt het een plugin-node met een snapshot, en die verbind je met een agent. Dat volgt hoe een bestand nu vanuit het files-panel op het canvas komt (canvas/drop.ts).

Ophalen en CORS

Een fetch naar de Jira-API vanaf de origin van de client (http://127.0.0.1:<port>) loopt waarschijnlijk tegen CORS aan. Afgeleid Er zijn twee doorgeefluiken:

  • De Electron-main. Die werkt niet in de Server Edition.
  • Een proxy op de daemon. Die laat alleen de hosts uit het manifest door. Hij haalt alleen op, dus hij blijft binnen "voeden".

Open vragen

  1. Snapshot, op aanvraag, of beide.
  2. Waar het token woont: per client (een tweede client moet opnieuw inloggen) of per machine (de daemon ziet het geheim).
  3. Of een plugin-node ook in project.json komt, en dus bij iedereen staat die het project opent, ook zonder de plugin.
  4. Of CORS bij Jira Cloud echt dicht is. Dat is snel te testen.

Fasen

  1. Interne registries

    Refactor zonder zichtbaar gedrag: render in PANELS, een NodeKindDef- en view-registry voor de ingebouwde kinds, VerbRegistry, TEXT_RENDERERS met matchBinary, palette-commando's en instellingen-secties uit lijsten, en een generieke toolbar-slot voor elke view en node.

    Klaar als: een nieuw ingebouwd kind op één plek wordt toegevoegd in plaats van tien, bun run check en de tests groen zijn en er niets zichtbaar veranderd is.

  2. Compatibiliteitsrelease

    Contracts verdragen wat plugins later schrijven: node- en view-kind plugin met data, panel.kind als string met terugval, panels.plugins, bronkind plugin, optioneel plugins in EndpointInfo. De lokale staat verliest bij één onbekend veld niet meer de hele rij.

    Klaar als: er een release uit is waarin een project met een plugin-node en een onbekend panel-id opent, als plaat tekent, ongewijzigd terugschrijft en camera en raster behoudt. Een test borgt dat.

  3. Spike

    Uitzoeken of een gecompileerde daemon tijdens runtime een gebundeld JS-bestand en een .ts-bestand laadt, en wat er met node_modules gebeurt. Draai dat in de gesigneerde verpakte app, want op deze Mac stopte elke ad-hoc gecompileerde binary. Meet ook een plugin-proces met JSON over stdio: opstarttijd en geheugen.

    Klaar als: vaststaat welke vorm een plugin moet hebben om in de verpakte app te laden, en of een apart proces per plugin betaalbaar is.

  4. Declaratieve plugins (A)

    Manifest en @ruimte/plugin-api. Laden uit $RUIMTE_HOME/plugins, verbs als argv met een schakelaar per machine voor agents, palette-commando's, web-panels en -nodes in partitie plugin:<id> (iframe in de Server Edition), instellingen, thema's, grammatica's, terminal-links en een contextbron als commando. Een pane Plugins per machine, met permissies die een persoon goedkeurt en een hash-pin.

    Klaar als: een voorbeeldplugin een verb, een panel, een link provider en een contextbron levert. Een agent leest de bron via een edge, een tweede client ziet de plugin op dezelfde machine, en een project uit een clone met een plugin-map voert niets uit.

  5. Geïsoleerde code (B)

    De broker met een geversioneerde capability-API, plugin.request en plugin.event, het plugin-proces op de daemon, ViewFileStore<T> en de observer-bus los van attach.

    Klaar als: een plugin-view met een eigen bestand onder .ruimte/plugins/<id>/ werkt met rev en conflictbanner, een crashend plugin-proces de daemon niet raakt, en een plugin van machine A geen request naar machine B kan sturen.

Open beslissingen

  1. Waar wonen client-only plugins? Voorstel: ook op een machine, zodat elke client die ze ziet dezelfde krijgt. Thema's en link providers zijn data. Het alternatief is per client in userData, wat bij meerdere clients per machine verwarrend wordt.
  2. Wie mag installeren? Voorstel: elke gepairde client, met bevestiging en permissies op het scherm, want die kan op de machine al een shell openen. Nooit een agent via een verb.
  3. Mogen agents plugin-verbs gebruiken? Voorstel: per plugin een schakelaar per machine, uit tot iemand hem aanzet, naast agentsDeleteAnyView.
  4. Komt laag C er ooit als laadweg? Voorstel: nee voor derden. Alleen als interne registry voor wat Ruimte zelf meelevert.
  5. Aanbevolen plugins per project. Een lijst in project.json die een banner geeft ("dit project gebruikt Jira"), of niets. Voorstel: pas na laag A.
  6. Distributie. Een map of tarball installeren, of een index zoals een Git-repo met manifesten. Voorstel: eerst lokaal en via URL, een index pas als er plugins zijn.

Risico's

  • Plugin-code in de client of in de daemon draait met de rechten van de gebruiker. Wie een plugin van machine A in de client laat draaien, geeft A de sleutels van elke gepairde machine.
  • Een verb start code die niet van Ruimte is, en een agent die onvertrouwde context leest kan het aanroepen. Het sessietoken heeft geen scopes.
  • Hete paden: Session.receive op de daemon, link providers bij elke hover en scroll, rehype bij elke delta. Een plugin daar heeft een budget nodig of blijft eruit.
  • Een versoepeling in contracts die zonder compatibiliteitsrelease uitgaat, laat een oudere Ruimte een project weigeren of de lokale staat weggooien.
  • Een webview ligt boven alles op het canvas (#13). Web-nodes van plugins erven dat.
  • Of een gecompileerde daemon plugin-code laadt, is niet vastgesteld.
  • Een API die te vroeg publiek wordt, bevriest interne keuzes. JupyterLab en Hyper braken bij elke major van de host.
