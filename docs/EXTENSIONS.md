# Extensions

What an author reads lives at https://ruimte.app/docs/extensions (`apps/site/src/app/docs/extensions`). This file keeps what only matters to working on Ruimte itself: the development extensions, the store's setup and the choices behind the API.

An extension adds panels, canvas nodes, views, sidebar cards, commands or themes to Ruimte, optionally with a process on the machine. It runs as trusted code, like a plugin in an IDE: its React sits in the client's page and its `server/` runs as the person who runs the machine. A `frame:` surface is the one place with isolation. Permissions in the manifest tell a person what it does and gate the API, but they are no sandbox.

## A package

```
manifest.json     id, name, version, api, color, permissions, themes
assets/icon.svg   its mark, always at this path
client/index.ts   runs in the client, calls define*
server/index.ts   runs on the machine, optional
locales/ assets/ views/ themes/   copied into the pack
```

The mark shows in Settings and the store: `assets/icon.svg` (up to 64 KB) is drawn as one ink on `color` (`#rrggbb`), so only its shape counts. Without an icon it gets a package, without a color a plain ground. A panel or node that names no Lucide `icon` shows the same mark.

Types come from `@ruimte/extension` on npm (`/client`, `/server`, `/ui`, `/testing`). The code comes with Ruimte, and `pack` rewrites those imports and React to what the client supplies.

## The CLI

```
bunx ruimte extension create    scaffold a project
ruimte extension dev            build on save and load it into the running Ruimte
ruimte extension test           bun test against a test host
ruimte extension pack           build a .rex
ruimte extension publish        open a pull request on the store
ruimte extension logs           what server/ wrote
```

`test` writes the preload into the project's `node_modules/.cache`, so it imports the project's own React, and runs `bun test` with it. With a `*.dom.test.tsx` file in the project it puts happy-dom's page first, and says what to add when `@happy-dom/global-registrator` is missing; it warns when the project's React has another major than `CLIENT_REACT_MAJOR` (`scaffold.ts`, held to the client's `package.json`).

`createTestHost` (`test-host.ts`, `test-client.ts`, `test-hosts.ts`) is a client with a project in memory. It decides what the client host decides from the same rules in `@ruimte/contracts/extension-client`: the permission of each call, the slot names, a lazy component, a shortcut and a path in the project. What only the machine or a person knows comes from the test's `answers`, and an unanswered call is `unavailable`, as in a test server. `render` (`test-dom.ts`) draws with the project's own React and waits over turns of the event loop, never a clock. `createTestServer` loads `server/index.ts` in the test's own process on the API and policy of the machine (below, under Failure). For each test host and test server, `test-loader.ts` bundles the entry with the project's own files, so no module state carries over, and binds `@ruimte/extension/client` or `/server` in that bundle to its own host. An extension in this repository keeps its tests in `test/`, which `bun run test` leaves out: `apps/server/src/cli/extension-test.integration.test.ts` runs those of `limits`, the products in `extensions/dev` and `poc-contract`, and the test a new project starts with.

The contract suite keeps the test hosts from drifting from the real ones. `extensions/poc/contract/contract` holds one set of scenarios for the client (every call refused without its permission, storage per scope, a slot's context and run, a note and its link, what a context read selects, a client event, a node's defaults and its migration, a read of the wrong kind, where an agent starts, the UI components, a kept answer after a reload and a reconnect, what another window wrote, a stream aborted before it began, failing halfway or stopped after a piece, a throw and an inherited name of `server/`, a key deleted with undefined or by `server/`, the canvas `createCanvas` opens, a new note's size, title and place, a group's members and frame, lines to itself and between agents, what `remove` takes, a node of another canvas, a chat in a view of its own, the kind of an extension's view, a file watch, opening the view in front, an action a person stopped and a section in a project's settings with the field a surface reads) and one for `server/` (an event behind its permission, an await as its module loads, a tool, the send limit, a refusal, a machine action's input, an emit without payload, an event it stopped following, a key it deleted, an ask of an agent and of the chats, a secret with its log line, a terminal opened with a profile and typed into, a proposed part in an installed extension, a launch source that lists and tells of a change until it is asked to stop, problems reported, replaced, cleared and refused past their limit, a project's files read, listed and followed, a launch and a project heard in the shape an extension gets, and a machine source that lists its places and describes a start until a person stops it, a notification channel that and a reference and a slash command of `server/` with the text each puts in a prompt). The machine's world links the probe as `extension dev` does when a scenario's manifest uses a proposed part, its terminals are sessions on fake PTYs, and its project files are in memory behind the port the machine reads through (`project-files.test.ts` holds the real port on a fake watch). The client host's world answers through JSON and the reply schemas, as a machine does, and the machine's world reads each event through its schema. Each runs against the test hosts in `extensions/poc/contract/test`, against `clientApiFor` on a `FakeMachine` in `apps/client/src/extensions/host/contract.dom.test.tsx`, and against `ExtensionHost` with a real process in `apps/server/src/extensions/contract.integration.test.ts`. A call the permission table gains needs a row in its scenario, or the suite fails, and every row of the API needs its scenario or a known gap (below, "The inventory").

`extensions/limits` is a worked example on the public API alone. Try it with `bun run dev` in that folder while Ruimte runs.

## Slots

A slot is a place, with a function that gets what is true there and answers `false`, `true` or changes (`title`, `icon`, `disabled`, `badge`, `order`). `defineAction`, `defineMenu` and `defineWidget` all go in slots: a button or menu item, a menu of the extension's own, and its own React. An action without slots only shows where a menu puts it.

The places are `selectionBar`, `nodeHeader`, `nodeMenu`, `canvasMenu`, `viewToolbar`, `viewMenu`, `panelHeader`, `commandPalette`, `projectMenu`, `sidebarFooter`, `editorStatusBar`, `composer`, `messageActions`, `lineMenu`, `fileMenu`, `editorToolbar`, `editorMenu`, `diffToolbar`, `terminalToolbar` and `browserToolbar`. `sidebarRow`, `tabMenu`, `emptyCanvas`, `startScreen`, `projectBanner`, `threadHeader`, `emptyThread`, `toolActions`, `fileRowBadge`, `fileBreadcrumb`, `terminalMenu`, `browserMenu`, `textMenu`, `noteToolbar`, `routineMenu` and `viewAccessory` come on top. In a menu an extension always comes below Ruimte's own items. A widget works in every slot, also in a menu.

While `extension dev` runs, "Show extension slots" in the command palette outlines every slot on its spot with its name, and its tooltip lists what the slot tells.

While `run` is pending, the nodes it is about show a spinner that also stops it through `signal`, and its button is disabled for those nodes. A throw reaches the person as a toast. Work that is no action uses `host.busy`.

`defineOverlay` opens your own UI over the app and answers what it closed with. `host.confirm`, `host.prompt` and `host.pick` ask through the dialogs of Ruimte.

## Permissions

Reading what is on screen needs none. `useProviders()` needs none either. It holds only the id and name of each CLI the machine offers, never what an agent is doing (that is `agents.status`). The ones that open something are `EXTENSION_PERMISSIONS` in `packages/contracts/src/extension-permissions.ts`, plus `net:<host>` for a frame. `ruimte extension pack`, the machine's install and link, and the shell's install refuse any other name and a `net:` that is no host name (`extensionPermissionProblems`), and only a host name reaches a frame's `connect-src`. An extension already installed with an unknown name keeps loading, and Settings does not show that name. A permission the API gains is a row in that list, in the table on `/docs/extensions/manifest`, and in the call or policy table that needs it.

`chats.send` from `server/` is limited to 20 messages per chat per hour, so a loop with a chat stops on its own.

An extension types only into a terminal it opened itself, and never answers an agent's prompt. What only a person does (`packages/actions/src/person-only.ts`) opens to no permission.

## Logging

`ruimte extension dev` prints what the extension says while it runs. That is `console.*` and `log` in `server/`, and `console.*` in `client/` marked `[client]`, with failed actions, failed surfaces and a failed load. An installed extension's client logs only to the page's own console.

## Development extensions

A development extension lives in `extensions/dev` or `extensions/poc` (`DEVELOPMENT_EXTENSION_FOLDERS` in `apps/server/src/extensions/provenance.ts`) and exists to try the API by hand and in tests. `extensions/dev` holds fictional products: Trackline, Harbor, Lintel, Boardwalk, Beacon and Pulseboard. Each has a fake service of fixed data in `server/service.ts` and no network, an icon and a color, and tests in `test/` against the test host and the test server. `extensions/poc` holds the older ones per layer of the API. One goes once a product has what it shows and the tests that leaned on it moved; the two that break on purpose and the probe of the contract suite stay.

Three places run a product's code in tests. Its own `test/` runs under `ruimte extension test`, which `apps/server/src/cli/extension-test.integration.test.ts` does for each. `apps/server/src/extensions/development.integration.test.ts` packs and installs every development extension that uses no proposed part, links the others, and runs Trackline's `server/` in a real process. `providers.integration.test.ts` links Harbor and Lintel into a test daemon, each in a process of its own, and holds what phase 2 of the API was built for: the services of `harbor.yaml` show as launches, a change to that file asks for approval again, and `language_problems` gives Lintel's problems back. It also holds phase 4 as far as a test goes: the machine of `harbor.yaml` listed to the app on this computer only, its start held until approved, its programs run in order through the fake seam up to the sign-in, and a changed file asking again. It links Pulseboard too, whose channel hears nothing while it is off and what a phone would get once the app on this computer turned it on, and Trackline, whose issues an agent is told of and a block reads, and whose reference and `/issue` a client lists and resolves over the wire. `apps/client/src/extensions/dev-*.dom.test.tsx` load a product's `client/` into the real client host (`loadProduct` in `apps/client/testing/poc.ts`).

`bun dev` loads them and nothing else does. `apps/server/scripts/dev.ts` starts `scripts/dev-extensions.ts` beside the development daemon, which builds every folder with a `manifest.json` into its own `dist` and links it over the route `ruimte extension dev` uses, so there is one loader. One watcher per folder of development extensions builds and links an extension again on a save in it. A link stays in the development home after `bun dev` ends, and a folder added while it runs is linked at the next start. `poc-broken` and `poc-broken-load` are linked off (`startsOff` on the link) and stay off until a person turns them on in Settings; `poc-contract` is not linked, since it offers every agent a tool and has nothing to look at.

The machine decides what a development extension is: a dev link whose folder lies inside those folders of the checkout the daemon runs from (`extensionProvenance`). A compiled daemon has no checkout, so it knows none. `extension.list` carries the answer as `provenance` (`installed`, `dev-link`, `development`; a client adds `built-in` for what it ships itself), and Settings, Extensions lists them under "Test extensions" on that field alone, with a switch that works, where a link of `extension dev` is on for as long as its run. A rule that depends on where an extension came from asks `extensionProvenance`, never the manifest.

No build holds one. The client imports only what `apps/client/src/extensions/built-in.ts` names, and neither the desktop app nor npm packs these folders. `scripts/check-build-outputs.ts` searches what a build wrote (the client, Station and Bench bundles, the desktop's main process, a compiled daemon) for the id and the folder of each and fails on a hit: the `build` job of `ci.yml` runs it after its last bundle, and the package test runs it on the daemon it compiled. `extensions/dev/development-extensions.test.ts` keeps their ids apart from the ids of what ships.

## The inventory

`packages/contracts/scripts/generate-extension-inventory.ts` reads every call, hook, define-function, slot and event from `client.d.ts` and `server.d.ts` and every field of the manifest schema into `extension-inventory.generated.ts`, one row each as `<side>/<kind>/<name>`, with the permission a row takes and whether it answers a function that stops it. `extensions/poc/contract/contract/inventory.ts` names, per row, the scenario of the contract suite that uses it, the one that refuses it without its permission and the one that stops it, by the title of the test. A row the suite does not hold yet sits in `EXTENSION_API_KNOWN_GAPS` with its reason.

`bun run check` runs the generator with `--check`, which fails for a stale file, a row in neither list, a row that takes a permission without a refusal, one that stops without a cleanup, a title the suite does not hold, and a gap without a reason. So a call the API gains lands with its scenario, and the list of gaps only shrinks unless someone writes down why not.

## Themes

A theme is data. It needs no `client/` and applies before the first render. It sits in the picker beside System, Light and Dark with its required `thumbnail`, and Palette is only there for Ruimte's own themes.

```json
{
    "name": "Midnight",
    "side": "dark",
    "tokens": { "--surface": "#0b1020" },
    "css": "themes/midnight.css"
}
```

`css` is optional. `url()` reaches only files in the pack and `@import` is refused, both when packing and when loading. The stable hooks are `[data-surface='sidebar']`, `'panel'` and `'node'` (the first two sit on a column, so its ground is `> div`); an internal class can change in any release. Safe mode starts without a theme.

## Built-ins

A built-in ships inside the client: `pets` and `theme-umbra`. `apps/client/src/extensions/built-in.ts` is the one file that names them, each with `defineBuiltIn` (`extensions/built-ins.ts`): its manifest, icon, words, themes and, for one with `client/`, its entry imported with `?activate`. It lists under Settings, Extensions like an installed one, and a person turns it off there (`ruimte.builtIns.disabled`, followed by every window).

A built-in runs on the public API alone, loaded as an installed extension is (`host/loads.ts`), so it keeps working if it is ever packed like one. `scripts/check-built-ins.ts`, part of `bun run check`, holds both sides: the core never imports a built-in, and a built-in's sources import only relative paths, `@ruimte/extension/*`, React, clsx, zod, zustand and lucide-react.

The binding happens at build time, in `apps/client/built-ins.ts`. In a built-in's folder it rewrites `@ruimte/extension/client` to `host/built-in-api.ts?extension=<id>&lang.ts`, a module of its own per built-in whose calls reach that built-in's current load, and `/ui`, `/agents-ui` and `/charts` to what the client draws with. The `lang.ts` keeps the id ending in `.ts`, since Vite would otherwise read `ruimte.pets` as the file's language. `?activate` wraps the entry's statements in the function a load runs, so turning it on again runs them anew. An entry that exports anything fails the build.

Vite runs this as a plugin. Bun's tests run the same function from an `onLoad` in `apps/client/testing/built-in-preload.ts`, because a Bun `onResolve` per importer does not reach a bare specifier. The DOM run applies it inside the React Compiler's `onLoad` too, since Bun keeps the first plugin that loads a module.

Only a built-in gets a settings section of its own. `grantsSettingsSection` in `host/client-api.tsx` decides that on `builtIn`, never on the manifest's `publisher`, in one place so it can widen later. Any other extension's call puts its page under Settings, Extensions, and the dev log says so once.

The client measures a chat's composer card for the `viewAccessory` slot (`ViewAccessorySlot.tsx`), by an ADE CORE class until ADE CORE marks the card itself. That lookup lives in the host, never in an extension.

## The store

An author builds a `.rex` and `publish` opens a pull request on `ruimte-app/extensions`. Ruimte never builds someone else's code, and every update gets a human review before it is signed.

Still to set up before the store opens:

1. Create the repository `ruimte-app/extensions`.
2. Generate an ed25519 key and keep its private half out of every repository.
3. Put the public half in `EXTENSION_STORE_PUBLIC_KEY` (`packages/pulsar/src/extension-store.ts`). While it is empty, the store shows as unavailable.
4. Publish the placeholder of `@ruimte/extension` and have npm trust `npm.yml` for it (`docs/RELEASE.md`, "npm"). From then on every release publishes it at the app version.

## Safe mode

A window with `?safe-mode` on its address loads no extension and no theme, so a person can always remove one that hangs the app. A desktop window has no address bar: Help, Restart Without Extensions starts the app again with `--safe-mode`, which puts it on every window of that start (`apps/desktop/src/main/safe-mode.ts`). A page that no longer answers its menu needs the app quit and started with the flag by hand (`open -a Ruimte --args --safe-mode` on macOS). The next ordinary start loads them again.

## The machine

`definePaletteSource({ id, title, search })` adds rows to the command palette. It runs after a pause in the typing, and a slow or failing one costs only its own rows.

`launches`, `routines`, `artifacts`, `browser` and `devices` call the actions of the same name (`launches.start({ launch })` is `launch.start`). The daemon checks each call against `EXTENSION_ACTIONS` and the manifest, and `apps/server/src/extensions/machine-actions.ts` turns the extension's input (refs, not ids) into the action's and the output into the smaller one `MachineActions` promises. From `server/`, `machine.run(project, 'launch.start', input)` does the same.

## Failure

A call that can fail answers a `Result`, under one of `EXTENSION_ERROR_CODES`, which `packages/contracts/scripts/generate-extension-vocabularies.ts` reads from the `ExtensionErrorCode` of `client.d.ts` (and fails when `server.d.ts` names others), as it does the slot names from `SlotContexts`. A new call is a row of `EXTENSION_CLIENT_PERMISSIONS` or of `EXTENSION_CALLS_WITHOUT_PERMISSION` (`extension-client.ts`), which `extension-client.test.ts` requires of every call the `.d.ts` files declare. The daemon refuses with `ExtensionRefusal` (`apps/server/src/extensions/refusal.ts`); the client host maps any other wire code with `extensionErrorCodeOf`. Only `invalid-input` or `bad-request`, an argument of the wrong shape, reaches an extension as a throw; the input of a machine action is checked by `parseExtensionActionInput`, on the machine and in a test server alike. A `Result<void>` always carries `value: undefined`, with the key there, while a method of `server/` crosses as JSON, so one that returns nothing answers `null` (`Returned` in the types). A refusal is no throw, so the host writes it to the log of `extension dev`: the client with `sendDevLog`, the daemon to the extension's log file for what `server/` asked. `client-api.tsx`, `server-api.ts` and the fakes of `test-runtime.ts` each `satisfies` their `.d.ts`, so the types and the hosts cannot drift apart.

What `server/` may do is decided in `apps/server/src/extensions/policy.ts`: which events it follows and what of them it hears, the permission of each ask and action, the sends per chat and the clock of `schedule`. It is pure, so the host refuses with it and `ruimte extension test` holds an author's code to the same answers. `server-api.ts` is `@ruimte/extension/server` with its pipes, files and clock handed in; `server-runtime.ts` hands in the real ones inside the extension's process, and answers the daemon before the extension's module loads, so a top-level `await` gets its answer. Its `storage` asks the daemon, the one writer of `storage.json`, which a client's `useStorage` writes too. A compiled daemon has no source tree, so `apps/server/scripts/generate-extension-runtimes.ts` bundles it, and the preload of `ruimte extension test`, into `apps/server/src/extensions/generated`, which the daemon and the CLI carry as text. Run `bun run generate:extension-runtimes` after a change; `bun run check` fails on a stale bundle.

The host makes one change to what an extension runs at a time: turning it on or off, a new version, its removal, and a language server its process adds. A start waits for a change under way and reads the store again after a stop, so it never acts on what the store said before. It also waits until a stopped process exited, which a kill only asks for. A save under `extension dev` starts an extension again when it runs with the machine. `lifecycle-harness.ts` holds every step of the store, the files, the language servers and the processes, its exit included, until a test lets it go. `extension-host-lifecycle.test.ts` forces orders with it, and `extension-host-interleavings.test.ts` runs 300 seeded interleavings against the invariants: one process per extension, none that was stopped and never exited, nothing running, no language server and no tool after a turn off or removal, no lost storage write, and nothing heard after a client or process is forgotten. A failure prints its seed, and `RUIMTE_SEED=<seed>` runs that one alone.

## Terminals

`terminals.read(node)` returns a terminal's screen. `terminals.open` and `terminals.write` go through the machine (`extension.terminalOpen`, `extension.terminalWrite`, and the asks of the same name from `server/`). The machine makes the node through `ProjectStore.mutate` and starts its session (`apps/server/src/extensions/terminals.ts`), so a write right after the open lands, and under the project's lock it writes down which extension opened the terminal and which profile starts it, in `$RUIMTE_HOME/extension-terminals.json` (`ExtensionTerminals`). Never in a project file: an agent with a shell can rewrite that. The record goes with its node, on the `placed` event of the node lifecycle.

`terminals.write` is decided on that record alone (`terminalWriteRefusal` in `policy.ts`): `refused` for a terminal another extension, a person or an agent opened, also one a person opened with the extension's own profile, and `refused` while `SessionManager.awaitsPerson` says an agent's hook reported a question or an approval. Not every CLI reports one, which is why who opened the terminal carries the rule. The text goes to the PTY without a client, so it sizes the terminal to no window. No action of the catalog opened to the `extension` actor for this: a person's typing stays `session.write`.

`terminals.watch` of the design is not built. A session gives its output as the raw bytes of the PTY, and only to a client that took its screen through `Session.snapshotFor`. An extension that followed them would be handed the screen protocol, which a session event never carries to one, and text alone exists only as the whole screen `terminals.read` returns.

## Provider points and the proposed tier

A manifest lists what it supplies under `provides`, per kind and by id, so Ruimte shows a provider without starting `server/`. `EXTENSION_PROVIDER_POINTS` in `packages/contracts/src/extension-providers.ts` is the one table: per kind the `define` function of `server/`, its permission and whether it is still proposed. `pack`, an install, a dev link, both hosts and both test hosts read it. A new provider point is one row there, its permission in `EXTENSION_PERMISSIONS`, and its `define` function in `server-api.ts`, which calls `mayDefine` before it registers.

A proposed part works only where `allowsProposed` says so: under a dev link, for a development extension and for a built-in. The machine asks `extensionProvenance` and the client goes by `dev` of the shell's list, which the machine's dev links set; a built-in loads apart from both and always may. An extension a person installed that names or uses one does not run:

- `readExtensionPack` refuses the pack, so neither the machine nor the shell installs it. `pack` warns and `publish` stops (`proposedPackWarning`).
- One that is installed all the same is not started (`ExtensionHost.refusedReason`) and not loaded (`notLoadedReason` in `loader.ts`). `extension.list` carries the reason as `refused`, and Settings shows it on the row.
- A `define` call for a kind the manifest does not name under `proposed`, or an id it does not list, throws in `server/` (`providerRefusal`), and the host refuses the same from a process that speaks the pipe by hand.
- `createTestServer` takes `provenance: 'installed'` and rejects with the reason a person reads.

`defineTerminalProfile` is the first. The menu of a new terminal on a canvas and in the sidebar asks `extension.terminalProfiles`, which lists the ids of every enabled extension from its manifest. One whose process runs is asked `available` and names the row; one that does not run is not started for a list, and shows under the extension's name. Picking a row asks `extension.terminalOpen` with `picked`, which writes the profile on the record and no opener. When the session of such a node starts, `SessionManager` asks `profileFor`, which has the extension's process describe the program (`ExtensionHost.profileSpawn`, checked by `SpawnDescriptionSchema`). The session runs it as a launch runs its command, as the argument of the person's shell with the profile's variables on top, in a folder `checkCwd` keeps inside the project. Nothing holds it for approval: the command comes from an extension a person installed, not from a project file, and a node that names a command of its own keeps that one and its approval. An extension that is off, gone or refuses leaves a plain shell with a line that says why, and a terminal that already runs is left alone.

`defineLaunchSource` is the second. `LaunchSources` (`apps/server/src/launches/sources.ts`) asks every enabled extension that lists `provides.launchSources` what it lists in a project once that project's launches load, which starts its process, and keeps the answer until the project is let go of. `LaunchStore.resolveAll` puts those launches after the ones of the files, each under the id `<extension>:<source>:<id>` (`sourcedLaunchId`), so the runner, the agent tools, a routine and the approval of an external MCP client reach them as any launch. They are held like a command from a project file, on a digest that also holds the fingerprint the source gave; `apps/server/src/launches/CLAUDE.md` has the rule. Three things read the list again: the `changed` of the source's `watch`, a change of what an extension runs (`providersChanged` of the host), and every start (`LaunchStore.fresh`), so a source without a watch never starts a stale description. A client hears of them in `sourced`, an optional field of the launches document in `launches.read` and `launches.changed`, apart from `launches`: a client saves that list whole, and an older client would otherwise write an extension's launch into a project file. `LaunchHeld` carries the source, and `launches.approveSource` is a person's yes to everything one source lists as it stands.

`defineProblemSource` names a source, and `problems.report` and `problems.clear` speak for it. `ExtensionProblems` (`apps/server/src/extensions/problems.ts`) keeps what each source said per project, in memory, and sends it to the clients that hold the project as `language.diagnostics` under the name `<extension>/<source>`, so the Problems panel draws it with no code of its own. A window that opens later asks `language.reportedProblems`. `AgentLanguage` lists it in `language_problems` beside the servers' own. A `Problem` counts from 1 and is smaller than a diagnostic of LSP (`extension-problems.ts`): a line, an optional column and end, a severity, a message and an optional code. A source holds at most 200 problems per file and 500 files per project, and a report past either answers `limit`. The host drops everything an extension said when its process stops or ends, and the wiring when a project closes.

`defineMachineSource` lists places where a machine can run for a project, and describes what starts one. `MachineSources` (`apps/server/src/extensions/machine-sources.ts`) asks the source `list` when the app on this computer opens Settings, Machines, and `start` when a person presses Start. `start` answers programs (`MachineStartDescriptionSchema`: up to 16 steps, an optional `login`, a fingerprint), and the machine runs none of them until a person approved a digest of them all, with their folders, their variables and the fingerprint. The yes lives in the ledger a launch of a source is held by (`CommandApprovals`, under `machine-source:<extension>:<source>:<place>`), and `extension.machineStart` carries it as `approve` with the digest the person was shown, so a source that describes something else by then is held again. The three requests (`extension.machineList`, `extension.machineStart`, `extension.machineStop`) are owner only: the app on this computer, on the local secret. Only a client that asked for the list hears `extension.machineChanged`, since the lines of a start hold the page and the code of a sign-in. The programs run through the seam `machineSteps` (`machine-steps.ts`), with no shell and each argument as described; a test daemon has `FakeMachineSteps`.

A machine a source starts joins as a second machine of a person always did, which is why the feature ends at a person's step:

- A daemon mints its id and key pair in `endpoint.json` at its first start. Nothing hands it one.
- It gets on an account only by signing a registration, which only its own local secret may ask for: the app on that computer (`endpoint.signRegistration`, `apps/client/src/workspace/auto-register-watch.ts`), or `ruimte login` there (`POST /machine/registration`, `apps/server/src/cli/login.ts`). `ruimte login` prints a page and a code, a person signs in on the page and approves, and the address book answers only which account said yes. No account token reaches a daemon.
- From then on every client of the account finds it in the address book and reaches it over a direct channel, signaled through the broker or the door on the local network.

So `login` in a start is a program that runs `ruimte login` on the new machine. The local secret it uses stays in that place, its output goes to the person and never to the extension, and the client shows "Add the new machine to your account" with the page it named. Once it ends with 0 the client reads the account's machines again. Nothing here signs for the new machine, and there is no call that hands an extension a key, a token or a channel. A container that announces itself to no broker and opens no door is on the account and still unreachable, which is the source's to describe (`apps/server/docker/README.md` has the flags the test container needs).

A stop asks the running program to end with one SIGTERM and waits for it. Nothing stops or removes a container, a volume or a file a start made, also not after a failure or when the extension is turned off, and a start is kept in memory alone.

`defineNotificationChannel` delivers what a phone would get somewhere else. `PushService.deliverAlert` is the one place an alert leaves the machine, past the hold at a desk, a snooze and an approval answered meanwhile, and it tells `NotificationChannels` (`apps/server/src/extensions/notification-channels.ts`) once per alert, before it looks at the phones. What is a phone's own does not hold a channel: its quiet hours, what it follows, the app in front. The round for one phone whose quiet hours ended tells no channel again, a usage limit is told once however many chats stop on it, and a process warning is not told, since `Notification.reason` has no word for it. A channel is off until the app on this computer turns it on (`extension.notificationChannels`, `extension.notificationChannelSet`, both owner only), and the switches live in `$RUIMTE_HOME/extension-notification-channels.json`. Settings, Notifications lists the channels from the manifests, so one shows before its `server/` ran. A delivery starts the extension's process, runs under the timeout of every ask of a process, and a throw or a timeout costs that one notification and a line in the extension's log. No push payload and no enum of one changed.

`defineUiSource` gives a `ruimte-ui` block live data of an extension. The agent writes `@Query("extension", { source: "<extension>/<id>", args })`: one source of Ruimte's own (`EXTENSION_UI_SOURCE`, in `apps/server/src/chat/ui-sources.ts`) whose arguments name the extension's. The design sketched the extension's name as the source itself. That cannot be built here: ADE CORE's `ChatUiQueries` copies the argument schemas of `host.sources` once, when the chat core is made, and the compiler refuses a source that copy does not hold, so a source that comes with an extension linked later would never compile. Once ADE CORE reads the sources live, a name per source is a small change on top. The catalog of components is untouched, and the iPhone, which takes a compiled block and never checks a source name, needs nothing. `ExtensionUiSources` (`apps/server/src/extensions/ui-sources.ts`) keeps what the extensions said of their sources from the last ask, since a prompt is written without waiting: it asks when a project opens (which starts the process of each extension that lists one), when what an extension runs changes (without starting anything), for each `ui_catalog`, and once more when a block names a source nobody listed. The prompt of a chat told about blocks names up to 12 sources with their description (`extensionSourcesNote` in `context-note.ts`), and `ui_catalog` prints each with its `parameters`. A read is authorized as every source is, on the access the chat captured when the agent wrote the block, and the extension is handed the project of that access. Ruimte does not hold `args` to `parameters`. The answer crosses as JSON, at most 32 KB (`uiAnswerRead`), under ADE CORE's own limit and its timeout.

`defineReference` and `defineSlashCommand` have a twin in `server/`, for a client that did not load an extension's `client/`: the iPhone, Station on a machine in front, and a window before the extension loaded. Three requests carry them, open to every client of the machine: `extension.composerItems` lists what the enabled extensions offer in a project (which starts their processes), and `extension.referenceRead` and `extension.commandExpand` answer the text for the prompt. Nothing here sends: the client puts the text in its composer, as for the client versions. The desktop asks through `useMachineComposer` (`apps/client/src/extensions/machine-composer.ts`) and merges in `useExtensionReferables` and `useExpandingCommands`, where the client's own come first and the machine's are left out under the same id (`<extension>/<reference>/<item>`) or the same command name. The iPhone does not ask yet. Its composer needs the three requests behind `MachineClient.answers`, the references among what `#` lists and the commands among what `/` lists, each pick replaced by the text the machine answered; the generated wire models are there.

A proposed part of `client/` is a row of `EXTENSION_CLIENT_POINTS`, in the same file as the provider points and read by the same places. The client lists nothing before its code runs, so such a part has no ids under `provides` and no permission of its own: the manifest names it under `proposed`, which makes an installed pack refuse and not load as for any proposed part. The define function calls `mayUse` in `client-api.tsx`, which throws on `clientPointRefusal` unless the load is a dev link or a built-in, and the test host holds the same rule with the manifest it was given.

`defineProjectSettings` is the first. It puts a section in the settings of a project, after Ruimte's own, with fields Ruimte draws (`ProjectSchemaSettings.tsx`). The dialog reads the sections from `useContributions` beside `projectSettingsSectionRegistry`, since a registry of `registry/` only grows and an extension comes and goes. A section shows only for the project the window holds, where the extension runs. What a person chooses is kept in what the extension stores on the machine, under `projectSettingKey` (`project:<project>:setting.<key>`), so nothing new goes into `project.json`, `useProjectSetting` reads it through the storage a `project` scope of `useStorage` uses, and `projectSettings.get` of `server/` reads the same key with no ask of its own. The default of a field lives in `client/`, so `server/` gets `undefined` until someone chose.

`defineLanguage` names the files of a language and the TextMate grammar that colors them. Two things had to be found for it. The machine says which language a file is in (`fs.read`, `disk/language-of.ts`), so `useFileLanguage` (`apps/client/src/extensions/languages.ts`) puts the language of an extension behind it in `CodeFile`, for a file the machine reads as none. And the editor and the viewer ask Shiki for a grammar by name, through ADE CORE's `loadGrammar`, which only loads what Shiki bundles but takes a language that is in the highlighter already. The highlighter is the client's own (`code-highlighter.ts`), so `registerGrammar` keeps a loader per language there and `ensureGrammar` puts the grammar in before the editor's tokenizer (`editor-engine.ts`) and the viewer (`highlight.ts`) ask. Nothing in ADE CORE changed. The grammar is a JSON file of the pack, at most `MAX_LANGUAGE_GRAMMAR_BYTES`, fetched when the first such file is colored. Shiki only adds grammars, so one stays until the window reloads, and a language Shiki bundles never takes one from an extension. The language id is the one a `defineLanguageServer` lists, which is how Lintel's grammar, icon and server for `.lintel` files meet.

`defineEditorDecoration` marks lines in the margin of an editor. The seam is `highlightLayers` of `@adecore/editor-react`, which shares the editor's one set of line highlights between owners: `useEditorDecorations` (`apps/client/src/extensions/editor-decorations.ts`), called from `CodeFile`, asks each decoration for the marks of the file and sets them under the owner `extension:<extension>/<id>`. A mark is a highlight with a `sign` and a transparent `fill`, so it shows as a dot beside the line number in the token of its kind (`DECORATION_COLORS`), tints no text and leaves the change mark of git beside it. The editor keeps highlights on their text through edits. An owner that is set first sits below a later one on the same line, so a review or a conflict Ruimte tints later keeps its line. The extension is handed the file's path, name and extension and nothing else: no editor, no text, no selection, no keymap. The design also sketched hover text and blame. Hover text is not built, since the editor reports a hover over a change mark and over an attribution bar but not over the sign of a line highlight. It needs a hover of that sign in ADE CORE's editor, or a label on `EditorLineHighlight` the editor shows itself.

`defineAgentProvider` offers an agent that speaks ACP and is not in the registry. It rides on the path an agent of the registry takes: `ExtensionAgentProviders` (`apps/server/src/extensions/agent-providers.ts`) makes a provider with ADE CORE's `createAcpProvider` from what the extension described and hands it to `ProviderRegistry.add`, whose change reaches every client's pickers as for any provider. `AgentKind` is open, so the kind is `x-<extension>-<id>` in the letters a kind takes (`extensionAgentKind`), at most 32 characters, and no wire shape changed. The design sketched `spawn({ cwd })` per start. The ACP backend takes its command when the provider is made, so `spawn` is asked once, as `server/` loads, and the chat's folder is the session's own. `server/` sends the description with its registration (after `models()` settled, so it can come a moment after the process is up, which `agentsDescribed` of the host tells), and no chat start asks the process anything. The provider is asked for when a project opens, which starts the process, stays offered while the extension is on and lists it, also once that process ended, and leaves with the extension. The command comes from installed code and not from a project file, so nothing holds it for approval, as for a terminal profile. The credential rule holds by what is left out: `accountProbe` is off, so nothing starts the program to ask for an account or its models, `detect` reads the path and never runs it, and the agent gets the person's own environment with the described variables on top, like an agent of the registry. Ruimte's MCP server is added to its chats as for every agent.

`defineEnvironment` is not built. The spike of November 24 wrapped a terminal with `docker exec` and found that every stop Ruimte has ends only the client on this computer, while a chat also needs a relay for the loopback API, paths translated both ways and a login, part of which lives in ADE CORE. The API has nothing for it.

`server/` reads a project's files through `files` (`project-files.ts`), by the rules a client's `fs.read` is held to: inside the project folder past every symlink, and never the machine's own state. A watch of a file follows its folder, since a save that swaps the file in would leave a watch of the file itself behind. `EXTENSION_SERVER_PERMISSIONS` holds the permission of a call only `server/` has; a call both sides have takes the client's.

`defineLanguageServer` in `server/` adds a server like one a person added, and it starts without asking: installing the extension was the approval. The same name changes it, and removing the extension removes it, unless a person edited it in Settings.

## Station

Station has no shell, so it runs what the machine in front has. `extension.clientFiles` hands over everything but `server/`, the page caches it under the machine it came from (a dev link under a digest of its files, since its build number starts over with the machine), and `extension-files-sw.js` answers it on the page's own origin, under the same `script-src 'self'`. A window runs the extensions of its own machine. A `frame` surface shows a notice there: a sandboxed frame gets no policy from the worker.

## Choices against the report

Every action a person can run is weighed for an extension, and opens one at a time: the `extension` actor joins the `actors` of an action in `packages/actions/src/catalog` after a look at its handler and fields, with its row in `EXTENSION_ACTIONS` and the smaller input and output Ruimte promises (`extension-actions.ts`). A list picked by hand was the other choice, and it had nothing that made it grow. The actions of `person-only.ts` never open, and `person-only.test.ts` holds that list a second time, so nobody takes one off unnoticed.

An extension describes and Ruimte runs: a provider on the machine hands back a description, such as a command with its arguments, and the session, its scrollback, its status and its stop stay Ruimte's. What a provider read from a project file waits for a person's approval of a fingerprint of it, as a command from a project file does. An environment may be a second boundary beside the CLI's sandbox, and Ruimte promises nothing about it. A container gets a login of its own from the CLI in a volume; nothing mounts the host's. A machine an extension starts joins the account the way every machine does, with an identity of its own, so there is no third way in.

An extension hears an event in a shape of its own per area, never the wire's payload: an event of Voice carries the token a phone confirms with, and one of a session a terminal's screen. `SERVER_EVENTS` in `policy.ts` holds each with the read permission of its area, and gains one only when a development extension follows it: `launch.status` for Harbor, `project.opened` and `project.closed` for Lintel. A change in git and a worktree that comes or goes wait for an extension that follows them. `terminals.watch` stays out, as above.

The launch and routine actions were weighed for the `extension` actor. `launch.create` and `launch.edit` opened behind `launches.write`: both save through `saveByAgent`, which approves nothing, and `shared` stays a person's and an agent's, so an extension never adds to the file a team commits. `launch.save` stays a person's, since saving approves. `routine.create` and `routine.edit` stay closed for now. Their handler takes the permission mode, the CLI and the maker of a routine from the chat that calls, and an extension is no chat; they open once a routine has a ceiling and a maker for an extension. No `routines.write` exists until then, since a permission that opens nothing only misleads.

The chat, agent and task actions were weighed too, and one opened. `chat.inspect` runs for an extension behind `chats.read` (`chats.inspect`, or `machine.run` from `server/`), for a chat of the project the call came from, on this machine. `machine-actions.ts` hands on what the chat runs on, counts, and `waitsOn` as `approval`, `question` or null. The text of a question, an approval or a queued message and every request id stay behind, since answering is the person's. The rest stays closed, each for a reason in its handler:

- `chat.read`, `chat.send` and `chat.clear` on the machine are Voice's: they follow the turn for a voice session and take its project. An extension already reads and sends through `chats.read` and `chats.send`, with the send limit, and clearing asks a confirmation an extension cannot give.
- `task.list` answers the tasks of the caller, `task.create` gives work only to an agent the caller opened and wakes the caller with the result, and `task.complete` reports the caller's own task. An extension is no chat, opened no agent by lineage and cannot be woken, so there is no `tasks.read` or `tasks.write` yet.
- `agent.notify`, `agent.alert`, `chat.attach` and the machine's `chat.fork` act for the node that calls, along its lines or on a chat it opened. An extension has no node.
- Stopping a turn, the queue, compacting, restarting, the model, mode and account of a chat, summaries, a turn's diff, sub-agents, goals, search and a move run in the client's registry, and `extension.action` reaches only the machine's. They wait for a `chats.control` that has a path to them. No permission was added that opens nothing.
- `chat.approve`, `chat.answer`, `chat.dismissQuestion`, `chat.uiChoice`, `chat.sendNow` and `agent.answer` never open (`person-only.ts`). `agent.start` was open already.

`ruimte-ui` gets no components of an extension: the iPhone validates that catalog whole, and `defineMarkdownBlock` draws a fence an agent writes. Git stays as it is, by choice: a code host writes through proposals a person confirms. Plans stay out: a plan belongs to a chat and only that chat may ask for it. `browser.control` and `devices.control` drive any page or device of the project without a line, since an extension has no node for a line to reach. Margin decorations of the editor are open to an extension; the selection in `editorMenu`, edits and a keymap stay out, by choice.

`defineStatusItem` became the slots `sidebarFooter` and `editorStatusBar`, `defineMessageBlock` is `defineMarkdownBlock`, and `messageMenu` is `messageActions`. A `defineNotificationAction` is `host.notify` with an `action`. `defineTemplate` shows under Extensions in the canvas menu. A reference and a slash command come down to text in the prompt, which the person still sends. `agents.start` runs under the `extension` actor, bound as Voice is when it starts a chat: an AI Chat under the person's own CLI, supervised at most, on a canvas or as a view of its own. `server/` names the project. `hosts` are the `net:` permissions of a frame. Webhooks and `secrets.request` stay out. Voice reaches an extension through the two actions `extension.voiceList` and `extension.voiceRun`, since the catalog of tools is fixed.
