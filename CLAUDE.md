# Ruimte

Ruimte is a workspace for AI engineering, built around projects, views and persistent sessions. `README.md` has the principles. This file is the map and the rules the code does not tell you.

## Layout

Bun workspaces (`bun install` at the root). Shared config at the root: `tsconfig.base.json`, `.oxlintrc.json`, `.editorconfig`, `bun.lock`.

- `apps/client`: the React UI (Vite). Never imports Node or Bun APIs. Talks to a daemon only through the `Transport` interface. A window shows a start screen or one workspace, which is one project on one machine and never exists without it (`state/window.ts`, `transport/connections.ts`). A project is in one window at a time: a page asks the shell before it shows one (`desktop/window-claim.ts`), and what the window shows rides in its address (`state/window-target.ts`), so a reload stays put. In dev Vite proxies `/ws` to the daemon.
- `apps/server`: the daemon (Bun). Owns sessions, PTYs, chats and persistence under `$RUIMTE_HOME` (default `~/.ruimte`). WebSocket API on `localhost:4210`. In dev (`bun dev`) it runs on `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, so it never meets an installed Ruimte; its door on the local network is `4221`, and `bun src/main.ts status --port 4211` says how clients reach it. Flags, hooks and on-disk layout: `apps/server/README.md`. Work on another machine has two halves in the daemon: `src/remote` is the machine whose person works elsewhere (the binding of a node to a machine, the links, the reconnect, the tasks it gives), `src/peering` is the machine that is worked in (the links a person made, what a peer may ask, the tasks it takes). `src/daemon.ts` calls the modules in `src/wiring` in boot order, each returning a typed bundle; one that needs a bundle wired after it reaches it through `later`, and the agent verbs get the services themselves through `CanvasHost` (`src/wiring/canvas-host.ts`). A chat outside any project is a chat view in the machine's Chats project at `$RUIMTE_HOME/scratch`, in a folder of its own that no screen shows (`src/projects/scratch-project.ts`, `scratch` on a summary, `project/new-chat.ts` in the client).
- `apps/desktop`: the Electron shell around the client, with the daemon beside it. Whether it runs one is the machine mode in `machine.json` under `userData` (`src/machine-mode.ts`): `local` runs a daemon, `none` only connects to other machines, and `ask` is a new install that shows the first-run screen until a person chose. What follows about the daemon holds for `local` only: in any other mode the shell starts none and passes no `daemonUrl`, the preload leaves out `localSecret`, `takeStartupMs` and `backgroundService`, and no `service:*` channel is installed. The shell serves the built client itself on its own scheme (`app://ruimte`, `src/app-scheme.ts`), so a window never waits on a daemon, and hands the page the daemon's address over the bridge (`daemonUrl`); under `bun dev` the page is Vite's and reaches the daemon through its proxy. The windows open while the machine still comes up, and the local secret waits until the daemon on the port proved it holds it (`src/startup.ts`, `src/daemon-proof.ts`), so a page connects only then. Only a small, fixed set crosses IPC: `src/preload.ts` builds the bridge and checks it with `satisfies DesktopBridge` from `packages/desktop-bridge`, which the client re-exports in `apps/client/src/desktop/bridge.ts`, and every bridge method added after the first release is optional. The main process installs its channels per domain from `src/main`. It keeps a window per project, and the windows of the last session open again at the next start (`createWindows`); every handler answers the window that asked, and what the app shares (updates, the service, the theme) goes to every window. What a shell of any app does (the windows, the menu tree, the updater, the guards every app shares) is `@adecore/shell`, a package of `basmilius/adecore` that AfterMotion's shell uses too; the shapes it passes over IPC reach the client through `packages/desktop-bridge`. The refresh token stays in the shell (`src/pulsar-store.ts`); the page only gets access tokens. Browser pages have their own preload (`src/guest.ts`). The application menu is the client's: it sends a tree (`menu:set`) built from what has the focus, and a click comes back as a command id (`menu:run`); the shell only keeps a fixed menu until the first tree and after a reload. A packaged app on macOS and Linux runs the daemon as a background service (`src/service`); the dev app never touches launchd or systemd.
- `apps/ios`: native iPhone/iPad client, iOS 27, Swift. `project.yml` is XcodeGen input; the generated Xcode project and `Package.resolved` are committed for Xcode Cloud. Regenerate with `bun run --cwd packages/contracts generate:swift` and `xcodegen generate --spec apps/ios/project.yml`; `bun run check` verifies generated models and fixtures. See `apps/ios/README.md`. Continue implementation autonomously; device measurements remain explicit acceptance evidence.
- `apps/ios-device-bridge`: the macOS-only Rust helper that keeps Apple's private device protocols out of the daemon. It joins the wireless `remoted` tunnel through `remotepairingd`, forwards Annex-B HEVC from the CoreDevice display service over the helper pipe and sends touch, buttons and rotation back through CoreDevice HID; a cabled device falls back to usbmuxd. See its README.
- Android emulators and phones have no app of their own: the daemon drives them with the SDK a person installed (`adb`, and `emulator` to start one) on macOS and Linux (`apps/server/src/devices/android.ts`), and pushes the pinned scrcpy server for the screen, touch and typing, which pastes through the device clipboard. Nothing is installed on the device. `apps/server/README.md` ("Devices") sets it beside iOS and lists what it cannot do.
- `apps/computer-use`: the macOS-only Swift app that lets an agent see and operate another Mac app, through accessibility, window captures and synthesized input, behind a phantom cursor, a session bar and a menu bar item where the person pauses (⌥Space), takes over or stops (⌥⎋); the daemon drives the cursor's state with `presence`. It is an app because macOS attaches the Accessibility and Screen Recording grants to a bundle; it ships in `Ruimte.app/Contents/Helpers` and has a dev bundle id of its own. The daemon launches it with `--home` and talks over `$RUIMTE_HOME/computer-use/agent.sock`, and every request carries the local secret. `cu` is its debugging CLI and does not ship. See its README.
- `apps/foundation-models`: the Swift helper on the machine's own Apple model, behind the Apple provider (a chat) and the editor's on-device help (`--oneshot`, no tools). macOS on Apple silicon only. CI builds and tests it (`.github/workflows/ci.yml`); `apps/server/scripts/compile.ts` builds it into the arm64 daemon's `native/`, and `apps/desktop/build/sign.cjs` and `after-pack.cjs` sign it and refuse a Mac build without it. The daemon starts it from `src/providers/apple-helper.ts` and `src/ondevice/model.ts`. See its README.
- `apps/speech-bridge`: the Rust helper behind Speech to Text, a local streaming model the Electron shell owns. macOS only in a release. See its README.
- `basmilius/language-server-php` and `basmilius/language-server-sql`: the standalone Rust PHP and SQL language servers (`php-native`, `sql-native`), with no npm dependency in Ruimte and versions of their own. A development daemon builds the checkout beside Ruimte or beside its primary checkout (`../language-servers/php` or `../language-servers/sql`, or the `RUIMTE_PHP_LANGUAGE_SERVER_SOURCE` and `RUIMTE_SQL_LANGUAGE_SERVER_SOURCE` overrides), and discovery never changes a repository. Without one, and always in a compiled daemon, Install takes the release pinned in `apps/server/src/language/php-native-release.json` or `sql-native-release.json`, checked against its checksum and version. `apps/server/README.md` ("Language servers") has the details. The SQL server reads the schema snapshots the daemon takes of a project's connections (`apps/server/src/database/schema-snapshots.ts`), and so does the SQL in PHP strings; which connection a file reads is one person's choice in the private project file (`apps/server/src/database/sql-analysis.ts`).
- `apps/station`: the web client at `station.ruimte.app` (Cloudflare Worker with static assets, `IS_STATION` in `apps/client/src/station.ts`). No local machine there (`state/local-machine.ts`).
- `apps/bench`: the model comparison alone at `bench.ruimte.app` (Cloudflare Worker with static assets): the client's `bench` build (`apps/client/bench.html`, `src/bench`), which draws `ModelsBenchmarks` against the production address book and nothing else.
- `apps/site`: the website at `ruimte.app` (Next.js on a Cloudflare Worker through OpenNext, every page prerendered). `/download/<platform>` looks up the latest release on GitHub and redirects to its build, so a release never needs a new deploy. The scenes on the page are drawn in React, not recorded: when a feature changes what it looks like, its scene in `src/components/film` or `src/components/features` changes with it, and `src/components/app` copies the client's own measures.
- `apps/pulsar-broker`: relays signals between ed25519 keys (Bun). Never reads an envelope and stores nothing. It hands out ICE servers, so no client or daemon holds a TURN secret. See its README.
- `apps/maps-worker`: the map service at `maps.ruimte.app` (Cloudflare Worker, no database). It proxies TomTom's Orbis map display behind a ticket from the address book, holds the TomTom key and logs nothing. The ticket rides in the `authorization` header, checked with the shared `MAP_TICKET_SECRET` and `verifyMapsTicket`; the client takes tiles from it only while its "Map tiles" setting is on and a person is signed in (`apps/client/src/chat/map-source.ts`). Ruimte looks up no addresses (the Search API stays off), so agents give `lat` and `lon` for every `Place`. See its README.
- `apps/pulsar-worker`: the address book at `pulsar.ruimte.app` (Cloudflare Worker, D1): accounts, sessions bound to a key, machines, signed access statements, device links, and the model catalogs a daemon picks up a new model from without a release. See its README.
- `@adecore/ui` (a package of its own repository, `basmilius/adecore`, not a workspace): the components the client and `agents-react` draw with that know nothing of Ruimte (buttons, icon buttons, fields, menus, dialogs, popovers, tooltips, shortcuts, the formatters and the settings dialog). Named imports from four entry points: the root, `/settings`, `/format` and `/testing`. `UIProvider` in `App.tsx` adds its words (the `ui` namespace), hands the formatters their source and mounts the tooltip provider. Its tokens, type scale and shared control rules are `@adecore/ui/theme.css`, which the client's `styles.css` imports before its own tokens and scans with `@source`. It comes from npm; `bun run adecore:link` swaps all shared dependencies to the live `../adecore` folder, and `bun run adecore:npm` restores the pinned registry versions. Restart dev after switching. The source condition and first test preload keep development on current TypeScript with one React. `docs/ADECORE-DEVELOPMENT.md` covers the workflow.
- `@adecore/terminal` (the same repository, released with `@adecore/ui` under one version): `TerminalView`, the xterm pane every terminal of the client draws in (`nodes/TerminalBody.tsx`, the launches panel, the login dialog), with its fit, its tokens (`--term-bg`, `--term-fg`, the ANSI palette) and the page's budget of WebGL contexts. The client feeds it through its handle and keeps its own keys (`terminal/xterm.ts`), the screens of its terminals (`terminal/registry.ts`) and the session behind each. Its stylesheet follows the theme in `styles.css`.
- `@adecore/agents`: the shared agent backends, chat lifecycle, outbox, lineage, tasks, messages, provider accounts and pricing. Import from its root and its area entry points (`/chat`, `/context`, `/coordination`, `/host`, `/providers`, `/usage`, `/testing`). Ruimte's `apps/server/src/chat/chat-manager.ts`, `tasks/wiring.ts`, `context/notices.ts` and `providers/registry.ts` supply application persistence, terminal behavior, commands and words. Model catalogs and pricing snapshots are maintained in Adecore.
- `packages/contracts`: zod 4 schemas for every message on the wire and the types derived from them. Nothing else may define a wire shape, except `agent-contracts`, whose schemas it re-exports.
- `@adecore/agent-contracts`: shared agent, model, provider account, chat and usage wire schemas. `@ruimte/contracts` places them in its existing request/event tables, keeping Ruimte's protocol and generated Swift models stable.
- `@adecore/agents-react`: the shared chat UI, composers, provider settings and usage views. `apps/client/src/chat/host.ts` configures storage with the `ruimte` namespace before any store is used and supplies application actions; `workspace-host.ts` supplies workspace components. Its CSS follows the Adecore theme and Tailwind scans the installed package sources.
- `packages/pulsar`: zod schemas for the wires to services outside a daemon (broker, WebRTC signaling, address book) and `BrokerPeer`. The bytes every signature covers live in `signing.ts`, each with its own prefix line so a signature for one purpose never verifies as another.
- `packages/actions`: what a person can do, as a catalog of typed actions and the registry that runs them, so voice, the UI and the daemon execute the same thing. Every call names its actor: a person, voice, an agent or automation.
- `packages/voice`: what a Voice session does whoever runs it, so the desktop's window and the daemon share one implementation of the hard cases: reports to GPT-Live in appends under the byte bound, one at a time against their acks (`delivery.ts`), the tool loop that runs each call once (`tool-loop.ts`), following the sessions Voice set to work over `ChatItem[]` (`session-watch.ts`, `follow-up.ts`), the replies after an action, spoken-name matching and the mint body. TypeScript without DOM, Node or Bun APIs: sending, running and timers are injected, and the client keeps only adapters over its own state.
- `@adecore/plan`: generic plan schemas and pure plan tree operations. Ruimte's `packages/contracts/src/plan-host.ts` adds chat-scoped wire envelopes, and its plan store and UI remain application code.
- `@adecore/drawing`, `@adecore/diagram`: generic document schemas, pure drawing/diagram operations and exports. `packages/contracts/src/drawing-host.ts` and `diagram-host.ts` add Ruimte's project/view/revision envelopes. The iOS document renderer resolves these installed packages, including their dependency license records.
- `@adecore/editor-core`, `@adecore/editor`, `@adecore/lsp`, `@adecore/editor-react`: document editing, DOM engine, protocol client and shared language features/popups. Ruimte injects its Shiki highlighter and `RUIMTE_EDITOR_KEYMAP`. The client adapters are `language/ruimte-project-language.ts`, `ruimte-editor-language.ts` and `RuimteLanguagePopups.tsx`; they retain the daemon transport, machine diagnostics, app navigation and AI features. Ghost suggestions keep priority over shared completion on Tab.
- `@adecore/merge`: pure three-way conflict analysis and line/word diff operations, shared by the conflict UI and daemon.
- `@adecore/database`: browsing, querying and editing SQLite and MySQL/MariaDB through a native helper. The daemon runs its host (`apps/server/src/database`, behind `database.request`, with Ruimte's checks on connections and files) and keeps a project's connections in `.ruimte/databases.json` and its private twin, never with a password; the compiled daemon carries the helper in `native/`. The client draws the panel, the table and console views, the designer and row editing from it (`apps/client/src/database`).
- `@adecore/service`: generic launchd/systemd definitions and managers. `@ruimte/service/host` supplies Ruimte's service identity, paths, environment and runtime adapters; the desktop and CLI both use that host entrypoint.
- `packages/desktop-bridge`: the shapes the Electron shell and the page it hosts pass over IPC, the `DesktopBridge` interface among them, as types and a few constants. Not a wire in the sense of `contracts`: it never leaves the machine, and it is one place because the preload hands every answer over as `unknown`.
- `packages/csp`: the Content Security Policy of the client as directives, read by the desktop shell and the station; a test holds the `<meta>` tag in `apps/client/index.html` against it. Also the path and policy of a visual's sandbox host page.
- `packages/npm`: the `ruimte` launcher and per-platform binary packages. Manifests are generated by `scripts/build.ts`. The application workflow publishes these only; shared libraries release independently from Adecore.

The old shared packages, PHP workspace and superseded generic editor/tree implementations were removed before the manual test round. Shared behavior comes from Adecore through pinned npm packages or the local development links. Commit `db8f1afee` retains the originals for comparison or rollback. Active FileTree rendering uses `@adecore/ui`; listing caches, persisted expansion keys, Git commands and staging remain in the client.

## Wire protocol

One WebSocket (or the same frames over a WebRTC DataChannel), JSON frames validated with zod on both ends.

- The one binary frame is a `bytes.read` reply to a request that set `binary`: a JSON header and the bytes as they are (`encodeBytesReply`, `packages/contracts/src/bytes.ts`), in binary pieces over a DataChannel (`splitBinaryFrame`). An error and every other frame stay JSON.
- Request: `{ id, type, payload }`. Reply: `{ id, ok: true, result }` or `{ id, ok: false, error: { code, message } }`. Event: `{ type: 'event', event, payload }`.
- `REQUEST_SCHEMAS` and `EVENT_SCHEMAS` in `packages/contracts` are the tables both sides derive `RequestMap` and `EventMap` from.
- `PROTOCOL_VERSION` (`packages/contracts/src/protocol.ts`) is bumped only for an incompatible change, and both ends refuse any other version. `endpoint.info` names every request the machine answers (`features`). A client checks a request newer than 0.18.0 with `machineAnswers` (`apps/client/src/transport/features.ts`, `MachineClient.answers` on iOS) and never catches `unknown-request`. A machine whose `endpoint.info` has no `features` is refused at the gate as older (`transport/protocol.ts`), so 0.18.0 is the oldest machine a client talks to.
- A client fails a request the machine does not answer within 60 seconds, except those that wait on a network, a model or a database (`UNBOUNDED_REQUESTS` in `apps/client/src/transport/link-transport.ts`).
- A new request or event is named `<area>.<name>` in two parts, the area in the singular and the name in lowerCamelCase (`session.runHeld`, `chat.status`), never kebab-case or a third level, and a subscription is `<area>.watch` with `<area>.unwatch`.
- A session id is chosen by the client (the node id), so a node reattaches after a reload.
- `session.attach` answers with the serialized screen from `@xterm/headless`, then streams raw output. A client never replays history. A byte is in the screen or in the stream, never both. A client gets a screen only through `Session.snapshotFor` (attach, resync, clear). It holds back that client's output from the moment of the call until the screen is taken, with no await in between.
- Agent status comes from the CLIs' hooks only (`POST /hooks/<kind>`, `apps/server/src/agents`), never from parsing output. A chat speaks the CLI's own protocol (stream-json, Codex's app-server or ACP), no SDK.
- Chat events carry a `seq` per chat and are logged (`@adecore/agents/chat/chat-log`), so `chat.attach` with `since` resumes.
- A chat's thread goes to whoever attached to it, since it streams word by word; what the chat is _doing_ goes to every client (`chat.status`, on a change only), the way a terminal's `session.status` always has. Without that a node waiting on a person says nothing on a view nobody has open. A client asks `chat.list` on every fresh socket for the standing answer. `project.changed` goes only to the clients that hold the project; every other client hears `project.summary` (`apps/server/src/projects`).
- Bytes for an `<img>` or `<video>` come only from `useMachineUrl` (`transport/machine-url.ts`). No draw site knows whether the link is a socket or a direct channel.
- A direct connection that fails says why and never falls back to the socket.

## Invariants and seams

- A project lives in two files. `<folder>/.ruimte/project.json` is what a team commits; `<folder>/.ruimte/private/project.json` is one person's and is kept out of git by the `.gitignore` the daemon writes once beside it. The private file holds the monotonic `rev`, the sidebar order over both, and per shared node the fields that cannot travel (`resume`, `runtimeMode`, `worktree`, any absolute path, and a name a session gave, for which the shared file carries the name of the kind). Every write goes against the rev it read, and a conflict comes back as `rev-conflict`. Drawings and diagrams follow the same discipline in their own files.
- The unit of sharing is a view, whole. Nothing is shared until a person's `project.save` names it in `shared`: a verb hands back content and never that list, so an agent cannot move a view between the files. A file view pointing outside the project folder cannot be shared at all. The shared file is only written when its text changes, so moving a private node leaves `git status` alone.
- Local state (open view, camera, grid layout, panels) is per client and never goes in `project.json`.
- A view or node of a kind this version does not know is kept as kind `unknown` and written back unchanged. A new kind is only safe to write once the previous release already had that fix.
- Every key of a stored node, view, text or layout survives a Ruimte that does not know it: it is written back unchanged, a duplicate copies it, and a node becoming a view (and back) carries it. The schemas parse loose and the types stay the known fields (`keepingUnknown`, `packages/contracts/src/project.ts`), so a later field must stay correct when an older Ruimte copies it along. A new field is written only from the release after the first one that keeps it, so 0.19 adds no stored field.
- A field that is one person's on a shared view is kept in the overlay and named in the private file's `overlayFields`. A Ruimte that does not know it keeps it in the overlay and never reads it from the shared file. `overlayFields` only acts on keys this version does not know, so a newer release cannot turn off a field an older one depends on.
- A new stored field goes at the end of its schema. An older release writes the shared file in the key order it read, so the same order keeps a private change out of `git status`. A loose `.pick()` of a node (`pickKeepingUnknown`, `packages/contracts/src/project.ts`) drops the keys it did not pick, since loose would keep them unchecked.
- A file node or view is a path, relative to the project folder and absolute outside it (`packages/contracts/src/stored-path.ts`). The bytes are the file system's; there is no store.
- The source address never grants access (behind a tunnel everyone is loopback). A local process proves itself with `$RUIMTE_HOME/local.key` (`apps/server/src/auth/local-secret.ts`); every other client comes in through the account, on a statement from the address book, and proves its ed25519 key from then on. There are no pairing links. Only the local secret may have the machine sign a registration. The daemon never holds an account token.
- A remote client reaches a daemon only over a direct channel, whose signals come over the broker or through the door on the local network (`apps/server/src/pulsar/lan-door.ts`), both through one `SignalGate`. The door answers nothing but its signaling socket, the machine proves its key there before a client says who it is, and the API itself stays on loopback.
- A machine of the account works in another only as a peer: B lets it in on a peer statement, answers it a fixed list (`dispatcher.ts`), starts everything as an agent and bounds mode, depth, project and launches itself (`apps/server/src/peering/CLAUDE.md`). The binding of a node to B lives in `$RUIMTE_HOME/remote` and rides on the wire as `machine`, never in a project file.
- A client the machine let in, or an agent, is not the owner of the machine, and what only the local secret may do stays with the local secret. So no file request of a client (`fs.read`, `fs.grep`, `fs.write`, `fs.rename`, `fs.delete`, `bytes.read`, `archive.list`, `archive.extract`, `GET /fs/file`) reaches under `$RUIMTE_HOME`, except the folders that hold a person's own work or a picture made for them (`apps/server/src/fs/machine-home.ts`).
- An agent's page (a visual) runs only inside the sandbox host page at `VISUAL_HOST_PATH` (`/__visual/`, `packages/csp`) on the client's own origin, in a frame with `sandbox="allow-scripts allow-forms"` and never `allow-same-origin`, under the host page's own policy (`VISUAL_HOST_CSP`), which repeats that sandbox. The Vite dev server (`apps/client/visual-host.ts`), the desktop app's scheme and the station answer it; the frame never leaves it (`appSubframeNavigation` in `apps/desktop/src/web-guards.ts`, the client's `frame-src 'self'`). The daemon never serves a visual inline on its own origin: its bytes go out as a download or over `bytes.read`.
- Agents manage project views and nodes through `ruimte-context`, parsed and validated on the daemon (`apps/server/src/canvas/verbs.ts`). Project writes go through `ProjectStore.mutate`. A refusal is a 422 starting with `refused\t<code>\t<message>`.
- The daemon types a command from a project file only after a person on this machine approved it for that node. The approval is written under `$RUIMTE_HOME/command-approvals` (`apps/server/src/sessions/command-approvals.ts`). Until then the shell starts without the command and the session holds it (`heldCommand`, `session.runHeld`). A person's `project.save` that sets the command counts as approval; a verb never does.
- A child agent never gets a wider permission mode than its parent (`@adecore/agents/modes.ts`, bound to a verb in `apps/server/src/canvas/mode.ts`); the ceiling rides on every `start-agent` entry. A `--worktree` agent gets its own worktree under the machine's worktree folder, `$RUIMTE_HOME/worktrees` unless a person on the machine chose another, never removed automatically. A worktree merge (`apps/server/src/git/worktree-merge.ts`) runs in the checkout that has the target branch out, never stashes and never moves a ref behind a working tree; an agent merges only the worktree of a node it opened, into a checkout without tracked changes, and a conflict is taken back for it. An agent's merge only merges: the child keeps running and its worktree and branch stay until a person removes them.
- Per-area invariants and the product rules of one feature sit in a `CLAUDE.md` beside the code and load when a file there is read: `apps/client/src/browser` (parked pages, no pinch-zoom), `apps/client/src/canvas` (selection, `bodyFocusId`, connectors), `apps/client/src/dictation` (Speech to Text, who may start a recording, where its text lands), `apps/client/src/shell/panels` (where the rules behind the git panel live), `apps/client/src/state` (keys, attention), `apps/client/src/transport` (machine holds), `apps/server/src/agents` (the CLIs' global settings), `apps/server/src/browser` (where a page lives, driving by address), `apps/server/src/canvas` (agent verbs, depth, mode ceiling), `apps/server/src/chat` (forks, plans), `apps/server/src/computer` (grants, one agent at a time), `apps/server/src/database` (what agents read and write, passwords), `apps/server/src/devices` (driving a device), `apps/server/src/git` (checkouts, the panel, conflicts, pulls), `apps/server/src/language` (documents, merging, restarts, installs), `apps/server/src/launches` (what an agent may run and stop), `apps/server/src/outbox` (outbox, tasks, ending children), `apps/server/src/power` (sleep with the lid closed), `apps/server/src/projects` (file layout, versions), `apps/server/src/provenance` (who wrote which lines, an observer that only notes), `apps/server/src/visuals` (render children, the proxy, local images, visual replies), `apps/server/src/voice` (Voice run by the daemon: the matrix, who a session acts for, the lineage of what it starts, audio and data).

## Product rules

Decisions the code cannot show. Do not reverse one without asking Bas.

- Three things wake a chat, each once: a finished task wakes the chat that delegated it, a message wakes the chat it was sent to, and a PR-watch a person turned on for one chat wakes that chat once per terminal check state of the current head, or new review; the wake runs through the outbox (an observer only notes). A message goes one step deep, so the turn it opened wakes nobody, and neither does a PR-watch's; a terminal is never woken at all.
- A child that stops on a limit pauses its task: the turn says which limit and when it lifts (`limit`, read only from the CLI's own stream), the task stays open with `paused`, and its parent sleeps on until the child finishes after the reset. An overload the daemon does not try again is an error like any other and fails the task.
- A task settles only once its child is really done. A turn that ends while its CLI still runs work in the background (a background subagent, a Claude workflow, an agent Codex spawned: `@adecore/agents/chat/background-work.ts`) settles nothing, and the parent is not woken in between. The task settles on the turn the CLI opens by itself once that work ended, on the child's last turn when its CLI opens none (Codex), or on `ruimte-context done`, which works all the while. A command or a monitor the child's CLI runs in the background (its own or one a subagent of it started, as the chat's `background` shows it) holds the task too, but for at most 30 minutes from the moment it is all that is left, since a dev server never ends. That limit is a `background-limit` outbox entry with a time: it survives a restart, runs once and lapses when the task settles otherwise. When it passes, the task settles on the child's last result, which then names the commands that still ran. A restart of the daemon takes the CLI and its commands down, so a task only commands held then fails at once with the child's last result and a line naming what was lost, and wakes its parent once, as when the CLI goes within one run. Subagents and workflows have no limit. An active goal (`/goal`) holds the task the same way and with no limit, through every turn its CLI opens toward it: the task settles once the goal is met, paused or cleared and the turn has ended, and fails with the child's last result when the CLI goes while the goal is still active.
- Resuming after a limit runs on a clock, and only when a person turned it on: a machine setting (`resumeAtReset` in `endpoint.json`, off by default) and a chat's own switch beside it, which absent follows the machine. A `resume-limit` outbox entry carries the time: the reset of a usage limit, or 1, 5 and 15 minutes after an overload, after which the overload is an ordinary error. The entry lapses when a person writes first, stops the chat, turns a switch off or the node goes. These two, the limit on a child's background commands, the end of a snooze (`apps/server/src/push/snoozes.ts`), the poll of a PR-watch (`apps/server/src/github/pr-watch.ts`), the hold on a push while a person is at a desktop (`apps/server/src/push/service.ts`) and the reconnect of a link to another machine while work for it is owed (`apps/server/src/remote/connect-peer.ts`) are the only work the daemon schedules on a clock. A PR-watch polls only while a person has one on, backs off while nothing changes, and ends when a person stops the watch or removes the chat (a turn's Stop leaves it), when the pull request is merged or closed, or after 7 days. A reconnect backs off while the machine does not answer and ends when nothing is owed to that machine any more, when a person stops the task or removes the link, or after 7 days, when every task still owed to that machine fails with a line that says so and wakes its parent once. Leaving the account fails every task owed to a machine at once in the same way.
- A child with a task that waits on a question or an approval leaves its parent one note per request (`deliver-waiting`, `@adecore/agents/tasks/waiting-child.ts`), and does not wake it. The note is due 15 seconds after the request came and is written only if the request still waits then, so a request settled at once leaves none. A child on another machine leaves no such note: its requests wait on that machine, where a person answers them, and its parent hears only the result. A parent may answer a question of a child it opened itself with `ruimte-context answer`, the way a person's `chat.answer` does, and whoever answers first wins; approvals, logins and every other card stay with the person. A parent may also `ruimte-context read` a child it opened itself without a line from it, by the same lineage. A chat may read another chat of its project without a line once a person attached that chat to one of its messages with `@` (`apps/server/src/context/chat-references.ts`), checked again at every read, so a chat that left the project is closed to it again. Every other node still needs a line.
- A push to a phone waits while a person is at a desktop. Each client reports `presence.report` from the system's idle state (input in any app counts, a locked screen does not), and the report lapses after a minute. A wait or an attention alert waits 60 seconds, an approval 10, and goes out only if it is still unread or unanswered then. A finished turn or a process warning that came due while the person stayed goes nowhere. Once the person leaves, everything still held goes out at once. An alert someone asked for (`ruimte-context alert`) never waits.
- A terminal's permission prompts and questions stay in its TUI: a person chose the TUI for a reason. Ruimte only shows that it needs you (status, stack card, notification) and never answers for it; an AI chat is where approvals are answered from the app or a phone.
- Every shortcut needs a modifier. The only bare keys are a drawing view's tools, and only while no text is typed and no dialog is up, the widget keys inside a prompt card (arrows, Home, End, Space, Enter), only while the focus is in that card, and Space for Quick Look (Space or Escape again closes it), only while the focus is on a file in the tree of the files panel, on macOS and for a project on this machine.
- Never highlight the canvas grid in the accent color. Type: only the four sizes in `@theme`, no bracket sizes, nothing below 12px, except a model's badge (11px, in capitals); Geist only for the wordmark, Kalam only for drawing text.
- The wire only gains optional fields, new requests and new events. Never a new `ChatItemSchema` member or enum value in a chat or push payload: the iPhone app validates `chat.attach` and `chat.history` whole.
- Agents cannot type into or close another node's session or start a command through a verb (only `agent` starts anything); `--cwd` stays inside the project folder or its worktrees. Every other door an agent has into a feature is that feature's own, with its rules beside its code: a launch, the one exception that starts a command (`apps/server/src/launches`), a browser node (`apps/server/src/browser`), a device node (`apps/server/src/devices`), computer use (`apps/server/src/computer`) and a database (`apps/server/src/database`). In short: an agent starts, restarts or stops only a launch a person approved as it stands now; drives a browser node only by address, over a line; drives a device only by screenshots, taps and its tools, with a path only inside the project folder or its worktrees, over a line (a chat view by naming the canvas instead, see below), and never starts, stops, restarts, erases or folds one or sets its camera; operates an app through computer use only after a person let it into that app; and writes to a database only on a connection a person set to write, never from `supervised`.
- An AI chat that is a view of its own arranges a canvas the way a person does. No line can run to a view, so with `--view <canvas>` it adds, edits, renames, arranges and groups that canvas's nodes, draws lines between them, and reads and operates every node there without a line (`read`, `node edit`, `browser`, `device`); a node it adds gets no line to it. Without `--view` those refuse with `view-required`. An agent that is a node on a canvas keeps to its lines exactly. The rest holds for a chat view too: it never types into or closes another session, and the mode ceiling, `--cwd`, launch approvals and the database and computer use grants keep their own checks (`apps/server/src/canvas/chat-view.ts`).
- Whatever the daemon enforces against an agent (depth, lineage, tasks) lives under `$RUIMTE_HOME`, never in `project.json`, which an agent with a shell can rewrite. An observer only notes; only the outbox acts. Nothing removes a worktree on its own.
- Nothing reads a vendor credential (keychain, `~/.codex/auth.json`, usage endpoints); plan windows come from the CLIs. The exceptions are keys a person typed into Ruimte. One is for a provider with no CLI, which the daemon may also send to that provider's own usage endpoint (NanoGPT's `/usage`). The other is the OpenAI key for Voice, typed into the desktop settings (or `ruimte voice key set`): the shell hands it to the daemon on the local secret, and the daemon sends it only to OpenAI, in the `Authorization` header (`apps/server/src/voice`). One vendor credential is read, by Bas's choice: Grok shows its plan only in its own interface, so the daemon reads the token `grok login` left in an account's `auth.json` (xAI's own sign-in only, never an API key), never renews or writes it, and sends it only to the billing endpoint the CLI asks (`apps/server/src/usage/grok-plan.ts`). A stuck process gets a warning, never a signal a person did not press.
- Closing a project is one client's. The machine keeps it, and keeps its sessions running, as long as another client still has it open; only the last client out ends them and drops the project under Recent. Closing a window is not closing its project: the window writes what it had and lets its sockets go, and the project stays open on the machine. Which projects a person keeps in their own menu is that client's and is written there, so closing on a laptop leaves the iPhone where it was. A socket that drops ends nothing.
- A page never sees a refresh token, a daemon never holds an account token, and accounts are never merged.
- A machine is on at most one account and is shared only with its owner: only the local secret (the app on it, `ruimte login`) puts it on one, another account gets `machine-has-account` until a person on the machine leaves the first, a machine takes only a statement v2, and a machine on an account only one of that account (`apps/server/README.md`, "One account per machine").

## Conventions

- TypeScript in the Bun workspaces, Swift in `apps/ios`. 4 spaces, LF; `.editorconfig` is the rule.
- American English in code, comments, commit messages and UI text. No em dashes or en dashes anywhere.
- Always curly braces, also for one-line early returns. No one-letter variable names except `i`, `e`, `x`, `y`.
- Named top-level functions use function declarations, exported with `export function`. Keep functions produced by factories or wrappers as `const`, and mutable callback slots as variables.
- Arrow functions for callbacks and inside functions; class methods are never arrow properties.
- Comments explain WHY, never what the code already says.
- Keyboard shortcuts are bound on `window`, once: the window's own in `shell/app-shortcuts.ts`, anything acting on the project once, by the workspace, in `canvas/canvas-shortcuts.ts`, so the start screen has none of those. Never per cell or per node.
- A new command is a row in the command table (`apps/client/src/shell/command-table.ts`): its place in the menu, its palette row, its shortcut and the listener that binds it. Only the generated rows (a row per view, launch or agent, roles, submenus) stay in `shell/menu/model.ts`. The menu only shows a key: a command its accelerator fires is dropped by the shell when the page had that key first, since its own listeners answered it (`createMenuCommands` in `@adecore/shell`); a page in a browser node never sees it, and an item picked through accessibility or a key sent to a window that is not key never reached the page, so there the menu answers.
- A new surface that draws data of its own gets an `ErrorBoundary` (`@adecore/ui`), keyed so it resets only while it holds an error.
- A zustand selector that builds a new array or object per call loops forever under `useShallow`: select the object and derive from it in render.
- The client and the TypeScript of ADE CORE's React packages build with the React Compiler, in Vite and in the DOM and browser tests but not the unit run (`apps/client/react-compiler.ts`), and oxlint holds the client to its rules. Write no `useMemo`, `useCallback` or `memo` the compiler covers; keep one only where an effect depends on the value, for a row of a long list, or in a function the compiler leaves as written. A value read in render from outside React (a mutable object, a version counter) goes through `useSyncExternalStore` with a snapshot, and a hook is called by its `use` name, never handed on as a value. A language or region change empties every compiled cache (`src/compiler-runtime.ts`).
- The start screen and the workspace are separate chunks, so the station's first load carries no workspace code. Nothing that `main.tsx` or the start screen imports statically may reach `shell/WorkspaceShell.tsx` or what only it draws. A panel, view or dialog that not every workspace opens loads through `lazyNamed` or `lazyDialog` (`@adecore/ui`), inside its `ErrorBoundary`. The library's `prefetcher` fetches the workspace once the start screen is idle, and then everything that loads through those two one module at a time once a workspace is idle; a lazy module registers there by itself. A chunk that fails to load reloads the web page once (`src/stale-chunks.ts`), unless only a prefetch asked for it.
- UI: only semantic tokens from `@adecore/ui/theme.css`, `@adecore/agents-react/theme.css` and `styles.css`, no raw colors elsewhere. A border is an alpha over what is behind it, never a gray of its own, and every surface clips its background to the padding box so the line mixes with the ground and not with the surface it edges. Tooltips are `Tooltip`, never a `title` attribute. An icon button is `IconButton`, and related ones go in a `ButtonGroup`. Icons are Lucide through `Icon`; the only exceptions are file icons (`FileIcon`, `@pierre/trees` with its own colors), provider marks (`ProviderLogo`) and the mark of Ruimte itself (`RuimteMark`, in `currentColor`). No fractional pixels; a `rem` or `em` must resolve to whole pixels.
- UI that knows nothing of Ruimte belongs in `basmilius/adecore`, and so does a fix to it. When Ruimte needs something the library lacks or draws wrong, open an issue there with `gh issue create --repo basmilius/adecore`, titled `<Component>: <the need>`, labeled `Ruimte` and `Bug` or `Enhancement`, with three sections: `## Problem` (what is missing or wrong, the call sites here as `path:line`, and how Ruimte works around it today), `## Wish` (the need as what a person does or sees, not a fix; a proposed API is optional) and `## Impact on AfterMotion` (search `../aftermotion` for the same component or pattern and name the call sites a change would touch and whether it would change what they draw or break them, or say there are none). Edit a shared repository only through its real filesystem path, never through `node_modules`, and only when the task authorizes changes there. Validate ADE CORE changes there and in linked Ruimte, and keep its commits separate. Never copy shared implementations into Ruimte.
- After a dependency change, run `bun install` in that repository before relinking ADE CORE in Ruimte. Push Ruimte code using a new ADE CORE API only together with a bump to the already published dependency in its manifests and `bun.lock` (`bun run adecore:bump <version>` moves every pin at once and refuses a linked checkout), after `adecore:npm`, `adecore:status --npm` and relevant npm consumer checks pass. Linked checks do not validate the registry install used by CI. No pre-push hook is required. The source conditions in the current release builders are deliberate: npm consumer checks bundle published sources, while ADE CORE CI's `test:pack` validates packed `dist` and source exports. See `docs/ADECORE-DEVELOPMENT.md`.
- In anything a person reads (UI text, tooltips, errors, toasts, empty states) a daemon is a **machine**. Code, comments and docs say daemon.
- The interface is written in English and in Dutch (`apps/client/src/i18n`, react-i18next, a file per namespace per language). English is the source and the fallback; a key that has no Dutch reads English rather than showing itself, and `locales.test.ts` fails the run when the two drift apart. Conventions, the glossary and what stays untranslated are in that folder's README. Tests read the English words through the `preload` in `bunfig.toml`, so a pure function that builds a label is asserted on the sentence and not on the key.
- Every number, date, time and duration a person reads is written by `@adecore/ui/format`, the only place in the client that builds an `Intl` formatter. It reads the two settings through the source `apps/client/src/format/source.ts` hands it at startup. Two settings decide what it looks like and they are apart on purpose: the language writes the words, the region writes the order, the separators and the clock. The region follows the language unless a person says otherwise, and `system` is what the desktop shell passes in (`app.getSystemLocale()` beside `app.getPreferredSystemLanguages()`); Chromium's own locale is the language of the bundle, so it would write `08:00 AM` on a Dutch Mac. An English interface on a Dutch machine is a pair a person can set, and it reads `19 Sep, 08:05`. A surface that would otherwise sit still through a region change calls `useFormatLocale()`.
- Tests: `bun run test`, next to the code (`foo.test.ts`). No test in the default run depends on wall-clock timing, a real shell or a file watcher: use a fake (`FakePtyAdapter` in `apps/server/src/pty/fake-pty.ts`, an injected clock or watch, `jest.useFakeTimers()`, `setSystemTime`) and await what the code resolves. `bun run lint` refuses a read of the wall clock in a `*.test.ts(x)` outside a fake clock's setup (`scripts/check-test-clock.ts`). A test that fails on a timeout is made deterministic or deleted, never given a longer timeout.
- Real shells, watchers, sockets or processes go in `*.integration.test.ts` (`bun run test:integration`), which cleans up its own processes. A real `git` fixture is fine; build it once per file (`apps/server/src/git/test-repo.ts`). A test whose subject exists on one platform only skips with `skipIf(process.platform !== '<platform>')` and imports that platform's module inside, never by catching a missing tool.
- CI runs unit tests in two shards with isolated files, balanced by the per-file durations in `test-timings.json`; `bun run test:timings` measures them again. Type, lint and formatting checks and the unit shards run on Linux, since every platform a unit test names is passed in. The core integration tests and the packaged daemon run on macOS and on Linux (`ubuntu-latest`; the packaged daemon on `ubuntu-22.04`, the release's glibc floor). Generated native fixtures, builds and the file system tests again (a case-insensitive volume) run on macOS only. `bun run check` includes types, generated files, lint and formatting. Checks, the client/desktop build, core integrations (`--suite core`) and the packaged daemon (`*.package.integration.test.ts`, `bun run test:package`) run independently; the final CI check requires them all. The default integration command still includes the packaged daemon.
- Tests that need a running simulator or physical device go in `*.device.integration.test.ts` and run only on request with `bun run test:devices`. Default integration discovery excludes them before loading files, so CI never probes for a device.
- Tests of what a person does in the window go in `*.dom.test.tsx` and run through `bun run test:dom`, in happy-dom that `dom.bunfig.toml` preloads before React; the unit run leaves them out. They draw the whole window where they can (`renderApp` in `apps/client/testing/dom.tsx`) against a `FakeMachine` put behind the pool (`testing/fake-machine.ts`, `fake-workspace.ts`), and assert what a person sees and what goes over the wire, never an action or command id. CI runs them on Linux.
- Tests that start a browser or Electron go in `*.browser.integration.test.ts` and run only on request through `bun run test:browser` or the manual Browser tests workflow. They are excluded from CI, including release checks. The browser command builds the client before testing.
- `bun run format` and `bun run check` (typecheck, generated files, oxlint in every workspace, where a warning fails too, and `format:check`) pass before a commit. Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`).
- Written from scratch. Do not copy code from any other product; sharing ideas and npm packages is fine.

## Releasing

A release runs to the end without asking. Bas names a version and the next thing he reads is that it is live.

- CI decides, not this machine. The `ci.yml` run on the commit being tagged has to be green; nothing is built, checked or tested here for a release, and a published build is never downloaded to try the daemon in it.
- A red CI is fixed before the tag: find it, fix it, push to main, wait for green. Only what Bas alone can decide comes back to him.
- The notes ride on the tag, so the draft is never empty and publishing takes no second edit. Write them to a file and tag with `git tag -a v<version> -F <file> --cleanup=verbatim`; without that flag git strips every `##` heading out of the message. `release.yml` builds macOS and Linux into that draft, and once the run succeeds it is published as Latest at once.
- Publishing starts `npm.yml`, which puts `ruimte` and its three platform packages on npm at the same version. `docs/RELEASE.md` has the recipe, the secrets and what has broken in them.
- Adecore libraries release independently. Ruimte pins the consumed version in its manifests and lockfile; `libraries-v*` tags no longer publish libraries from this repository.
