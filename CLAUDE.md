# Ruimte

Terminals, agents and browsers on one infinite canvas. Read `README.md` for the principles and `docs/DECISIONS.md` for the decisions that are not in the code, the traps already paid for, and what comes next. This file is for anyone (human or agent) changing code.

## Layout

Bun workspaces (`bun install` at the root):

- `apps/ios`: the native iPhone/iPad client, minimum iOS 26. SwiftUI shell, UIKit timeline/canvas, SwiftTerm terminal, local `RuimtePulsar` and `RuimteTransport` packages, notification-service and ActivityKit extensions. `project.yml` is XcodeGen input; regenerate and commit the Xcode project and Package.resolved for Xcode Cloud. User state and build output stay ignored. No `package.json` or local daemon. Generate with `bun run --cwd packages/contracts generate:swift` and `xcodegen generate --spec apps/ios/project.yml`; `bun run check` checks generated models and fixtures. One ed25519 key and SessionVault across scenes, shared connection and attachment leases per machine. Build, device checks and APNs/distribution setup are in `apps/ios/README.md`. Continue implementation autonomously; device measurements remain explicit acceptance evidence.
- `apps/client`: the React UI (Vite). Never imports Node or Bun APIs. Talks to the server only through the `Transport` interface. One window holds one or more workspaces (`transport/connections.ts`), each a project on a daemon with stores of its own; the sidebar lists the workspace in focus or every one in the window (`settings.sidebarScope`).
- `apps/server`: the daemon (Bun runtime). Owns sessions, PTYs and persistence. Serves the WebSocket API on `localhost:4210` by default (`--host`, `--port`), and a built client with `--serve`. In dev (`bun dev`, an unpackaged desktop app) it runs on `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, so it never meets an installed Ruimte; pair against it with `bun src/main.ts pair --port 4211`.
- `apps/desktop`: the Electron shell. One window, the client inside it, the daemon next to it. Only window chrome, native dialogs, guest devtools, the power block, what the agents add up to, the application menu, the release notes, the daemon's local secret, signing in to the address book and the shell's own versions cross IPC (`src/preload.ts` mirrors `apps/client/src/desktop/bridge.ts`). Signing in is `pulsar` on the bridge: the page runs the PKCE login (`apps/client/src/pulsar`, free of anything a phone lacks), the shell listens on a random loopback port for the redirect (`src/pulsar-login.ts`, which works unpackaged as well, where a `ruimte://` scheme would not; the same listener carries a login that adds a provider to the account, whose code the page trades with its own access token rather than through the shell) and holds the refresh token encrypted with `safeStorage` in `userData` (`src/pulsar-store.ts`, through `SessionVault` in `packages/pulsar`) beside the ed25519 key the session is bound to (`fileSessionKey`, `pulsar-key.bin`), and the page only ever gets access tokens. A page without the shell signs in on its own where the address book sends a login back to its origin (`apps/client/src/pulsar/web.ts`: `station.ruimte.app` and the Vite dev origin), with a full-page redirect and the session in IndexedDB bound to the client's own key; anywhere else it is told signing in works in the desktop app and at `station.ruimte.app`. A sign-in or an added provider started in the account section opens the Remote pane with how it went, a line that stays until it is dismissed or the next attempt (`pulsar/confirmation.ts`; on the web the flag rides in the pending login, spent on the way back), while approving a machine and the station welcome carry on with a next step of their own; the shell brings its window to the front once the loopback redirect lands. A browser page has a preload of its own (`src/guest.ts`, registered on the browser partition and never on the sealed preview one) that talks to its `<webview>` element rather than to the shell: wheel samples while the client says swiping is on, a mouse's side buttons and Cmd+[ / Cmd+] from inside the page, read in `browser/registry.ts` and decided in `browser/swipe.ts`, which ignores a pinch. A page does not pinch-zoom: Chromium scales only the top-most widget, never a `<webview>` guest (see `docs/DECISIONS.md`). The release notes come from the GitHub REST API rather than the updater's feed (`src/release-notes.ts`: drafts, prereleases and tags that are not semver left out, kept in `userData/release-notes.json` with an ETag, refreshed with every update check of a packaged app and when the dialog opens), and the client draws them in a dialog of its own (`shell/ReleaseNotesDialog.tsx`, opened from a link in About) and shows one toast the first start after an update, with the version it last saw in localStorage under `ruimte.seenVersion`. On macOS the first menu column is a template of its own: About sends `menu:settings` with its pane and Settings with none (`onOpenSettings`), and the client opens that pane even when the dialog is already on another one, or the dialog where it was, and everything else keeps its role, Quit included, so the question before quitting still runs. `versions` carries Electron, Chromium and Node for About. Both are optional on the bridge, like every method added after the first release. The power block is `setKeepAwake`: the client works out that an agent is in the middle of a turn (`state/keep-awake.ts`, driven by the session and chat stores) and the shell holds a `powerSaveBlocker` for as long as it is asked to, dropping it on a reload and with the window. It is a client setting (`agentsKeepAwake`, off unless a person turned it on) and the row is not drawn where there is no bridge to keep the promise. `setAgentActivity` is the same seam for attention: the client counts (`state/attention.ts`) and the shell badges the dock with the nodes waiting to be looked at and asks before quitting while an agent works, so it never counts anything itself. A packaged app on macOS or Linux runs the daemon as a background service that outlives it (`src/service`, with the definitions and the managers in `packages/service`): a LaunchAgent (`~/Library/LaunchAgents/app.ruimte.daemon.plist`) or a systemd user unit (`ruimte-daemon.service`) running the binary in the bundle, behind a `ServiceManager` interface with a fake in the tests. On start the shell asks `/health` and attaches to the same build (`build` is the id `compile.ts` stamps in and writes beside the binary as `ruimte.build`), restarts the service onto a new binary, starts it, or spawns its own daemon as before when the service is off (`service/decide.ts`). The switch is the shell's (`userData/background-service.json`, on unless a person turned it off), drawn in the dialog of This machine through `backgroundService` on the bridge; a switch takes effect when the app quits, and "Stop the machine" is a quit that also stops and removes the service until the next start. An AppImage, Windows and the dev app get no service, and the dev app never touches launchd or systemd. `bun dev` starts it next to the client and the server, and `bun run dev:desktop` starts it alone; unpackaged it is "Ruimte Dev" with a `userData` of its own. A packaged app (`bun run dist`, `electron-builder.yml`) carries the compiled daemon (`apps/server/scripts/compile.ts`) and the built client as resources. On macOS and Linux a packaged app runs the daemon as a background service (`src/service`, launchd or a systemd user unit, with `RUIMTE_SERVICE=1` in its environment). An update never ends work silently: the daemon under the service reads `ruimte.build` beside its binary and exits once idle so the service starts the new one (`apps/server/src/service`, idle is `workOf`), and a new app that finds an older build with work running asks `GET /machine/work` (local secret only) and leaves the restart to a dialog in the client (`shell/MachineUpdateDialog.tsx`, "When idle" by default) instead of restarting it.
- `apps/pulsar-broker`: the Pulsar broker for remote access (Bun). A peer announces an ed25519 key and signs the broker's nonce; the broker holds a `Map` from key to socket and passes a signal from a client to a machine or back, with limits per address and per key and nothing on disk. It never verifies or reads an envelope, since the receiver does. A peer that is `ready` may ask `ice` for the ICE servers it may use, limited per key like announcements: a `TurnProvider` answers (`src/turn.ts`: `noTurn` unless `--turn` says otherwise, `sharedSecretTurn` for a coturn on the same host with TURN REST credentials bound to the key for 24 hours, `cloudflareTurn` for Cloudflare's service), so the daemon and the client never see a TURN secret. `deploy/` holds the systemd unit, the Caddyfile, coturn's config and the drop-ins that give coturn and the broker one secret file; nothing deploys itself. Its README has the steps to try it against the Docker container.
- `apps/pulsar-worker`: the Pulsar address book, a Cloudflare Worker with D1 at `https://pulsar.ruimte.app` (wrangler config, migrations and README in the app folder). Signing in with GitHub or Apple behind a redirect allowlist (`isAppRedirectUri`): an account holds one identity per provider (`src/identities.ts`, the `identity` table, unique on provider and subject), a signed-in person adds the other provider from the Account section with a single-use link token bound to the session and completes it with that session and the login's PKCE verifier, an identity on another account is refused and never merged, and the last one cannot be removed; Apple (`src/apple.ts`) answers with a form post, so its login cookie is `SameSite=None`, its client secret is an ES256 JWT from the `.p8` and its `id_token` is checked against Apple's keys with the verifier's hash as the nonce, and until its four secrets are set `/v1/providers` leaves it out and no client draws the button; sessions bound to a key that signs every refresh, the machines on an account (and the ones a person removed), and access statements signed with a key whose public half is pinned in `packages/pulsar`, plus linking a machine with a code (`src/device.ts`, `/v1/device/*`, the `device_link` table); its tests run the bundled Worker in Miniflare under `bun test`. Deployed by `.github/workflows/pulsar-worker.yml` on a push to main touching it or `packages/pulsar`.
- `apps/station`: the web client at `https://station.ruimte.app`, a Cloudflare Worker with static assets. `bun run build` there builds the client with `vite build --mode station` into its `dist` and lays `public/` (the web app manifest and the app icons) over it; the Worker answers every path with the security headers in `src/headers.ts`, and a path that is no file with the page. Deployed by `.github/workflows/station.yml` on a push to main touching it, the client or `packages/*`. In that build (`IS_STATION` in `apps/client/src/station.ts`) the row of this machine is a `DormantTransport` that opens nothing, pairing with a plain http machine is refused with a sentence (`mixedContentRefusal`), and the main column shows `shell/StationWelcome.tsx` (sign in, then the account's machines) until one is picked. A page that turns visible reconnects every machine waiting out a backoff (`transport/wake.ts`), since Safari on iPadOS stops sockets in the background.
- `packages/contracts`: zod 4 schemas for every message on the wire, plus the TypeScript types derived from them. Both apps import from here; nothing else may define a wire shape. `REQUEST_SCHEMAS` and `EVENT_SCHEMAS` are the tables both sides derive `RequestMap` and `EventMap` from.
- `packages/pulsar`: zod schemas and signed bytes for remote access (the broker, signaling, the address book). It describes the wires to services outside a daemon; `packages/contracts` carries its signal envelope for `direct.signal` and depends on it. `BrokerPeer` is a peer's side of a broker socket without the socket, used by the daemon, the client and the broker's tests alike.
- `packages/drawing`: the pure part of a drawing (geometry, hit tests, the rough and freehand paths, the SVG painter, the reading order). No DOM: the client uses it for hit tests and export, the daemon for what an agent reads. The canvas painter stays in the client, which is the only side with a `CanvasRenderingContext2D`.
- `packages/diagram`: the pure part of a diagram (`layoutOf`, the shape paths, `toSvg`, `readingOrder`). No DOM and no layout library: the layers and every coordinate come out of the file alone, so the view, an export and the daemon draw the same picture.
- `packages/pulsar`: zod 4 schemas for the two wires of remote access, apart from `packages/contracts` because neither is the wire between client and daemon: the broker protocol (announce a key, answer its challenge, relay to a key), the WebRTC signaling that rides inside a relay or over a connection that is already authenticated, and the address book API (the machine list, registering a machine, access statements). The bytes every signature covers are functions in `signing.ts`, each opening with a prefix line of its own so a signature for one purpose never verifies as another. No servers and no transport. `BrokerPeer` is a peer's side of a broker socket without the socket, used by the daemon, the client and the broker's tests alike.
- `packages/service`: the background service without Electron, shared by `apps/desktop` and `ruimte service`. The pure definitions (`launchAgentPlist`, `systemdUnit`, `definitionRunsProgram`, which is how each side leaves the other's service alone, since both write the label `app.ruimte.daemon` and the unit `ruimte-daemon.service`), the `ServiceManager` for launchd and systemd over an injected command runner and file system, and the real `runCommand` and `diskFiles`.
- `packages/npm`: Ruimte on npm for a machine without the app, in the esbuild pattern. `ruimte` is a launcher bundled for Node (`src/bin.ts`, the decisions in `src/launcher.ts`) that execs the binary of `@ruimte/darwin-arm64` (Apple silicon only), `linux-x64` or `linux-arm64`, its `optionalDependencies` pinned to the same version, and says so on Windows. Nothing there is checked in as a package: `scripts/build.ts` writes every package.json with the release version (`src/manifest.ts`) around the binaries `apps/server/scripts/compile.ts --target <os-cpu> --outdir <dir>` built, and `scripts/publish.ts` publishes the platform packages first and `ruimte` last, skipping a version the registry has (`src/publish-plan.ts`). `.github/workflows/npm.yml` runs both on a published release or by hand, with Trusted Publishing (OIDC, environment `npm`) and no token; the darwin binaries build on macOS, because only `codesign` repairs the signature Bun leaves. `placeholders/` holds the `0.0.0` packages that had to exist before npm could trust the workflow. The binary serves the commands itself: `ruimte service install|uninstall|status` (`apps/server/src/cli/service.ts`) copies it with `ruimte-context` and `ruimte.build` to `$RUIMTE_HOME/bin` and points the service there, never at the npx cache, refuses a service that runs another program, and explains lingering on Linux without enabling it; `ruimte --version` prints the version.

Shared config at the root: `tsconfig.base.json` (every package extends it), `.oxlintrc.json`, `.editorconfig`, `bun.lock`. `bun run check` runs `typecheck` in every workspace and then oxlint. In dev the Vite server proxies `/ws` to the daemon, so the client always connects to its own origin.

## Wire protocol

One WebSocket. JSON frames validated with zod on both ends.

- Both ends speak one `PROTOCOL_VERSION` (`packages/contracts/src/protocol.ts`), bumped only for an incompatible change, and refuse any other: a socket offers it as `?protocol=N` and a daemon on another version closes it with 4406, the client checks `endpoint.info.protocol` before it calls a socket open (`transport/protocol.ts`, where a daemon without one is the older case), and a direct channel carries it in `direct.challenge` and the proof. The refusal says which side has to update, on the machine's row and where the connection fails.
- Request from client: `{ id: string, type: string, payload }`. Reply from server: `{ id, ok: true, result }` or `{ id, ok: false, error: { code, message } }`.
- Event from server (no `id`): `{ type: 'event', event: string, payload }`.
- The same frames can travel over a WebRTC DataChannel instead of the socket, an experiment a person turns on per machine ("Direct" in the Machines pane, `Endpoint.direct`). The client offers over a socket it already holds to that daemon (`direct.signal`, answered with `direct.signaled`, carrying the `packages/pulsar` envelope; no broker yet) and closes that socket once the channel is in. The channel inherits nothing from it: its first frames are the challenge handshake (`direct.challenge`, then `direct.key` or `direct.secret`, then `direct.accepted` or `direct.refused`), signed over the DTLS fingerprints of the offer and the answer (`channelBinding` in `packages/contracts/src/direct.ts`), and a frame is split into pieces under the SCTP message size (`splitFrame`). The daemon side is `apps/server/src/pulsar` on werift (`DirectPeers` answers offers from wherever they came, `directChannel` is the `ClientChannel` adapter, `authenticateChannel` the handshake); the client side is `transport/webrtc-link.ts` on the browser's own `RTCPeerConnection`. A direct connection that fails says why in the machine's row and never falls back to the socket. ICE takes its servers per attempt: on the client the `directStunServer` setting merged with what the route hands out (`mergeIceServers` in `transport/ice.ts`; over the broker the answer to `ice`, asked once per broker socket before any signal goes out), on the daemon `--stun` plus the credentials `BrokerRelay` holds, through `DirectPeersOptions.iceServers()` and cut to the one TURN URL werift 0.24.4 reads (`weriftIceServers`). Nothing prefers the relay: ICE picks a direct pair on its own. A connection whose selected candidate pair has a relay candidate on either end sets `relayed` on `ConnectionState` (`relayedFromStats`, read from `getStats` on every liveness tick, so a path that moves off the relay is seen), and the machine's row and the connection tooltip say "via relay". The bytes an `<img>` or a `<video>` draws (a chat attachment, a project icon, an image or video file) come from one hook, `useMachineUrl` (`transport/machine-url.ts`), and no draw site knows which transport is on: over a socket it is the HTTP route with the ticket, over a direct connection it is `bytes.read` in 256 KiB pieces the client pulls one after the other (`readBytes` in `apps/server/src/bytes`, with the routes' own lookups and at most 32 MB) turned into a blob URL from a refcounted cache (`transport/blob-cache.ts`), even where the address happens to answer HTTP. A quiet channel is pinged after 2 s and ended after 10 s in which not a single packet arrived (`ChannelLiveness` in `packages/contracts/src/direct-liveness.ts`, reading the received bytes from `getStats`), because a ping reply queues behind output and is no measure of a live link. `apps/server/scripts/webrtc-probe.ts` tests whether a channel comes up between two networks.
- Terminal output travels as `{ event: 'session.output', payload: { sessionId, data } }` where `data` is a UTF-8 string, coalesced per animation frame on the server.
- Agent status travels as `session.status` (`agent: AgentInfo | null`), chat threads as `chat.event` (`item` upsert, `delta`, `info`, with a `seq` per chat). Every event is appended to `$RUIMTE_HOME/chats/<id>.log` beside the snapshot (`apps/server/src/chat/chat-log.ts`), so `chat.attach` with `since` answers only the events after it while the log still holds them and the whole thread otherwise, which is what the desktop client offers on a reconnect (`chat/chat-client.ts`); a turn that was running when the daemon went down stays running and is resumed from the outbox (`resume-run`, with `--resume` under the same turn and the next `attempt`). The daemon coalesces the deltas on one item per 16 ms (`apps/server/src/chat/delta-coalescer.ts`), flushed ahead of any other event, on attach and on detach, and the client derives the timeline from `structure` (`state/chats.ts`), which a delta growing a reply that already has text leaves alone, so only that row renders. A delta grows an assistant or thinking item and is applied the moment it lands; how it is drawn is the client's (`chatStreaming`, `words`, `blocks` or `whole`): a block at a time, the row draws the blocks `settledBlocksText` says closed, each fading in under `data-arriving`, with "Writing..." below them; a word at a time, `chat/ui/reveal.ts` lets the text catch up over time a whole word at a time, `rehype-fade.ts` fades each new word in and `markdown-blocks.ts` parses a reply a block at a time, and `CodeBlock.tsx` highlights a fence a line at a time as it grows (`code-lines.ts`, carrying Shiki's grammar state from one line to the next) and holds its place invisibly until Shiki and the grammar are loaded; not streamed, the row says "Writing..." and fades in whole when the item is done. The daemon also serves `POST /hooks/<kind>` for the CLIs' hooks, bearer token per session.
- Usage travels as `usage.summary` (buckets per slot, provider and model in the viewer's own time zone, plus the models, projects, the day's exchange rate and the provenance the buckets cannot express), `usage.subscribe` / `usage.unsubscribe` (keep scanning while a page is open) and `usage.limits` / `usage.refreshLimits`; the daemon pushes `usage.changed` (only the moment of the scan, so a page asks again for the period it has) and `usage.limitsChanged`. Everything under `apps/server/src/usage`: transcripts read incrementally into `$RUIMTE_HOME/usage/index.json`, priced with the LiteLLM table (24 h, bundled snapshot as the fallback, `--no-price-fetch` to stay on it), converted with the ECB rate of the day (frankfurter.app, same lifetime, dollars without one), and plan windows asked of the CLIs themselves rather than of any endpoint. The page is about one machine, picked in its own header (`shell/usage/picker.ts`, the choice held for the session and never stored); the limit bars in the sidebar stay on the machine the workspace runs on.

## Terminal sessions (the daemon)

- A session is keyed by an id the CLIENT chooses (the node id), so a node reattaches to its own session after a reload.
- PTY via `Bun.spawn({ terminal: { cols, rows } })` behind the `PtyAdapter` interface (`apps/server/src/pty`). No node-pty, no tmux.
- Every session runs `@xterm/headless` with `@xterm/addon-serialize` in the daemon. `session.attach` answers with the serialized screen, then streams raw output. A client never replays history itself.
- Output is buffered per attached client and flushed every 16 ms, on detach and on exit. `Session.attach` registers the client in the same tick the serialize resolves, so a byte is either in the screen or in the stream, never both.
- Scrollback snapshot to `$RUIMTE_HOME/sessions/<id>.txt` (default `~/.ruimte`) every 30 s and on SIGINT/SIGTERM; written temp-file plus atomic rename, file name via `encodeURIComponent(id)`.
- A shell that ends on its own leaves the session listed as `exited` (last screen still attachable). `session.kill` removes the session after its `session.exit` event and deletes the snapshot. `session.create` on an exited or snapshotted id starts a fresh shell with the old screen above a `[session restored, previous shell ended]` line.
- `ClientConnection.id` is the per-socket client id; `main.ts` subscribes each socket to the `SessionManager` and the `ChatManager` and calls `detachAll` on both when it closes. See `apps/server/README.md` for flags, hooks, chats and the on-disk layout.
- Agent status comes from the CLIs' hooks only (`apps/server/src/agents`), never from parsing output. A chat node is the CLI's stream-json protocol (`apps/server/src/chat`), no SDK. One hook is answered late: Claude Code's `PermissionRequest` is held on the daemon (`agents/approvals.ts`) while a person answers it from the node's header (`canvas/ApprovalStrip.tsx`), travelling out as `session.approvals` and back as `agent.answerApproval`. The CLI shows its own prompt beside it the whole time, so this is a second way to answer one question rather than the only one: the first answer wins, and a hold that runs out (or `--no-approvals`, or no client that wants one) prints nothing and leaves the TUI exactly where it was. Whether a client offers the request to a person is that client's own setting (`agentsApprovals`, on), told to every machine it has a socket to with `agent.setApprovals`; nothing is held while every attached client has said no, and a second client that wants them is asked as before. The composer preference travels the same way (`chat.setPreferences`: the mode, a model per CLI and when it last changed, from `chat/preferences.ts`) for the chats the daemon starts itself; the daemon holds it per socket and takes the newest (`apps/server/src/chat/composer-preferences.ts`), and with nobody connected a chat gets `full-access` and the CLI's own model.
- A project is `<folder>/.ruimte/project.json`, version 2: a name, a color, an icon and a list of views with a monotonic `rev` (`apps/server/src/projects`). A view is a canvas (nodes, texts, edges, layouts) or, later, a standalone chat, terminal or browser. The daemon reads version 1 and 2 and writes only 2 (`migrateDocument` in `packages/contracts`); at parse time it refuses a project where a view id or a node id repeats and drops an edge that points outside its own view. A view or a canvas node of a kind this version does not know is no reason to refuse a file: it is read as an entry of kind `unknown` with the entry as it was in `raw`, written back unchanged by `storedContentOf` (only the frame of a node a person moved or resized is laid over it), listed as a dimmed row or drawn as a plate that does not open, and counted as live by the orphan cleanup of drawings and diagrams. That only protects a version from this fix on, so a new kind is safe to write once the release before it had the fix (see "Kinds a newer Ruimte wrote" in `docs/DECISIONS.md`). Local state (which view was open, the camera and focus per view, the grid, the panels) is per client and never in the shared file. The client keeps its own copy in localStorage under `ruimte.local`, a row per `${endpointId}:${projectId}` (`apps/client/src/project/client-local.ts`), and still sends all of it to `<projectId>.local.json` through `project.save-local`, which is where a client that never saw the project starts. On open `overlayLocal` lays the client's copy over the machine's: its grid, panels and open view win, a view it has no camera for takes the machine's, and `panels.favicons` is always the machine's. A camera is stored as the world point in the middle of its cell plus the zoom (`ViewCameraSchema`) and becomes `{ x, y, zoom }` once the editor has a size (`pendingCamera`); one in the old screen-offset shape reads as none. The client saves through `project.save` with the rev it loaded and reacts to `project.changed` from the daemon's watcher, from a verb an agent ran and from a save of another client (every client but the one that saved it is told, since the watcher reads the daemon's own write as its own). A document that arrives is merged, on a clean client and on one with unsaved edits alike (`apps/client/src/project/merge.ts`, three-way against the document the file held at the rev the client is on): views, nodes, texts and edges by id with maps and then per field, where a side that left a field as the base had it takes the other side's. Some keys merge as one field (a node's frame `x y w h`, its title with `titleSource`, a group's folding, a text's position, an edge's ends), so additions, deletions, moves, resizes, renames and whatever a node carries all come over, and so do the name and icon of a view, the order of the views, the stacking order and the arrangements. What arrives lands in the editor of its view as a `CanvasPatch` (`CanvasState.applyExternal`), marked as a load, so no undo step, no camera move and no editor swap; a node under a gesture (`heldNodeIds`) keeps its local frame even when the other side moved it, and the save after the drag goes out against the merged rev. A conflict is the same field changed to different values on both sides, a deletion on one side against a change on the other, an edge left without an end, both sides reordering views differently, or the project's own name, color or icon: on a client with unsaved edits it keeps the conflict dialog, with `ProjectClient.mergeRefusal` naming the id and the field, and a clean client replaces what is on screen. A save that was already on the wire is refused with `rev-conflict` and made again against the merged rev. Switching away from a project is `project.release`, which only stops the watcher; `project.close` is a person closing it, which stamps `closedAt` on the registry entry so every client keeps the project under Recent until `project.open` clears it again. Closing also ends the sessions of the project's nodes, behind a confirmation that counts them (`sessionNodesOf` in `apps/client/src/project/project-sessions.ts`, `endProjectSessions` in `apps/client/src/terminal/lifecycle.ts`): the client kills each terminal and chat before it empties the canvas, because the watcher that ends a node leaving the document skips a document that is swapping out. Nothing makes a project as a side effect: `project.list` on a daemon nobody has opened one on answers an empty list, a boot opens only what that machine had open before, and with no project open the main column carries an empty state instead of a canvas (every surface that would write into a canvas is gone in that state).
- The project list is every machine at once: `project.list` per endpoint, folded into `state/project.ts`, where a row names the endpoint it came from (`apps/client/src/project/list.ts`). The last answer of a machine is cached in localStorage, so a daemon without a link still lists its projects, dimmed; the list only reads links that are open and asks a machine again the moment its link opens for any reason (`watchOpenLists`), and opening a cached row goes through `openProject` and so through `ensureMachine`. The switcher draws them as one list rather than a group per machine (`menuProjects` in the same file): most recently opened first, the machine behind the name once this client knows more than one, the folder in a tooltip, and everything with a `closedAt` under a Recent submenu. What can be done to the project that is open (reveal, rename, icon, close, delete) is not in the switcher but in `shell/ProjectActionsMenu.tsx`, the overflow menu beside the panel toggles. `openProject(endpointId, projectId)` (`apps/client/src/project/open.ts`) is the only way in and sets the active endpoint on the way, with `openFolderOn(endpointId, folder, createFolder)` as its folder twin and `openMachine(endpointId)` for the station welcome's pick of a machine. All three go through one `ProjectSwitch` (`project/project-switch.ts`, the pure half: connecting, opening, going back, failed), and `shell/ProjectSwitchScreen.tsx` stands over the main column with the project, the machine and the step once a switch has taken longer than `REVEAL_DELAY_MS`: Cancel aborts the wait `ensureMachine` holds (a signal, which lets go of the hold once no other caller waits) and, once the client has moved, lets the open finish and returns to the machine and project before (`switchRun`'s `back`); a failure stays on that screen with its reason, Try again and Go back. The palette closes the moment a folder is submitted and leaves the rest to that screen; `ruimte.lastProject` holds `last` (which machine a cold boot lands on) next to `byEndpoint` (what a switch reopens). Anything drawn per row (the icon URL, a reveal in the file manager) uses that row's endpoint, never the active one.
- A machine has a name and an icon of its own, kept in `endpoint.json` beside its id and key pair so every paired client sees the same ones: `endpoint.info` and the pairing answer carry them, `endpoint.setIdentity` sets them from any client, and `endpoint.changed` tells the others. The icon is the `ProjectIconChoice` a project and a view already use. A name typed in a client wins over `--label` and `RUIMTE_LABEL`, which say what a machine nobody has named answers to. The client draws that icon with `MachineGlyph` (`apps/client/src/endpoint/MachineGlyph.tsx`, a server when nobody picked one) and sets both in one dialog from the Machines pane, since the wire takes name and icon together; `startEndpointWatch` (`apps/client/src/endpoint/watch.ts`) listens for `endpoint.changed` on every socket, and a name a person chose also becomes the label of the endpoint row this client keeps. `refuseStatements` and `broker` ride along the same way, set in the machine's dialog in the Machines pane (`shell/settings/MachineSettings.tsx`). `agentsDeleteAnyView` rides along in all three and is a switch per machine, under Agents in the settings rather than in the Machines pane (`shell/settings/DeleteAnyViewSection.tsx`, one row per machine with its name and icon): it is what an agent's `view delete` may take there, and it belongs to the machine because the daemon enforces it.
- The source address never grants access: behind a tunnel or a reverse proxy every visitor is loopback. A process on the daemon's machine presents the local secret instead, `$RUIMTE_HOME/local.key` (written by the daemon on its first start, `0600`, `apps/server/src/auth/local-secret.ts`), as a third credential beside a ticket and a session token: `ruimte pair` reads it and sends it as a bearer to `POST /auth/pairing-token`, and the desktop shell reads it on every connection attempt and hands it to the client's local row over the bridge (`localSecret`, `endpoint/credentials.ts`). Only a client on the secret may mint a pairing link, over HTTP and over `auth.pairingToken` alike (`mayInvite` in `auth/access.ts`). A browser tab without the shell pairs like any other client. Any other client pairs once (`POST /auth/pair`), registering an ed25519 public key, and then signs a challenge from the daemon on every connection (`POST /auth/challenge`, `POST /auth/ticket`) for a ticket that rides in `?token=` on the socket and, over a socket, on the HTTP routes an `<img>` fetches (`apps/server/src/auth`, `apps/client/src/endpoint`). The daemon has a key pair of its own next to its id and signs every challenge, so a client pins the machine it paired with rather than believing whatever answers on the address. The client's private key is a non-extractable `CryptoKey` in IndexedDB. A client that paired before this holds a session token and keeps working; `auth.registerKey` moves it onto a key over its own connection and the token is dropped the first time a signature lands. A daemon is keyed on the id it mints for itself, not on its address (`apps/client/src/state/endpoints.ts`). A client that never paired gets in on a statement from the address book instead: the broker offer carries it (`access` on the offer, signed with it), `StatementGate` (`apps/server/src/pulsar/statement.ts`) checks machine, key, lifetime and signature against the pinned keys, spends the nonce in `auth.json` and records the key with the origin `statement`, which `auth.sessions` reports beside `link`. A key a person revoked stays out until it pairs with a link again, and `refuseStatements` in `endpoint.json` turns every statement away. On the client a machine from the account list is a row with no address, Direct on and `needsStatement`, which asks the account for a statement per offer (`pulsar/statements.ts`) until the machine lets it in once. While signed in, a client puts every machine whose connection is open on the account without a button (`pulsar/auto-register.ts`, wired in `auto-register-watch.ts`): the machine signs `endpoint.signRegistration`, the client posts it marked `automatic`, once per machine per account for the life of the page and with a backoff on failure, and the address book answers `removed` for a machine a person took off until someone adds it again from its row. A machine without the app joins with `ruimte login` (`apps/server/src/cli/login.ts`): the daemon signs `deviceLinkStartMessage` over the local secret, the terminal starts a link at the address book and prints `station.ruimte.app/link` with a code and the key fingerprint, a signed-in person approves it there (`shell/LinkMachineDialog.tsx`, also under Add a machine), and on the next poll the daemon signs the ordinary registration for the account that approved, which the terminal hands in with its device code; the rules are in `packages/pulsar/src/device-link.ts`. The client holds a connection per daemon in a `TransportPool` (`apps/client/src/transport/pool.ts`), each a `LinkTransport` with its own reconnect loop that opens a WebSocket or a direct channel per attempt, whichever the row says (`linkFor` in `transport/index.ts`), so switching a machine over is `pool.reconnect` and every client built on that transport stays. A link opens only for a hold, and there are four: a workspace with a project open or on its way in on that machine (a project a boot restores counts, `wantsLink` in `transport/workspace-hold.ts`), `ensureMachine` while an explicit action waits for it (the palette, the station welcome, `openProject` and `openFolderOn`, the active machine included), the machine's dialog in the Remote pane and the machine the usage dialog shows (`useMachineHold`). A link nobody holds closes after 30 seconds. Nothing else opens one: not the project list, a status dot, the Remote list, auto-registration, the limit bars, git or a mirror, so agents, attention and the account sync cover the machines with an open link. A machine without one reads `noLink` on its `ConnectionState`, drawn as a hollow dot with "Not connected" and when it was last connected (`state/last-seen.ts`, in localStorage under `ruimte.lastSeen`). The clients of a workspace and a machine sit on `machineTransport(id)` (`transport/machine-transport.ts`), one object per machine that follows the pool's link as it opens and closes and never opens one, so nothing is rebuilt when a link comes back. A direct channel's offer and answer go through one seam (`transport/signaling.ts`): over a socket to the machine (`direct.signal`), or over the broker (`broker-signaling.ts`, one broker socket per page shared by every attempt) when the row has Direct on, a pinned machine key and the `brokerUrl` that the pairing answer and `endpoint.info` hand out (`brokerRouteOf`), and then nothing at all is asked of the machine's HTTP address. On the daemon `BrokerRelay` (`apps/server/src/pulsar/broker-relay.ts`, behind the `Relay` seam) keeps a socket to the broker signed with the `endpoint.json` key and hands a signal to `DirectPeers` only when a paired key signed it. After every `ready` it asks `ice`, and asks again with a third of the credentials' lifetime left; they outlive a lost broker, and `guardWeriftTurn` (`pulsar/turn-guard.ts`) keeps a TURN failure inside werift from ending the daemon. Which broker is `BrokerSwitch` (`apps/server/src/pulsar/broker-switch.ts`, the rule in `effectiveBrokerUrl` in `packages/pulsar/src/broker-url.ts`): `--broker`, `--no-broker` or `RUIMTE_BROKER_URL` first, then `broker` in `endpoint.json` (default, a custom URL or off), then the build's `wss://broker.ruimte.app`; a setting changed from a client stops the relay and starts one on the new URL without a restart, and `brokerUrl` in `endpoint.info`, the pairing answer and `endpoint.changed` follows the effective one (or `--broker-advertise`), so the account record follows too; a key nobody paired gets a signed `not-paired` for its offer and no peer connection; `transportFor(id)` is one machine's link if this client has one and null otherwise, never opening one, and the exported `transport` is a facade over the machine that is active, left for the few call sites that really mean "whichever machine the app is pointed at". `transport/connections.ts` builds a session and a chat client per machine (several may be alive at once) and a project and drawing client per workspace.
- State that is about a daemon is keyed on it. `apps/client/src/state/keys.ts` is where `${endpointId}:${nodeId}` is written down, with `useEndpointId()` as the one place that says which machine the code on screen is about. The sessions, chats, browser pages, terminal screens and drawing mirrors are rows under that key; the server info, the providers and the usage numbers sit under `byEndpoint`. A switch throws nothing away any more, and forgetting a machine drops its rows.
- A workspace is one open project: the daemon it lives on, its project and drawing client, and the stores that hold it (`useCanvas`, `useDocument`, `useDrawing`, `useProject`). `document` and `project` are one store each; `canvases` and `drawings` are registries of one editor per view on screen (`state/editors.ts`), because a grid of cells edits several views at once. All of it is built in `state/workspace.ts` behind hooks that read the workspace they are rendered in (`state/workspace-stores.ts`); an editor hook resolves in three steps: the cell the component is drawn in (`CellViewContext`), else the cell that has the focus, else the blank editor a unit test gets. Outside React every hook means the workspace with the focus, which is what every existing call site already meant. The union of every machine's projects is not a workspace's and lives in `state/project-list.ts`. `WorkspaceProvider` (`transport/context.tsx`) puts a `Connection` and the stores over a subtree: a panel, a node or a dialog inside it reads `useTransport()` and `useEndpointId()` and never names a machine. `App.tsx` draws one workspace; a second pane is a feature of its own, and `openWorkspace(id, endpoint)` is what it will ask for. Splitting _views_ of one project is a different feature and is built: see the grid below. The palette, the settings and the toasts sit outside every workspace and work on the one with the focus (`useFocusedConnection`). The Machines pane is the account on top (sign in or out) and one list of machines under it: this client's rows joined with the machines on the account by machine id (`shell/settings/machine-list.ts`), each row the name, the icon, the connection dot and how the machine is reached ("Paired", "On your account" or both), with "Add a machine" for a pairing link. A row opens the machine's dialog (`shell/settings/MachineDialog.tsx`): name and icon, Direct, the broker, refusing statements, Apps with access with origin and revoke, and two destructive actions that are confirmed apart, "Forget on this client" and "Remove from account". A machine joins the account on its own once a signed-in client reaches it; removing it from the account removes it from every signed-in client, a row paired by link included, the next time that client reads the account list (`pulsar/removal-watch.ts`), while a signed-out client keeps its row and pairing it again by link while signed in puts it back (`reclaimAfterPairing`). The daemon never holds an account token. The settings dialog fits a tablet: the controls of a row wrap under its label, and the navigation narrows below 960 pixels and turns into a menu below 640, at the same density as the desktop. The STUN server is no field there any more: `directStunServers` stays a stored setting with Ruimte's own coturn (`stun:turn.ruimte.app:3478`) as the default, like the daemon's `--stun`; opening a project is what says where the work is.
- Picking a folder to open as a project is a step of the command palette, not a dialog of its own: `browse: { endpointId, machines, path } | null` says where browsing is, and a path typed into the palette is a second way in (`apps/client/src/shell/CommandPalette.tsx`, with the pure parts and the step rules in `shell/palette-browse.ts`). It opens on the machines when the client knows several and on the folders of the one machine otherwise, lists through `transportFor(browseEndpointId)`, and `fs.browse` answering `exists` is what lets the button offer to create a path that is not there. The machines step lists paired machines and the machines on the account as one list, each with a status line; picking one that is not connected connects it first through `ensureMachine` (`endpoint/reach.ts`, the rules in `endpoint/ensure-machine.ts`), the one helper `openProject`, `openFolderOn` and the welcome screen of the web client share, which reaches the machine before it moves the client and ends on the first attempt that fails with that attempt's reason. `hasLocalMachine()` (`state/local-machine.ts`) leaves This machine out of every list on the web client, which has no daemon behind its origin, and `endpoint.info` and `server.hello` are asked of every machine whose link opens (`transport/open-machines.ts`), not only of the active one.
- Edges into an agent node become readable context: the daemon derives what each agent may read from the project documents it knows (`deriveContextSources` in `packages/contracts/src/context-sources.ts`, held per project by `ProjectIndex` in `apps/server/src/projects/project-index.ts`, which outlives `project.release` and is warmed from the registry at start), serves `GET /context` with the session's token, and `ruimte-context` (a script on every session's PATH that runs `ruimte context`) is how an agent reads it. `read <id> --tail N` is the cheap read: the daemon counts the lines, since only the side that renders a chat, a drawing or a diagram knows what a line of it is. A line drawn while an agent is already running reaches a chat between two turns and a terminal agent through its prompt hook (`ContextStore.changeSince`), which is the only channel into a running CLI; along that same line `notify` leaves a short message for another node's agent (`apps/server/src/context/notices.ts`), on the screen of a shell with nothing running in it and otherwise waiting in `$RUIMTE_HOME/notices` until that agent's next turn. Two edges between the same two nodes are one line with a head at both ends on the canvas (`apps/client/src/canvas/edge-lines.ts`); the data stays two edges, because the direction is what the daemon reads. Worktrees live under `$RUIMTE_HOME/worktrees` (`apps/server/src/git`).
- An agent changes the canvas through verbs on the same CLI: `ruimte-context <verb> ...` posts its words to `POST /canvas/<verb>` beside `/context`, with the same bearer, and the daemon parses them (`apps/server/src/canvas`). One object per verb in `verbs.ts` holds the synopsis, the zod schemas for its positionals and flags, and `run`, so `help` renders from what validation checks; `list` and `read` sit in the same registry without a `run` (`served: 'context'`), so `help` names everything the CLI does while `GET /context` keeps answering them. The caller is found with `ProjectIndex.locate`, never among the open projects, and a verb that needs a canvas takes `--view` or the canvas the caller is a node on. A write goes through `ProjectStore.mutate`, which reads the file under the save lock whether the project is open or released, writes `rev + 1`, updates the index and sends `project.changed` to every socket. The answer is tab-separated lines; a refusal is a 422 whose first line is `refused\t<code>\t<message>`, and the CLI exits 3 on it. What `agent` and `team` make is started by the daemon, not by the first client that shows it: once the write lands the verb holds the prompt and owes a `start-agent` entry in `$RUIMTE_HOME/outbox` (`apps/server/src/outbox`), and `OutboxWorker` starts the chat, or the terminal at 120x40, without waiting for any socket and survives a restart in between; a client that mounts the node attaches to what runs (`chat.create` answers the existing chat, `session.create` answers `session-exists`), and both managers make one id at a time so the two never race into a second shell or chat.
- A file is a path and nothing else: a node of kind `file` and a view of kind `file` both carry one, relative to the project folder and absolute outside it (`storedPathOf` and `resolveStoredPath` in `packages/contracts/src/stored-path.ts`). The bytes are the file system's, so there is no store, no rev and no request of its own: `FileSurface` resolves the path and `FileBody` reads it with the same `useFileRead` and `renderFile` the preview panel uses, read-only. Every reader holds a counted `fs.watch` on the folder it is in (`state/fs-watch.ts`), the files panel included, because a node on a canvas with that panel closed would otherwise never hear that the file changed. A file lands on the canvas by dragging it out of the files panel, off a preview tab or out of the file manager, on the sidebar as a view of its own, from the row menus, or through the palette's file step (`openFilePicker`). The rules of a drag are pure in `canvas/drop.ts`: it leaves a directory out, and `dropEffectFor` keeps the cursor to what the source allowed, since the files tree allows a move and a target asking for a copy makes the browser refuse the drop without ever delivering it. A drag out of the file manager is the one that needs more than rules: a browser never tells a page where a file came from, so `pathForFile` on the desktop bridge (`webUtils.getPathForFile`, preload only) is what names it, and `finderRefusal` turns both dead ends (no shell, a project on another machine) into a toast that says which one it is (`canvas/finder-drop.ts`). The controls of a file (wrap, source or preview, the overflow menu) live in the renderer that draws it, so where the surface already carries a bar they are portaled into it rather than drawn a second time under it: `file-toolbar-slot.ts` holds that seam, the window's toolbar offers the host for a view (`App.tsx`, `ViewToolbar.tsx`) and a node offers its own header (`NodeFrame.tsx`), while a preview tab has none and keeps its own bar. The menu itself splits the same way: `FileActionItems` is what can be asked of the file on any of the three surfaces, and `FileMenuItems` adds what is about a tab (pin, close, stage, the diff). Reading a file is the whole cost of the node, so a node that is out of view or under `READABLE_ZOOM` (`canvas/culling.ts`) draws a plate with its mark and its name and reads nothing at all, and a file past `HIGHLIGHT_MAX_LINES` is drawn as plain text with a pill that says so. An edge from a file node into an agent is the cheapest source there is: `ContextSourceSchema` carries the path and the daemon answers with that path and a line telling the agent to read the file itself, since its own tools see a fresher copy and a megabyte of source would crowd out everything else in the window.
- The views of one project stand beside each other in a grid of at most three columns of at most three cells (`shell/split.ts` is the pure model, `shell/SplitGrid.tsx` draws it). One view stands in at most one cell: a view already on screen moves rather than appearing twice, and a drop on the middle of a cell swaps the two. The document store owns the layout and `activeViewId` is the view of the cell that has the focus, derived from it and never set apart from it. The layout is local state, so it is kept per client beside the camera and the panels, with the machine's `<projectId>.local.json` as the starting point, and never in `project.json`. A drag carries `application/x-ruimte-view` from a sidebar row or a cell's own toolbar (`shell/view-drag.ts`); the payload is unreadable until the drop, so the one drag in flight is held in module state. With one cell the window's toolbar speaks for the view; split, every cell carries its own bar (`shell/CellToolbar.tsx`) and the window's goes back to being the application's. Every shortcut that acts on a project is bound once per workspace in `canvas/canvas-shortcuts.ts`, never per cell: nine cells would be nine listeners all resolving to the focused one. A view an agent asks for (`ruimte-context open`, the one canvas verb that writes nothing) arrives as `project.showView` and `project/show-view-watch.ts` hands it to every workspace that has that project on that machine. Whatever it has to say is one line in the banner over the views (`shell/Banner.tsx`, the card the save conflict and the save failure already use, held per workspace as `viewNotice` in the document store and replaced rather than queued when a second one arrives). The `agentsShowViews` setting is off until a person turns it on, so nothing moves and the banner offers "Go there"; on, the view lands in the grid through `showViewIn` and the same banner offers the way back (`undoShowView`). A banner goes when what it offers stops meaning anything: the button, a dismiss, a move of the grid for a way back, arriving at the view for a request.
- A drawing view keeps its elements in `<folder>/.ruimte/drawings/<viewId>.json`, one element per line, under the rev discipline of the project file (`drawing.open`, `drawing.save`, `drawing.close`, `drawing.copy`, `drawing.changed` from a watcher of its own in `apps/server/src/projects/drawing-store.ts`). The client edits it through `useDrawing` and `DrawingClient` (`apps/client/src/drawing`), the same shape as `useCanvas` and `ProjectClient`. Colors are palette names, never hex; a drawing follows the theme.
- A diagram view is a directed graph with groups in `<folder>/.ruimte/diagrams/<viewId>.json` (`packages/contracts/src/diagram.ts`), written rather than drawn: nodes with a label, a shape and a tone, groups that wrap nodes, edges between nodes, and no coordinates except `pos` on a node a person dragged. It follows the drawing on the wire (`diagram.open`, `diagram.save`, `diagram.close`, `diagram.copy`, `diagram.changed`) and on disk (one node, group or edge per line, the same watcher and settle in `apps/server/src/projects/diagram-store.ts`), with two differences. `diagramProblemIn` refuses an id that repeats or that an edge or a group names without it being a node, by that id, on a save and on a read; and `DiagramStore.write` replaces a diagram whether or not a client has its project open (it finds the project on disk through `ProjectStore.place`, writes under the store's own lock and tells every client). That is what `ruimte-context diagram <viewId>` writes through (`apps/server/src/canvas/diagram-verb.ts`): the whole document on stdin, which the CLI sends as `--document`, checked against a strict copy of the schema and `diagramProblemIn`, refused with the zod path or the id it is about so an agent can repair it, and answered with the view, the rev and the counts; `help diagram` renders every field and every closed value from the schemas. An agent reads a diagram as a context source of kind `diagram` (`context/context-diagram.ts`: the reading order of `packages/diagram` above the SVG, `--tail` counting only the list) through `DiagramStore.read`, which finds the project on disk as the write does; a node of kind `diagram` on a canvas (its `viewId` the view it mirrors, placed by a person with "Show on the canvas" or by an agent with `ruimte-context node diagram --source <viewId>`) derives that source beside the drawing's. `layoutOf` (`packages/diagram`) computes the picture: a layer is the longest path from a node without incoming edges after the edges that close a cycle are set aside by a walk in file order; an edge that skips layers gets a point per layer so it runs between boxes, the order inside a layer comes from barycenter sweeps that keep a group's members together, every stretch between two layers has a port and a track of its own in the channel, and a label sits in that channel clear of boxes and other labels. Text is estimated per class of character and wrapped at the widest a box gets; the layout hands out the wrapped lines, so the view and `toSvg` draw the same ones (see "A diagram" in `docs/DECISIONS.md`). The client holds a diagram through `useDiagram` and `DiagramClient` (`apps/client/src/diagram`, a registry in `state/editors.ts` beside the drawings') and draws it as SVG in the DOM (`DiagramView.tsx`), where a person pans and zooms; the zoom and the PNG and SVG exports sit in a dock of its own at the bottom (`DiagramDock.tsx`, on `DockShell` like the canvas and the drawing), and opening and copying the JSON are portaled into the bar through `file-toolbar-slot.ts`. A person drags a node (which writes `pos` in whole numbers, and the rest of the layout closes up), renames it on a double-click or from its context menu, picks its tone from the drawing's `Swatches` and resets its position; the store keeps an undo of whole contents, shown in the dock and bound once per workspace in `canvas/canvas-shortcuts.ts`, and a save goes through `DiagramClient` with the rev, so an agent's write in between is the banner. A node on a canvas mirrors a diagram view read-only (`canvas/nodes/DiagramNode.tsx` through `diagram/mirror.ts`, the drawing mirror's twin: keyed on machine and view id, refcounted, one `diagram.changed` listener per machine, live with an open editor), as a plate under `READABLE_ZOOM` or out of view, and with the drawing node's empty state when there is nothing to draw.
- Attention is what a person still has to look at, counted once in `apps/client/src/state/attention.ts` and read by everything that shows a number. A turn that ends while nobody is looking leaves a mark on its node: the window has to have the keyboard, the node's view has to stand in a cell, and a node on a canvas has to fall inside the camera above `READABLE_ZOOM`, or it was not seen. Looking at the node is the only thing that takes the mark off, which is the same rule read the other way round. The mark itself is `attention/UnseenMark.tsx`, on the node header and on the sidebar row: the finished count's own check in the idle color, nothing to press, and deliberately not the warning a stuck agent wears beside it. `groupAttention` gives the three lists the toolbar draws (`shell/StatusSummary.tsx`: needs you, working, finished), and `agent-work.ts` is what "working" means anywhere, since `nodeStatus` calls every attached shell running. The watcher notifies (`shell/notifications.ts`, `agentsTurnNotify` on and `agentsTurnSound` off) and pushes the same numbers to the shell for the dock badge and the quit dialog. A permission a terminal agent waits on notifies from that same watcher, on `agentsApprovals` rather than the turn switch, and carries the node's own tag so it stands in place of the plain "Needs you" instead of beside it. It is withdrawn the moment the request is answered anywhere (here, another client, the CLI's own prompt) or the hold runs out: `shell/approval-notices.ts` is the pure half of that (what stands, what it says, what is raised and what is withdrawn), with a timer on `expiresAt` for the hold that ends while this client is hearing nothing from the machine.
- The processes panel is the process table of the machine a workspace runs on (`apps/server/src/processes`). A sampler per platform reads cumulative counters (libproc and the Mach host calls through `bun:ffi` on macOS, `/proc` on Linux, none on Windows, which the panel says) and `processRates` turns two readings into rates, so a reading five minutes after the one before averages over five minutes. A process is its pid plus its start time, and unreadable is `null`, never zero. `ProcessMonitor` reads every 2 s while any socket on that machine holds `processes.subscribe` and every 5 minutes otherwise, plus one reading out of rhythm when a turn ends, a shell exits or a session is killed (`SessionManager.onProcessChange`). It keeps a fine series (300 points at 2 s, filled only while subscribed) and a coarse one (288 points at 5 minutes) in memory, and starts both over when the machine slept (the boot clock ran ahead of the awake clock), never because of the length of a gap. `tree.ts` groups the table per node (a session's shell pid, a chat backend's `pid`), the desktop app around the daemon and the daemon's own tasks; the client puts the node's title on the row. `stuck.ts` lays the hook status beside the measurements (silent while working, busy after the turn, memory, agent gone, orphan, a hung probe, every threshold in `STUCK_THRESHOLDS`) and `processes.alerts` goes to every socket, for the mark on a node and its sidebar row (`processes/ProcessAlertMark.tsx`). Nothing acts on its own: a warning carries a button, and `processes.signal` checks pid, start time and user before it sends anything. `scripts/calibrate-processes.ts` logs samples beside the hook statuses to `$RUIMTE_HOME/processes`, to tune those thresholds on real sessions.

## Conventions

- TypeScript in the Bun workspaces, Swift in `apps/ios`; 4 spaces, LF, `.editorconfig` is the rule.
- American English in code, comments, commit messages and UI text. No em dashes or en dashes anywhere; use a comma, colon or parentheses.
- Always curly braces, also for one-line early returns. No one-letter variable names except `i`, `e`, `x`, `y`.
- Arrow functions inside functions; class methods are never arrow properties.
- Comments explain WHY, never what the code already says. Delete a comment that restates the line below it.
- Keyboard shortcuts are bound on `window` and say which they are: the window's own (the palette, find in files, the settings, the sidebar) live once in `shell/app-shortcuts.ts`, and anything that acts on a project lives once per workspace in `canvas/canvas-shortcuts.ts` behind `isFocusedWorkspace`, so with two workspaces a shortcut never lands on the one beside it and with nine cells it fires once.
- A render failure stays in the box it happened in: `ErrorBoundary` (`src/ui/ErrorBoundary.tsx`, the pure half in `ui/error-boundary.ts`) stands around a node's body in `NodeFrame` (resets on the project rev and the node's kind), around the view in `ViewSurface` inside its cell, below the cell's toolbar and the dock (the view id, the project rev, and the drawing's elements or the diagram's content), around the usage dialog, the sidebar, a panel's body (its kind) and the preview (the active tab), and once around the whole `App` as the last resort with a Reload button. It resets only while it holds an error, so a key that changes never remounts a healthy terminal or page. A new surface that draws data of its own gets one.
- Components: only semantic tokens from `styles.css` (`bg-surface`, `text-text-muted`, ...). No raw colors outside that file. Tooltips are the `Tooltip` component (`src/ui/Tooltip.tsx`), never a `title` attribute. Icon buttons that belong together go in a `BTN_GROUP` (`src/ui/classes.ts`, where the class strings more than a couple of call sites share live). Icons are Lucide through the `Icon` component (`src/ui/Icon.tsx`), never another icon set. Two exceptions: the icon of a file is the `@pierre/trees` set through `FileIcon` (`src/ui/FileIcon.tsx`) and keeps that set's own colors, and the mark of a provider is `ProviderLogo` (`src/ui/ProviderLogo.tsx`), a word mark per company in `currentColor`, because Lucide carries no brand marks. No fractional pixels: sizes, spacing and stroke widths are whole numbers, and a `rem` or `em` has to resolve to one. In anything a person reads a daemon is a **machine**: UI text, tooltips, errors, toasts and empty states. Code, comments and documentation keep saying daemon.
- Tests with `bun test` next to the code they test (`foo.test.ts`). No test in the default run may depend on wall-clock timing, a real shell or a file watcher: drive the logic through a fake (`FakePtyAdapter` in `apps/server/src/pty/fake-pty.ts`, an injected watch or clock, `jest.useFakeTimers()`) and await what the code resolves rather than sleeping or polling against a deadline. A test that fails on a timeout is made deterministic or deleted, never given a longer timeout. What only a real shell, watcher, socket or process can prove goes in a `*.integration.test.ts` file, which `bun test` skips and `bun run test:integration` runs; it must clean up its own processes. A real `git` in a fixture is fine; build the fixture once per file (`apps/server/src/git/test-repo.ts`).
- `bun run format` (prettier, `.prettierrc`) and `bun run check` (typecheck plus lint) must pass before a commit. Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`).
- Written from scratch. Do not copy code from any other product; sharing ideas and npm packages is fine.
