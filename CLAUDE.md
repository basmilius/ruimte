# Ruimte

Terminals, agents and browsers on one infinite canvas. `README.md` has the principles. This file is the map and the rules the code does not tell you.

## Layout

Bun workspaces (`bun install` at the root). Shared config at the root: `tsconfig.base.json`, `.oxlintrc.json`, `.editorconfig`, `bun.lock`.

- `apps/client`: the React UI (Vite). Never imports Node or Bun APIs. Talks to a daemon only through the `Transport` interface. A window shows a start screen or one workspace, which is one project on one machine and never exists without it (`state/window.ts`, `transport/connections.ts`). A project is in one window at a time: a page asks the shell before it shows one (`desktop/window-claim.ts`), and what the window shows rides in its address (`state/window-target.ts`), so a reload stays put. In dev Vite proxies `/ws` to the daemon.
- `apps/server`: the daemon (Bun). Owns sessions, PTYs, chats and persistence under `$RUIMTE_HOME` (default `~/.ruimte`). WebSocket API on `localhost:4210`. In dev (`bun dev`) it runs on `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, so it never meets an installed Ruimte; its door on the local network is `4221`, and `bun src/main.ts status --port 4211` says how clients reach it. Flags, hooks and on-disk layout: `apps/server/README.md`. A chat outside any project is a chat view in the machine's Chats project at `$RUIMTE_HOME/scratch`, in a folder of its own that no screen shows (`src/projects/scratch-project.ts`, `scratch` on a summary, `project/new-chat.ts` in the client).
- `apps/desktop`: the Electron shell around the client, with the daemon beside it. The shell serves the built client itself on its own scheme (`app://ruimte`, `src/app-protocol.ts`), so a window never waits on a daemon, and hands the page the daemon's address over the bridge (`daemonUrl`); under `bun dev` the page is Vite's and reaches the daemon through its proxy. Only a small, fixed set crosses IPC; `src/preload.ts` mirrors `apps/client/src/desktop/bridge.ts`, and every bridge method added after the first release is optional. It keeps a window per project, and the windows of the last session open again at the next start (`createWindows`); every handler answers the window that asked, and what the app shares (updates, the service, the theme) goes to every window. What a shell of any app does (the windows, the menu tree, the updater, the guards every app shares) is `@adecore/shell`, a package of `basmilius/adecore` that AfterMotion's shell uses too; the shapes it passes over IPC reach the client through `packages/desktop-bridge`. The refresh token stays in the shell (`src/pulsar-store.ts`); the page only gets access tokens. Browser pages have their own preload (`src/guest.ts`). The application menu is the client's: it sends a tree (`menu:set`) built from what has the focus, and a click comes back as a command id (`menu:run`); the shell only keeps a fixed menu until the first tree and after a reload. A packaged app on macOS and Linux runs the daemon as a background service (`src/service`); the dev app never touches launchd or systemd.
- `apps/ios`: native iPhone/iPad client, iOS 27, Swift. `project.yml` is XcodeGen input; the generated Xcode project and `Package.resolved` are committed for Xcode Cloud. Regenerate with `bun run --cwd packages/contracts generate:swift` and `xcodegen generate --spec apps/ios/project.yml`; `bun run check` verifies generated models and fixtures. See `apps/ios/README.md`. Continue implementation autonomously; device measurements remain explicit acceptance evidence.
- `apps/ios-device-bridge`: the macOS-only Rust helper that keeps Apple's private device protocols out of the daemon. It joins the wireless `remoted` tunnel through `remotepairingd`, forwards Annex-B HEVC from the CoreDevice display service over the helper pipe and sends touch, buttons and rotation back through CoreDevice HID; a cabled device falls back to usbmuxd. See its README.
- `apps/computer-use`: the macOS-only Swift app that lets an agent see and operate another Mac app, through accessibility, window captures and synthesized input, behind a phantom cursor, a session bar and a menu bar item where the person pauses (⌥Space), takes over or stops (⌥⎋); the daemon drives the cursor's state with `presence`. It is an app because macOS attaches the Accessibility and Screen Recording grants to a bundle; it ships in `Ruimte.app/Contents/Helpers` and has a dev bundle id of its own. The daemon launches it with `--home` and talks over `$RUIMTE_HOME/computer-use/agent.sock`, and every request carries the local secret. `cu` is its debugging CLI and does not ship. See its README.
- `apps/speech-bridge`: the Rust helper behind Speech to Text, a local streaming model the Electron shell owns. macOS only in a release. See its README.
- `@adecore/php-language-server`: the PHP language server, including its Rust sources and native release metadata, owned by Adecore. The daemon uses an explicit `RUIMTE_PHP_LANGUAGE_SERVER_SOURCE` override or the installed package sources in development, and the pinned `src/language/php-native-release.json` descriptor in a compiled build. Installation remains a person's action. The npm and native versions are independent.
- `apps/station`: the web client at `station.ruimte.app` (Cloudflare Worker with static assets, `IS_STATION` in `apps/client/src/station.ts`). No local machine there (`state/local-machine.ts`).
- `apps/site`: the website at `ruimte.app` (Next.js on a Cloudflare Worker through OpenNext, every page prerendered). `/download/<platform>` looks up the latest release on GitHub and redirects to its build, so a release never needs a new deploy. The scenes on the page are drawn in React, not recorded: when a feature changes what it looks like, its scene in `src/components/film` or `src/components/features` changes with it, and `src/components/app` copies the client's own measures.
- `apps/pulsar-broker`: relays signals between ed25519 keys (Bun). Never reads an envelope and stores nothing. It hands out ICE servers, so no client or daemon holds a TURN secret. See its README.
- `apps/pulsar-worker`: the address book at `pulsar.ruimte.app` (Cloudflare Worker, D1): accounts, sessions bound to a key, machines, signed access statements, device links, and the model catalogs a daemon picks up a new model from without a release. See its README.
- `@adecore/ui` (a package of its own repository, `basmilius/adecore`, not a workspace): the components the client and `agents-react` draw with that know nothing of Ruimte (buttons, icon buttons, fields, menus, dialogs, popovers, tooltips, shortcuts, the formatters and the settings dialog). Named imports from four entry points: the root, `/settings`, `/format` and `/testing`. `UIProvider` in `App.tsx` adds its words (the `ui` namespace), hands the formatters their source and mounts the tooltip provider. Its tokens, type scale and shared control rules are `@adecore/ui/theme.css`, which the client's `styles.css` imports before its own tokens and scans with `@source`. It comes from npm; to work on it beside Ruimte, `bun link` in `packages/ui` of that checkout and `bun link @adecore/ui` in `apps/client` swap in the checkout, read through the `source` export condition (Vite, the tsconfigs and `bun test --conditions=source`), and the first test preload keeps one React.
- `@adecore/terminal` (the same repository, released with `@adecore/ui` under one version): `TerminalView`, the xterm pane every terminal of the client draws in (`nodes/TerminalBody.tsx`, the launches panel, the login dialog), with its fit, its tokens (`--term-bg`, `--term-fg`, the ANSI palette) and the page's budget of WebGL contexts. The client feeds it through its handle and keeps its own keys (`terminal/xterm.ts`), the screens of its terminals (`terminal/registry.ts`) and the session behind each. Its stylesheet follows the theme in `styles.css`.
- `@adecore/agents`: the shared agent backends, chat lifecycle, outbox, lineage, tasks, messages, provider accounts and pricing. Import its public per-file entrypoints. Ruimte's `apps/server/src/chat/chat-manager.ts`, `tasks/wiring.ts`, `context/notices.ts` and `providers/registry.ts` supply application persistence, terminal behavior, commands and words. Model catalogs and pricing snapshots are maintained in Adecore.
- `packages/contracts`: zod 4 schemas for every message on the wire and the types derived from them. Nothing else may define a wire shape, except `agent-contracts`, whose schemas it re-exports.
- `@adecore/agent-contracts`: shared agent, model, provider account, chat and usage wire schemas. `@ruimte/contracts` places them in its existing request/event tables, keeping Ruimte's protocol and generated Swift models stable.
- `@adecore/agents-react`: the shared chat UI, composers, provider settings and usage views. `apps/client/src/chat/host.ts` configures storage with the `ruimte` namespace before any store is used and supplies application actions; `workspace-host.ts` supplies workspace components. Its CSS follows the Adecore theme and Tailwind scans the installed package sources.
- `packages/pulsar`: zod schemas for the wires to services outside a daemon (broker, WebRTC signaling, address book) and `BrokerPeer`. The bytes every signature covers live in `signing.ts`, each with its own prefix line so a signature for one purpose never verifies as another.
- `packages/actions`: what a person can do, as a catalog of typed actions and the registry that runs them, so voice, the UI and the daemon execute the same thing. Every call names its actor: a person, voice, an agent or automation.
- `@adecore/plan`: generic plan schemas and pure plan tree operations. Ruimte's `packages/contracts/src/plan-host.ts` adds chat-scoped wire envelopes, and its plan store and UI remain application code.
- `@adecore/drawing`, `@adecore/diagram`: generic document schemas, pure drawing/diagram operations and exports. `packages/contracts/src/drawing-host.ts` and `diagram-host.ts` add Ruimte's project/view/revision envelopes. The iOS document renderer resolves these installed packages, including their dependency license records.
- `@adecore/editor-core`, `@adecore/editor`, `@adecore/lsp`, `@adecore/editor-react`: document editing, DOM engine, protocol client and shared language features/popups. Ruimte injects its Shiki highlighter and `RUIMTE_EDITOR_KEYMAP`. The client adapters are `language/ruimte-project-language.ts`, `ruimte-editor-language.ts` and `RuimteLanguagePopups.tsx`; they retain the daemon transport, machine diagnostics, app navigation and AI features. Ghost suggestions keep priority over shared completion on Tab.
- `@adecore/merge`: pure three-way conflict analysis and line/word diff operations, shared by the conflict UI and daemon.
- `@adecore/service`: generic launchd/systemd definitions and managers. `@ruimte/service/host` supplies Ruimte's service identity, paths, environment and runtime adapters; the desktop and CLI both use that host entrypoint.
- `packages/desktop-bridge`: the shapes the Electron shell and the page it hosts pass over IPC, types only. Not a wire in the sense of `contracts`: it never leaves the machine, and it is one place because the preload hands every answer over as `unknown`.
- `packages/csp`: the Content Security Policy of the client as directives, read by the desktop shell and the station; a test holds the `<meta>` tag in `apps/client/index.html` against it.
- `packages/npm`: the `ruimte` launcher and per-platform binary packages. Manifests are generated by `scripts/build.ts`. The application workflow publishes these only; shared libraries release independently from Adecore.

The old shared packages, PHP workspace and superseded generic editor/tree implementations were removed before the manual test round. Use the published Adecore packages for shared behavior. Commit `db8f1afee` retains the originals for comparison or rollback. Active FileTree rendering uses `@adecore/ui`; listing caches, persisted expansion keys, Git commands and staging remain in the client.

## Wire protocol

One WebSocket (or the same frames over a WebRTC DataChannel), JSON frames validated with zod on both ends.

- The one binary frame is a `bytes.read` reply to a request that set `binary`: a JSON header and the bytes as they are (`encodeBytesReply`, `packages/contracts/src/bytes.ts`), in binary pieces over a DataChannel (`splitBinaryFrame`). An error and every other frame stay JSON, and a daemon from before it answers the same request in base64.

- Request: `{ id, type, payload }`. Reply: `{ id, ok: true, result }` or `{ id, ok: false, error: { code, message } }`. Event: `{ type: 'event', event, payload }`.
- `REQUEST_SCHEMAS` and `EVENT_SCHEMAS` in `packages/contracts` are the tables both sides derive `RequestMap` and `EventMap` from.
- `PROTOCOL_VERSION` (`packages/contracts/src/protocol.ts`) is bumped only for an incompatible change, and both ends refuse any other version.
- A session id is chosen by the client (the node id), so a node reattaches after a reload.
- `session.attach` answers with the serialized screen from `@xterm/headless`, then streams raw output. A client never replays history. A byte is in the screen or in the stream, never both. A client gets a screen only through `Session.snapshotFor` (attach, resync, clear). It holds back that client's output from the moment of the call until the screen is taken, with no await in between.
- Agent status comes from the CLIs' hooks only (`POST /hooks/<kind>`, `apps/server/src/agents`), never from parsing output. A chat is the CLI's stream-json protocol, no SDK.
- Chat events carry a `seq` per chat and are logged (`@adecore/agents/chat/chat-log`), so `chat.attach` with `since` resumes.
- A chat's thread goes to whoever attached to it, since it streams word by word; what the chat is _doing_ goes to every client (`chat.status`, on a change only), the way a terminal's `session.status` always has. Without that a node waiting on a person says nothing on a view nobody has open. A client asks `chat.list` on every fresh socket for the standing answer.
- Bytes for an `<img>` or `<video>` come only from `useMachineUrl` (`transport/machine-url.ts`). No draw site knows whether the link is a socket or a direct channel.
- A direct connection that fails says why and never falls back to the socket.

## Invariants and seams

- A project lives in two files. `<folder>/.ruimte/project.json` is what a team commits; `<folder>/.ruimte/private/project.json` is one person's and is kept out of git by the `.gitignore` the daemon writes once beside it. The private file holds the monotonic `rev`, the sidebar order over both, and per shared node the fields that cannot travel (`resume`, `runtimeMode`, `worktree`, any absolute path, and a name a session gave, for which the shared file carries the name of the kind). Every write goes against the rev it read, and a conflict comes back as `rev-conflict`. Drawings and diagrams follow the same discipline in their own files.
- The unit of sharing is a view, whole. Nothing is shared until a person's `project.save` names it in `shared`: a verb hands back content and never that list, so an agent cannot move a view between the files. A file view pointing outside the project folder cannot be shared at all. The shared file is only written when its text changes, so moving a private node leaves `git status` alone.
- Local state (open view, camera, grid layout, panels) is per client and never goes in `project.json`.
- A view or node of a kind this version does not know is kept as kind `unknown` and written back unchanged. A new kind is only safe to write once the previous release already had that fix.
- A file node or view is a path, relative to the project folder and absolute outside it (`packages/contracts/src/stored-path.ts`). The bytes are the file system's; there is no store.
- The source address never grants access (behind a tunnel everyone is loopback). A local process proves itself with `$RUIMTE_HOME/local.key` (`apps/server/src/auth/local-secret.ts`); every other client comes in through the account, on a statement from the address book, and proves its ed25519 key from then on. There are no pairing links. Only the local secret may have the machine sign a registration. The daemon never holds an account token.
- A remote client reaches a daemon only over a direct channel, whose signals come over the broker or through the door on the local network (`apps/server/src/pulsar/lan-door.ts`), both through one `SignalGate`. The door answers nothing but its signaling socket, the machine proves its key there before a client says who it is, and the API itself stays on loopback.
- A client the machine let in, or an agent, is not the owner of the machine, and what only the local secret may do stays with the local secret. So no file request of a client (`fs.read`, `fs.grep`, `fs.write`, `fs.rename`, `fs.delete`, `bytes.read`, `GET /fs/file`) reaches under `$RUIMTE_HOME`, except the folders that hold a person's own work or a picture made for them (`apps/server/src/fs/machine-home.ts`).
- A browser page is an Electron `<webview>`, and Electron destroys the guest whenever the element or anything above it changes parent, a state-preserving `moveBefore` included. So every page is parked in one layer over the canvas (`apps/client/src/browser/WebviewParking.tsx`), whatever a cell draws over a page is portaled into the layer above it (`apps/client/src/shell/CellOverlay.tsx`), and a page cuts a hole out of itself for every node standing on top of it, so the canvas under the layer shows through and the page keeps running (`apps/client/src/browser/page-clip.ts`).
- Agents change the canvas only through `ruimte-context <verb>`, parsed and validated on the daemon (`apps/server/src/canvas/verbs.ts`). Writes go through `ProjectStore.mutate`. A refusal is a 422 starting with `refused\t<code>\t<message>`.
- The daemon types a command from a project file only after a person on this machine approved it for that node. The approval is written under `$RUIMTE_HOME/command-approvals` (`apps/server/src/sessions/command-approvals.ts`). Until then the shell starts without the command and the session holds it (`heldCommand`, `session.runHeld`). A person's `project.save` that sets the command counts as approval; a verb never does.
- A browser node's page lives where it is shown: a `<webview>` in the client on the desktop, a page on the daemon for a client that has no browser of its own. The daemon reaches the first kind only while that client holds it (`browser.hold`, `browser.drive`), drives both through one door (`apps/server/src/browser/drive.ts`), and nobody holding the page is an answer and never an error.
- A child agent never gets a wider permission mode than its parent (`@adecore/agents/modes.ts`, bound to a verb in `apps/server/src/canvas/mode.ts`); the ceiling rides on every `start-agent` entry. A `--worktree` agent gets its own worktree under `$RUIMTE_HOME/worktrees`, never removed automatically. A worktree merge (`apps/server/src/git/worktree-merge.ts`) runs in the checkout that has the target branch out, never stashes and never moves a ref behind a working tree; an agent merges only the worktree of a node it opened, into a checkout without tracked changes, and a conflict is taken back for it. An agent's merge only merges: the child keeps running and its worktree and branch stay until a person removes them.
- A project folder holds one or more checkouts: the repository it is in, its initialized submodules, and the repositories sitting beside it one level down (`apps/server/src/git/repos.ts`). The git panel has no active repository: the staged files say where a commit lands, so one message commits every repository that has something staged, and nothing staged with more than one repository changed is nothing to commit yet. The changes, the commit log and the counts in the header are every repository at once, and so are fetch, pull and push. What names a single repository (merge, rebase, stash, a branch, a pull request) sits in that repository's own level of the branch menu, one level in, since `main` says nothing about which repository is on it. A folder with exactly one repository reads as the panel always did, chip and actions menu included.
- A conflict is worked out in the app and never through a marker in a file. The daemon hands over the three versions git holds in its index (`git.conflict`), and a resolution is written over the digest it was read at, so a file that moved since refuses instead of losing what moved it. The checkout says what stopped in it (`operation` on `git.status`), which is what opens the overlay again after a reload, on a second client and from a terminal that left a merge halfway. Finishing or taking one back is one verb (`git.operation`), and a worktree merge aborts through the very same call.
- Per-area invariants sit in a `CLAUDE.md` beside the code and load when a file there is read: `apps/client/src/canvas` (selection, `bodyFocusId`, connectors), `apps/client/src/state` (keys, attention), `apps/client/src/transport` (machine holds), `apps/server/src/chat` (forks, plans), `apps/server/src/outbox` (outbox, tasks, ending children), `apps/server/src/projects` (file layout, versions).

## Product rules

Decisions the code cannot show. Do not reverse one without asking Bas.

- Two things wake a chat, each once: a finished task wakes the chat that delegated it, and a message wakes the chat it was sent to. A message goes one step deep, so the turn it opened wakes nobody, and a terminal is never woken at all.
- A child that stops on a limit pauses its task: the turn says which limit and when it lifts (`limit`, read only from the CLI's own stream), the task stays open with `paused`, and its parent sleeps on until the child finishes after the reset. An overload the daemon does not try again is an error like any other and fails the task.
- A task settles only once its child is really done. A turn that ends while its CLI still runs work in the background (a background subagent, a Claude workflow, an agent Codex spawned: `@adecore/agents/chat/background-work.ts`) settles nothing, and the parent is not woken in between. The task settles on the turn the CLI opens by itself once that work ended, on the child's last turn when its CLI opens none (Codex), or on `ruimte-context done`, which works all the while. A command or a monitor the child's CLI runs in the background (its own or one a subagent of it started, as the chat's `background` shows it) holds the task too, but for at most 30 minutes from the moment it is all that is left, since a dev server never ends. That limit is a `background-limit` outbox entry with a time: it survives a restart, runs once and lapses when the task settles otherwise. When it passes, the task settles on the child's last result, which then names the commands that still ran. A restart of the daemon takes the CLI and its commands down, so a task only commands held then fails at once with the child's last result and a line naming what was lost, and wakes its parent once, as when the CLI goes within one run. Subagents and workflows have no limit.
- Resuming after a limit runs on a clock, and only when a person turned it on: a machine setting (`resumeAtReset` in `endpoint.json`, off by default) and a chat's own switch beside it, which absent follows the machine. A `resume-limit` outbox entry carries the time: the reset of a usage limit, or 1, 5 and 15 minutes after an overload, after which the overload is an ordinary error. The entry lapses when a person writes first, stops the chat, turns a switch off or the node goes. These two, the limit on a child's background commands and the end of a snooze (`apps/server/src/push/snoozes.ts`) are the only work the daemon schedules on a clock.
- A child with a task that waits on a question or an approval leaves its parent one note per request (`deliver-waiting`, `@adecore/agents/tasks/waiting-child.ts`), and does not wake it. The note is due 15 seconds after the request came and is written only if the request still waits then, so a request settled at once leaves none. A parent may answer a question of a child it opened itself with `ruimte-context answer`, the way a person's `chat.answer` does, and whoever answers first wins; approvals, logins and every other card stay with the person. A parent may also `ruimte-context read` a child it opened itself without a line from it, by the same lineage. A chat may read another chat of its project without a line once a person attached that chat to one of its messages with `@` (`apps/server/src/context/chat-references.ts`), checked again at every read, so a chat that left the project is closed to it again. Every other node still needs a line.
- A terminal's permission prompts and questions stay in its TUI: a person chose the TUI for a reason. Ruimte only shows that it needs you (status, stack card, notification) and never answers for it; an AI chat is where approvals are answered from the app or a phone.
- Every shortcut needs a modifier. The only bare keys are a drawing view's tools, and only while no text is typed and no dialog is up, and the widget keys inside a prompt card (arrows, Home, End, Space, Enter), only while the focus is in that card.
- Never highlight the canvas grid in the accent color. Type: only the four sizes in `@theme`, no bracket sizes, nothing below 12px, except a model's badge (11px, in capitals); Geist only for the wordmark, Kalam only for drawing text.
- A page in a `<webview>` does not pinch-zoom (Chromium scales only the top-most widget); a `WebContentsView` per page and `setZoomFactor` were weighed and rejected.
- The wire only gains optional fields, new requests and new events. Never a new `ChatItemSchema` member or enum value in a chat or push payload: the iPhone app validates `chat.attach` and `chat.history` whole.
- Agents cannot type into or close another node's session or start a command through a verb (only `agent` starts anything); `--cwd` stays inside the project folder or its worktrees. The one exception is a launch: `ruimte-context launches` lists and reads them, and starts, restarts and stops only a launch a person approved on this machine for its command, folder and environment as they stand now (`apps/server/src/launches/agent-host.ts`). Anything else is refused with `launch-held` and the chip asks the person. An agent's stop is Ctrl+C and then SIGTERM; SIGKILL is only a person's Force stop, and an agent never adds, edits or approves a launch. A browser node is driven only over a line between it and the agent, and only by address: where the page goes, its own history and a picture of it (`ruimte-context browser`), never a click, a keystroke or a scroll. A device node is driven only over a line between it and the agent, by screenshots and taps (`ruimte-context device`), with no approval card: the device is its own sandbox. Computer use is the desktop's own door: off per machine until a person turns it on, then `ruimte-context computer` operates any app, Ruimte included, only after a person let the agent into that app (this time or always, in every mode), and never a terminal. Letting an agent into Ruimte itself is the person's own risk: it can do there whatever the person can, and the daemon refuses nothing extra from the Ruimte window while it does.
- Whatever the daemon enforces against an agent (depth, lineage, tasks) lives under `$RUIMTE_HOME`, never in `project.json`, which an agent with a shell can rewrite. An observer only notes; only the outbox acts. Nothing removes a worktree on its own.
- Nothing reads a vendor credential (keychain, `~/.codex/auth.json`, usage endpoints); plan windows come from the CLIs. A stuck process gets a warning, never a signal a person did not press.
- Keep awake with the lid closed turns sleep off (`pmset -a disablesleep 1`) only through a sudoers rule a person on the Mac installed for exactly the two pmset commands, never with root in the daemon, and only the local secret installs or removes that rule (`apps/server/src/power/closed-lid.ts`). It holds only while keep awake holds, on the power adapter or on battery from 20% up, follows the power source through `pmset -g pslog` and never a clock, and sleep goes back on when it lets go, when the daemon stops, through a watchdog when the daemon dies, and at the next start when this home's marker says it was left off.
- A pull only fast-forwards until a person says how a branch that moved on both sides comes together, since a merge commit nobody asked for is a commit to undo. An agent CLI may propose a resolution, one stretch at a time or over every file at once, and a proposal is an edit in the overlay: nothing is written to a file, staged or committed on an agent's word alone.
- Closing a project is one client's. The machine keeps it, and keeps its sessions running, as long as another client still has it open; only the last client out ends them and drops the project under Recent. Closing a window is not closing its project: the window writes what it had and lets its sockets go, and the project stays open on the machine. Which projects a person keeps in their own menu is that client's and is written there, so closing on a laptop leaves the iPhone where it was. A socket that drops ends nothing.
- A page never sees a refresh token, a daemon never holds an account token, and accounts are never merged.
- A machine is on at most one account and is shared only with its owner: only the local secret (the app on it, `ruimte login`) puts it on one, another account gets `machine-has-account` until a person on the machine leaves the first, a machine takes only a statement v2, and a machine on an account only one of that account (`apps/server/README.md`, "One account per machine").
- A zustand selector that builds a new array or object per call loops forever under `useShallow`: select the object and derive with `useMemo`.

- Language servers (`apps/server/src/language`) are installed only when a person presses Install, and never by an agent or a verb. The daemon runs them itself, one per project per kind, shared by every client of the project, and a server that ends by itself after it had been ready for a minute is started again once at once (the decision is made on the exit, never on a timer), while one that ends sooner, or the one it started again ending within that minute, stays crashed until a person restarts it. A server starts with the first document that needs it and ends only when its project closes on the machine (or the daemon stops), so moving between files never restarts it. A server of a person's own (a command they typed) is saved only through a request of the local secret, which approves exactly that command, arguments and environment, and lives under `$RUIMTE_HOME`, never in a project file; no verb or agent adds or changes one.
- Speech to Text is optional and off by default. Enabling downloads one verified local streaming model; it never opens the microphone. Audio is never uploaded or saved. Voice Control is the separate cloud-backed feature; both share the microphone and language settings and never record together.
- Dictation previews text and inserts only after stopping. A terminal receives an editable draft and only an explicit paste writes sanitized text without Enter. Agents cannot start dictation.

## Conventions

- TypeScript in the Bun workspaces, Swift in `apps/ios`. 4 spaces, LF; `.editorconfig` is the rule.
- American English in code, comments, commit messages and UI text. No em dashes or en dashes anywhere.
- Always curly braces, also for one-line early returns. No one-letter variable names except `i`, `e`, `x`, `y`.
- Named top-level functions use function declarations, exported with `export function`. Keep functions produced by factories or wrappers as `const`, and mutable callback slots as variables.
- Arrow functions for callbacks and inside functions; class methods are never arrow properties.
- Comments explain WHY, never what the code already says.
- Keyboard shortcuts are bound on `window`, once: the window's own in `shell/app-shortcuts.ts`, anything acting on the project once, by the workspace, in `canvas/canvas-shortcuts.ts`, so the start screen has none of those. Never per cell or per node.
- A new command gets its place in the menu tree (`apps/client/src/shell/menu/model.ts`) as well as the palette. The menu only shows a key: a command its accelerator fires is dropped by the shell when the page had that key first, since its own listeners answered it (`createMenuCommands` in `@adecore/shell`); a page in a browser node never sees it, and an item picked through accessibility or a key sent to a window that is not key never reached the page, so there the menu answers.
- A new surface that draws data of its own gets an `ErrorBoundary` (`@adecore/ui`), keyed so it resets only while it holds an error.
- The start screen and the workspace are separate chunks, so the station's first load carries no workspace code. Nothing that `main.tsx` or the start screen imports statically may reach `shell/WorkspaceShell.tsx` or what only it draws. A panel, view or dialog that not every workspace opens loads through `lazyNamed` or `lazyDialog` (`@adecore/ui`), inside its `ErrorBoundary`. The library's `prefetcher` fetches the workspace once the start screen is idle, and then everything that loads through those two one module at a time once a workspace is idle; a lazy module registers there by itself. A chunk that fails to load reloads the web page once (`src/stale-chunks.ts`), unless only a prefetch asked for it.
- UI: only semantic tokens from `@adecore/ui/theme.css`, `@adecore/agents-react/theme.css` and `styles.css`, no raw colors elsewhere. A border is an alpha over what is behind it, never a gray of its own, and every surface clips its background to the padding box so the line mixes with the ground and not with the surface it edges. Tooltips are `Tooltip`, never a `title` attribute. An icon button is `IconButton`, and related ones go in a `ButtonGroup`. Icons are Lucide through `Icon`; the only exceptions are file icons (`FileIcon`, `@pierre/trees` with its own colors) and provider marks (`ProviderLogo`). No fractional pixels; a `rem` or `em` must resolve to whole pixels.
- UI that knows nothing of Ruimte belongs in `basmilius/adecore`, and so does a fix to it. When Ruimte needs something the library lacks or draws wrong, open an issue there with `gh issue create --repo basmilius/adecore`, titled `<Component>: <the need>`, labeled `Ruimte` and `Bug` or `Enhancement`, with three sections: `## Problem` (what is missing or wrong, the call sites here as `path:line`, and how Ruimte works around it today), `## Wish` (the need as what a person does or sees, not a fix; a proposed API is optional) and `## Impact on AfterMotion` (search `../aftermotion` for the same component or pattern and name the call sites a change would touch and whether it would change what they draw or break them, or say there are none). Never patch the library from here and never copy its code into Ruimte.
- In anything a person reads (UI text, tooltips, errors, toasts, empty states) a daemon is a **machine**. Code, comments and docs say daemon.
- The interface is written in English and in Dutch (`apps/client/src/i18n`, react-i18next, a file per namespace per language). English is the source and the fallback; a key that has no Dutch reads English rather than showing itself, and `locales.test.ts` fails the run when the two drift apart. Conventions, the glossary and what stays untranslated are in that folder's README. Tests read the English words through the `preload` in `bunfig.toml`, so a pure function that builds a label is asserted on the sentence and not on the key.
- Every number, date, time and duration a person reads is written by `@adecore/ui/format`, the only place in the client that builds an `Intl` formatter. It reads the two settings through the source `apps/client/src/format/source.ts` hands it at startup. Two settings decide what it looks like and they are apart on purpose: the language writes the words, the region writes the order, the separators and the clock. The region follows the language unless a person says otherwise, and `system` is what the desktop shell passes in (`app.getSystemLocale()` beside `app.getPreferredSystemLanguages()`); Chromium's own locale is the language of the bundle, so it would write `08:00 AM` on a Dutch Mac. An English interface on a Dutch machine is a pair a person can set, and it reads `19 Sep, 08:05`. A surface that would otherwise sit still through a region change calls `useFormatLocale()`.
- Tests: `bun run test`, next to the code (`foo.test.ts`). No test in the default run depends on wall-clock timing, a real shell or a file watcher: use a fake (`FakePtyAdapter` in `apps/server/src/pty/fake-pty.ts`, an injected clock or watch, `jest.useFakeTimers()`) and await what the code resolves. A test that fails on a timeout is made deterministic or deleted, never given a longer timeout.
- Real shells, watchers, sockets or processes go in `*.integration.test.ts` (`bun run test:integration`), which cleans up its own processes. A real `git` fixture is fine; build it once per file (`apps/server/src/git/test-repo.ts`).
- `bun run format` and `bun run check` (typecheck plus oxlint in every workspace, where a warning fails too) pass before a commit. Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`).
- Written from scratch. Do not copy code from any other product; sharing ideas and npm packages is fine.

## Releasing

A release runs to the end without asking. Bas names a version and the next thing he reads is that it is live.

- CI decides, not this machine. The `ci.yml` run on the commit being tagged has to be green; nothing is built, checked or tested here for a release, and a published build is never downloaded to try the daemon in it.
- A red CI is fixed before the tag: find it, fix it, push to main, wait for green. Only what Bas alone can decide comes back to him.
- The notes ride on the tag, so the draft is never empty and publishing takes no second edit. Write them to a file and tag with `git tag -a v<version> -F <file> --cleanup=verbatim`; without that flag git strips every `##` heading out of the message. `release.yml` builds macOS and Linux into that draft, and once the run succeeds it is published as Latest at once.
- Publishing starts `npm.yml`, which puts `ruimte` and its three platform packages on npm at the same version. `docs/RELEASE.md` has the recipe, the secrets and what has broken in them.
- Adecore libraries release independently. Ruimte pins the consumed version in its manifests and lockfile; `libraries-v*` tags no longer publish libraries from this repository.
