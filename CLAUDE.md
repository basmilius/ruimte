# Ruimte

Ruimte is a workspace for AI engineering, built around projects, views and persistent sessions. `README.md` has the principles. This file is the map and the rules the code does not tell you.

## Layout

Bun workspaces (`bun install` at the root). Shared config at the root: `tsconfig.base.json`, `.oxlintrc.json`, `.editorconfig`, `bun.lock`.

- `apps/client`: the React UI (Vite). No Node or Bun APIs; it reaches a daemon only through `Transport`. A window shows a start screen or one workspace, which is one project on one machine and never exists without it (`state/window.ts`, `transport/connections.ts`). A project is in one window at a time: a page asks the shell first (`desktop/window-claim.ts`). The window's address carries what it shows (`state/window-target.ts`), so a reload stays put. In dev Vite proxies `/ws` to the daemon.
- `apps/server`: the daemon (Bun). Owns sessions, PTYs, chats and persistence under `$RUIMTE_HOME` (default `~/.ruimte`), WebSocket API on `localhost:4210`. `bun dev` runs it on `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, apart from an installed Ruimte, with its local network door on `4221`; `bun src/main.ts status --port 4211` says how clients reach it. `apps/server/README.md` has flags, hooks and the disk layout.
    - Work on another machine: `src/remote` is the machine whose person works elsewhere (node bindings, links, reconnect, tasks it gives), `src/peering` the machine worked in (links a person made, what a peer may ask, tasks it takes).
    - `src/daemon.ts` calls the `src/wiring` modules in boot order, each returning a typed bundle. A module needing a later bundle reaches it through `later`; agent verbs get services through `CanvasHost` (`src/wiring/canvas-host.ts`).
    - A chat outside any project is a chat view in the machine's Chats project at `$RUIMTE_HOME/scratch`, in a folder no screen shows (`src/projects/scratch-project.ts`, `scratch` on a summary, client `project/new-chat.ts`).
- `apps/desktop`: the Electron shell, with the daemon beside it.
    - The machine mode in `machine.json` under `userData` (`src/machine-mode.ts`): `local` runs a daemon, `none` only connects to other machines, `ask` shows the first-run screen until a person chose. Only `local` has a daemon. Otherwise the shell passes no `daemonUrl`, installs no `service:*` channel, and the preload leaves out `localSecret`, `takeStartupMs`, `backgroundService` and `countUsage`.
    - Daily usage totals (`src/usage.ts`) follow the machine's `usageStats` switch. A new command needs a row in the allow-list (`packages/pulsar/src/usage-desktop.ts`).
    - The shell serves the built client on `app://ruimte` (`src/app-scheme.ts`), so a window never waits on a daemon, and passes the daemon's address as `daemonUrl`. Under `bun dev` the page is Vite's. Windows open while the machine comes up; the local secret waits until the daemon on the port proved it holds it (`src/startup.ts`, `src/daemon-proof.ts`).
    - Only a small, fixed set crosses IPC. `src/preload.ts` builds the bridge and checks it with `satisfies DesktopBridge` (`packages/desktop-bridge`, re-exported in `apps/client/src/desktop/bridge.ts`). Every bridge method added after the first release is optional. The main process installs channels per domain from `src/main`.
    - One window per project; the last session's windows reopen at start (`createWindows`). A handler answers the window that asked; what the app shares (updates, the service, the theme) goes to every window. Generic shell work (windows, menu tree, updater, shared guards) is `@adecore/shell` from `basmilius/adecore`, also used by AfterMotion's shell; its IPC shapes reach the client through `packages/desktop-bridge`.
    - The refresh token stays in the shell (`src/pulsar-store.ts`); the page gets only access tokens. Browser pages have their own preload (`src/guest.ts`).
    - The client owns the application menu. It sends a tree built from the focus (`menu:set`); a click returns a command id (`menu:run`). The shell keeps a fixed menu only until the first tree and after a reload.
    - A packaged app on macOS and Linux runs the daemon as a background service (`src/service`). The dev app never touches launchd or systemd.
- `apps/ios`: native iPhone/iPad client, iOS 27, Swift. `project.yml` is XcodeGen input; the generated Xcode project and `Package.resolved` are committed for Xcode Cloud. Regenerate with `bun run --cwd packages/contracts generate:swift` and `xcodegen generate --spec apps/ios/project.yml`; `bun run check` verifies generated models and fixtures. See `apps/ios/README.md`. Continue implementation autonomously; device measurements remain explicit acceptance evidence.
- `apps/ios-device-bridge`: macOS-only Rust helper that keeps Apple's private device protocols out of the daemon (wireless `remoted` tunnel through `remotepairingd`, CoreDevice display and HID, usbmuxd for a cable). See its README.
- Android has no app of its own; the daemon drives it (`apps/server/src/devices/CLAUDE.md`).
- `apps/computer-use`: macOS-only Swift app through which an agent sees and operates another Mac app (accessibility, window captures, synthesized input), behind a phantom cursor, a session bar and a menu bar item where the person pauses (⌥Space), takes over or stops (⌥⎋). The daemon drives the cursor's state with `presence`. It is an app because macOS ties the Accessibility and Screen Recording grants to a bundle. It ships in `Ruimte.app/Contents/Helpers` with a dev bundle id of its own. The daemon launches it with `--home` and talks over `$RUIMTE_HOME/computer-use/agent.sock`; every request carries the local secret. `cu` is its debugging CLI and does not ship. See its README.
- `apps/foundation-models`: Swift helper on the machine's Apple model, behind the Apple provider and the editor's on-device help (`--oneshot`, no tools). macOS on Apple silicon only. CI builds and tests it (`.github/workflows/ci.yml`); `apps/server/scripts/compile.ts` builds it into the arm64 daemon's `native/`; `apps/desktop/build/sign.cjs` and `after-pack.cjs` sign it and refuse a Mac build without it. The daemon starts it from `src/providers/apple-helper.ts` and `src/ondevice/model.ts`. See its README.
- `apps/speech-bridge`: Rust helper behind Speech to Text, a local streaming model the Electron shell owns. macOS only in a release. See its README.
- `basmilius/language-server-php` and `basmilius/language-server-sql`: standalone Rust language servers (`php-native`, `sql-native`) with their own versions and no npm dependency in Ruimte. How a daemon builds or installs them: `apps/server/src/language/CLAUDE.md`.
- `apps/station`: web client at `station.ruimte.app` (Cloudflare Worker, static assets, `IS_STATION` in `apps/client/src/station.ts`). No local machine there (`state/local-machine.ts`).
- `apps/bench`: the model comparison alone at `bench.ruimte.app` (Cloudflare Worker, static assets). The client's `bench` build (`apps/client/bench.html`, `src/bench`) draws only `ModelsBenchmarks` against the production address book.
- `apps/site`: the website at `ruimte.app` (Next.js on a Cloudflare Worker through OpenNext, all prerendered). `/download/<platform>` redirects to the latest GitHub release's build, so a release needs no deploy. Scenes are drawn in React, not recorded. When a feature changes how it looks, its scene in `src/components/film` or `src/components/features` changes with it; `src/components/app` copies the client's measures.
- `apps/pulsar-broker`: relays signals between ed25519 keys (Bun). Never reads an envelope, stores nothing. It hands out ICE servers, so no client or daemon holds a TURN secret. See its README.
- `apps/maps-worker`: map service at `maps.ruimte.app` (Cloudflare Worker, no database). It proxies TomTom's Orbis map display behind an address book ticket and holds the TomTom key. It logs no request; only its own errors and warnings go to Observatory, never a path or tile. The ticket rides in the `authorization` header, checked with `MAP_TICKET_SECRET` and `verifyMapsTicket`. The client takes tiles only while its "Map tiles" setting is on and a person is signed in (`apps/client/src/chat/map-source.ts`). Ruimte looks up no addresses (the Search API stays off), so agents give `lat` and `lon` for every `Place`. See its README.
- `apps/pulsar-worker`: the address book at `pulsar.ruimte.app` (Cloudflare Worker, D1): accounts, key-bound sessions, machines, signed access statements, device links, and model catalogs a daemon picks up without a release. See its README.
- `@adecore/ui` (repository `basmilius/adecore`, not a workspace): components that know nothing of Ruimte. Named imports from the root, `/settings`, `/format` and `/testing`. `UIProvider` in `App.tsx` adds its words (`ui` namespace), hands the formatters their source and mounts the tooltip provider. `styles.css` imports `@adecore/ui/theme.css` (tokens, type scale, control rules) before its own tokens and scans it with `@source`. `bun run adecore:link` swaps all shared dependencies to `../adecore`, `bun run adecore:npm` restores the pinned versions; restart dev after switching. The source condition and first test preload keep development on current TypeScript with one React. Workflow: `docs/ADECORE-DEVELOPMENT.md`.
- `@adecore/terminal` (released with `@adecore/ui` under one version): `TerminalView`, the xterm pane of every client terminal (`nodes/TerminalBody.tsx`, the launches panel, the login dialog), with fit, tokens (`--term-bg`, `--term-fg`, ANSI palette) and the page's WebGL context budget. The client keeps its own keys (`terminal/xterm.ts`), the screens (`terminal/registry.ts`) and the sessions. Its stylesheet follows the theme in `styles.css`.
- `@adecore/agents`: shared agent backends, chat lifecycle, outbox, lineage, tasks, messages, provider accounts and pricing. Import from its root and area entry points (`/chat`, `/context`, `/coordination`, `/host`, `/providers`, `/usage`, `/testing`). `apps/server/src/chat/chat-manager.ts`, `tasks/wiring.ts`, `context/notices.ts` and `providers/registry.ts` supply persistence, terminal behavior, commands and words. Model catalogs and pricing snapshots are maintained in Adecore.
- `packages/contracts`: zod 4 schemas for every wire message and their types. Nothing else defines a wire shape, except `agent-contracts`, whose schemas it re-exports.
- `@adecore/agent-contracts`: shared agent, model, provider account, chat and usage wire schemas. `@ruimte/contracts` places them in its existing tables, so the protocol and generated Swift models stay stable.
- `@adecore/agents-react`: shared chat UI, composers, provider settings and usage views. `apps/client/src/chat/host.ts` configures storage with the `ruimte` namespace before any store is used and supplies application actions; `workspace-host.ts` supplies workspace components. Its CSS follows the Adecore theme; Tailwind scans the installed package sources.
- `packages/pulsar`: zod schemas for wires to services outside a daemon (broker, WebRTC signaling, address book) and `BrokerPeer`. `signing.ts` holds the bytes every signature covers, each with its own prefix line, so a signature for one purpose never verifies as another.
- `packages/actions`: the catalog of typed actions a person can do and the registry that runs them, shared by voice, the UI and the daemon. Every call names its actor: a person, voice, an agent or automation.
- `packages/voice`: a Voice session's hard cases, shared by the desktop window and the daemon: appends to GPT-Live under the byte bound, one at a time against acks (`delivery.ts`), the tool loop that runs each call once (`tool-loop.ts`), following sessions over `ChatItem[]` (`session-watch.ts`, `follow-up.ts`), replies after an action, spoken-name matching and the mint body. No DOM, Node or Bun APIs; sending, running and timers are injected, and the client keeps only adapters over its own state.
- `@adecore/plan`: plan schemas and pure tree operations. `packages/contracts/src/plan-host.ts` adds chat-scoped envelopes; the plan store and UI stay in Ruimte.
- `@adecore/drawing`, `@adecore/diagram`: document schemas, pure operations and exports. `packages/contracts/src/drawing-host.ts` and `diagram-host.ts` add project/view/revision envelopes. The iOS document renderer resolves these installed packages with their license records.
- `@adecore/editor-core`, `@adecore/editor`, `@adecore/lsp`, `@adecore/editor-react`: editing, DOM engine, protocol client, shared language features and popups. Ruimte injects its Shiki highlighter and `RUIMTE_EDITOR_KEYMAP`. The client adapters (`language/ruimte-project-language.ts`, `ruimte-editor-language.ts`, `RuimteLanguagePopups.tsx`) keep the daemon transport, machine diagnostics, navigation and AI features. Ghost suggestions win over completion on Tab. What a server asks of a person goes through `language/server-prompts.ts`, never the service's `onShowDocument` or `onServerMessage`, which would open a server's address without a press.
- `@adecore/merge`: pure three-way conflict analysis and line/word diffs for the conflict UI and the daemon.
- `@adecore/database`: SQLite and MySQL/MariaDB through a native helper. The daemon runs its host (`apps/server/src/database/CLAUDE.md`); the client draws from it in `apps/client/src/database`.
- `@adecore/service`: launchd/systemd definitions and managers. `@ruimte/service/host` supplies Ruimte's identity, paths, environment and adapters for the desktop and CLI.
- `packages/desktop-bridge`: the IPC types and constants between the Electron shell and its page, `DesktopBridge` among them. Not a wire: it never leaves the machine. One place because the preload hands every answer over as `unknown`.
- `packages/csp`: the client's Content Security Policy as directives, read by the desktop shell and the station; a test holds the `<meta>` tag in `apps/client/index.html` against it. Also the path and policy of a visual's sandbox host page.
- `packages/npm`: the `ruimte` launcher and per-platform binaries, manifests generated by `scripts/build.ts`. The application workflow publishes only these.

Shared behavior comes from Adecore, through pinned npm packages or local links. Commit `db8f1afee` keeps the removed shared packages, PHP workspace and old editor and tree for comparison or rollback. FileTree renders with `@adecore/ui`; listing caches, persisted expansion keys, Git commands and staging stay in the client.

## Wire protocol

One WebSocket (or the same frames over a WebRTC DataChannel), JSON frames validated with zod on both ends.

- The one binary frame is a `bytes.read` reply to a request with `binary`: a JSON header and the raw bytes (`encodeBytesReply`, `packages/contracts/src/bytes.ts`), split over a DataChannel (`splitBinaryFrame`). Errors stay JSON.
- Request `{ id, type, payload }`. Reply `{ id, ok: true, result }` or `{ id, ok: false, error: { code, message } }`. Event `{ type: 'event', event, payload }`.
- Both sides derive `RequestMap` and `EventMap` from `REQUEST_SCHEMAS` and `EVENT_SCHEMAS` in `packages/contracts`.
- `PROTOCOL_VERSION` (`packages/contracts/src/protocol.ts`) moves only for an incompatible change; both ends refuse any other. `endpoint.info` lists every request the machine answers (`features`). A client checks a request newer than 0.18.0 with `machineAnswers` (`apps/client/src/transport/features.ts`, `MachineClient.answers` on iOS) and never catches `unknown-request`. The gate refuses a machine without `features` (`transport/protocol.ts`), so 0.18.0 is the oldest machine a client talks to.
- A client fails a request unanswered after 60 seconds, except those waiting on a network, a model or a database (`UNBOUNDED_REQUESTS` in `apps/client/src/transport/link-transport.ts`).
- Name a new request or event `<area>.<name>`: area singular, name lowerCamelCase (`session.runHeld`, `chat.status`), never kebab-case or a third level. A subscription is `<area>.watch` with `<area>.unwatch`.
- The client picks the session id (the node id), so a node reattaches after a reload.
- `session.attach` answers with the serialized `@xterm/headless` screen, then streams raw output. A client never replays history. A byte is in the screen or the stream, never both. A screen comes only from `Session.snapshotFor` (attach, resync, clear), which holds back that client's output from the call until the screen is taken, with no await in between.
- Agent status comes only from the CLIs' hooks (`POST /hooks/<kind>`, `apps/server/src/agents`), never from parsing output. A chat speaks the CLI's own protocol (stream-json, Codex's app-server or ACP), no SDK.
- Chat events carry a per-chat `seq` and are logged (`@adecore/agents/chat/chat-log`), so `chat.attach` with `since` resumes.
- A chat's thread goes only to attached clients. What a chat is _doing_ goes to every client (`chat.status`, on change only), like `session.status`, so a node waiting on a person shows on a view nobody has open. A client asks `chat.list` on every fresh socket. `project.changed` goes only to clients holding the project; others hear `project.summary` (`apps/server/src/projects`).
- Bytes for an `<img>` or `<video>` come only from `useMachineUrl` (`transport/machine-url.ts`). No draw site knows whether the link is a socket or a direct channel.
- A failed direct connection says why and never falls back to the socket.

## Invariants and seams

- A project lives in two files. `<folder>/.ruimte/project.json` is what a team commits. `<folder>/.ruimte/private/project.json` is one person's, kept out of git by the `.gitignore` the daemon writes once beside it. The private file holds the monotonic `rev`, the sidebar order over both, and per shared node the fields that cannot travel (`resume`, `runtimeMode`, `worktree`, any absolute path, and a session-given name, for which the shared file carries the kind's name). Every write goes against the rev it read; a conflict returns `rev-conflict`. Drawings and diagrams follow the same discipline.
- The unit of sharing is a whole view. Nothing is shared until a person's `project.save` names it in `shared`; a verb never returns that list, so an agent cannot move a view between files. A file view pointing outside the project folder cannot be shared. The shared file is written only when its text changes, so moving a private node leaves `git status` alone.
- Local state (open view, camera, grid layout, panels) is per client, never in `project.json`.
- A view or node of an unknown kind is kept as `unknown` and written back unchanged. A new kind is safe to write only once the previous release already had that fix.
- Every key of a stored node, view, text or layout survives a Ruimte that does not know it: written back unchanged, copied by a duplicate, carried when a node becomes a view and back. Schemas parse loose, types keep the known fields (`keepingUnknown`, `packages/contracts/src/project.ts`), so a later field must stay correct when an older Ruimte copies it. A new field is written only from the release after the first that keeps it, so 0.19 adds no stored field.
- A field that is one person's on a shared view sits in the overlay, named in the private file's `overlayFields`. A Ruimte that does not know it keeps it there and never reads it from the shared file. `overlayFields` acts only on unknown keys, so a newer release cannot turn off a field an older one depends on.
- A new stored field goes at the end of its schema: an older release writes the shared file in the key order it read, which keeps a private change out of `git status`. A loose `.pick()` of a node (`pickKeepingUnknown`) drops unpicked keys, since loose would keep them unchecked.
- A file node or view is a path, relative to the project folder, absolute outside it (`packages/contracts/src/stored-path.ts`). There is no store.
- The source address never grants access (behind a tunnel everyone is loopback). A local process proves itself with `$RUIMTE_HOME/local.key` (`apps/server/src/auth/local-secret.ts`). Every other client comes in through the account on an address book statement and proves its ed25519 key from then on. No pairing links. Only the local secret may have the machine sign a registration. The daemon never holds an account token.
- A remote client reaches a daemon only over a direct channel, signaled over the broker or the local network door (`apps/server/src/pulsar/lan-door.ts`), both through one `SignalGate`. The door answers only its signaling socket, the machine proves its key there first, and the API stays on loopback.
- A machine of the account works in another only as a peer (`apps/server/src/peering/CLAUDE.md`). Which machine a node runs on lives in `$RUIMTE_HOME/remote` and rides on the wire as `machine`, never in a project file.
- A client the machine let in, or an agent, is not the owner; what only the local secret may do stays with it. No client file request (`fs.read`, `fs.grep`, `fs.write`, `fs.rename`, `fs.delete`, `bytes.read`, `archive.list`, `archive.extract`, `GET /fs/file`) reaches under `$RUIMTE_HOME`, except the folders with a person's own work or a picture made for them (`apps/server/src/fs/machine-home.ts`).
- A visual runs only inside the sandbox host page at `VISUAL_HOST_PATH` (`/__visual/`, `packages/csp`) on the client's own origin, in a frame with `sandbox="allow-scripts allow-forms"`, never `allow-same-origin`, under `VISUAL_HOST_CSP`, which repeats that sandbox. The Vite dev server (`apps/client/visual-host.ts`), the desktop scheme and the station serve it, and the frame never leaves it (`appSubframeNavigation` in `apps/desktop/src/web-guards.ts`, the client's `frame-src 'self'`). The daemon never serves a visual inline on its own origin, only as a download or over `bytes.read`.
- Agents manage views and nodes through `ruimte-context`, parsed and validated on the daemon (`apps/server/src/canvas/CLAUDE.md`). Project writes go through `ProjectStore.mutate`.
- The daemon types a command from a project file only after a person on this machine approved it for that node (`$RUIMTE_HOME/command-approvals`, `apps/server/src/sessions/command-approvals.ts`). Until then the shell starts without it and the session holds it (`heldCommand`, `session.runHeld`). A person's `project.save` that sets the command approves it; a verb never does.
- A child agent never gets a wider permission mode than its parent (`@adecore/agents/modes.ts`, `apps/server/src/canvas/mode.ts`); the ceiling rides on every `start-agent` entry. A `--worktree` agent gets its own worktree under the machine's worktree folder (`$RUIMTE_HOME/worktrees` unless a person chose another), never removed automatically. A worktree merge (`apps/server/src/git/worktree-merge.ts`) runs in the checkout with the target branch out, never stashes and never moves a ref behind a working tree. An agent merges only the worktree of a node it opened, into a checkout without tracked changes; a conflict goes back to it. The merge only merges: the child keeps running, and its worktree and branch stay until a person removes them.
- Area invariants and one feature's product rules sit in a `CLAUDE.md` beside the code, loaded when a file there is read. In `apps/client/src`: `browser`, `canvas`, `dictation`, `shell/panels`, `state`, `transport`. In `apps/server/src`: `agents`, `artifacts` (Output), `browser`, `canvas` (agent verbs), `chat`, `computer`, `database`, `devices`, `git`, `language`, `launches`, `outbox` (tasks too), `peering`, `power`, `projects`, `provenance`, `routines`, `templates`, `visuals`, `voice`.

## Product rules

Decisions the code cannot show. Do not reverse one without asking Bas.

- Three things wake a chat, each once, through the outbox (an observer only notes): a finished task wakes the chat that delegated it; a message wakes the chat it was sent to; a PR-watch a person turned on for one chat wakes it once per terminal check state of the current head, or new review. The turn a message or PR-watch opened wakes nobody. A terminal is never woken.
- A child that stops on a limit pauses its task. The turn says which limit and when it lifts (`limit`, read only from the CLI's stream), the task stays open with `paused`, and the parent sleeps until the child finishes after the reset. An overload the daemon does not retry is an error and fails the task.
- A task settles only once its child is really done.
    - A turn that ends while its CLI runs background work (a background subagent, a Claude workflow, an agent Codex spawned: `@adecore/agents/chat/background-work.ts`) settles nothing and wakes nobody. The task settles on the turn the CLI opens itself once that work ended, on the child's last turn when its CLI opens none (Codex), or on `ruimte-context done`, which works at any time.
    - A background command or monitor of the child's CLI (its own or a subagent's, as the chat's `background` shows) holds the task for at most 30 minutes from when it is all that is left, since a dev server never ends. That limit is a `background-limit` outbox entry: it survives a restart, runs once, and lapses when the task settles otherwise. When it passes, the task settles on the child's last result, which names the commands still running.
    - A daemon restart takes the CLI and its commands down. A task held only by commands then fails at once with the child's last result and a line naming what was lost, and wakes its parent once, as when the CLI goes within one run.
    - Subagents and workflows have no limit. An active goal (`/goal`) holds the task the same way, with no limit, through every turn toward it. The task settles once the goal is met, paused or cleared and the turn ended, and fails with the child's last result when the CLI goes while the goal is active.
- Resuming after a limit runs on a clock only when a person turned it on: the machine's `resumeAtReset` (`endpoint.json`, off by default) and a chat's own switch, which follows the machine when absent. A `resume-limit` outbox entry carries the time: a usage limit's reset, or 1, 5 and 15 minutes after an overload, after which the overload is an ordinary error. It lapses when a person writes first, stops the chat, turns a switch off or the node goes.
- The only work the daemon schedules on a clock: the resume after a limit, the limit on background commands, the end of a snooze (`apps/server/src/push/snoozes.ts`), a PR-watch poll (`apps/server/src/github/pr-watch.ts`), the hold on a push while a person is at a desktop (`apps/server/src/push/service.ts`), the reconnect to another machine while work for it is owed (`apps/server/src/remote/connect-peer.ts`), an approved routine at its time (`apps/server/src/routines`), and the hourly sweep of expired disposable files (`apps/server/src/maintenance`).
    - A routine runs at most once per due time and once on wake for missed times, never beside its previous run, never while paused.
    - The sweep runs at start and hourly, only while no agent is in a turn (a terminal never holds it), never beside its previous pass. It takes only screenshots, unplaced device captures, the computer use helper's captures, the chat store's abandoned temporary writes past their writer's age, and PHP index caches beyond a 512 MiB budget or of vanished checkouts, never while a PHP server uses them.
    - A PR-watch polls only while on and backs off while nothing changes. It ends when a person stops it or removes the chat (a turn's Stop leaves it), when the PR is merged or closed, or after 7 days.
    - A reconnect backs off while the machine does not answer. It ends when nothing is owed to that machine, when a person stops the task or removes the link, or after 7 days, when every task still owed there fails with a line saying so and wakes its parent once. Leaving the account fails all those tasks at once in the same way.
- A child whose task waits on a question or approval leaves its parent one note per request (`deliver-waiting`, `@adecore/agents/tasks/waiting-child.ts`) without waking it. The note is due 15 seconds after the request, written only if it still waits. A child on another machine leaves none; its requests wait there for a person, and its parent hears only the result.
- A parent may answer a question of a child it opened with `ruimte-context answer`, like a person's `chat.answer`; the first answer wins. Approvals, logins and every other card stay with the person. A parent may `ruimte-context read` a child it opened without a line.
- A chat reads and writes, as along a line, in every view or node of its project a person referenced with `#` in one of its messages, while that message is in its thread (`apps/server/src/context/references.ts`). This is checked at every call, so one that went or left the project closes again. A referenced terminal stays read-only (`notify` reaches it). A referenced chat gets `notify`, never `task new`. A `#` to a canvas reads everything on it and adds nodes (`node new`), but writes only in a node with its own `#` or line. Every other node needs a line.
- A push to a phone waits while a person is at a desktop. Each client sends `presence.report` from the system idle state (input in any app counts, a locked screen does not); a report lapses after a minute. A wait or attention alert waits 60 seconds, an approval 10, and goes out only if still unread or unanswered. A finished turn or process warning due while the person stayed goes nowhere. When the person leaves, everything held goes out. An alert asked for (`ruimte-context alert`) never waits.
- A terminal's permission prompts and questions stay in its TUI; a person chose the TUI for a reason. Ruimte only shows that it needs you (status, stack card, notification) and never answers. Approvals are answered from the app or a phone only in an AI chat.
- Every shortcut needs a modifier. The only bare keys: a drawing view's tools while no text is typed and no dialog is up; the widget keys in a prompt card (arrows, Home, End, Space, Enter) while it has the focus; Space for Quick Look (Space or Escape closes it) while the focus is on a file in the files panel tree, on macOS, for a project on this machine.
- Never highlight the canvas grid in the accent color. Type: only the four sizes in `@theme`, no bracket sizes, nothing below 12px except a model's badge (11px, capitals). Geist only for the wordmark and as an interface font a person picks, never the default. Kalam only for drawing text.
- The wire only gains optional fields, new requests and new events. Never a new `ChatItemSchema` member or enum value in a chat or push payload; the iPhone app validates `chat.attach` and `chat.history` whole.
- Agents never type into or close another node's session, or start a command through a verb (only `agent` starts anything). `--cwd` stays inside the project folder or its worktrees. Every other door into a feature has its rules beside its code. In short, an agent:
    - starts, restarts or stops only a launch a person approved as it stands now, and adds and edits launches that wait on that approval (`apps/server/src/launches`);
    - adds and edits routines that wait on a person's approval, and runs one now only once approved as it stands (`apps/server/src/routines`);
    - drives a browser node only by address, over a line (`apps/server/src/browser`);
    - drives a device only by screenshots, taps and its tools, with paths only inside the project folder or its worktrees, over a line, and never starts, stops, restarts, erases or folds one or sets its camera (`apps/server/src/devices`);
    - operates an app through computer use only after a person let it into that app (`apps/server/src/computer`);
    - writes to a database only on a connection a person set to write, never from `supervised` (`apps/server/src/database`).
- An AI chat that is a view of its own arranges a canvas as a person does. No line reaches a view, so with `--view <canvas>` it adds, edits, renames, arranges and groups that canvas's nodes, draws lines between them, and reads and operates every node there without a line (`read`, `node edit`, `node color`, `browser`, `device`). A node it adds gets no line to it. Without `--view` those refuse with `view-required`. An agent that is a node keeps to its lines exactly. A chat view still never types into or closes another session and deletes only what it made; the mode ceiling, `--cwd`, launch approvals and the database and computer use grants keep their checks (`apps/server/src/canvas/chat-view.ts`).
- Whatever the daemon enforces against an agent (depth, lineage, tasks) lives under `$RUIMTE_HOME`, never in `project.json`, which an agent with a shell can rewrite. An observer only notes; only the outbox acts. Nothing removes a worktree on its own.
- Nothing reads a vendor credential (keychain, `~/.codex/auth.json`, usage endpoints); plan windows come from the CLIs. The exceptions are keys a person typed into Ruimte:
    - a key for a provider without a CLI, also sent to that provider's own usage endpoint (NanoGPT's `/usage`);
    - an Anthropic API key for the Claude API, set only through the local secret, kept 0600 under `$RUIMTE_HOME/anthropic-claude-api` and sent only to `api.anthropic.com` (`apps/server/src/providers/anthropic-claude-api-service.ts`);
    - the OpenAI key for Voice, sent only to OpenAI in the `Authorization` header (`apps/server/src/voice/CLAUDE.md`).
- One vendor credential is read, by Bas's choice: Grok shows its plan only in its own interface, so the daemon reads the token `grok login` left in an account's `auth.json` (xAI sign-in only, never an API key). It never renews or writes it and sends it only to the billing endpoint the CLI asks (`apps/server/src/usage/grok-plan.ts`).
- A stuck process gets a warning, never a signal a person did not press.
- Closing a project is one client's. The machine keeps it and its sessions running while another client has it open; only the last client out ends them and drops it under Recent. Closing a window does not close its project: the window writes what it had and lets its sockets go. Which projects a person keeps in their menu is per client, so closing on a laptop leaves the iPhone as it was. A dropped socket ends nothing.
- A page never sees a refresh token, a daemon never holds an account token, and accounts are never merged.
- A machine is on at most one account and shared only with its owner. Only the local secret (the app on it, `ruimte login`) puts it on one. Another account gets `machine-has-account` until a person on the machine leaves the first. A machine takes only a statement v2, and only one of its own account (`apps/server/README.md`, "One account per machine").

## Conventions

- TypeScript in the Bun workspaces, Swift in `apps/ios`. 4 spaces, LF; `.editorconfig` rules.
- American English in code, comments, commit messages and UI text. No em dashes or en dashes anywhere.
- Always curly braces, also for one-line early returns. No one-letter names except `i`, `e`, `x`, `y`.
- Named top-level functions are declarations, exported with `export function`. Functions from factories or wrappers stay `const`; mutable callback slots stay variables.
- Arrow functions for callbacks and inside functions; class methods are never arrow properties.
- Comments explain WHY, never what the code already says.
- Keyboard shortcuts bind on `window`, once, never per cell or node: the window's own in `shell/app-shortcuts.ts`, project actions in `canvas/canvas-shortcuts.ts`, bound by the workspace, so the start screen has none of those.
- A new command is a row in `apps/client/src/shell/command-table.ts`: menu place, palette row, shortcut and the listener that binds it. Only generated rows (per view, launch or agent, roles, submenus) stay in `shell/menu/model.ts`. The menu only shows a key: the shell drops an accelerator's command when the page had the key first (`createMenuCommands` in `@adecore/shell`). The menu answers where the page never saw the key: a browser node's page, an item picked through accessibility, a key sent to a window that is not key.
- A new surface that draws its own data gets an `ErrorBoundary` (`@adecore/ui`), keyed so it resets only while it holds an error.
- A zustand selector that builds a new array or object per call loops forever under `useShallow`. Select the object and derive in render.
- The client and ADE CORE's React packages build with the React Compiler in Vite and in DOM and browser tests, not the unit run (`apps/client/react-compiler.ts`); oxlint enforces its rules. Write no `useMemo`, `useCallback` or `memo` the compiler covers. Keep one only where an effect depends on the value, for a row of a long list, or in a function the compiler leaves as written. Read a value from outside React (a mutable object, a version counter) through `useSyncExternalStore` with a snapshot. Call a hook by its `use` name, never pass it as a value. A language or region change empties every compiled cache (`src/compiler-runtime.ts`).
- The start screen and the workspace are separate chunks, so the station's first load has no workspace code. Nothing `main.tsx` or the start screen imports statically may reach `shell/WorkspaceShell.tsx` or what only it draws. A panel, view or dialog not every workspace opens loads through `lazyNamed` or `lazyDialog` (`@adecore/ui`) inside its `ErrorBoundary`. The library's `prefetcher` fetches the workspace once the start screen is idle, then each lazy module one at a time once a workspace is idle; a lazy module registers itself. A chunk that fails to load reloads the page once (`src/stale-chunks.ts`), unless only a prefetch asked for it.
- UI uses only semantic tokens from `@adecore/ui/theme.css`, `@adecore/agents-react/theme.css` and `styles.css`; no raw colors elsewhere. A border is an alpha over what is behind it, never its own gray. Every surface clips its background to the padding box, so the line mixes with the ground. Tooltips are `Tooltip`, never `title`. Icon buttons are `IconButton`, related ones in a `ButtonGroup`. Icons are Lucide through `Icon`, except file icons (`FileIcon`, `@pierre/trees` with its colors), provider marks (`ProviderLogo`) and Ruimte's mark (`RuimteMark`, `currentColor`). No fractional pixels; a `rem` or `em` resolves to whole pixels.
- UI that knows nothing of Ruimte belongs in `basmilius/adecore`, and so does a fix to it. When the library lacks something or draws it wrong, run `gh issue create --repo basmilius/adecore`, titled `<Component>: <the need>`, labeled `Ruimte` and `Bug` or `Enhancement`, with three sections:
    - `## Problem`: what is missing or wrong, the call sites here as `path:line`, and today's workaround.
    - `## Wish`: the need as what a person does or sees, not a fix; a proposed API is optional.
    - `## Impact on AfterMotion`: search `../aftermotion` for the component or pattern; name the call sites a change would touch and whether it would change what they draw or break them, or say there are none.
- Edit a shared repository only at its real path, never through `node_modules`, and only when the task authorizes it. Validate ADE CORE changes there and in linked Ruimte; keep its commits separate. Never copy shared implementations into Ruimte.
- After a dependency change, run `bun install` in that repository before relinking ADE CORE. Push Ruimte code using a new ADE CORE API only with a bump to the published version in the manifests and `bun.lock` (`bun run adecore:bump <version>` moves every pin and refuses a linked checkout), after `adecore:npm`, `adecore:status --npm` and the relevant npm consumer checks pass. Linked checks do not validate CI's registry install. No pre-push hook is required. The source conditions in the release builders are deliberate: npm consumer checks bundle published sources; ADE CORE CI's `test:pack` validates packed `dist` and source exports. See `docs/ADECORE-DEVELOPMENT.md`.
- In anything a person reads (UI text, tooltips, errors, toasts, empty states) a daemon is a **machine**. Code, comments and docs say daemon.
- The interface is in English and Dutch (`apps/client/src/i18n`, react-i18next, a file per namespace per language). English is source and fallback; a key without Dutch reads English. `locales.test.ts` fails when the two drift apart. That folder's README has conventions, glossary and what stays untranslated. Tests read English through the `preload` in `bunfig.toml`, so assert a label-building function on the sentence, not the key.
- `@adecore/ui/format` writes every number, date, time and duration a person reads, and is the client's only `Intl` formatter builder. It reads two settings from the source `apps/client/src/format/source.ts` hands it at startup, apart on purpose: the language writes the words, the region the order, separators and clock. The region follows the language unless set. `system` is what the desktop shell passes (`app.getSystemLocale()` beside `app.getPreferredSystemLanguages()`), since Chromium's locale is the bundle's and would write `08:00 AM` on a Dutch Mac. English on a Dutch machine reads `19 Sep, 08:05`. A surface that would sit still through a region change calls `useFormatLocale()`.
- Tests: `bun run test`, beside the code (`foo.test.ts`). The default run never depends on wall-clock timing, a real shell or a file watcher. Use a fake (`FakePtyAdapter` in `apps/server/src/pty/fake-pty.ts`, an injected clock or watch, `jest.useFakeTimers()`, `setSystemTime`) and await what the code resolves. `bun run lint` refuses a wall-clock read in a `*.test.ts(x)` outside a fake clock's setup (`scripts/check-test-clock.ts`). A test failing on a timeout is made deterministic or deleted, never given a longer timeout.
- Real shells, watchers, sockets or processes go in `*.integration.test.ts` (`bun run test:integration`), which cleans up its processes. A real `git` fixture is fine, built once per file (`apps/server/src/git/test-repo.ts`). A test of a one-platform subject skips with `skipIf(process.platform !== '<platform>')` and imports that module inside, never by catching a missing tool.
- CI: unit tests in two isolated shards balanced by `test-timings.json` (`bun run test:timings` remeasures). Checks and unit shards run on Linux, since a unit test gets its platform passed in. Core integrations (`--suite core`) and the packaged daemon (`*.package.integration.test.ts`, `bun run test:package`) run on macOS and Linux (`ubuntu-latest`; the packaged daemon on `ubuntu-22.04`, the release's glibc floor). Generated native fixtures, builds and the file system tests again (case-insensitive volume) run on macOS only. Checks, the client/desktop build, core integrations and the packaged daemon run independently; the final CI check requires all. The default integration command still includes the packaged daemon.
- Tests needing a simulator or physical device go in `*.device.integration.test.ts`, run only with `bun run test:devices`. Integration discovery excludes them before loading, so CI never probes for a device.
- Tests of what a person does in the window go in `*.dom.test.tsx`, run by `bun run test:dom` in happy-dom (`dom.bunfig.toml` preloads it before React); the unit run skips them. They draw the whole window where they can (`renderApp` in `apps/client/testing/dom.tsx`) against a `FakeMachine` behind the pool (`testing/fake-machine.ts`, `fake-workspace.ts`), and assert what a person sees and what crosses the wire, never an action or command id. CI runs them on Linux.
- Tests that start a browser or Electron go in `*.browser.integration.test.ts`, run only through `bun run test:browser` (which builds the client first) or the manual Browser tests workflow. CI excludes them, release checks included.
- `bun run format` and `bun run check` (typecheck, generated files, oxlint in every workspace with warnings failing, `format:check`) pass before a commit. Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`).
- Written from scratch. Copy no code from any other product; sharing ideas and npm packages is fine.

## Releasing

A release runs to the end without asking. Bas names a version, and the next thing he reads is that it is live.

- CI decides, not this machine. The `ci.yml` run on the tagged commit must be green. Nothing is built, checked or tested here for a release, and a published build is never downloaded to try its daemon.
- A red CI is fixed before the tag: find it, fix it, push to main, wait for green. Only what Bas alone can decide goes back to him.
- The notes ride on the tag, so the draft is never empty and publishing needs no second edit. Write them to a file and run `git tag -a v<version> -F <file> --cleanup=verbatim`; without that flag git strips every `##` heading. `release.yml` builds macOS and Linux into the draft and publishes it as Latest once the run succeeds.
- Publishing starts `npm.yml`, which puts `ruimte` and its three platform packages on npm at the same version. A release that became Latest also starts `station.yml` and `bench.yml` to deploy that tag's web clients; a push to main deploys neither. `docs/RELEASE.md` has the recipe, the secrets and past breakages.
- Adecore libraries release independently. Ruimte pins their versions in its manifests and lockfile; `libraries-v*` tags no longer publish from this repository.
