# Ruimte

Terminals, agents and browsers on one infinite canvas. Read `README.md` for the principles and `docs/DECISIONS.md` for the decisions that are not in the code, the traps already paid for, and what comes next. This file is for anyone (human or agent) changing code.

## Layout

Bun workspaces (`bun install` at the root):

- `apps/client`: the React UI (Vite). Never imports Node or Bun APIs. Talks to the server only through the `Transport` interface. One window holds one or more workspaces (`transport/connections.ts`), each a project on a daemon with stores of its own; the sidebar lists the workspace in focus or every one in the window (`settings.sidebarScope`).
- `apps/server`: the daemon (Bun runtime). Owns sessions, PTYs and persistence. Serves the WebSocket API on `localhost:4210` by default (`--host`, `--port`), and a built client with `--serve`. In dev (`bun dev`, an unpackaged desktop app) it runs on `4211` with `RUIMTE_HOME` defaulting to `~/.ruimte-dev`, so it never meets an installed Ruimte; pair against it with `bun src/main.ts pair --port 4211`.
- `apps/desktop`: the Electron shell. One window, the client inside it, the daemon next to it. Only window chrome, native dialogs and guest devtools cross IPC (`src/preload.ts` mirrors `apps/client/src/desktop/bridge.ts`). `bun dev` starts it next to the client and the server, and `bun run dev:desktop` starts it alone; unpackaged it is "Ruimte Dev" with a `userData` of its own. A packaged app (`bun run dist`, `electron-builder.yml`) carries the compiled daemon (`apps/server/scripts/compile.ts`) and the built client as resources.
- `packages/contracts`: zod 4 schemas for every message on the wire, plus the TypeScript types derived from them. Both apps import from here; nothing else may define a wire shape. `REQUEST_SCHEMAS` and `EVENT_SCHEMAS` are the tables both sides derive `RequestMap` and `EventMap` from.
- `packages/drawing`: the pure part of a drawing (geometry, hit tests, the rough and freehand paths, the SVG painter, the reading order). No DOM: the client uses it for hit tests and export, the daemon for what an agent reads. The canvas painter stays in the client, which is the only side with a `CanvasRenderingContext2D`.

Shared config at the root: `tsconfig.base.json` (every package extends it), `.oxlintrc.json`, `.editorconfig`, `bun.lock`. `bun run check` runs `typecheck` in every workspace and then oxlint. In dev the Vite server proxies `/ws` to the daemon, so the client always connects to its own origin.

## Wire protocol

One WebSocket. JSON frames validated with zod on both ends.

- Request from client: `{ id: string, type: string, payload }`. Reply from server: `{ id, ok: true, result }` or `{ id, ok: false, error: { code, message } }`.
- Event from server (no `id`): `{ type: 'event', event: string, payload }`.
- Terminal output travels as `{ event: 'session.output', payload: { sessionId, data } }` where `data` is a UTF-8 string, coalesced per animation frame on the server.
- Agent status travels as `session.status` (`agent: AgentInfo | null`), chat threads as `chat.event` (`item` upsert, `delta`, `info`). The daemon also serves `POST /hooks/<kind>` for the CLIs' hooks, bearer token per session.
- Usage travels as `usage.summary` (buckets per slot, provider and model in the viewer's own time zone, plus the models, projects, the day's exchange rate and the provenance the buckets cannot express), `usage.subscribe` / `usage.unsubscribe` (keep scanning while a page is open) and `usage.limits` / `usage.refreshLimits`; the daemon pushes `usage.changed` (only the moment of the scan, so a page asks again for the period it has) and `usage.limitsChanged`. Everything under `apps/server/src/usage`: transcripts read incrementally into `$RUIMTE_HOME/usage/index.json`, priced with the LiteLLM table (24 h, bundled snapshot as the fallback, `--no-price-fetch` to stay on it), converted with the ECB rate of the day (frankfurter.app, same lifetime, dollars without one), and plan windows asked of the CLIs themselves rather than of any endpoint. The page is about one machine, picked in its own header (`shell/usage/picker.ts`, the choice held for the session and never stored); the limit bars in the sidebar stay on the machine the workspace runs on.

## Terminal sessions (the daemon)

- A session is keyed by an id the CLIENT chooses (the node id), so a node reattaches to its own session after a reload.
- PTY via `Bun.spawn({ terminal: { cols, rows } })` behind the `PtyAdapter` interface (`apps/server/src/pty`). No node-pty, no tmux.
- Every session runs `@xterm/headless` with `@xterm/addon-serialize` in the daemon. `session.attach` answers with the serialized screen, then streams raw output. A client never replays history itself.
- Output is buffered per attached client and flushed every 16 ms, on detach and on exit. `Session.attach` registers the client in the same tick the serialize resolves, so a byte is either in the screen or in the stream, never both.
- Scrollback snapshot to `$RUIMTE_HOME/sessions/<id>.txt` (default `~/.ruimte`) every 30 s and on SIGINT/SIGTERM; written temp-file plus atomic rename, file name via `encodeURIComponent(id)`.
- A shell that ends on its own leaves the session listed as `exited` (last screen still attachable). `session.kill` removes the session after its `session.exit` event and deletes the snapshot. `session.create` on an exited or snapshotted id starts a fresh shell with the old screen above a `[session restored, previous shell ended]` line.
- `ClientConnection.id` is the per-socket client id; `main.ts` subscribes each socket to the `SessionManager` and the `ChatManager` and calls `detachAll` on both when it closes. See `apps/server/README.md` for flags, hooks, chats and the on-disk layout.
- Agent status comes from the CLIs' hooks only (`apps/server/src/agents`), never from parsing output. A chat node is the CLI's stream-json protocol (`apps/server/src/chat`), no SDK.
- A project is `<folder>/.ruimte/project.json`, version 2: a name, a color, an icon and a list of views with a monotonic `rev` (`apps/server/src/projects`). A view is a canvas (nodes, texts, edges, layouts) or, later, a standalone chat, terminal or browser. The daemon reads version 1 and 2 and writes only 2 (`migrateDocument` in `packages/contracts`); at parse time it refuses a project where a view id or a node id repeats and drops an edge that points outside its own view. Machine state (which view was open, the camera and focus per view, the panels) lives in `<projectId>.local.json` and never in the shared file. The client saves through `project.save` with the rev it loaded and reacts to `project.changed` from the daemon's watcher and from a verb an agent ran. A document that arrives on a clean client replaces what is on screen; one that arrives on a client with unsaved edits is merged when the difference is nothing but node, text, edge and view ids this client does not know (`apps/client/src/project/merge.ts`, three-way against the document the file held at the rev the client is on). The additions land in the editor of the view they belong to and not only in the document, marked as a load, so no undo step, no camera move and no drag in progress is lost, and the rev they came with is the base of the next save. Anything else (a node the client knows that moved, a deletion, a rename, another order) keeps the conflict dialog, with `ProjectClient.mergeRefusal` saying which id made it one; a save that was already on the wire is refused with `rev-conflict` and made again against the merged rev. Switching away from a project is `project.release`, which only stops the watcher; `project.close` is a person closing it, which stamps `closedAt` on the registry entry so every client keeps the project under Recent until `project.open` clears it again. Closing also ends the sessions of the project's nodes, behind a confirmation that counts them (`sessionNodesOf` in `apps/client/src/project/project-sessions.ts`, `endProjectSessions` in `apps/client/src/terminal/lifecycle.ts`): the client kills each terminal and chat before it empties the canvas, because the watcher that ends a node leaving the document skips a document that is swapping out. Nothing makes a project as a side effect: `project.list` on a daemon nobody has opened one on answers an empty list, a boot opens only what that machine had open before, and with no project open the main column carries an empty state instead of a canvas (every surface that would write into a canvas is gone in that state).
- The project list is every machine at once: `project.list` per endpoint, folded into `state/project.ts`, where a row names the endpoint it came from (`apps/client/src/project/list.ts`). The last answer of a machine is cached in localStorage, so a daemon that is not answering still lists its projects, dimmed. The switcher draws them as one list rather than a group per machine (`menuProjects` in the same file): most recently opened first, the machine behind the name once this client knows more than one, the folder in a tooltip, and everything with a `closedAt` under a Recent submenu. What can be done to the project that is open (reveal, rename, icon, close, delete) is not in the switcher but in `shell/ProjectActionsMenu.tsx`, the overflow menu beside the panel toggles. `openProject(endpointId, projectId)` (`apps/client/src/project/open.ts`) is the only way in and sets the active endpoint on the way, with `openFolderOn(endpointId, folder, createFolder)` as its folder twin; `ruimte.lastProject` holds `last` (which machine a cold boot lands on) next to `byEndpoint` (what a switch reopens). Anything drawn per row (the icon URL, a reveal in the file manager) uses that row's endpoint, never the active one.
- A machine has a name and an icon of its own, kept in `endpoint.json` beside its id and key pair so every paired client sees the same ones: `endpoint.info` and the pairing answer carry them, `endpoint.setIdentity` sets them from any client, and `endpoint.changed` tells the others. The icon is the `ProjectIconChoice` a project and a view already use. A name typed in a client wins over `--label` and `RUIMTE_LABEL`, which say what a machine nobody has named answers to. The client draws that icon with `MachineGlyph` (`apps/client/src/endpoint/MachineGlyph.tsx`, a server when nobody picked one) and sets both in one dialog from the Machines pane, since the wire takes name and icon together; `startEndpointWatch` (`apps/client/src/endpoint/watch.ts`) listens for `endpoint.changed` on every socket, and a name a person chose also becomes the label of the endpoint row this client keeps.
- A loopback client needs no credential; any other client pairs once (`POST /auth/pair`), registering an ed25519 public key, and then signs a challenge from the daemon on every connection (`POST /auth/challenge`, `POST /auth/ticket`) for a ticket that rides in `?token=` on the socket and on the HTTP routes an `<img>` fetches (`apps/server/src/auth`, `apps/client/src/endpoint`). The daemon has a key pair of its own next to its id and signs every challenge, so a client pins the machine it paired with rather than believing whatever answers on the address. The client's private key is a non-extractable `CryptoKey` in IndexedDB. A client that paired before this holds a session token and keeps working; `auth.registerKey` moves it onto a key over its own connection and the token is dropped the first time a signature lands. A daemon is keyed on the id it mints for itself, not on its address (`apps/client/src/state/endpoints.ts`). The client holds a socket per daemon in a `TransportPool` (`apps/client/src/transport/pool.ts`), each with its own reconnect loop; `transportFor(id)` is one machine's socket and the exported `transport` is a facade over the machine that is active, left for the few call sites that really mean "whichever machine the app is pointed at". `transport/connections.ts` builds a session and a chat client per machine (several may be alive at once) and a project and drawing client per workspace.
- State that is about a daemon is keyed on it. `apps/client/src/state/keys.ts` is where `${endpointId}:${nodeId}` is written down, with `useEndpointId()` as the one place that says which machine the code on screen is about. The sessions, chats, browser pages, terminal screens and drawing mirrors are rows under that key; the server info, the providers and the usage numbers sit under `byEndpoint`. A switch throws nothing away any more, and forgetting a machine drops its rows.
- A workspace is one open project: the daemon it lives on, its project and drawing client, and the stores that hold it (`useCanvas`, `useDocument`, `useDrawing`, `useProject`). `document` and `project` are one store each; `canvases` and `drawings` are registries of one editor per view on screen (`state/editors.ts`), because a grid of cells edits several views at once. All of it is built in `state/workspace.ts` behind hooks that read the workspace they are rendered in (`state/workspace-stores.ts`); an editor hook resolves in three steps: the cell the component is drawn in (`CellViewContext`), else the cell that has the focus, else the blank editor a unit test gets. Outside React every hook means the workspace with the focus, which is what every existing call site already meant. The union of every machine's projects is not a workspace's and lives in `state/project-list.ts`. `WorkspaceProvider` (`transport/context.tsx`) puts a `Connection` and the stores over a subtree: a panel, a node or a dialog inside it reads `useTransport()` and `useEndpointId()` and never names a machine. `App.tsx` draws one workspace; a second pane is a feature of its own, and `openWorkspace(id, endpoint)` is what it will ask for. Splitting _views_ of one project is a different feature and is built: see the grid below. The palette, the settings and the toasts sit outside every workspace and work on the one with the focus (`useFocusedConnection`). The Machines pane keeps machines (pair, forget, status, paired clients); opening a project is what says where the work is.
- Picking a folder to open as a project is a step of the command palette, not a dialog of its own: `browse: { endpointId, machines, path } | null` says where browsing is, and a path typed into the palette is a second way in (`apps/client/src/shell/CommandPalette.tsx`, with the pure parts and the step rules in `shell/palette-browse.ts`). It opens on the machines when the client knows several and on the folders of the one machine otherwise, lists through `transportFor(browseEndpointId)`, and `fs.browse` answering `exists` is what lets the button offer to create a path that is not there.
- Edges into an agent node become readable context: the daemon derives what each agent may read from the project documents it knows (`deriveContextSources` in `packages/contracts/src/context-sources.ts`, held per project by `ProjectIndex` in `apps/server/src/projects/project-index.ts`, which outlives `project.release` and is warmed from the registry at start), serves `GET /context` with the session's token, and `ruimte-context` (a script on every session's PATH that runs `ruimte context`) is how an agent reads it. Worktrees live under `$RUIMTE_HOME/worktrees` (`apps/server/src/git`).
- An agent changes the canvas through verbs on the same CLI: `ruimte-context <verb> ...` posts its words to `POST /canvas/<verb>` beside `/context`, with the same bearer, and the daemon parses them (`apps/server/src/canvas`). One object per verb in `verbs.ts` holds the synopsis, the zod schemas for its positionals and flags, and `run`, so `help` renders from what validation checks; `list` and `read` sit in the same registry without a `run` (`served: 'context'`), so `help` names everything the CLI does while `GET /context` keeps answering them. The caller is found with `ProjectIndex.locate`, never among the open projects, and a verb that needs a canvas takes `--view` or the canvas the caller is a node on. A write goes through `ProjectStore.mutate`, which reads the file under the save lock whether the project is open or released, writes `rev + 1`, updates the index and sends `project.changed` to every socket. The answer is tab-separated lines; a refusal is a 422 whose first line is `refused\t<code>\t<message>`, and the CLI exits 3 on it.
- A file is a path and nothing else: a node of kind `file` and a view of kind `file` both carry one, relative to the project folder and absolute outside it (`storedPathOf` and `resolveStoredPath` in `packages/contracts/src/stored-path.ts`). The bytes are the file system's, so there is no store, no rev and no request of its own: `FileSurface` resolves the path and `FileBody` reads it with the same `useFileRead` and `renderFile` the preview panel uses, read-only. Every reader holds a counted `fs.watch` on the folder it is in (`state/fs-watch.ts`), the files panel included, because a node on a canvas with that panel closed would otherwise never hear that the file changed. A file lands on the canvas by dragging it out of the files panel, off a preview tab or out of the file manager, on the sidebar as a view of its own, from the row menus, or through the palette's file step (`openFilePicker`). The rules of a drag are pure in `canvas/drop.ts`: it leaves a directory out, and `dropEffectFor` keeps the cursor to what the source allowed, since the files tree allows a move and a target asking for a copy makes the browser refuse the drop without ever delivering it. A drag out of the file manager is the one that needs more than rules: a browser never tells a page where a file came from, so `pathForFile` on the desktop bridge (`webUtils.getPathForFile`, preload only) is what names it, and `finderRefusal` turns both dead ends (no shell, a project on another machine) into a toast that says which one it is (`canvas/finder-drop.ts`). The controls of a file (wrap, source or preview, the overflow menu) live in the renderer that draws it, so where the surface already carries a bar they are portaled into it rather than drawn a second time under it: `file-toolbar-slot.ts` holds that seam, the window's toolbar offers the host for a view (`App.tsx`, `ViewToolbar.tsx`) and a node offers its own header (`NodeFrame.tsx`), while a preview tab has none and keeps its own bar. The menu itself splits the same way: `FileActionItems` is what can be asked of the file on any of the three surfaces, and `FileMenuItems` adds what is about a tab (pin, close, stage, the diff). Reading a file is the whole cost of the node, so a node that is out of view or under `READABLE_ZOOM` (`canvas/culling.ts`) draws a plate with its mark and its name and reads nothing at all, and a file past `HIGHLIGHT_MAX_LINES` is drawn as plain text with a pill that says so. An edge from a file node into an agent is the cheapest source there is: `ContextSourceSchema` carries the path and the daemon answers with that path and a line telling the agent to read the file itself, since its own tools see a fresher copy and a megabyte of source would crowd out everything else in the window.
- The views of one project stand beside each other in a grid of at most three columns of at most three cells (`shell/split.ts` is the pure model, `shell/SplitGrid.tsx` draws it). One view stands in at most one cell: a view already on screen moves rather than appearing twice, and a drop on the middle of a cell swaps the two. The document store owns the layout and `activeViewId` is the view of the cell that has the focus, derived from it and never set apart from it. The layout is machine state, so it rides in `<projectId>.local.json` beside the camera and the panels, never in `project.json`. A drag carries `application/x-ruimte-view` from a sidebar row or a cell's own toolbar (`shell/view-drag.ts`); the payload is unreadable until the drop, so the one drag in flight is held in module state. With one cell the window's toolbar speaks for the view; split, every cell carries its own bar (`shell/CellToolbar.tsx`) and the window's goes back to being the application's. Every chord that acts on a project is bound once per workspace in `canvas/canvas-chords.ts`, never per cell: nine cells would be nine listeners all resolving to the focused one.
- A drawing view keeps its elements in `<folder>/.ruimte/drawings/<viewId>.json`, one element per line, under the rev discipline of the project file (`drawing.open`, `drawing.save`, `drawing.close`, `drawing.copy`, `drawing.changed` from a watcher of its own in `apps/server/src/projects/drawing-store.ts`). The client edits it through `useDrawing` and `DrawingClient` (`apps/client/src/drawing`), the same shape as `useCanvas` and `ProjectClient`. Colors are palette names, never hex; a drawing follows the theme.
- The processes panel is the process table of the machine a workspace runs on (`apps/server/src/processes`). A sampler per platform reads cumulative counters (libproc and the Mach host calls through `bun:ffi` on macOS, `/proc` on Linux, none on Windows, which the panel says) and `processRates` turns two readings into rates, so a reading five minutes after the one before averages over five minutes. A process is its pid plus its start time, and unreadable is `null`, never zero. `ProcessMonitor` reads every 2 s while any socket on that machine holds `processes.subscribe` and every 5 minutes otherwise, plus one reading out of rhythm when a turn ends, a shell exits or a session is killed (`SessionManager.onProcessChange`). It keeps a fine series (300 points at 2 s, filled only while subscribed) and a coarse one (288 points at 5 minutes) in memory, and starts both over when the machine slept (the boot clock ran ahead of the awake clock), never because of the length of a gap. `tree.ts` groups the table per node (a session's shell pid, a chat backend's `pid`), the desktop app around the daemon and the daemon's own tasks; the client puts the node's title on the row. `stuck.ts` lays the hook status beside the measurements (silent while working, busy after the turn, memory, agent gone, orphan, a hung probe, every threshold in `STUCK_THRESHOLDS`) and `processes.alerts` goes to every socket, for the mark on a node and its sidebar row (`processes/ProcessAlertMark.tsx`). Nothing acts on its own: a warning carries a button, and `processes.signal` checks pid, start time and user before it sends anything. `scripts/calibrate-processes.ts` logs samples beside the hook statuses to `$RUIMTE_HOME/processes`, to tune those thresholds on real sessions.

## Conventions

- TypeScript everywhere, 4 spaces, LF, `.editorconfig` is the rule.
- American English in code, comments, commit messages and UI text. No em dashes or en dashes anywhere; use a comma, colon or parentheses.
- Always curly braces, also for one-line early returns. No one-letter variable names except `i`, `e`, `x`, `y`.
- Arrow functions inside functions; class methods are never arrow properties.
- Comments explain WHY, never what the code already says. Delete a comment that restates the line below it.
- Keyboard chords are bound on `window` and say which they are: the window's own (the palette, find in files, the settings, the sidebar) live once in `shell/app-chords.ts`, and anything that acts on a project lives once per workspace in `canvas/canvas-chords.ts` behind `isFocusedWorkspace`, so with two workspaces a chord never lands on the one beside it and with nine cells it fires once.
- Components: only semantic tokens from `styles.css` (`bg-surface`, `text-text-muted`, ...). No raw colors outside that file. Tooltips are the `Tooltip` component (`src/ui/Tooltip.tsx`), never a `title` attribute. Icon buttons that belong together go in a `BTN_GROUP` (`src/ui/classes.ts`, where the class strings more than a couple of call sites share live). Icons are Lucide through the `Icon` component (`src/ui/Icon.tsx`), never another icon set. Two exceptions: the icon of a file is the `@pierre/trees` set through `FileIcon` (`src/ui/FileIcon.tsx`) and keeps that set's own colors, and the mark of a provider is `ProviderLogo` (`src/ui/ProviderLogo.tsx`), a word mark per company in `currentColor`, because Lucide carries no brand marks. No fractional pixels: sizes, spacing and stroke widths are whole numbers, and a `rem` or `em` has to resolve to one. In anything a person reads a daemon is a **machine**: UI text, tooltips, errors, toasts and empty states. Code, comments and documentation keep saying daemon.
- Tests with `bun test` next to the code they test (`foo.test.ts`). A test that needs a real shell may spawn one; it must clean up its own processes.
- `bun run format` (prettier, `.prettierrc`) and `bun run check` (typecheck plus lint) must pass before a commit. Conventional commits (`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`).
- Written from scratch. Do not copy code from any other product; sharing ideas and npm packages is fine.
